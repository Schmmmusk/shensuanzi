## 一、P2 定案：**机房机器那 9.8 秒是环境，不是代码**

三组启动，同一份 498 MB 库：

| 时刻 | 场景 | `T2p_sqlite_open` | `T2_db_open` | `dbMb` |
|---|---|---|---|---|
| 17:10:07 | **首次冷启动** | **83 ms** | 84 ms | 498.2 |
| 17:19:04 | **重启后冷启动** | **85 ms** | 85 ms | 498.2 |
| 17:21:21 | 热启动 | **42 ms** | 43 ms | 498.2 |

横向对照：

| 环境 | `sqlite3.open()` | 倍差 |
|---|---|---|
| **虚拟机（干净，1 层）** | **83–85 ms**（冷）/ 42 ms（热） | — |
| 机房机（`F:` 6 层 / `C:` 7 层） | **9822 / 13040 / 14692 ms** | **100–170×** |

**⇒ 结论：`sqlite3.open()` 那十几秒来自机房机器的过滤栈 / 还原保护，与我们代码无关。**
同一份库、同一条语句、同一个 0.7.8，干净环境 83 ms。

**⇒ 产品侧不需要为此改代码。**

**同时注意 `T2p` 的其余三格仍然正常**（`wal` / `configure` / `migrate` 各 +0～+1 ms），
与机房机器上「后三步合计 7 ms」完全一致 —— 说明这两步本来就不慢，
机房机器的问题精确地落在 `sqlite_open` 这一格。

**为什么这台机器上页面比机房机器慢 10 倍**（机房：196–281 ms）：

| 环境 | 开库 | 首次页面 | 解释 |
|---|---|---|---|
| 机房机 | **9.8 秒**（慢） | 200 ms（快） | 卡在过滤栈；库早被反复读过，页缓存在 |
| 虚拟机 | **83 ms**（快） | **2–3 秒**（慢） | 开库不卡；但**虚拟盘冷读 498 MB 慢** |

**两个环境的瓶颈不同，互不否定。** 机房那 9.8 秒是环境；虚拟机这 2–3 秒是
**真实的冷读成本**，而且它是**产品侧能优化的**（见 §四）。

⚠️ 注意 `initState` 里的查询**也是同步的、在首帧前**。所以「把聚合移出 `build`」
只解决了「重复计算」，**没有解决「首次进入要等一次全表」**。

## 三b、⚠️ **17 秒看不到窗口 —— 这是显示层，与 P2 无关**

**用户现场（17:10 那次首次冷启动）**：

> 首次冷启动花了足足 **17 秒**，**前 11 秒没有窗口**，后 6 秒才绘制了标题栏，
> **直到我拖动标题栏才发现已经绘制完成了**。

**应用侧同一时刻的记录**：

```
T0_main          0
T1_run_app      11
T4_first_frame  39     ← 埋点：首帧 39 ms 就画完了
T2p_sqlite_open 83
overview 首帧   3189 ms
```

**⇒ 应用侧 3.2 秒就全部就绪，用户 17 秒才看到窗口。差的 13.8 秒不在 Dart 里。**

### 埋点盲区（必须记账）

`T4_first_frame` 与 `frame-cost` 测的都是 **Flutter 自己画完一帧**，**不包含**：

- Windows 窗口的创建与显示
- DWM 合成
- 虚拟机的显示管线（VMware `svga3d`）

**「`T4` 小」从来不等于「用户能看到」。** 这条以前没写进文档，是个缺口。

### 判据：「拖动标题栏才发现已绘制」= 内容在后台缓冲，没有 present

这是个很典型的特征 —— **画好了，但没 swap 到屏幕**；拖动窗口会强制重绘 + 重新合成，
于是"突然"就出现了。它能同时解释三件事：

| 现象 | 解释 |
|---|---|
| 应用侧 3.2 秒好、用户 17 秒看到 | 差的时间在 DWM / 虚拟显卡 |
| `frame-cost` 14 秒窗口只有 **4 帧** | 主 isolate 被 overview 查询占 3.2 秒；之后没有新内容要画 —— **画完就不画了，但屏幕没更新** |
| 11-08 / 11-09 两轮「CPU 0% 却卡」 | 同一形状：应用不动、屏幕不动、人在等 |

### 待验证的假设 + 现成的对照

**假设**：虚拟机的 **3D 加速**让窗口内容不 present（DWM 与 `svga3d` 交互问题）。

这台机器上**已有天然对照**：

| 轮次 | 3D 加速 | 表现 |
|---|---|---|
| 11-08 `虚拟机测试结果（无显卡）` | 关 | 页面卡，但**能显示** |
| 11-09 `虚拟机测试结果（有3d加速）` | 开 | 切页快，但留下「34 秒零活动」的谜 |

**实验**：VM 设置 → 显示 → **取消「加速 3D 图形」**，再冷启动一次，只看一件事 ——
**窗口是不是立刻出现**。

| 结果 | 结论 |
|---|---|
| 关掉后窗口秒出 | **坐实**：3D 加速的呈现路径有问题。以后虚拟机测性能一律关 3D |
| 关掉后仍 17 秒 | 不是 3D，是窗口创建本身（VMware Tools / DWM 初始化），继续查 |

**⚠️ 这条与 §一 的 P2 结论互不影响**：开库 83 ms 是真的（`T2p` 直接测的），
而"看不到窗口"是另一层的问题。**两件事同时发生，但不是同一个原因。**

## 五、`dbprobe` 没有输出 —— 已定位并修复

三份 trace 里**一条 `dbprobe` 都没有**，但包**确实包含**这段代码
（`startup_trace.dart` 11:35 < 构建 16:59）。原因：

```
noteDatabase()     定下 _file
  → flushDbProbe()      异步 append，立即返回
  → …
  → mark('T3b') → flushStartup()   又一次异步 append，同一个文件
```

**两个 `writeAsString(append)` 撞在同一毫秒，`dbprobe` 被 `startup` 盖掉。**
（`startup` 行正常、`dbprobe` 整行消失 —— 文件本身没坏，这是"两次写互相覆盖"的典型形态。）

**这正是 §八之一 P8（埋点写入口无互斥）**，此前只有推测，现在是实证。

**修法（已落地）**：四个写入口（`flushStartup` / `flushDbProbe` / `appendSwitch` /
`appendSettled`）全部串到同一条 `Future` 链上，后一次一定等前一次落完。
`resetForTest` 同时清空这条链。
