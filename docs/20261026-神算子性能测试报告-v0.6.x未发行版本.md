## 三、缺陷清单

### 3.1 P0 致命 不得发布 长时间数据量累积后卡顿

### 影响范围：几乎所有需要查询的页面，在长时间使用下必定出现

**现象**：<br>
    1. 点击左侧导航栏中‘商品’、‘单据’、‘往来方’、‘库存’、‘账户’等标签。点击动作结束后，交互动画出现明显卡顿，等待约2秒后，右侧工作区才出现对应内容。<br>
    2. 造数结束后，首次冷启动时，窗口**花费了足足8秒**才出现。虽然界面内容一次性全部出现，且脚本在启动时正确捕获了对应实例，但此现象仍值得注意。<br>
    3. 使用导出功能时，交互也出现1中同款卡顿。测试记录中的平均值为两台机器的各自评分求得的平均值，其中第一台机器的评分为3，第二台的为1. <br>
    4. 在第一台真机测试期间使用备份功能时，按钮交互也出现1中同款卡顿，甚至导致了**界面假死**。之后备份中消息才弹出，然后自动弹出新的“备份完成”消息。*第二台真机测试时结果好了不少。*<br>
    5. 在诸如“往来方”“账户”“库存”等流水相关二级页面中，拖拽右侧滑块，出现明显掉帧。强行将滑块一次拖拽到底部，**界面出现假死**，等待约4秒后界面直接跳到页面底部。<br>
    6. 一二级页面切换卡顿，尤以“单据”页面及其二级页面最为明显。<br>

**证据**：见tool/testResult/第二台真机测试结果。第一次测试数据使用早期脚本，未能正确捕获造数后首冷启相关数据，故分析造数后首冷启相关数据及其描述应以第二次真机测试结果及本报告为准。

**反例**：三大开单页面使用期间，未发现明显卡顿（尤其是搜索商品期间）

**影响**：<br>
    对中老年用户的长时间使用影响具有**毁灭性影响**。

### 3.2 P2 易造成困惑 应用内消息不自行消退

### 影响范围：几乎所有应用内以SnackBar形式弹出的消息

**现象**：
    以导出功能为例，导出完成后，弹出的SnackBar**不自动退下**（考虑到有“打开文件夹”按钮，退下时长可予以宽限，但其存续时长仍超出可接受范围），下一次导出的消息弹出才能将上一条挤下去。测试期间*有概率出现“正在导出……”的snackbar*，之后因先前的问题，导致导出完成的消息未能及时弹出。

**证据**：本次测试为黑盒测试，故由开发机补充。

**影响**：
    容易误导中老年用户，以为软件出了问题。

## 四、缺陷分析

叠甲：由于测试人员没有源码，故无法给出基于源码的准确解析。以下分析仅供参考，若与源码有出入，请以源码为准。

### 4.1 P0 “长时间数据量累积后卡顿”缺陷推演

1. Flutter 应用中，完整的用户交互--界面渲染完成（单帧）时长一般为 16.67ms ~ 20ms（50 ~ 60fps）。考虑到本项目使用了数据库，前述交互流程中还应当插入数据库查询、渲染额外数据为应用内可浏览表格等事项，后续性能优化方向可参考此处。
2. 造数后首次冷启动期间的明显卡顿：从 `tool\testResult\第二台真机测试结果\samples.csv` 和 `tool\testResult\第二台真机测试结果\events.csv` 中可以得知，启动时读取了大量数据（高达 1 GiB），远大于数据库文件本身大小，显然**发生了读写放大**；同时，中央处理器占用峰值达到了120%，且界面*迟迟未出现*，证明**项目没对启动期间的加载做好异步或懒加载处理**。若应用迟迟未响应，用户可能会强杀应用（虽然对中老年用户来说很难做到，但不能不考虑），导致数据损坏。
3. 使用期间的卡顿：交互卡顿广泛存在于‘商品’、‘单据’、‘往来方’、‘库存’、‘账户’等页面，从前述监控结果中不难得出，每次切换页面，必定触发页面完全重建；而**页面重建需要数据库内的数据，必定会触发一次查询**，这两部分延迟在常规机器上难以感知（瞬发占用），但在中老年用户的机器上，延迟会被放大数百倍乃至上千倍，对用户的使用体验造成毁灭性打击。
4. 单据页面的卡顿必须单独指出：现有单据页面*显式指出“当前只展示前 200 条数据，要具体单据请用上方搜索”*；然而，切换到单据页面的明显卡顿与前述监控文件表明，应用读取到的数据量，远大于它最终展示出来的数据量。据此可以推导：**数据库读取量和展示声称量不一致**。结合第二次测试数据中造数时写入的单据量，该结论完全有可能成立。同时有推论：所有前端做了同类显式声明的页面，都有可能出现同类问题。
5. 由推演3和4还可以证明以下推论：
    1. 应用实例存续期间，高频使用的内容**完全没有缓存机制**，导致每次加载对应页面都要从头跑一次页面渲染流程；
    2. 应用实例存续期间，异步加载或懒加载机制完全不存在，全靠硬件反复大力出奇迹，用户对着三步一小卡五步一大卡七步一卡死的软件只会上网搜索“如何强行终止无响应的应用程序”。

综上所述，本次 P0 级问题属于**兜底机制完全不存在类问题**，必须尽早修复。

### 4.2 P2 “应用内消息不自行消退”缺陷推演

1. 开发机使用的 Flutter SDK 信息如下：
```powershell

Engine • hash cc8e596aa65130a0678cc59613ed1c5125184db4 (revision 3452d735bd) (8 months ago) • 2026-02-09 22:03:17.000Z
Tools • Dart 3.11.0 • DevTools 2.54.1
```
本次推演基于开发机条件进行。

2. 根据 Flutter 官方的公开资料，从 Flutter 3.38 开始，SnackBar 新增了 `persist` 参数。与此同时，Material 3 规范发生变更：**带有`action`的 SnackBar 不再自动消失**。

3. 以下列出按照推演 2 估计的所有可能：
- 显式强制常驻：只要设置了`persist: true`，无论有没有`duration`属性，必须手动关闭；
- 3.38+ 常驻行为：存在 `action` 且 `persist: null`
    只要写了 `SnackBarAction`，不设置 `persist:false` 就不会自动消失，这符合 M3 规范；旧版本（<3.38）不是这个逻辑。若要恢复旧行为：`SnackBar(..., persist: false)`
- `duration` 设置为 `Duration.zero` 或者超长时长
- `behavior: SnackBarBehavior.floating` 不影响自动消失，但容易和其他遮挡问题混淆

4. 测试结束后，测试人员根据推演 3 中列举项，对全仓进行了爆破。结果如下：
- 显式强制常驻：除本报告外，未发现任何`persist: true`字段

## 五、修复方案

以下方案仅供参考。

### 5.1 针对 P0 级缺陷的修复方案

抢救方案：
1. 立即为启动流程和所有需要查询的页面加上异步加载或懒加载功能，**优先保证界面响应**。同时为所有可能发生加载的地方添加转圈进度条，不需要显示精确进度，**只需要告诉用户“我们有在好好干活啦！”就行**。
2. 严查所有页面切换时发起的数据库查询语句，确保**查询语句查询的是表内总数目和指定的范围内数据**，而不是现在的查询数目声称值与实际查询不一致；

长远方案：
1. 数据库文件大小超限时的归档机制：
    对于数据库内已结清的单据、已停用的商品、已结清且被停用的往来方，若一定期限（用户指定）后无操作，可自动或用户手动将其归档。**归档文件仍以数据库文件保存，且仍能被导出，文件内嵌被归档的时间区间，修改文件名不影响后续再次启用。**归档后数据要被踢出主力数据库文件，并留下“当前区段数据已归档，请到归档文件内寻找”的提示。
    若真要落地，可以考虑改名为数据封存，中老年用户可能没见过“归档”这个词。
2. 主力数据库文件的剪裁：
    现有数据库的落地实现是一个单体文件，所有流水数据全挤在一个文件。是否可以考虑：
    1) 将数据库内无用的信息删去？
    2) 将几张表拆分为独立文件？
    该方案要对数据库动手术，若真要实施，请慎重考虑。
3. 引入流式加载机制，代价是要动底层加载机制，真实施了，用户会看到业务条目一条条蹦出来，还要考虑数据聚合相关事务。较为麻烦，须慎重考虑。

### 5.2 针对 P2 级缺陷的修复方案

立刻定位所有使用了`SnackBarAction`的代码块，检查它们是否有`persist: false`属性，若没有，请补上；若有，请忽略。
同时检查所有`Duration`相关属性，看有没有特别离谱的数值。

## 六、最终结论

本项目宣称“中老年用户友好”（本地文件有 53 个相关文件，提到了 116 次），界面上也确实做到了中老年用户友好。然而，本项目长期未考虑真实用户长期使用后业务数据累积的使用场景，也从未考虑针对此类场景做专门优化，在本次测试中暴露了极其致命的使用期间严重卡顿问题。仅此一条，便足以判定：**本次测试严重不合格，不得发布！**<br>
本测试报告开头除了参测的两台 OEM 台式机外，还额外列出了目标用户群体更有可能使用的设备配置（根据家人真机配置抄录）。Intel® Core™ i5-11500 + 16G DDR4 + 256G 西部数据 SSD 属于常见的中端配置，在本次测试中**仍然拉了坨大的**；那么，在AMD® RX-8120 + 8G DDR3 + 256GB 杂牌SSD + 160GB 希捷老机械这样的设备上长时间使用，将会是何等的无量灾劫！这一条，也足以判定：**本次测试严重不合格，不得发布！**<br>
