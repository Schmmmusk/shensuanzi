# 无显卡虚拟机实测判读（2026-11-08）

> 数据：`tool/testResult/虚拟机测试结果（无显卡）/`（`report.md` / `samples.csv` /
> `events.csv` / `神算子-日志.txt`）。
> 环境：Win10 LTSC 2021 / 2 核 / 4 GB / **VMware 虚拟 SATA 盘** / **无 3D 加速** /
> 无杀软 / 系统缩放 100% / 软件内缩放 125% / v0.7.5（schema v8）。
> 会话 13.8 分钟、3001 个采样点。

## 一、先说结论

1. **这一轮抓到一个真 bug：导出单据在 26 万单的库上直接失败**（已修，见 §三）。
2. 其余的「慢」**不是数据量问题，是软件渲染**：这台机器没有 3D 加速，
   Flutter 退回 CPU 光栅化，2 核会被打满（CPU p95 = 100%、峰值 156%）。
3. 报告里的 **`库文件 0.0 MB` 不可信**（探针没读到），实际库是 **26 万单**
   —— 证据见 §二。

## 二、怎么知道库不是空的

`神算子-日志.txt` 里 22:25:40 有一条未捕获异常：

```
SqliteException(1): while preparing statement, too many SQL variables
Causing statement: SELECT target_doc_id AS t, COUNT(*) AS n FROM settlements
                   WHERE target_doc_id IN (?,?,…)
```

这条语句里有 **262,603 个 `?`** —— 也就是把**全表 26 万张单的 id** 塞进了
一个 `IN (…)`。所以：

- 库是 **26 万单**（`db_mb: 0.0` 是探针没读到，别当成空库）；
- 这不是「慢」，是**直接失败**：导出点了没反应（异常冒到 zone 兜底，界面无提示）。

## 三、bug：`IN (…)` 占位符超上限（已修）

**链路**：导出单据 → `listDocumentsForExport()` → `_summaries(limit: null)`
→ `_summariesOfRows()` → `settlementCountsMany(found.map(id))`
→ 一条 `IN (26 万个 ?)`。

**上限**：`SQLITE_MAX_VARIABLE_NUMBER`（老版本 999、新版本 32766）。

**修法**：`settlementCountsMany` / `returnedAgainstMany` 分块，每批 500
（与 `SyncQueueDao.clearConfirmed` 同口径），结果合并。26 万单 = 529 批，
每批是索引内聚合，整条导出 **1.8 秒**（PC / NVMe 实测 264,165 行）。

**测试**（core +4，`documents_list_test.dart`）：
- 4 万个 id 不炸（**真正复现现场**的那条 —— 语句在 prepare 阶段就炸，不需要造数据）；
- 1200 张单导出、行数不丢；
- 1200 个 id 的核销计数、1200 个 id 的退货聚合都跨批合并正确。

**反向灵敏度**：把批量退回 `1 << 30`（= 不分块）⇒ 4 万 id 那条立刻红，
报的正是现场那句 `too many SQL variables`。

## 四、其余数据的读法

| 指标 | 值 | 判读 |
|---|---|---|
| 会话时长 / 采样 | 13.8 分钟 / 3001 点 | 够长 |
| CPU | p50 **3%**、p95 **100%**、峰值 **156%**（单核=100%） | 空闲时极低、一操作就吃满 2 核 —— **软件渲染**的典型形状 |
| CPU ≥25% 的采样 | **33.2%** | 三分之一的墙钟时间在算 |
| CPU ≥85% 的采样 | **10.4%** | 持续满载段（最长连续 17 点） |
| 内存 RSS | p50 **183 MB**、峰值 **397 MB** | 分段中位 177/183/172/190/211/173 MB ⇒ **振荡，不是泄漏** |
| 自动识别操作 | 51 次，其中 **33 次 ≥ 2 秒**，最慢 **26 秒** | 见下 |
| 读写 | 单次事件读 0~764 MB | 虚拟 SATA + 4 GB 内存 ⇒ 大量分页读，不是库在读 |

> ⚠️ **报告的「内存从 75 MB 涨到 237 MB（+217%）」是误导**：首点是**启动中**的
> 采样（75 MB 还没加载完），末点是稳定态。按分段中位数看是**平的**。

**这 51 次操作没法归因**：`events.csv` 里没有人工动作记录（`actions: []`），
脚本只能按 CPU/IO 猜「读库/界面重建」。下次要么现场用 `s/e` 记几个关键动作，
要么至少把「冷启动 / 概览 / 库存页 / 导出 / 备份」这几个时间点记下来。

## 五、要不要为这种机器做优化

**先别做。** 理由：

1. 这台机器的瓶颈是**没有 GPU**（Flutter 在 Windows 上没 GPU 就走 CPU 光栅化），
   不是我们的 SQL 或数据量 —— 同一份 26 万单的库在真机上 release 是 1.5 秒启动；
2. 目标用户是「店里那台电脑」，配独显/核显的占绝大多数；
3. 真要兜底，成本最低的一条是**检测 + 说实话**：启动时若能判断
   「这台电脑没有显卡加速」，在设置页提示一句「界面会偏慢，关掉其他程序会好一些」，
   而不是去做一套低配渲染模式（那是大工程，且会把代码分成两条路）。

> 若要继续查这类机器，下一步是**把 `SSZ_STARTUP_TRACE` 的埋点带上**
> （2026-11-01 已修好 Android 侧的落盘；Windows 侧一直可用），
> 它能直接给出 T0~T4 各段耗时，比看 CPU 曲线准得多。
