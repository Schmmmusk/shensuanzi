# UI 原则

> 目标读者是**中老年个体工商户**：40–60 岁，用电脑管店，不折腾设置。
> 原则一句话：**清晰优先于美观，但不要看起来像上个世纪。**

## 一、用户画像的两条推论

### 1.1 不是「不会用」，是「不愿意试」

他们能学会任何东西，但**不会主动探索**。
任何「这个按钮点一下试试」的设计，在他们那里等于「永远不点」。

| 常见设计 | 对他们的结果 |
|---|---|
| 图标按钮（无文字） | 不认识 → 不用 |
| 悬浮提示（hover） | 不会悬停 → 看不到 |
| 汉堡菜单 ☰ | 不懂 → 找不到 |
| 隐藏的右键菜单 | 不会右键 → 功能不存在 |
| 快捷键 | 不记 → 等于没有 |
| 手势 / 拖拽 | 不会想到 → 不用 |

**原则：所有功能必须有常驻可见的入口 + 文字标签。**
图标可以加，但**文字必须在**。

### 1.2 他们犯错的代价更高

错一次 → 认为「这软件有问题」→ 不再用。所以：

| 设计 | 目的 |
|---|---|
| 所有删除操作**二次确认** | 防误删 |
| 单号 / 金额 / 数量输入**即时校验** | 防误输 |
| 开完单显示「本次已保存，单号 XX」 | 让用户确信 |
| 允许撤销（尤其是撤单） | 给「我错了也能补救」的信心 |
| 错误信息说**怎么办**，不说哪里错了 | 见 §五 |

### 1.3 「警告」有形态之分：内联优先，弹窗只留给不可逆的操作

同一个「提醒」，做成弹窗还是做成内联，对用户的影响完全不同 ——
弹窗**每次都要读完再做一次选择**，读烦了就不读了，还可能手滑点错：

| 形态 | 中老年用户的行为 |
|---|---|
| 弹窗「XX 已存在，继续吗？[是][否]」 | 每次都停下来读 → 烦 → 逐渐不读 → 可能误点「否」 |
| **表单内联提示**（输入时就地出现） | 眼睛扫到就看到了，**不打断输入、不增加点击** |

**原则：**

- **可以不拦人的提醒一律内联** —— 就放在相关输入框的下方，与用户的动作同屏。
  例：商品条码重复 → 条码框下方一行橙字
- **内联提示必须同时说清「下一步会发生什么」**，否则用户仍然会以为软件坏了。
  例：「⚠️ 这个条码已经给『娃哈哈矿泉水 550ml』用过了。／保存后扫码会显示两条商品供选择。」
  （只写「已占用」＝只说现状，用户会担心「那我以后扫码怎么办」）
- **弹窗只留给「重大、危险、不可逆」的操作**（删除、覆盖、放弃未保存的内容、
  选择数据存放位置这类**启动硬依赖**）。这类弹窗的目的**不是告知，而是要一个明确的确认**
  —— 与 §1.2 的「所有删除操作二次确认」同一条。
- 内联提示用**橙色**（取深一档保证对比度），**不用错误红** —— 红只留给真错误（§二）

## 二、视觉基调

| 项 | 值 |
|---|---|
| 基础字号 | 16 px（默认 125% 缩放下的观感） |
| 行高 | 1.6 |
| 按钮最小点击区 | 44 × 44 px |
| 表格行高 | 48 px |
| 主要文字对比度 | ≥ 7:1（WCAG AAA） |
| 次要文字对比度 | ≥ 4.5:1 |
| 主色 | **一个**，不要多 |
| 动画 | 只在「操作成功」时用，≤ 200 ms |
| 阴影 / 渐变 | 不用 |
| 圆角 | 统一 4–6 px，不要更大 |

**配色**：避免纯白 + 纯黑的刺眼 —— 背景 `#FAFAFA`，正文 `#1A1A1A`。
主色用**低饱和蓝或绿**，**不要红**（红色只留给错误与告警）。

## 三、缩放

**不要用 `Ctrl + 滚轮`** —— 中老年用户不会发现这个操作。

放设置里，独立入口：

```text
设置 > 显示 > 界面缩放

  [ - ]   125%   [ + ]
  ─────────────────
  ○ 小     100%
  ● 标准   125%   ← 默认
  ○ 大     150%
  ○ 特大   175%
  ○ 超大   200%
```

| 项 | 做法 |
|---|---|
| 实现 | `MediaQuery` 的 `textScaler` 全局缩放 |
| 尺寸 | **全部用相对单位**（写 `14 * scale`，不写死 `fontSize: 14`） |
| 反馈 | 改动**实时预览**，不是「重启后生效」 |
| 存储 | 存 `config.json`（设备偏好，不是业务数据，见 [`data_directory.md`](data_directory.md) §四） |

**默认 125%** 的理由：Windows 显示设置里 1080p 显示器很多用户本来就调到 125%。
跟上它，用户第一眼看到的就是「合适的大小」，不需要再调。

## 四、数字输入

输入数量 / 单价 / 金额是**最高频动作**（零售批发场景）：

- 数量、金额输入框：**默认弹出数字键盘**
  - Android：`keyboardType: TextInputType.numberWithOptions(decimal: true)`
    —— 默认弹出的是带字母的键盘，用户要先切到数字，**这是纯粹的摩擦**
  - Windows：触摸键盘走数字布局
- 支持**回车确认**，不用鼠标点下一格
- `1.5` 与 `1.50` 等价（自动规范化到分）

## 五、错误信息

**说「怎么办」，不说「哪里错了」。**

| ❌ | ✅ |
|---|---|
| 外键约束失败 | 这个商品还没建过，请先到商品页添加 |
| 路径非法 | 请点「更改位置」，从「此电脑」里选一个文件夹 |
| 库存不足 | 现在只有 3 件，要按负数出库吗？（允许负库存，见 `threat_model.md` §3.4） |

实现上：错误信息由**领域层给出**（例如 `DirectoryAdvice.reason` + `advice`），
UI **只负责展示，不负责造句** —— 否则同一句提示会在多个页面写得不一样。

## 六、首次启动：一屏对话框，不是 5 步向导

> ⚠️ **本节在 2026-09-26 收紧过**：原先设想「5 步模态向导」，
> 现改为**只保留唯一必须的那一步**。理由见下。

### 6.1 向导的 5 步不是一回事

按「是不是硬依赖」拆开看，内部硬度差异极大：

| 步骤 | 是不是硬依赖 | 能否后补 |
|---|---|---|
| 1. 欢迎 | 否 | 完全可后补 |
| 2. **数据位置** | **是** | **必须先有**（没有它，数据库不知道放哪，程序起不来） |
| 3. 商店信息 | 否 | 可后补 |
| 4. 账户设置 | 否 | 可后补（有默认值） |
| 5. 完成 | 否 | 完全可后补 |

**第 2 步不包装成向导**，就用最朴素的方式满足它：一个标准的
「选择数据存放位置」对话框（见 [`data_directory.md`](data_directory.md) §九）。

```text
┌────────────────────────────────────┐
│  选择数据存放位置                   │
│                                    │
│  建议放在非系统盘：                 │
│  📁 D:\神算子数据\                  │
│     D 盘剩余 128 GB                 │
│                                    │
│     [ 更改 ]  [ 退出 ]  [ 开始使用 ] │
└────────────────────────────────────┘
```

**不做**：欢迎语、店名输入、账户预设、完成页。
**做**：默认路径 + 三档校验 + 创建标记文件。

### 6.2 为什么顺序是「闭环 → 向导」

1. **向导的设计依赖核心功能的行为** —— 第 3 步问「店名」、第 4 步预设账户，
   但这两个字段在开单页怎么用、默认账户是哪个，**要开单页真做出来才知道**。
   现在写向导 = **先冻结一套还没有使用场景约束的决策**。
2. **向导是一次性消耗品，闭环是天天用的** —— 用户看 5 分钟向导，用 5 年开单页。
   开单页的每个摩擦会被重复上千次，向导的每个瑕疵只被看到一次。
3. **向导容易变成拖延症** —— 做「欢迎页的配色」比做「采购入库的分派逻辑」
   舒服得多（没有对错、没有边界、可以无限打磨）。**先做闭环是一种防拖延的纪律**。

### 6.3 例外：第 2 步的决策必须一次做对

数据目录对话框虽然只有一屏，但**它的决策一旦错，用户数据就危险**
（`%LOCALAPPDATA%` 被清、OneDrive 冲突、U 盘拔盘）。
**不能「先凑合再改」** —— 因为一旦用户开始录入数据，改数据目录的代价就大了。

### 6.4 第 10 天回补时，也不做 5 步模态向导

```text
首启：
  数据目录对话框（已实现）
  → 主界面 + 一个欢迎浮层
      ┌──────────────────────────┐
      │ 欢迎使用神算子            │
      │ 你的数据存在：            │
      │ D:\神算子数据\            │
      │ [ 先去建个商品 ]  [ 跳过 ]│
      └──────────────────────────┘
```

理由：

- 中老年用户对「被要求一步步操作」敏感，**一屏浮层**更友好
- 店名 / 账户预设可以放进设置页，用户想改随时改
- 模态向导会**挡住用户「先随便看看」的冲动** —— 而这个冲动是最宝贵的

欢迎浮层里那句「**你的数据存在 `D:\神算子数据\`**」是核心承诺
（数据在你自己电脑里，不在我的服务器上），必须在第一次打开软件时让用户看到 ——
**用户不会从 README 里读到它**。

## 七、Windows 最小闭环

Android 端的同步依赖 Windows 主机先跑起来，所以 **Windows 先做**：

```text
商品建档 → 采购入库 → 库存查询 → 销售开单 → 收款
```

这一步跑通，加上已有的 `SyncServer`，Android 端就有了**可测的服务端**。

## 八、左侧常驻导航

### 8.1 为什么不用顶部标签页

1. **垂直空间比水平空间贵** —— 核心页面全是**表格**（商品 / 库存 / 单据 / 往来方），
   表格要的是高度，每多显示一行都少一次滚动。顶部标签页吃掉 40–60px，
   而且**行数越多越亏**。
2. **标签页超过 6 项会折叠成「更多」菜单** —— 折叠就是**隐藏入口**，
   而中老年用户不会去点「更多」。功能至少有 8–10 项，必然触发。
3. **桌面软件的认知范式** —— 微信、钉钉、企业微信、几乎所有 ERP / POS
   都是「左边一列、右边内容」。用户**见过这个模式**，不需要学习。
   顶部标签页是**浏览器心智**（看多个文档），不是「在多个功能间切换」。
4. **图标 + 文字的稳定组合** —— 左侧导航天然容纳这一对（顶部标签页做会很挤）。

### 8.2 分组与顺序

```text
┌──────────────┬──────────────────────────────┐
│  概览         │                              │
│  ─────────   │                              │
│  销售开单     │                              │
│  采购入库     │                              │
│  ─────────   │                              │
│  商品         │          内容区               │
│  库存         │                              │
│  单据         │                              │
│  往来方       │                              │
│  账户         │                              │
│  ─────────   │                              │
│  设置         │                              │
│  帮助         │                              │
└──────────────┴──────────────────────────────┘
       220px
```

| 组 | 项 | 为什么这样分 |
|---|---|---|
| 首页 | 概览 | 落地页：回答「数据在哪 / 能不能用」。**必须是第一项** |
| 高频动作 | 销售开单、采购入库 | 每天几十次，放最上面形成**肌肉记忆** |
| 数据查询 | 商品、库存、单据、往来方、账户 | 按「找什么」组织，符合日常语言 |
| 系统 | 设置、帮助 | 低频，放底部 |

**用分隔线和间距分组，不做嵌套折叠** —— 中老年用户不会展开。

> ⚠️ 「概览」是对裁定书原列表的**一处增补**（原列表 9 项）：
> 新版安装没有任何数据，直接落在「销售开单」这种沉浸式开单页是坏的落地体验；
> 而「你的数据在哪」这个承诺需要一个常驻位置。

### 8.3 高亮与位置感知

中老年用户对「我在哪里」感知弱，必须给**强信号**：

```text
当前项：左侧背景变色 + 左侧 3px 竖条 + 文字加粗
        （三重信号，不是只变颜色 —— 色觉异常的用户也能感知）
```

顶部加**面包屑**（`销售开单 > 已保存`）：开完单后用户知道自己在哪、
刚才发生了什么。

### 8.4 宽度与缩放

界面缩放 125% / 150% / 200% 时，导航宽度**按比例缩放**，但**文字不换行**：

| 模式 | 宽度 | 何时 |
|---|---|---|
| 展开（默认） | 220px × 缩放 | 常态 |
| 紧凑 | 160px × 缩放 | **高级选项，默认关闭**（设置页） |
| 仅图标 | 60px | 只在「缩放 200% + 窗口很窄」时**自动兜底**，不是默认 |

**绝不做**：图标 hover 才显示文字（中老年用户不会悬停）。

### 8.5 开单页的沉浸模式

销售开单与采购入库**占用整个右侧**：不显示面包屑、不显示列表 ——
开单是一个**连续的动作流程**，不是「浏览一个列表」。

**左侧导航仍然显示** —— 用户随时能跳走（比如发现商品没建档，
切到「商品」页加一个再回来），回来时开单页的草稿还在。

### 8.6 反模式

| 反模式 | 为什么 |
|---|---|
| 图标-only 导航（hover 显示文字） | 中老年用户不会悬停 |
| 汉堡菜单 ☰ | 不懂 |
| 折叠二级菜单 | 不会展开 |
| 顶部标签页 | 浪费垂直空间 + 会退化成「更多」 |
| 自定义拖拽排序导航 | 用户不会去调，反而会弄乱 |
| 深色主题作为默认 | 强对比，看久了累 |

### 8.7 实现分工

| 层 | 位置 | 内容 |
|---|---|---|
| **结构**（有哪些入口、分几组、顺序、哪个是沉浸模式、宽度常量） | `packages/shensuanzi_app/lib/src/navigation.dart` | 纯 Dart，**`dart test` 覆盖** |
| **图标映射** | `lib/src/ui/nav_icons.dart` | `iconKey` → `IconData`，查不到用兜底图标（不崩） |
| **摆放** | `lib/src/ui/app_shell.dart` | 220px 列 + 分隔线 + 三重高亮 + 面包屑 |

为什么这样拆：**「入口是否齐全、是否都带文字标签」是硬规则**，
放在纯 Dart 里就能用测试钉住，不必等界面截图靠人眼确认。
