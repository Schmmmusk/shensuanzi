# 50 · 单据列表排序的三条路：代价清单（供裁定）

> **本文双语**：每节先中文，紧随 `English` 段。两段内容等价；若有出入，**以中文为准**。

---

## 零、一句话

现状排序（日桶 + `created_at`）在 26 万单库上 **136.8 ms**（「全部」档）。
有两条路能降到 **0.1 ms**（1300 倍），但代价完全不同：
**② 改语义（省事但用户看得见）**，**③ 加列（等价但动 schema 与迁移纪律）**。
**建议等 B-2 数据到手再定**（单据页 settled 380 ms 里 SQL 只占 142 ms，排序只是其中一部分）。

### English

The current ordering costs **136.8 ms** on a 262k-document database. Two alternatives reach **0.1 ms**
(1300×), with very different costs: **② changes user-visible semantics**, **③ adds a column and touches
migration discipline**. Recommend deciding after B-2 data lands — SQL is only 142 ms of the 380 ms page cost.

---

## 一、实测数据（478 MB / 26.2 万单 / 16.1 万根单）

| 写法 | p50 | 结果与现状的差异 |
|---|---|---|
| **① 现状**：`ORDER BY (occurred_at+偏移)/86400000 DESC, created_at DESC` | **136.8 ms** | —— |
| **② 纯**：`ORDER BY created_at DESC, id DESC` + `INDEXED BY idx_documents_created` | **0.1 ms** | **4 / 200 行位置不同**（真语义变化） |
| **③ 加列**：`ORDER BY business_day DESC, created_at DESC` + `INDEXED BY idx_docs_bday_created` | **0.1 ms** | **排序键 0 行差异**；200 行集合相同；6 行只是**并列项**顺序不定 |

补充：③ 的迁移实测 —— `ALTER` 加列 **0.01 s**、回填 26 万行 **0.64 s**、建索引 **0.15 s**，合计 **≈0.8 s**。

> 说明：① 与 ③ 都有 6 行「位置不同」，原因是**两边都没写 `id` 兜底**，
> 同一 (日, 录入时刻) 的并列行顺序由执行计划决定。加 `, d.id DESC` 可让两边都稳定。

### English

Current: 136.8 ms. Pure `created_at` + index hint: 0.1 ms but **4 of 200 rows reorder** (real change).
`business_day` column: 0.1 ms with **zero ordering-key difference** (6 rows differ only as ties).
Migration cost measured: 0.01 s + 0.64 s backfill + 0.15 s index ≈ **0.8 s**.

---

## 二、逐条代价

### ① 维持现状

| 项 | 内容 |
|---|---|
| 性能 | 136.8 ms（「全部」）/ **57.6 ms（默认 30 天）** |
| 代码改动 | 零 |
| 迁移 | 零 |
| 语义 | 保持 #26①（同一天按录入时刻倒序、跨天按业务日期） |
| 风险 | 零 |
| 增长性 | 线性：每多 10 万根单约 +50 ms（全部档） |

**适用**：如果 B-2 显示单据页的 380 ms 主要不是排序贡献的，这条路就是对的。

#### English

No code, no migration, no risk. 136.8 ms (All) / 57.6 ms (default 30 days). Grows linearly.

### ② 纯 `created_at`（0.1 ms，改语义）

| 项 | 内容 |
|---|---|
| 性能 | **0.1 ms** |
| 代码改动 | `_listOrder` 一行 + `INDEXED BY idx_documents_created`（**硬提示**，必须配索引存在断言） |
| 迁移 | 零 schema |
| 语义变化 | 排序键从「业务日 + 录入时刻」变成「录入时刻」 |
| 用户可见后果 | **补录昨天的单会排到今天最上面**；跨天顺序按录入时间，不按业务日期 |
| 回滚 | 一行 SQL，容易 |
| 风险 | **中** —— 用户按日期对账时会错位 |

**判据**：如果你们的真实场景里「录入即发生」占绝大多数、补录很少，且能接受补录单窜到最前，才走这条。

#### English

0.1 ms, one-line change, no schema. But the sort key becomes "entry time" instead of "business day",
so **a back-dated document jumps to the top**. Rollback is trivial. Risk: medium (visible behaviour change).

### ③ `business_day` 列（0.1 ms，语义等价）

| 项 | 内容 |
|---|---|
| 性能 | **0.1 ms** |
| 语义 | **与现状完全等价**（实测排序键 0 行差异） |
| 时区 | 更稳：`business_day` 在**写入时固化**，用户改时区后历史不变（现状是每次按当前时区算） |
| 迁移 | schema **v6**：加列 + 回填 26 万行 + 建复合索引，实测 **0.8 s** |
| 代码改动 | 写入路径要算 `business_day`（RuleEngine 落库时）；查询换 `ORDER BY` + `INDEXED BY` |
| 风险 | **两处硬约束**，见下 |

**硬约束 1：与纪律 2/3 冲突。**
`Agents.md` 规定「业务数据只插入不更新」，且 `documents` 只允许 UPDATE `status` / `paid_amount` / `updated_at`。
回填 `business_day` 必然 UPDATE 26 万行。两条出路：

- **甲**：在迁移里写一次性例外，并在 `docs/` 明确记录「这是唯一一次 UPDATE documents」——
  简单，但开了口子；
- **乙**：走纪律 14 的「重建表 + 数据搬迁」（`CREATE` 新表 → `INSERT SELECT` → `DROP` → `RENAME`）——
  不违反 UPDATE 禁令，但迁移代码量大、26 万行搬迁要重建全部索引（实测 0.8 s 量级仍可接受）。

**硬约束 2：升级窗口期。**
字段只增不删，旧客户端读到新库会忽略新列 —— 但**旧客户端写入时不会填 `business_day`**。
混合版本期间（家里电脑先升、店里没升）新写入的行该列为 `NULL`。
若查询写成 `COALESCE(business_day, 表达式)`，**索引立刻失效**（退回到 136 ms）。
需要额外机制：迁移后写一个「已升级」标记，查询按标记走两条路 —— 复杂度明显上升。

#### English

0.1 ms, semantically identical, and more stable across timezone changes. Two hard constraints:
(1) backfilling violates "business data is insert-only" — either a one-off migration exception or a
table rebuild per discipline 14; (2) during mixed-version rollout, old clients write `NULL`, and
`COALESCE` in the ORDER BY kills the index.

## 三、对比总表

| 维度 | ① 维持 | ② 纯 created_at | ③ business_day |
|---|---|---|---|
| 性能（全部档） | 136.8 ms | **0.1 ms** | **0.1 ms** |
| 语义 | 正确 | **变了** | **等价** |
| schema 变更 | 无 | 无 | **v6 + 回填** |
| 触碰纪律 2/3 | 否 | 否 | **是**（需例外或重建表） |
| 升级窗口风险 | 无 | 无 | **有**（旧客户端写 NULL） |
| 回滚成本 | —— | 一行 | 一次迁移 |
| 工作量 | 0 | **约 2 小时**（含等价测试） | **约 2 天**（迁移 + 双写 + 混合版本兜底 + 测试） |

### English

① zero cost; ② ~2 hours, semantics change; ③ ~2 days, schema v6 + backfill + dual-write +
mixed-version fallback, but semantics preserved.

---

## 四、我的建议

1. **先等 B-2**（商品页/单据页 settled 的实测），确认排序在 380 ms 里占多少。
   如果只占 1/3，②③ 的收益上限就是 130 ms —— 值不值 2 天，要看你对「切页手感」的要求。
2. 若确实要动：**③ 乙案（重建表）** 比甲案干净，但工作量翻倍；
   **② 只在你能接受「补录单窜到最前」时才选**。
3. 无论选哪条，**`INDEXED BY` 必须配「索引存在」断言** —— F19 就是硬提示遇到缺索引直接报错，
   把整页打成灰屏。

### English

Wait for B-2 first. If you do proceed, option ③ via table rebuild is cleaner but doubles the work;
option ② only if you accept back-dated documents jumping to the top. Either way, `INDEXED BY` must be
guarded by an index-existence assertion (F19 was exactly this failure).
