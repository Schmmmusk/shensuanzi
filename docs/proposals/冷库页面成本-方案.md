## 〇、一句话结论

**这不是「页面写得慢」，是「首帧在等磁盘」。** 真机上这三个页面 88–320 ms，不构成问题；
在慢盘（虚拟机 / 机械盘 / 网盘同步目录）上同一份代码要 2–3 s。**但注意归因口径**：
「慢盘上九成时间花在冷读」目前只是**估计**（见 §1.2 的 ⚠️），不是同一次运行里量出来的
I/O 占比。能确定的只有两件事：真机上 320 ms 里 225 ms 是 SQL；慢盘上首帧比真机慢一个数量级。

English: this is not slow code — it is the first frame waiting on cold disk reads. On a real NVMe
those pages take 88–320 ms; on a slow disk the same code takes 2–3 s. Note the caveat: "~90% is
cold I/O on slow disks" is an **estimate**, not an I/O share measured in one run (§1.2).

## 一、数据（全部实测，可复现）

### 1.1 同一份代码、三种机器

| 环境 | 磁盘 | `overview` 首帧 | `stock` | `documents` |
|---|---|---|---|---|
| L13 真机 | SN530 NVMe | **320 ms** | 209 ms | 88 ms |
| 虚拟机 | 虚拟 SATA（宿主 NVMe） | **3189 ms** | 2676 ms | 2146 ms |
| 机房机 | 慢在过滤栈、页缓存热 | — | 196–281 ms | — |

来源：`docs/20261111-虚拟机0.7.8验证-判读.md` §三（真机与虚拟机的差是 10× / 3× / 24×）。
**普通用户看到的是 L13 那一行。**

### 1.2 SQL 本身多少钱（热缓存，2026-11-18 现量）

`tool/perf_bench.py --db D:\shensuanzi\perfbench.db`（498.7 MB / 26.3 万单 / schema v8）：

| 键 | p95 | 对应代码 |
|---|---|---|
| `overview_load`（概览首屏全部 SQL） | **224.8 ms** | `overview_page.dart:213-224` |
| ├ `in_transit`（在途数量） | 83.0 ms | `stock_page.dart:266` / `overview_page.dart:235` |
| ├ `account_balances`（账户余额） | 64.4 ms | `_load()` 内 |
| ├ `stock_merged`（库存两榜一次扫完） | 58.2 ms | `stockOverview()` |
| ├ `party_balances` × 2（应收 / 应付） | 27.8 × 2 ms | `_load()` 内 |
| ├ `gross_margin`（毛利 6 条腿） | 15.9 ms | `_load()` 内 |
| └ `today_summary` | **0.01 ms** | `_load()` 内 |
| `list_roots`（单据首屏） | 20 ms 级 | `documents_page.dart:122` |

**把两组数对齐，冷读成本就出来了** —— ⚠️ 但这是一个**减法估计**，不是实测：

| 环境 | 首帧 | 热缓存 SQL | 估计冷读 | 估计占比 |
|---|---|---|---|---|
| 真机 NVMe | 320 ms | 225 ms | ~95 ms | 30% |
| 虚拟机 | 3189 ms | 225 ms | **~2964 ms** | **~93%** |

> ⚠️ **口径警告（2026-11-18 评审）**：3189 ms 是**历史首次进入页面**的测量，
> 225 ms 是**今天、热缓存、另一台机器**上的 SQL p95。两者不是同一次运行、
> 不是同一缓存状态，甚至不保证是同一个代码版本 —— **相减只能算「冷读惩罚的估计值」**，
> 不能当作「磁盘 I/O 占首帧的比例」来引用。要拿到真数字，需要 §七 的那次同条件测量。
>
> 同样地，「压 SQL 帮不了慢盘」这句**也说得太满**：减少**计算量**与减少**实际读的页数**
> 是两件事。若某条查询扫了整张 `stock_ledger` / `documents`，换查询策略或加覆盖索引
> 会**少读页**，冷缓存下的 I/O 也会跟着少。**在没量过读页数之前，不能断言丙案对慢盘无收益。**

English: the 93% figure is a subtraction between two different runs — treat it as an estimate of
the cold-read penalty, not a measured I/O share. Likewise "optimising SQL cannot help slow disks"
is too strong: cutting computation and cutting pages read are different things, and the latter does
reduce cold I/O. Both need the same-condition measurement in §七 before being used as evidence.

## 二、根因分层（三件不同的事，别混着治）

| 层 | 事实 | 慢盘上能省 | 真机上能省 |
|---|---|---|---|
| ① **首帧同步等 I/O** | 三页都在 `initState` 里**同步**查完才 `build` | 首帧可省掉**全部**等待（出壳不再等） | 同上（感知） |
| ② **SQL 的计算量** | `overview_load` 224.8 ms（`in_transit` 83 + `account_balances` 64 + `stock_merged` 58…） | **待测**（见 §七） | 70% |
| ③ **SQL 读的页数** | 五张卡各扫一遍 `documents` / `stock_ledger` / `money_ledger` | **待测** —— 页数少 ⇒ 冷读少，这是丙案可能成立的地方 | 同上 |

① 是**交互问题**：用户点了「库存」，界面上什么都没有，鼠标也不响应 —— 他不知道点中了没有。
②③ 是**吞吐问题**，两者的慢盘收益**必须先量**（§七）才谈得上取舍。

## 三、三个方案

### 甲、骨架先行（首帧不等 SQL）—— 建议先做这个

`initState` 只置 `_pending = true` 立刻返回；真正的查询放到下一帧
（`addPostFrameCallback`）里跑，算完 `setState` 填数据。

| 项 | 内容 |
|---|---|
| 改动面 | 三页各 ~20 行（`_pending` 字段 + 骨架 widget + 一处回调）；数据层**一行不动** |
| 首帧 | 真机 320 → **≤ 16 ms**；虚拟机 3189 → **≤ 16 ms** |
| 慢盘体感 | 「壳马上出来，数字 3 秒后到」——**仍然会冻住一次**（同步 SQL 在同一 isolate），但用户知道点进来了 |
| 风险 | 低。骨架期间 `_data == null` 的分支要写全（空库 / 还没加载 / 加载失败三态不能混） |
| 测试成本 | 现有 widget 测试要 +1 次 `pump`（从「建好就有数」变「pump 后才有数」），三页各改几条 |

⚠️ **必须避免的假骨架**：查询抛错时不能一直显示骨架（要走现有的 `read_failure_banner`），
否则「查挂了」和「还在算」在界面上长得一样 —— 那比不加载更糟。

**⚠️ 验收必须拆成两件事**（2026-11-18 评审）：`post-frame` callback 在渲染流水线刷新后执行，
所以**骨架可见时间**会明显改善；但同步 SQL 一旦开始，**交互恢复时间**一点都不会改善
（鼠标照样不响应到查询结束）。两者要分别记，不能拿「首帧快了」当「卡顿没了」。

### 乙、查询挪进工作 isolate（慢盘上 UI 不冻）

在独立 isolate 里用**另一条只读连接**跑 `_load()`，结果回灌 UI。
首帧立刻出壳，且**冻结也没了**（慢盘上仍可点别的页面）。

| 项 | 内容 |
|---|---|
| 改动面 | 中：`QueryDao` 持有 `Database` 不能跨 isolate ⇒ isolate 内按路径新开只读连接；错误 / 取消 / 换库（`didUpdateWidget`）都要处理 |
| 收益 | 虚拟机：3189 ms **冻结** → 3 秒后数字自己出现，UI 全程可用；真机：几乎无感（225 ms 的壳后等待） |
| 风险 | 中。会话生命周期（换库 / 重连 / 手机镜像切换）与 isolate 的配对是最容易出洞的地方 |
| 前置 | 甲必须先落地（乙只是把甲的「下一帧」换成「另一个 isolate」） |

**硬要求（评审补充，做乙时必须满足）**：

1. 多条查询放进**同一个只读事务**（优先复用现有的 `Db.readTransaction()`），
   拿到**同一个数据快照** —— 否则五张卡可能显示不同时间点的数据（今日营收与应收对不上账）。
2. 换库 / 重连 / 手机镜像切换时，**过期结果不许回写**：请求带版本号，回写前比对，
   不一致就丢弃（与 `didUpdateWidget` 里那套判断同一口径）。
3. isolate 内的连接必须是**只读打开**，且用完即关 —— 不许把写连接带过去。

### 丙、压 SQL（物化日汇总表，schema v9）

把 `dailyRevenue` / `dailyGrossMargin` / 应收应付这类全历史聚合改成**日汇总表增量维护**。

| 项 | 内容 |
|---|---|
| 改动面 | 大：新表 + 迁移 + 历史回填 + 三个写入口维护 |
| 收益 | 真机 225 → 估计 60–80 ms（首帧 320 → ~150）；**慢盘收益未知** —— 取决于能少读多少页 |
| 风险 | 高。汇总表与明细不一致是**账目类软件最忌讳**的一类 bug |

⚠️ **暂不立项的理由是「证据不足 + 维护成本高」，不是「慢盘一定没收益」**（评审修正，
2026-11-18）。要判定它值不值，先做 §七 的测量：拿 `EXPLAIN QUERY PLAN` + 实际读页数
（`PRAGMA page_count` 前后差 / `sqlite3_stmt_status` 的 VM 步数）说清「汇总表能少读多少页」。

### 丁、不做结构改动，只在慢盘上给一句提示

作为甲的兜底文案：「这台电脑读盘较慢，第一次打开会等一会儿」。

**触发条件必须是量出来的，且要有明确的起止点**（评审要求，2026-11-18）：

| 项 | 定义 |
|---|---|
| 计时起 | 用户在导航上**点下**目标页面的那一刻（不是 `initState`，那是点完之后） |
| 计时止 | 该页**数据到达**（`setState` 填完）那一刻 |
| 阈值 | 首次进入该页 > **1500 ms** 才提示；同一进程内每页**只提示一次**（避免每次切页打扰） |
| 不触发 | 第二次及以后进入同一页（此时页缓存已热），以及慢盘抖动导致的偶发越线（连续 2 次越线才提示） |

## 四、建议

1. **做甲**（骨架先行），三页一起，因为三页是同一个病、同一个改法（纪律 18：同构漏改高发）。
2. **乙立为 0.8 的「慢盘体验」专项**，看甲的实机反馈再决定要不要动。
   —— 判据：用户是否还报「点了没反应 / 卡死」。甲的壳能消掉「没反应」，消不掉「卡」。
3. **丙暂不立项**，理由是**证据不足**（读页数没量过）**且维护成本高**（账目一致性风险）；
   先做 §七 的测量，再决定要不要进 0.8。
4. **丁顺手带上**（按上表的口径），但不单独占决策位。

English: do 甲 now; park 乙 behind feedback on 甲; do **not** fund 丙 yet — the reason is insufficient
evidence plus high accounting risk, not a claim that it cannot help slow disks; fold 丁 in with the
explicit timing definition above.

## 五、判据与门禁

| 判据 | 现在 | 甲之后 |
|---|---|---|
| 页面切换后**首帧**（`frame-cost.jsonl` 的 `build`） | 320 / 209 / 88 ms（真机）；3189 / 2676 / 2146（VM） | **≤ 16 ms**（三页、两种机器一致） |
| **骨架可见时间**（点下导航 → 骨架画出来） | —（没有骨架） | ≤ 50 ms（含一帧调度） |
| **交互恢复时间**（点下导航 → 界面重新响应点击） | ≈ 首帧 | **不变**（甲不解决这一项，这是乙的地盘） |
| 数字到达时间 | 同上 | 不变（320 / 3189 ms）—— **不改 SQL 就不该变** |
| `overview_load` p95（`tool/perf_bench.py`） | 224.8 ms | 不变（甲不碰 SQL；若哪天变了说明有人顺手改了查询） |

**门禁怎么加**：`perf_bench.py` 的 `GATES` 只管「用户每帧都跑的东西」，首帧不是每帧，
所以**不进 GATES**；改用 `frame_trace` 的 `build` 时长做**回归对照**（改前 / 改后各跑一次冷启 + 逐页进入，写进台账）。

`overview_load` 现在不进 GATES，**建议这次也不进** —— 它没有每帧风险，进 GATES 只会让
以后「正常的查询调整」频繁撞护栏。

## 七、先补一次「同条件冷缓存分项测量」（评审要求，做与不做丙案的前提）

现在缺的不是意见，是**同一条件下**的分项数：

| 要素 | 必须固定 |
|---|---|
| 机器 | 同一台（虚拟机；它就是慢盘的代表） |
| 库 | 同一份 `perfbench.db`（498.7 MB / 26.3 万单） |
| 提交 | 同一个 git commit（记哈希） |
| 缓存 | **每次冷启动虚拟机**，第一次进入该页即测（不进第二次） |
| 计时 | 逐条查询单独计（不是整页一个总数） |

**产出三张表**：

1. **冷缓存分项耗时**：概览 `_load()` 里的每条 SQL 各多少 ms（冷态）；对照 §1.2 的热态 p95。
2. **读页数**：每条查询前后 `PRAGMA page_count` 不变，但可用
   `sqlite3_stmt_status` / `EXPLAIN QUERY PLAN` 的扫描行数估算「它碰了多少页」；
   或直接比「冷态耗时 ÷ 页大小」反推 —— 目的只有一个：**说清哪条查询最贵、贵在读页还是算**。
3. **汇总表假设的收益上限**：把「日营收 / 日毛利 / 应收应付」换成读一张小的日汇总表，
   粗算它读多少页（汇总表按天存，30 天窗口约几十行），与现状的页数对比 ⇒ 丙案的收益上限。

量完才谈得上：丙到底「没有收益」还是「有收益但买不起」。

English: measure per-query cold timings and pages touched on one machine/db/commit before judging
whether a materialised daily-summary table (丙) can actually cut cold I/O.
