# 缺货榜 —— 落地方案（🔴 待裁定，未动实现）

> 2026-11-11 用户裁定：**压货榜保留，另外加一个缺货榜**。
> 所以这不是「把压货榜改反」，是**新增一张榜**。原判「压货榜做反了」据此作废。

---

## 一、现状（先对齐，避免改错东西）

| 项 | 现状 |
|---|---|
| 「压货榜」= **占用资金最多**的前 N 个 | `QueryDao.stockTop()`，`WHERE qty > 0 ORDER BY cost DESC` |
| 口径 | 库存流水聚合出的**成本余值**（历史加权平均），不是数量 |
| 三态 | `cost > 0` 进榜；`cost == 0` 记「待校准」；`cost < 0` 记「负成本」，两者都只报个数 |
| 位置 | 概览页（前 3 行 + 「查看全部」）· 库存页顶部（完整榜，默认收起） |
| 已有资产 | **`products.safety_stock`**（schema 里就有，商品表单可填）· 库存页三档颜色已经在用它 |

⇒ **不需要加字段、不需要迁移。** 缺货榜要的数据全都在。

## 二、缺货怎么定义（口径必须与库存页一致）

```
在店可售 = 账面 − 送货在途        ← 库存页 AA-2 的主列，三档颜色也用它
缺货     = safety_stock > 0 且 在店可售 ≤ safety_stock
```

**为什么必须用「在店可售」而不是「账面」**：同一个商品，如果在途 100 件、账面 0 件，
库存页显示橙色「该补货」，榜里却不出现 —— 用户会认为榜坏了。

**为什么 `safety_stock = 0` 不进榜**：那是「没设告警」的语义（库存页 AA-3 已这么定）。
把它当成「安全库存 0 ⇒ 永远缺货」会让全店商品都进榜。

## 三、四个必须定的决策

### 决策 1：排序依据（推荐 **乙**）

| 选项 | 排序 | 代价 |
|---|---|---|
| 甲 | 缺口**件数**降序 | 跨单位不可比（「一箱牙签缺 500」排在「十台电机缺 2」前面）—— 与压货榜当初否掉「按数量」的理由完全相同 |
| **乙（推荐）** | 缺口**金额**降序（缺口 × 均价） | 与压货榜同构，跨商品可比；且「补这批货要花多少钱」店主立刻能懂 |
| 丙 | 缺口**比例**降序（缺口 ÷ 安全库存） | 「只剩 10%」很直观，但对「安全库存 10、剩 0」和「安全库存 100、剩 90」不公平 |

**乙的三态处理**（照抄压货榜，不能假装金额是 0）：
- `均价 > 0` → 进榜，显示缺口金额
- `均价 == 0`（待校准）→ **不进金额榜**，只计个数
- 均价为负（超卖摊穿）→ 同上

### 决策 2：超卖（在店可售 < 0）要不要置顶（推荐 **要**）

超卖比「缺货」更严重：账已经对不上了。建议**单独一段置顶**，与「该补货」区分开：

```
⚠️ 已超卖（2 个）          ← 红色，最上面
   红富士苹果   −5 件
该补货（8 个）              ← 橙色
   大米         缺 40 件 ≈ ¥1,200
   ...
```

### 决策 3：放哪儿（推荐 **甲 + 丙**）

| 选项 | 概览页 | 库存页 |
|---|---|---|
| 甲（推荐）| 缺货榜在**上**、压货榜在**下** | 两榜并排（缺货榜在前） |
| 乙 | 只放缺货榜，压货榜移走 | 两榜都在 |
| 丙 | 两榜合成**一张卡**，上半缺货下半压货 | 同 |

- 为什么缺货在上：缺货要**行动**（补货），压货只是**知晓**（钱压着）。中老年店主的注意力在上面。
- 为什么不合并成一张卡（否决丙）：一张卡两种颜色两套口径，读起来要来回切上下文；而且两张卡可以各自收起。
- 概览页已有 5 张图，加一张 = 6 张。**可接受**（都是滚动区，不比现在多一次交互）。

### 决策 4：**没人设安全库存时怎么办**（这一条最关键，推荐 **乙**）

现状：`safety_stock` 默认 0 ⇒ **新装的软件、或从没设过安全库存的店，这个榜永远是空的**。

| 选项 | 表现 |
|---|---|
| 甲 | 不显示这张卡（与压货榜「没数据就整卡不显示」一致） |
| **乙（推荐）** | 显示一张**引导卡**：「还没设过『安全库存』——设了之后，快没货时这里会提醒你」+ 一行「怎么设：商品页 → 编辑 → 安全库存」 |
| 丙 | 自动按「近 30 天日均销量 × 7」建议一个值 | 

- 否决甲：用户会以为「这功能是坏的」，而不是「我没配」。
- 否决丙：要算销量趋势，是另一个功能，且自动填的数字用户不信任。

## 四、实现范围（改动清单，不含决策未定的部分）

| 层 | 文件 | 改动 |
|---|---|---|
| core | `query_dao.dart` | 新增 `lowStockTop({int limit})`：一条 SQL 聚合出「在店可售 + 安全库存 + 均价」，按 §三 决策 1/2 排序；返回模型 `LowStockSummary`（rows / supersold 段 / 未设安全库存数 / 待校准数） |
| core | 新模型 | `LowStockRow { productId, name, unit, inStore, safetyStock, gapQty, gapCents }` |
| ui | 新 `low_stock_card.dart` | 仿 `stock_top.dart`（同一套三态语言、同一个 `RatioBar`、同样的 `margin: zero`） |
| ui | `overview_page.dart` | 插一张卡（压货榜之上）+ 查询（**要在 build 外算一次**，别再犯乙方案第一版那个错） |
| ui | `stock_page.dart` | `_loadAggregates()` 里多算一次（与 `stockTop` 同频） |
| test | `query_dao` 单测 + `stock_page_test` / `overview_page_test` | 见 §五 |

⚠️ **性能**：`stockTop` 是全历史聚合（26 万单 ~35 ms）。缺货榜如果**另写一条 SQL**，
等于又扫一遍 36 万行流水。**建议复用 `stockTop` 那次扫描的结果** ——
它已经算了每个商品的 `qty` 和 `cost`，只差 `safety_stock` 和「在途」。
**这一条会决定是 +35 ms 还是 +0 ms**，实现时必须先看能不能合并，别各扫一遍。
（2026-10-24 的 4c-2 就是因为「三次全表聚合」被合并成一次的。）
