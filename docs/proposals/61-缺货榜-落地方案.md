## 一、现状（先对齐，避免改错东西）

| 项 | 现状 |
|---|---|
| 「压货榜」= **占用资金最多**的前 N 个 | `QueryDao.stockTop()`，`WHERE s.qty > 0 ORDER BY s.cost DESC` |
| 它的聚合方式 | `products p **JOIN** (SELECT product_id, SUM(quantity), SUM(total_cost) FROM stock_ledger GROUP BY product_id) s ON s.product_id = p.id` |
| 口径 | 库存流水聚合出的**成本余值**（历史加权平均），不是数量 |
| 三态 | `cost > 0` 进榜；`cost == 0` 记「待校准」；`cost < 0` 记「负成本」，后两者只报个数 |
| 位置 | 概览页（前 3 行 + 「查看全部」）· 库存页顶部（完整榜，默认收起） |
| 已有资产 | **`products.safety_stock`**（schema 有，商品表单可填）· **`products.cost_price`** · 库存页三档颜色已在用前者 |

⇒ **不需要加字段、不需要迁移。**

## 二、缺货怎么定义（口径必须与库存页**逐字**一致）

```
在店可售 = 账面 + 未同步 − 送货在途
缺货     = safety_stock > 0 且 在店可售 ≤ safety_stock
```

**这个公式不是我发明的，是库存页现有的那一个** —— `effectiveInStoreOf`
（`lib/src/ui/stock_page.dart:78`，顶层纯函数）：

```dart
int effectiveInStoreOf({required int book, required int unsynced, required int inTransit})
    => book + unsynced - inTransit;
```

它有三处消费者（行内大字 / 负低库存判定 / 列表排序），文件头注释写着用户的原话：
「抽一个统一的函数，不要各处算 —— 将来加字段或改公式时一定会漏」。
**缺货榜是第四个消费者，必须调它，不能另写一遍。**

三条边界（每一条都有既有裁定支撑）：

| 规则 | 理由 |
|---|---|
| 用「在店可售」不用「账面」 | 在途 100、账面 0 的商品，库存页显示橙色「该补货」，榜里却不出现 —— 用户会认为榜坏了 |
| `safety_stock = 0` **不进榜** | 那是「没设告警」的语义（库存页 AA-3 已这么定）；当成「安全库存 0 ⇒ 永远缺货」会让全店商品都进榜 |
| 桌面端 `unsynced ≡ 0` | `stockDelta == null` ⇒ 与旧公式逐字相同，桌面零回归 |

## 三、审查补上的两个洞（这一节是本版的核心修订）

### 洞 1：从没进过货的商品，会被 INNER JOIN 丢掉

`stockTop` 的聚合子查询是 `FROM stock_ledger GROUP BY product_id`，外层是 **`JOIN`**。
一个**从没进过货**的商品在流水里一行都没有 ⇒ 不进子查询 ⇒ **被 JOIN 丢掉**。

- 对压货榜：**正确**（没流水 = 没占用资金 = 不该上榜）。
- 对缺货榜：**致命**。「刚建档、安全库存填 50、还没进货」= 在店可售 0
  = **全店最紧急的缺货**，恰好完全不可见。

⚠️ 而且这直接否掉了上一版的一句话 ——「建议复用 `stockTop` 那次扫描的结果」：
**复用就继承 INNER JOIN，就必然漏掉这类商品。** 两者在 SQL 层冲突。

⚠️ 还有一层陷阱：**不能简单把 JOIN 改成 LEFT JOIN 了事**。改了之后，
所有没流水的商品 `cost = 0` ⇒ 全部落进压货榜的「待校准」计数
⇒ 那个数字从 3 变 297，压货榜当场回归。

⇒ 正确做法两条：
1. `products` 作主集合、`LEFT JOIN` 聚合；
2. **把「从没进过货」与「进过货但成本为 0」分成两个状态**
   （`s.product_id IS NULL` 可区分）。后者仍叫「待校准」，前者叫「**未进过货**」，
   两者都只计数、不进金额排序，但**不能合并**。

### 洞 2：口径少了 Android 的「未同步」

上一版写的是 `在店可售 = 账面 − 送货在途`，**漏了 `+ unsynced`**。

`unsynced` 是「这台手机本地开了、还没推给主机的单」的净影响，来自
`StockDelta.unsyncedDelta()`（`packages/shensuanzi_core/lib/src/sync/stock_delta.dart:79`），
由 UI 传进页面（`unsyncedByProduct`）。

**漏了它的后果很具体**：手机上刚开了一张销售单、还没推、账面还是 10。
缺货榜按「账面 − 在途」算 ⇒ 认为不缺；而库存页大字已经扣成 9
（`effectiveInStoreOf`）⇒ **同一屏上两个数字打架**。这正是那个函数被抽出来的原因。

⚠️ **连带推翻上一版的实现范围**：上一版写「core 新增 `lowStockTop` 一条 SQL 直接算出
在店可售」。**core 算不出 `unsynced`** —— 它是「这台客户端还没推上去的本地单」，
不在库里的任何一张表中（`stock_ledger` 里没有，否则就不叫未同步了）。
所以那条 SQL 在 Android 上口径**天生是错的**。见 §五。

### 洞 3（用户没点名，但决策 1 依赖它）：**无货时「均价」无定义**

上一版决策 1 乙 用「缺口 × 均价」，均价取「成本余值 ÷ 账面数量」。**这个算法在缺货场景下不成立**：

| 账面 | 成本余值 | 「均价」 | 后果 |
|---|---|---|---|
| 0 | 0 | **0 ÷ 0** | 除零 / 无定义 |
| −5（超卖） | 负 | **负数** | 缺口金额为负 ⇒ 排序错乱 |
| 从没进过货 | 无记录 | **无定义** | 洞 1 那类商品永远算不出金额 |

⇒ **改用 `products.cost_price`（商品档案的「成本价」）**，三个理由：

1. 缺货是「**要买**」的场景，该用**采购价**，不是历史加权成本（那是「已经花掉的钱」）；
2. 它对「从没进过货的商品」也有值（建档时填的），而流水均价对这类商品无定义；
3. 账面上它是稳定的，不会随超卖变成负数。

三态随之简化：`cost_price > 0` 进金额榜；`== 0` ⇒ 只显示**缺口件数**并标「单价未填」，
不进金额排序（放在金额榜之后，或只计入个数）。

> 这一条改变了决策 1 的表述，但**没有改变它的结论**（仍然是金额排序，不是件数）。
> 只是「金额从哪来」换了来源。

## 四、四个必须定的决策

### 决策 1：排序依据（推荐 **乙**，但价格来源已修正）

| 选项 | 排序 | 代价 |
|---|---|---|
| 甲 | 缺口**件数**降序 | 跨单位不可比（「一箱牙签缺 500」排在「十台电机缺 2」前面）—— 与压货榜当初否掉「按数量」的理由完全相同 |
| **乙（推荐）** | 缺口**金额**降序（缺口 × `cost_price`） | 与压货榜同构，跨商品可比；「补这批货要花多少钱」店主立刻能懂 |
| 丙 | 缺口**比例**降序（缺口 ÷ 安全库存） | 「只剩 10%」很直观，但对「安全库存 10、剩 0」和「安全库存 100、剩 90」不公平 |

金额三态（照抄压货榜的诚实做法，不假装 0 就是 0）：
`cost_price > 0` 进金额榜 · `cost_price == 0` 标「单价未填」只给件数 ·
**「未进过货」单独计数，不混进「待校准」**（洞 1）。

### 决策 2：超卖（在店可售 < 0）要不要置顶（推荐 **要**）

超卖比「缺货」更严重：账已经对不上了。建议**单独一段置顶**，与「该补货」区分开：

```
⚠️ 已超卖（2 个）          ← 红色，最上面
   红富士苹果   −5 件
该补货（8 个）              ← 橙色
   大米         缺 40 件 ≈ ¥1,200
   ...
```

### 决策 3：放哪儿（推荐 **甲 + 丙**，但概览页有真实代价，见 §六）

| 选项 | 概览页 | 库存页 |
|---|---|---|
| 甲（推荐）| 缺货榜在**上**、压货榜在**下** | 两榜并排（缺货榜在前） |
| 乙 | 只放缺货榜，压货榜移走 | 两榜都在 |
| 丙 | 两榜合成**一张卡**，上半缺货下半压货 | 同 |

- 为什么缺货在上：缺货要**行动**（补货），压货只是**知晓**（钱压着）。中老年店主的注意力在上面。
- 为什么不合并成一张卡（否决丙）：一张卡两种颜色两套口径，读起来要来回切上下文；两张卡可以各自收起。
- ⚠️ 概览页加这张卡**不是零成本**，见 §六「代价」—— 它现在没有缺货榜需要的三个数据源。

### 决策 4：**没人设安全库存时怎么办**（这一条最关键，推荐 **乙**）

现状：`safety_stock` 默认 0 ⇒ **新装的软件、或从没设过安全库存的店，这个榜永远是空的**。

| 选项 | 表现 |
|---|---|
| 甲 | 不显示这张卡（与压货榜「没数据就整卡不显示」一致） |
| **乙（推荐）** | 显示一张**引导卡**：「还没设过『安全库存』——设了之后，快没货时这里会提醒你」+ 一行「怎么设：商品页 → 编辑 → 安全库存」 |
| 丙 | 自动按「近 30 天日均销量 × 7」建议一个值 |

- 否决甲：用户会以为「这功能是坏的」，而不是「我没配」。
- 否决丙：要算销量趋势，是另一个功能，且自动填的数字用户不信任。

### 为什么库存页是「零成本」，概览页不是

| 页 | 已有数据 | 缺什么 | 代价 |
|---|---|---|---|
| 库存页 | `products` · `_book` · `_inTransit` · `unsyncedByProduct` | **什么都不缺** | **+0 查询**，纯内存筛选排序（几千商品 = 亚毫秒） |
| 概览页 | 只有 `stockTop` 一次 | `products`（含 safety/cost_price）· 账面 · 在途 · 未同步 | 见 §六 |

⚠️ **库存页的 `products` 已经不是「前 200 个」**：它用的是
`widget.products.listForExport(active: true)`（`stock_page.dart:540`），
注释写着「用 `list()` 时第 201 个商品在库存页根本不出现（2026-10-27 现实用户暴雷）」。
⇒ 缺货榜接在它后面是安全的。**概览页必须同样用 `listForExport(active: true)`，
不能图省事用 `findAll()`（默认 `limit: 200`）** —— 否则商品过 200 的店，
缺货榜会静默少掉后面全部商品，而「缺货」正是最不能少的那一类。

### 显式不做的

- **不新增 `lowStockTop` 一条「直接算出在店可售」的 SQL**（洞 2：core 看不到 `unsynced`）。
- **不改 `stockTop` 的 `JOIN` 为 `LEFT JOIN`**（会污染压货榜的「待校准」计数，见洞 1）。
- 不复用 `stockTop` 的扫描结果（同上，复用即继承 INNER JOIN）。

## 六、概览页的代价（这一条要你点头）

概览页现在**没有**缺货榜需要的三个数据源。三种做法：

| 选项 | 做法 | 代价 | 风险 |
|---|---|---|---|
| **甲（推荐）** | 复用现有 `stockAggregates()` + `inTransitByProduct()` + 读一次商品列表 | 实测约 **+130 ms**（两次全表聚合 50 / 85 ms）+ 一次商品表读 | 零新 SQL，全部是被测过的方法；但概览页首帧从 320 ms 涨到 ~450 ms |
| 乙 | 专用一条 SQL（上面那两个聚合并进去，省一次往返） | 约 **+70~90 ms** | 新 SQL 要考虑索引与解释计划；且仍要读商品列表 |
| 丙 | 概览页只显示「缺货 N 个 → 去库存页看」，不放明细 | **+0** | 用户要多点一次；但缺货的真正处置本来就在库存页 |

我倾向**甲**（0.45 s 的首帧在这个数据量下可接受，且不引入新 SQL）；
如果你觉得概览页不该再慢，**丙** 是最省的折中。

⚠️ **还有一个 Android 的问题**：概览页现在**没有** `stockDelta` 参数
（`OverviewPage` 的构造参数里没有），所以手机壳上的缺货榜会**少算未同步** ——
与库存页口径不一致。两条路：① 给概览页加 `stockDelta`（与 `stock_page` 同款）；
② 手机壳的概览页不显示缺货榜（用丙的计数占位）。**推荐 ①**，否则同一台手机上两个页面数字不一致。
