## 零、结论速览

| 方案 | 结论 | 一句话 |
|---|---|---|
| **数据封存（归档）** | ✅ **值得做，但不是现在** | 技术上可行，但**库存/往来是累计量**，迁走老流水必须留「结转流水」，且**老单不能再退货** —— 这是产品取舍，不是技术问题 |

documents — a product trade-off. Splitting tables across files and streaming load are both rejected.

## 一、数据封存：技术可行性

### 1.1 为什么「只挪 documents」不行（这是最容易被忽略的一点）

神算子的库存/资金/往来**不是余额表，是流水求和**（`Agents.md` §二·4）：

```
库存 = SUM(stock_ledger.quantity)
资金 = accounts.initial_balance + SUM(money_ledger.amount)
往来 = SUM(party_ledger.amount)
```

⇒ 把某个日期之前的流水挪到归档库，**主库的库存、余额会立刻变少**。
这不是 bug，是「真相在流水」这条设计的必然结果。

**唯一正确形态**：归档时在主库**留一条「结转」流水**（carry-over），数量/金额 = 被归档区间的净和。
这样 `SUM` 仍然正确，且结转本身也是一次「插入」（不违反纪律 2）。

### 1.2 归档必须整组迁出

一张单据牵动六张表（`documents` / `document_lines` / `stock_ledger` / `money_ledger` /
`party_ledger` / `settlements`）。**不能只迁单据不迁流水** —— 那会让「单据在、流水不在」，
核销与退货全部失效。所以归档的单位是**时间区间**，不是「某类单据」。

### 1.3 三个会断掉的功能（产品取舍，必须你拍）

| 功能 | 归档后的后果 | 可否补救 |
|---|---|---|
| **退货** | 原单在归档库 ⇒ 详情页发起的退货**找不到原单**（退货成本要按原单比例回退） | 可以：退货时先查归档库（ATTACH），但跨库 JOIN 慢且复杂 |
| **核销** | 老单不能再被收款单核销 | 同上 |
| **跨区间报表** | 「今年 vs 去年」要同时查两个库 | ATTACH 可查，但两库分别聚合再合并 |

**我的判断**：个体户真正会「翻旧账」的场景是**退货与对账**，而这两件恰好是最容易断的。
所以封存规则必须保守 —— 比如「结清 + 超过 3 年 + 无退货记录」。

### 1.4 技术上可行（已验证过的部分）

- **ATTACH 跨库查询**：同一进程内可以 `ATTACH '归档.db' AS old`，SQL 直接 JOIN。
  代价：跨库 JOIN 走的是「逐行查另一个库」，比同库慢一个量级 —— 所以只适合「偶尔查一次」。
- **归档文件仍是 SQLite**：能导出、能改名、能被本软件重新打开（与报告 §5.1 的要求一致）。
- **文件内嵌时间区间**：写在库里一张 `archive_meta` 表（区间起止 + 生成时间 + 版本），
  比写进文件名更稳（用户改名不影响识别）—— 这一点报告里的想法方向是对的，只是位置该在**库里**而不是文件名里。

### English

Stock/money/party balances are **sums of ledger rows**, so moving old rows out silently shrinks balances.
Archiving must therefore insert a carry-over ledger row. Archiving also breaks returns, settlements and
cross-period reports on old documents — a product trade-off. ATTACH works for occasional lookups but is
an order of magnitude slower across databases.

## 二、数据封存：什么时候才该做

| 场景 | 单据量估算 | 库体积估算 |
|---|---|---|
| 个体户 10 年（每天 20 单） | ≈ 7.3 万 | ≈ 130 MB |
| 个体户 10 年（每天 30 单） | ≈ 11 万 | ≈ 200 MB |
| **本次测试库** | **26.2 万** | **478 MB** |

⇒ 测试库已经是「10 年真实用量」的 **2.4 倍**。而在这个量级上：
- 启动 14 ms（三台机器一致）
- 切页 158–374 ms 首帧 / 380–800 ms 稳定

**所以现在的问题不是「数据太多」，而是「每次切页都在重跑查询」** —— 那是另一件事（已部分修）。

**建议的触发阈值**（等你确认后写进文档）：
- 库 > 1 GB，或
- 单据 > 30 万，或
- 用户反馈「翻旧单明显变慢」

到那时再做，且**先做「结转 + ATTACH 只读查询」这个最小闭环**，不要一上来做自动归档。

### English

A 10-year real-world maximum is ~110k documents / ~200 MB; the test database is already 2.4× that.
So the current problem is repeated queries per page switch, not data volume. Suggested trigger:
database > 1 GB or > 300k documents.

## 三、拆表到多文件：为什么我建议否掉

报告 §5.1 提的「把几张表拆成独立文件」，在 SQLite 上有四个硬问题：

1. **跨库不能建外键**。`document_lines.document_id` 指向另一个文件的 `documents` —— 约束直接没了，
   而本项目大量不变量靠外键兜底。
2. **跨库事务不保证原子性**。ATTACH 下的事务崩溃时可能只提交了一个库 ⇒
   「单据写了、流水没写」这种最坏状态。
3. **与「拷一个文件就走」冲突**。现有承诺是「数据目录 = 一个 `shensuanzi.db`」，
   用户（中老年）会拷、会备份、会挪盘。多文件后「拷漏一个」= 数据不全，且**他看不出来**。
4. **跨库 JOIN 慢一个量级**，而本项目的核心查询几乎都是 JOIN。

**唯一的合理形态**就是「冷数据整组迁到独立文件」= 第一节的数据封存，**不是按表拆**。

### English

Cross-database foreign keys and atomic transactions are unavailable in SQLite; splitting tables would
break invariants and the "copy one file" promise. The only sound form is archiving cold data as a whole,
not splitting by table.

## 四、流式加载：为什么我建议否掉

报告 §5.1 自己写了「较为麻烦，须慎重」。补三条实测依据：

1. **瓶颈不在「数据量大」**：商品页首帧只有 **7 ms**（数据瞬间就出来了），
   2.7 秒的尾段是**每帧重跑查询**造成的 —— 那个已经修了（`_rows` 从 getter 改成缓存）。
   流式加载解决不了「每帧查库」。
2. **流式会引入新的体验问题**：数据一条条蹦出来，对中老年用户比「等一下再一次性出来」更困惑；
   而且滚动时列表高度变化会导致滚动位置跳动。
3. **事务一致性**：分页流式读取意味着跨多个事务读，期间若有写入，用户会看到「前后不一致」的列表
   （比如同一张单出现两次）。

**替代方案**（如果将来真需要）：保持一次性读取，但把「取数」与「渲染」分离 ——
先 `await` 一次取完（不阻塞 UI 的 isolate 或后台），再一次性渲染。这比流式简单得多。

### English

The products page renders in 7 ms; its 2.7 s tail was per-frame re-querying, now fixed. Streaming solves a
non-existent problem and adds jitter, height changes and cross-transaction inconsistency.

---

## 五、建议

1. **数据封存**：写进「候选项」，等**库 > 1 GB 或单据 > 30 万**再启动设计。
   启动时先做最小闭环（结转流水 + ATTACH 只读查询 + `archive_meta` 表），不做自动归档。
2. **拆表 / 流式**：从长远方案里**划掉**，理由见三、四节。若将来有人重提，先回答这四条。
3. 真正该继续做的是**已量到的两件事**：切页 380–800 ms 的构成（等 B-2）、
   以及 `business_day`（已裁定 ③ 乙案，明天实施）。

### English

Archive: park as a candidate until the database exceeds 1 GB / 300k documents. Strike out table splitting
and streaming. Continue with the measured work: page-switch breakdown (B-2) and `business_day` (decided).
