## 零、结论速览

1. **可做，且大部分成本很低** —— 因为最难的那部分（识别损坏）SQLite 已经提供了，
   而「借一个健康的文件头」这个技巧实测能把**文件头损坏**的库**全部救回来**。
2. **但「抢救」不等于「恢复」**：神算子的账靠四张流水表求和（`Agents.md` §二·4），
   救回一部分行 = **账不平**。所以抢救的产物必须是**新库 + 一份「哪些数据不完整」的报告**，
   绝不能静默覆盖原库。
3. **建议分三层**：P0 备份回滚向导（1–2 天）→ P1 只读抢救导出（3–5 天）→ P2 页级扫描（**不做**）。
4. **现在最缺的不是技术，是出口**：库打不开时用户只看到「重试 / 换一个文件夹」，
   而他手里的备份（每日自动 + 迁移前 `.before-vN`）**没有任何界面能选**。

### English

Feasible, and mostly cheap: SQLite already tells us what is corrupt, and grafting a healthy 100-byte
header onto a header-damaged file recovers everything (measured). But rescue is not recovery — balances are
sums over four ledger tables, so partial salvage means unbalanced books. Output must be a **new database
plus a completeness report**, never an in-place overwrite. Recommended: P0 backup rollback wizard (1–2 days),
P1 read-only salvage export (3–5 days), P2 page-level scan (not doing it).

## 二、实测：四种损坏形态下 SQLite 的表现

方法：用随仓 `tool/schema_snapshot.json`（v6）建一个 100 张单 / 200 行的库，
人为制造四种损坏，再用只读连接逐表 `COUNT(*)`。

| # | 损坏形态 | `integrity_check` | 能否打开 | 可读行数 |
|---|---|---|---|---|
| 0 | 未损坏（基线） | ok | ✅ | 300 |
| 1 | 一页叶子/索引页整页清零（模拟坏道） | ok（那页是索引） | ✅ | **300（无损）** |
| 2 | **文件头 100 字节清零**（被别的东西覆盖） | `file is not a database` | ❌ | **0** |
| 3 | **文件截断到 60%**（拷贝中断 / 断电） | `database disk image is malformed` | ❌ | **0** |
| 4 | 只坏一个索引的根页 | `malformed` | ✅ | **300（无损）** |

**读出来的三条结论**：

1. **索引坏了不影响读数据** —— 只要查询不走那个索引（`COUNT(*)` 走全表扫描）。
   ⇒ 抢救时**先丢掉全部索引**再读，成功率立刻上一个台阶。
2. **文件头坏 = SQLite 连页大小都读不出**，直接拒绝，一行都读不到。
3. **截断 = 头里的「页数」大于实际页数**，同样直接拒绝。

### English

Measured on a 100-document database: damaged index pages cost nothing (300/300 rows still readable);
a zeroed 100-byte header and a truncated file both yield **zero** rows because SQLite refuses to open.

## 三、三个关键发现（决定可行性）

### 发现 1：文件头坏 —— **借一个健康的头就能全救回来**

头 100 字节里放的是页大小、编码、页数等**与数据无关的元信息**。
把同版本空库的头贴回去，实测**数据全部读回（100 + 200 行）**。

实现极简：`Db.open(临时空路径)` 建一个空库 → 读它的前 100 字节 → 贴到坏库的副本上。
**前提**：页大小相同、schema 版本相同（都是本程序建的库，必然满足）。

### 发现 2：截断 —— 改页数、补零都**无效**

| 尝试 | 结果 |
|---|---|
| 把头里的页数改成实际页数 | ❌ 仍然 `malformed` |
| 补零回原大小 | ❌ 仍然 `malformed` |

原因：截断丢的是**页本身**（某张表 B 树的一部分），不只是元信息。
⇒ 这类损坏只能靠**逐页扫描**（SQLite CLI 的 `.recover` 就是干这个的），成本高、收益低。
**结论：不做**（见 §六）。

### 发现 3：抢救必须先「丢索引」

`integrity_check` 会因索引坏而报 `malformed`，但那只是**索引**坏了。
抢救的正确顺序是：`DROP INDEX`（在副本上）→ 逐表读 → 写进新库 → 重建索引。

### English

A header-damaged file can be fully recovered by grafting a healthy 100-byte header (measured). Truncation
cannot be fixed by patching the page count or zero-padding — the pages themselves are gone. And salvage must
drop indexes first, because a broken index makes `integrity_check` cry "malformed" even when all rows are fine.

## 四、建议的方案：三层，按成本递增

### P0 · 体检 + 备份回滚向导（**推荐先做**，1–2 天）

**入口**：`brokenDatabase` 错误页加第三个按钮「**数据体检与恢复**」。

| 步骤 | 做什么 |
|---|---|
| 1 | 对坏库跑 `PRAGMA quick_check`（478 MB 实测 850 ms）+ 逐表 `COUNT(*)`，给出「哪张表读不出来」 |
| 2 | 列出**所有可用的恢复源**：每日备份（含时间、大小、`quick_check` 结果）、`.before-v{N}` 迁移备份 |
| 3 | 用户选一份 → **先把当前坏文件改名留档**（`shensuanzi.db.broken-<时间>`）→ 把选中的那份复制成 `shensuanzi.db` → 重启进主界面 |

**为什么这一步价值最高**：绝大多数真实场景（误删、覆盖、升级出错）**根本不需要抢救技术**，
只需要「让他看见自己有哪些备份、并且敢点」。现在这些文件在磁盘上，但**界面上不存在**。

#### ✅ 已落地（2026-10-29）—— 与上面原计划的四处偏离，都记了理由

| # | 原计划 | 实际做法 | 为什么改 |
|---|---|---|---|
| 1 | 按钮叫「数据体检与恢复」 | **「找回数据」** | 用户补充建议：「体检 / 恢复」像医生下诊断；「找回数据」是他自己的话 |
| 2 | 对**坏库**跑 `quick_check` 逐表统计 | **不对坏库做任何检查**，只体检**候选备份** | 坏库已经打不开了，再花 850 ms 查它一遍对用户毫无用处；用户要的是「哪份能用」 |
| 3 | 直接列出可用恢复源 | 每份都给出 **单据数 + 最后一张单的日期** | 只给时间戳用户没法判断「这份里有没有我要的东西」；这两项是他唯一能验证的信息 |
| 4 | 复制选中的那份覆盖 | 先**改名留存**（`.broken-<时间>`，含 `-wal` / `-shm`），再复制；失败自动回滚 | 用户补充建议：「原来的文件我们帮你留着了」是恐慌的解药。`-wal` 必须一起挪，否则新库一开就被旧 WAL 覆盖 |

**另外两条实现细节**（都是踩出来的）：

- 体检用 `immutable=1` 只读打开。普通的 `mode: readOnly` 打开 WAL 库**仍会创建**
  `-shm` / `-wal` —— 体检十次就在「神算子备份」里留二十个空文件，而那个目录
  正是用户最需要看得懂的地方。实测：`immutable` 打开前后目录内容逐字相同。
- 错误页文案整段重写，**不出现「损坏 / 数据库」**（用户补充建议：中老年用户看到
  「数据库损坏」第一反应是「我是不是把电脑弄坏了」）。现在的说法是
  「数据文件**暂时**打不开 → 别担心，软件每天都会自动备份 → 点「找回数据」」。

### P1 · 只读抢救导出（3–5 天）

**前置铁律：只操作副本**。先把坏库复制成 `rescue-work.db`，原件一个字节都不碰。

> **2026-10-29 用户补充建议（做 P1 时必须照做）**：
>
> 1. **副本必须真复制**：用 `File.copySync` 拷到**临时目录**，在副本上做「借头」「砍索引」。
>    原文件**设为只读**（`File.setLastModified` 不够，要 `attrib +R` / `chmod`）——
>    防的不是程序，是**手滑**（用户自己拿工具去改原文件）。
> 2. **报告文案不许出现 SQL 术语**。不要写「表 documents 恢复 1234/1300 行」，
>    要写「**成功找回了 100 笔进货单，其中 2 笔的明细可能缺失，已放到「待确认」列表**」。
>    判据：用户读完知道「我损失了什么、下一步做什么」，而不是「有个叫 documents 的东西坏了」。
> 3. **「不完整」必须是一个可操作的列表**，不是一个数字。缺明细的单据要能被用户逐条打开看
>    —— 否则他只能整批接受或整批放弃，两种都是赌博。

| 步骤 | 做什么 |
|---|---|
| 1 | 尝试打开副本；打不开 ⇒ 走「借头」（§三·发现 1）；仍打不开 ⇒ 放弃并说明原因 |
| 2 | `DROP INDEX` 全部索引（副本上） |
| 3 | 逐表 `SELECT *`，**按业务单元**判断完整性（见 §五） |
| 4 | 把完整的业务单元写进**新库**（`shensuanzi-抢救-<时间>.db`，schema 用当前版本建） |
| 5 | 生成**抢救报告**：每张表救回 N 行 / 应有 M 行、哪些单据不完整、哪些表完全读不出 |
| 6 | 界面上让用户选：「用抢救结果继续」（切到新库）或「先留着，我再想想」 |

#### ✅ 已落地（2026-10-29）—— 以及**六个实测更正**

落地时逐条验证，有六条与原计划不同，**都是踩出来的**，不记下来下次还会踩：

| # | 原来的想法 | 实测真相 | 后果 |
|---|---|---|---|
| 1 | 「借一个健康的头」就能全救回 | **必须同时把「数据库页数」改成真实值**（头偏移 28..31）。只贴头 ⇒ 能打开、`quick_check` 也过，但**一行都读不出** | 旧实验的 300 行小库恰好页数与空库接近，掩盖了这个 bug。测试要用**数据量够大**的库才钉得住 |
| 2 | 逐表 `SELECT *` 读 | 坏页会让**整表失败**（`database disk image is malformed`）⇒ 一行都拿不到 | 必须逐 `rowid` 分批 |
| 3 | 分批就够 | 一批 500 行跨十几页，**一页坏 ⇒ 整批 500 行全丢**。84 页的库坏 5 页时，`batch=500` **一张单据都读不出** | 失败必须**二分重试到单行**，把损失精确到坏页上那几行 |
| 4 | 只读打开副本最安全 | ① 只读连接上 `DROP INDEX` **静默失败**（被 catch 吞掉）⇒ 索引还在 ⇒ 读表走坏索引 ⇒ 全读不出；② `immutable=1` 会**忽略 `-wal`**，而 `DROP INDEX` 的改动就在 wal 里 | 副本用**可写连接**：砍索引 + 读数据同一条连接 |
| 5 | 打开失败再借头 | `sqlite3.open` 是**懒打开**，头坏的库也「打开成功」；一旦真读，SQLite 把它当空库处理，实测能把文件搞到只剩几百字节 | **先验头**（前 16 字节魔数）再打开 |
| 6 | 读不出就是没数据 | 根页坏时 SQLite **不报错、直接返回空表**（0 行、0 坏批） | 加判据：所有业务表 0 行 + 文件不小 ⇒ **明确报「读不出任何数据」**，不许出个空报告让用户以为里面本来没东西 |

**另外两条 Dart 平台坑**（写文件时踩的）：

- `RandomAccessFile` **没有「随机写且不截断」的模式**：`FileMode.write` / `writeOnly`
  在 Windows 上都截断（实测 1000 字节变 3 字节），`append` 又是 O_APPEND（`setPositionSync`
  被忽略，写入永远在末尾）。只能「读全部 → 改 → 整体写回」。
  内存代价：一次 `Uint8List` = 库大小（478 MB 库就占 478 MB），只在「头坏了」这条罕见路径上跑。
- SQLite 头里「页大小 = 1」表示 **65536**（2 字节放不下）。不处理这条，65536 页大小的库会被当成 1 字节页。

**没做的那一步**（第 6 条原计划的「用抢救结果继续」）：
产物落在「神算子导出」文件夹里，**不自动切过去** —— 抢救结果不完整，用户该先看看报告
再决定。要切的话走「找回数据」那条路（把产物当备份接回去），逻辑已经现成。

### P2 · 页级扫描（**不做**，除非出现真实案例）

要读出「截断」的库，得自己解析 SQLite 页格式（或用 `SQLITE_ENABLE_DBPAGE_VTAB`），
成本约 1–2 周，而它能覆盖的场景（文件被截断）在真实世界里**几乎总是伴随备份可用**。
**先不做**，等真出现「没有备份 + 文件被截断」的案例再说。

### English

P0: health check + backup rollback wizard, entered from the existing error page — highest value, lowest cost.
P1: read-only salvage into a **new** file, working on a copy only, dropping indexes first, judging
completeness per business unit. P2 (page-level scan) not doing it: costly, and truncation almost always
comes with a usable backup.

## 五、最关键的约束：**救「业务单元」，不是救「行」**

神算子的账不是余额表，是**四张流水表的求和**（`Agents.md` §二·4）：

```
库存 = SUM(stock_ledger.quantity)
资金 = accounts.initial_balance + SUM(money_ledger.amount)
往来 = SUM(party_ledger.amount)
核销 = SUM(settlements.amount)
```

⇒ 救回「单据在、流水缺」的一行，等于**制造一笔对不上的账**，比不救更糟（用户会拿它当真）。

**所以完整性判据必须按单据分组**：

| 判据 | 处理 |
|---|---|
| 单据 + 它的全部 lines + 它的全部流水 + 它的 settlements **都在** | ✅ 完整，可导入 |
| 缺任何一项 | ⚠️ 标记「不完整」，**默认不导入**，在报告里列出单号让用户自己决定 |
| `products` / `parties` / `accounts` 缺行 | ⚠️ 该行引用的单据全部降级为不完整 |

报告要给用户看得懂的话，例如：
「共 26,261 张单据，**26,240 张完整**、21 张缺少流水（已列出单号）。建议先用抢救结果核对，
确认无误后再继续开单。」

### English

Balances are sums over four ledger tables, so a salvaged document without its ledger rows is worse than
nothing — it produces books that silently disagree. Completeness is judged **per document group**;
incomplete groups are reported (with document numbers) and excluded by default.

## 六、工作量、优先级与不做的事

| 项 | 工作量 | 价值 | 建议 |
|---|---|---|---|
| P0 体检 + 备份回滚 | 1–2 天 | **高**（覆盖绝大多数真实场景） | ✅ 先做 |
| P1 只读抢救导出 | 3–5 天 | 中（罕见但一旦发生就是全部身家） | ✅ 接着做 |
| P2 页级扫描 | 1–2 周 | 低（场景罕见） | ❌ 不做 |
| 「借头」技巧 | 半天 | **高**（把头损坏从「全丢」变成「全救回」） | ✅ 含在 P1 里 |
| 手机镜像反哺 | 3 天 | 低（镜像不是权威数据、可能不全） | ❌ 不做，只在报告里提一句「手机上的镜像也可作为参考」 |

**风险与对策**：

| 风险 | 对策 |
|---|---|
| 借头把库弄得更糟 | 只对**副本**操作；原件永不打开写入 |
| 抢救结果账不平 | 按业务单元判完整；不完整的默认不导入；报告写清 |
| 用户以为「抢救 = 完好如初」 | 报告首行就写「这是**抢救结果**，不是原始数据，请核对后再用」 |
| 备份本身也坏 | 每份备份在选择时都跑 `quick_check`，坏的那份标红并说明 |

### English

P0 first (covers most real cases), then P1 including the header-graft trick; page-level scan and phone-mirror
reimport are not worth it. All work happens on a copy; completeness is per business unit; every backup is
verified before being offered.

## 七、一句话总结

**这个功能的难点不在「怎么读出数据」，而在「让用户在崩溃的时候看见自己其实有备份」。**
技术侧最值钱的不是页级解析，而是那个 100 字节的借头技巧 + 「先丢索引」这个顺序。

### English

The hard part is not reading bytes out of a damaged file — it is showing a panicking user that backups
already exist. Technically, the two things worth building are the header graft and dropping indexes first.
