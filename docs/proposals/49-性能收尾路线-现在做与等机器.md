## 二、栏 A：现在就能做（开发机可自证）

### A-1 单据页列表第一段 132 ms（**推荐**）

现状：`_summaries` 第一段取 200 个 id 要 **131.7 ms**，`EXPLAIN` 是
`SEARCH d USING INDEX idx_documents_ref` + `TEMP B-TREE FOR ORDER BY`。

排序是**日桶表达式** `(occurred_at + 偏移) / 86400000`，**用不了现成索引** —— 所以
「加 `INDEXED BY`」这条已作废（会让排序语义变）。

可试的三条（都能在开发机 478 MB 库上直接量出数）：

| 案 | 做法 | 风险 |
|---|---|---|
| 甲 | 试 `INDEXED BY idx_documents_occurred`：日桶在 `occurred_at` 上单调，让规划器沿时间倒扫，凑满 200 就停 | **不保证等价** —— 同一天内次序由 `created_at` 决定，沿 `occurred_at` 扫会打乱。**必须先写一条「排序结果与旧实现逐行一致」的对照测试**，不一致就否决 |
| 乙 | 加复合索引 `(occurred_at, created_at)`，再让 `ORDER BY occurred_at DESC, created_at DESC` 走它 | 需要 schema v6 + 迁移；且日桶边界（时区）会与表达式排序有细微差异 |
| 丙 | 不改查询，只把「最近 30 天」的窗口继续收窄（默认档已经 57.6 ms，够用） | 收益为零，只对「全部」有用 |

**建议**：先做甲，**以对照测试为前提** —— 一致就采纳（预计 132 → 十几 ms），
不一致就当场否决、不硬上。乙留到确实需要动 schema 时一起做。

> ### ✅ 已执行（2026-10-28 21:50）：**甲案否决，实测更慢**
>
> | 写法 | 实测 p50 |
> |---|---|
> | 现状（规划器自选索引） | **136.7 ms** |
> | 甲：`INDEXED BY idx_documents_occurred` | **155.0 ms** |
> | 乙：`INDEXED BY idx_documents_ref` | 133.9 ms |
>
> **为什么**：`ORDER BY` 是日桶表达式，任何索引都用不上 —— **排序那一步省不掉**，
> 强换索引只是让扫描变贵（多走一遍索引 + 回表）。**按裁定「实在不行就维持现状」，132 ms 保留。**
>
> ### ⚠️ 但量到一个新选项（丙），需要你裁定
>
> 把排序从「日桶 + created_at」换成**纯 `created_at DESC, id DESC`**：
>
> | 写法 | 实测 p50 |
> |---|---|
> | 日桶（现状） | 136.7 ms |
> | 纯 created_at（不加提示） | 123.7 ms |
> | 纯 created_at + `INDEXED BY idx_documents_created` | **0.1 ms** |
>
> **代价是语义变了**：`created_at` 是**录入时刻**，不是业务日期。后果 ——
> **补录昨天的单会排到今天最上面**（个体户补录很常见）。
>
> 现状的日桶排序是 #26①（2026-10-18 你的裁定）专门为「同一天按录入时间倒序、
> 跨天按业务日期」设计的，这次等于要改它。**这是产品判断，不是技术判断**，所以我不动。
>
> 三条路：**① 维持现状**（132 ms）/ **② 改纯 created_at**（0.1 ms，补录单会窜到最前）/
> **③ 加 `business_day` 列 + `(business_day, created_at)` 索引**（也快，但要 schema v6 + 回填 + 双写）。

### English

The list's first stage costs 131.7 ms and sorts by a **day-bucket expression**, so no existing index applies
(the earlier `INDEXED BY` idea is void — it would change ordering). Option A tries `idx_documents_occurred`
**only if a row-by-row equivalence test passes**; otherwise reject on the spot. Option B (composite index)
needs schema v6 and is deferred.

### A-2 `perf_bench` 加门禁（**推荐，最便宜**）

现在 `count_roots` / `list_roots` 只报数、不判红。建议加一条阈值断言：
**`list_roots` > 200 ms 或 `count_roots` > 120 ms 即退出码非零**，与现有 `--explain` 的「不许出现 SCAN」同级。

理由：这次能发现「测的不是跑的」，靠的是人肉看；下次没人看就又会漏。

### English

Turn the two new benchmarks into a gate: non-zero exit if `list_roots` > 200 ms or `count_roots` > 120 ms.

### A-3 备份校验搬进 isolate（可选）

现状 `quick_check` 仍要 **850 ms**，且跑在主 isolate（`Db.open` 不能跨 isolate）。
搬进 isolate 需要在该 isolate 里重新初始化 sqlite3 原生库 —— 属独立改造，有「隔离环境加载不了」的风险。

**建议**：先不做。850 ms 已经不影响「备份能完成」，而这次的真问题是切页。
若你希望「备份时完全无卡顿」，我再单独立项。

### English

Moving the `quick_check` into an isolate needs sqlite3 re-initialised there. Recommended: skip for now —
850 ms no longer breaks backup, and page switching is the real issue.

### A-4 补 `docs/perf_test_guide.md` 的埋点流程（**推荐**）

这五轮都是靠口头传「打哪个包、点什么、发哪个文件」，已经出过两次岔（跑成小库、忘带库信息）。
建议把「打埋点包 → 跑哪几步 → 发哪个文件 → 怎么判读」写成固定小节，下次照着做。

### English

Document the trace workflow (build command, steps, output file, how to read it) so the next round needs no back-and-forth.

## 四、明确不做

- **归档 / 分表 / 流式加载**（原报告 §5.1 长远方案）：结构性改动，必须在「查询浪费」清干净之后再谈，
  否则会把 SQL 问题埋进新架构里。
- **给 `settlements` 加复合索引**：实测消掉了 `TEMP B-TREE FOR count(DISTINCT)`，但耗时 215.7 → 218.0 ms，**无效**。
- **库存页查询移出 `build()`**：已试过并撤回（会让「别处改了库存，页面看不见」），判据见台账。

### English

Not doing: archiving/sharding/streaming (must wait until query waste is gone); the settlements composite index
(measured: no gain); caching the stock page (breaks cross-page refresh).

### English

(half a day, gated by an equivalence test). Shortest reply: `A-1 甲 + A-2 + A-4`, or `A-2 + A-4 only`.
