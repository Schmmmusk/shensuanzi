| 查什么 | 结论 | 状态 |

### ⚠️ 但扫出一个**新隐患**（本次未修，见 **D-e**）

`rebuildMirror()` 依赖手写的顺序常量：

```dart
static const List<String> applyOrder = <String>[
  Schema.products, Schema.parties, ..., Schema.settlements,
];
```

现有测试只断言了**顺序**（products 必须在 documentLines 之前），**没有断言覆盖性**。
后果：将来 `Schema.createStatements` 加了一张表、忘了加进 `applyOrder` ⇒
重建时**那张表既不被 drop 也不被重建**，旧数据静默留着（正是 F19 同一类"重建不完整"）。

### English

A repo-wide sweep closes the blast radius: only two `INDEXED BY` sites (both on
`idx_documents_occurred`) and only one `DROP TABLE` site (`rebuildMirror`), all covered by
the F19 fix. But the sweep found a sibling risk: `applyOrder` is hand-maintained and no test
asserts its *coverage* — adding a table to the schema without registering it there would
silently leave stale data across rebuilds (see D-e).

## 三、逐条理由（为什么这么推荐）

### D-a 适老化（F18，推荐甲：现在就修）

真机证据（`docs/复跑发现-v0.6.5.md` §二·补 F18，超大档截图）：日期折成 `2026-1` / `0-26`、
**收款「金额」输入框被挤成一条缝**（必填项）、**「全款」按钮只有 43 px 高且文字被裁**。

- 这三处**恰好打在目标用户身上**：「界面大小」这个开关就是为看不清的人准备的，
  而它在这个档位把必填输入框和常用按钮压没了 —— 属于「功能对目标用户失效」，不是美观问题。
- **代价**：`sale_page.dart` 的收款区要改布局（账户/金额在超大档改上下两行 + `全款` 并进 `Wrap`），
  预计动 2 处 + 3 条测试；日期格给最小宽度，1 处 + 1 条测试。
- 选**乙**的代价：这个缺陷会一直留在"最需要它的人"手里；选**丙**只是砍一半工作量，
  但 F18-1（日期折行）同样会让人读错日期，不建议单独留。

### D-b F16 徽标（推荐乙：先挂起）

原假设（路由缓存旧 `shell` 实例）**已被自己的测试反证**（见方案 §2.4）。
现在的判据改成**主机 `documents.created_at`**（主机收到那一刻，秒级，不需要人抢拍）。
第一组数据：主机 20:24:53 收到，我 20:24:44 左右截图 —— **那一刻徽标说的是真话**。

- 换句话说：**F16 很可能不是缺陷**（和 F17 同一类误判）。
- 但定案还需要一次秒级复现，而**它不影响任何功能**（徽标最多晚几秒）。
- ⇒ 挂起，等下次真机跑别的用例时顺带看一眼。选**甲**的话要占用你一次真机操作。

### D-c F9 列表（推荐乙：不加）

详情页已经落地「已确认 · 未结清」。列表那一行**紧跟着**就印「未收 ¥20.00」，
再给状态加后缀是同一句话讲两遍；而且列表行窄，8 个字的状态容易换行。

### D-d F8 与 #26（推荐甲：保持 F8）

两条都是用户自己说的：
- **#26 批 3（2026-10-18）**：退货记录上移，当列表折叠退货单的「救生圈」；
- **F8（2026-10-25 复跑）**：明细提到退货记录上方。

F8 更晚、更具体。而且两条的**意图**（退货/核销不能压到底部）已经用「首屏可见（< 600）」
的断言继续守住 —— 反向灵敏度证明：把顺序挪回去 ⇒ 3 条红。

### D-e `applyOrder` 护栏（推荐甲：加测试）

一条测试就够：`applyOrder` 必须覆盖 `Schema.createStatements` 里**除队列/游标之外**的所有表
（队列表是有意不进 applyOrder 的：重建镜像不能丢用户还没传过去的单）。

代价几行；收益是把 F19 同一类「重建不完整」变成**编译期之后的机械保证**，而不是靠人记得。

### D-f F11 序号列（推荐乙：不加）

导出列是给会计对账用的，`seq_no` 是内部游标，业务上没意义；
而且加列会改变已有导出文件的列数（对账模板要跟着改）。
