# 54 · 经营图表 —— 调研与方案

> **本文双语**：每节先中文，紧随 `English` 段。两段内容等价；若有出入，**以中文为准**。

> **性质**：调研 + 方案。**不含代码**。所有性能数字都是 478 MB / 26.2 万单的真库实测。

> ## ✅ 用户裁定（2026-10-30）：**方向通过，先做查询层，图表 UI 暂不开工**
>
> 原话要点：*「宁可少显示一个数字，也不要显示一个看起来合理、实际上会误导经营决策的数字。」*
>
> 开工前必须先纠正四件事（已并入下面各节，标 **🆕 裁定补充**）：
>
> 1. **营收口径有漏洞**：客户拒收时原送货单被置 `cancelled`（不计营收），而关联的
>    `sale_return` 仍被当作负营收扣掉 ⇒ **这笔本来就没确认收入的交易，反而让销售额变负**。
> 实测这条影响 **458 张单 / ¥45.8 万 / 占销售额 3.9%**（见 §五）。
> 2. **周聚合不能用 `business_day / 7`**：那是「从 1970-01-01 起每 7 天切一刀」，
>    不等于自然周。要按周一起点分组。
> 3. **库存 Top 10 不能按数量混单位比**（500 个 vs 20 箱 vs 80 千克）⇒ 改按**库存成本价值**排序。
> 4. **「每根柱子标金额 + 15sp」在窄窗口/125% 缩放下可能挤** ⇒ 先做**最小原型**验证排版，
>    挤不下就调聚合粒度，而不是为了守规则让图不可读。`Semantics` 还要能**逐日**读，不是一句总摘要。

## 零、结论速览

1. **现状是零图表**：概览页只有两组文字（今日销售 / 要留心），没有任何趋势、对比、占比。
   全仓没有图表库，唯一自绘的是配对二维码。
2. **查询层缺「时间序列」能力**：现有聚合都是「当前快照」（`stockByProduct` / `accountBalances`）
   或「单日汇总」（`todaySummary`），**没有按日/周/月分组**。
3. **实测：图表查询需要一条新索引**。没有它，按类型查 30 天要 **108–144 ms**；
   加 `documents(doc_type, business_day)` 之后 **3.7–6.1 ms**（快 24–29 倍），
   建索引一次性 **184 ms**（26 万单）。
4. **建议不引图表库**，自绘 `CustomPainter`。理由是**中老年可读性要完全可控**
   （字号、对比度、每根柱子标数字），第三方库的默认样式恰恰是最难改的那部分。
5. **营收口径必须先定**：`sale + delivery − sale_return`，且用 `business_day`（v6 新增）
   而不是 `occurred_at` —— 后者会随时区漂移。

### English

No charts today — the overview page shows two text blocks only. The query layer has no time-series
aggregation. Measured: type-filtered 30-day aggregation costs 108–144 ms without a
`documents(doc_type, business_day)` index and 3.7–6.1 ms with it (index build: 184 ms on 262k documents).
Recommend hand-drawn `CustomPainter` rather than a chart library, because legibility for older users must be
fully controllable. Revenue definition must be settled first: `sale + delivery − sale_return`, bucketed by
`business_day`.

## 一、现状盘点

### 概览页现在有什么

| 卡片 | 内容 |
|---|---|
| 今日销售（按单据日期） | 店内销售 N 笔 · ¥X；送货 N 笔 · ¥Y（未签收 M 张） |

| 快捷入口 | 开单 / 库存 / 单据 / 往来方… |

**全是「此刻的数字」，没有「一段时间的形状」。** 用户想知道「这个月比上个月好吗」，
只能自己去单据页翻、心里加。

### 查询层缺什么

| 有 | 没有 |
|---|---|
| `todaySummary(dayStart)` —— 单日按类型汇总 | 按**日 / 周 / 月**分组的金额序列 |

- **v6 的 `business_day` 正好是图表需要的**：它是整数、有索引、不随时区漂移。
  这个列本来是为「单据列表排序」加的，现在成了图表聚合的基础（**零额外 schema 成本**）。
- 自绘有先例：`PairingQrPainter`（`host_service_section.dart`）就是 `CustomPainter`。

### English

for list sorting — is exactly what charts need, at zero extra schema cost.

## 二、实测：图表查询要多久（478 MB / 26.2 万单）

| 查询 | 无新索引 | 有 `(doc_type, business_day)` |
|---|---|---|
| 近 30 天，单指标（`GROUP BY business_day`） | 6.1 ms | 6.1 ms |
| 近 90 天，单指标 | 14.6 ms | 14.6 ms |
| **近 30 天，销售/送货分开** | **143.8 ms** | **6.1 ms** |
| **近 30 天，只查销售** | **108.4 ms** | **3.7 ms** |
| 全历史按日（730 组） | 100.5 ms | 100.5 ms |
| 全历史按月（25 组） | 101.5 ms | 101.5 ms |

**为什么会差 24 倍**：按 `doc_type` 过滤时，规划器走的是 `idx_documents_type_status`，
于是要扫「该类型的全部历史」再筛日期。加了 `(doc_type, business_day)` 之后，
`doc_type=? AND business_day>?` 能一次定位（计划里可见 `SEARCH ... USING INDEX`）。

**代价**：建索引 184 ms（一次性，在 v7 迁移里跑）；每次插入单据多维护一个索引
（26 万单的库上写一单的额外成本 < 1 ms，可忽略）。

**建议**：**加这条索引**（schema v7）。它是「图表能不能做到 5 ms 级」的分水岭。

> 另一个可选优化：全历史 100 ms 的查询**只在打开图表页时跑一次**，不进 `build()`
> —— 这与前面「查询移出 build」的判据一致（查询够贵 + 数据只被本页改动）。

### English

Type-filtered aggregation is 108–144 ms because the planner uses `idx_documents_type_status` and scans
the whole type history. A `(doc_type, business_day)` index brings it to 3.7–6.1 ms. Build cost 184 ms
once; per-insert overhead negligible. Recommend adding it in schema v7.

## 三、该画什么（按优先级）

### 第一优先：近 30 天销售额（柱状图）

- **一根柱子 = 一天**，高度 = 当天销售额（`sale + delivery − sale_return`）
- **每根柱子上面标金额**（不靠高度猜）—— 这是中老年可读性的关键，不是装饰
- 图上直接写一行大字：**「最近 30 天合计 ¥12,340，平均每天 ¥411」**
- 柱子超过 30 根就按周聚合，保持「一屏看完」

> **🆕 裁定补充：不能写 `business_day / 7`。** `business_day` 是「自 1970-01-01 起的日序号」，
> 除以 7 得到的是「从纪元起点每 7 天一刀」，**与日历上的周不对应** —— 跨月/跨年时用户看到的
> 「本周」根本不是他理解的那一周。
>
> 正确做法：先把 `business_day` 还原成日期，再取**该周的周一**：
>
> ```
> weekday = (business_day + 3) % 7   // 1970-01-01 是周四 ⇒ +3 让周一 = 0
> weekStart = business_day - weekday
> ```
>
> 或者直接用 Dart 的 `DateTime.weekday` 算（在纯函数里做，可单测）。
> **口径写死为「周一 ~ 周日」**，并在图上标出周的范围（如 `10/21–10/27`），
> 让用户一眼知道这是哪一周。

### 第二优先：应收 / 应付（横向条 + 数字）

数据**已经有了**（`receivablesSummary` / `payablesSummary`），只是没画出来。
两条横向条 + 各自金额 + 「几家未结」。这条几乎零成本，但解决的是
「我到底欠人多少、人欠我多少」这个每天都会想的问题。

### 第三优先：压货最多的 10 个商品（横向条）

> **🆕 裁定补充：不能按「数量」排序。** 用户举的例子成立：500 个、20 箱、80 千克 ——
> 数字大小说明不了谁压货多（单位不同，且单价差异巨大）。按数量排出来的「Top 10」
> 会把「一箱牙签」排在「十台电机」前面，**误导经营决策**。

**改按「库存成本价值」排序**：`SUM(stock_ledger.quantity) × 当前成本`，取前 10。

- 主指标：占用资金（元）
- 旁边附：数量 + 单位（各自单位，**不求和**）
- 标题写「压货最多的 10 个商品（按占用资金）」，不写「库存最多」

数据来源：`stockByProduct()`（数量）+ `costByProduct()`（成本）—— **两个都已经有了**。

如果确实想做「数量排行」，那必须**按单位分组**（「瓶」类里排、「箱」类里排），
且标题明说「按件数」，不能包装成总量排名。

### 可选：毛利趋势（需要成本数据）

毛利 = `销售额 − 成本`，成本来自 `stock_ledger.total_cost`（退货的成本是正数，要减）。
**技术上算得出来**，但要不要给中老年用户看毛利，是产品判断 —— 建议**先不做**，
等前三个图用一段时间再问。

### 明确不做

| 不做 | 为什么 |
|---|---|
| **饼图** | 中老年读占比最吃力；而且「销售构成」对个体户没什么决策价值 |
| **折线图** | 30 个点连成线，比 30 根柱子难读得多；柱子还能标数字 |
| 实时刷新 / 自动轮播 | 打开时算一次就够，反复重算只会卡 |
| 导出图表为图片 | 有 CSV 导出了，图表截图不是刚需（P2） |
| 手机端图表 | 先桌面；手机屏幕放不下 30 根柱子（P2 可用「近 7 天」） |

### 🆕 裁定补充：先做最小原型，再谈「五条规则」

用户指出的冲突是真实的：**30 根柱子 × 每根标金额 × 字号 ≥15sp × 一屏读完**，
在默认窗口、125% 缩放、窄窗口下**不一定能同时满足**。

所以顺序要反过来：

1. **先做原型**：一个 `CustomPainter` + 一组真实金额分布（用造数库的数据），
   在 1280×720 / 125% 缩放 / 900px 窄窗三种条件下截图看
2. 如果挤 ⇒ **先调聚合粒度**（30 天 → 按周 4~5 根），而不是缩小字号或省略数字
3. 规则可以调整，但**「不让人从高度反推金额」这条不能让**

**`Semantics` 要能逐日读**：一句总摘要不够 —— 读屏用户要能听到「10 月 21 日，¥412」。
做法：整个图表包一层 `Semantics(label: 总摘要)`，再给一个「明细」按钮/可展开列表
（也顺便解决了「看不清图时想抄数字」的问题）。

### 中老年可读性五条硬规则

1. **数字写在图上**，不让人从高度/角度反推
2. **一屏能看完**（≤30 根柱子），多了就聚合
3. **只用两种颜色**（正常 / 退货），不用渐变色阶
4. **图下面必有一句人话总结**（「这个月比上个月多 ¥2,100」），不是让人自己比
5. **字号不小于正文**（≥15sp），对比度按 `ui_principles.md` §二（≥4.5:1）

### English

Priority: (1) 30-day sales bar chart with amounts printed on bars and a one-line total;
(2) receivables/payables bars (data already exists); (3) top-10 stock bars. Optional: gross margin (skip
for now). Not doing: pie charts, line charts, live refresh, image export, mobile charts.
Five legibility rules: print numbers, fit one screen, two colors only, always a plain-language summary
line, font ≥ body size.

## 四、技术选型：自绘，不引库

| 方案 | 优点 | 缺点 |
|---|---|---|
| **自绘 `CustomPainter`（推荐）** | 零依赖；字号/对比度/标签位置**完全可控**；体积不增 | 要自己写约 200 行；无障碍语义要手写 |
| `fl_chart` 等第三方库 | 开箱即用 | 依赖 + 体积；默认样式恰恰是最难改的部分（中老年要的「每根柱标数字」它支持但要调很多）；升级会带来 API 变动 |

**理由**：这个需求的难点**不在画图**（柱状图是最简单的图形），而在**可读性细节**。
第三方库能省的是最容易的部分，省不掉的是最难的部分。

**实现要点**（写代码时照做）：
- 一个 `BarChartPainter`（纯 `CustomPainter`，输入 `List<({int day, int cents})>`）
- **纯函数先算好**：`buildDailySeries(rows) → List<Bucket>`（补零、聚合、算平均）
  —— 这样「补零」这类逻辑可以单测，不用靠截图
- 图表外再包一层 `Semantics(label: '近 30 天销售额，合计 X 元，最高一天 Y 元')`（读屏可用）

### English

Hand-draw it. The hard part is legibility, not drawing. Keep the series-building logic in a pure function
so "fill missing days / aggregate by week" is unit-testable; wrap the painter in `Semantics`.

## 五、口径：必须先定，否则图会撒谎

#### 🆕 裁定补充：营收公式要区分「正常退货」与「客户拒收」

原公式 `sale + delivery − sale_return` 有一个确定的漏洞。用户指出、实测证实：

**拒收的机制**（`rule_engine.dart:553-566`）：未签收的送货单被拒收时，
同一事务里生成一张 `sale_return`（`ref_doc_id` 指向送货单）**并把原送货单置为 `cancelled`**。

于是原公式算出：

```
原送货单：status = cancelled ⇒ 被排除，不计营收
关联的 sale_return：仍被减掉 ⇒ 负营收
结果：这笔从未确认收入的交易，让销售额**变成负数**
```

**实测影响**（478 MB 库，全历史）：

| 项 | 数值 |
|---|---|
| 拒收型（送货作废 + 有退货单） | **458 张** |
| 简单减的净额 | 115,297,524 分 |
| 只减「原单有效」的退货 | 115,755,813 分 |
| **虚减** | **45,828,896 分 ≈ ¥45.8 万（销售额的 3.9%）** |

**正确公式**：

```
营收 = SUM(d.total_amount)
         WHERE d.doc_type IN ('sale','delivery') AND d.status != 'cancelled'
     − SUM(r.total_amount)
         WHERE r.doc_type = 'sale_return' AND r.status != 'cancelled'
           AND 原单(r.ref_doc_id) 存在且 status != 'cancelled'
```

即：**退货只在「原单计入过营收」时才冲减**。原单被作废（拒收）⇒ 这笔交易从未进过营收 ⇒
退货也不该冲减。

**边界**：原单读不到（数据缺失）⇒ 保守**按冲减处理**（不知道就别擅自加回来）。

> 实现上是一次 `LEFT JOIN documents o ON o.id = r.ref_doc_id`。要实测它对
> 30 天窗口查询的影响（预计不大，因为退货单只占少数）。

#### 🆕 顺带发现：送货「在途」算不算营收？（**需要你定**）

实测退货单按原单状态分布：

| 原单状态 | 退货单数 | 金额 |
|---|---|---|
| `cancelled`（拒收） | 466 | ¥458,288.96 |
| `confirmed` | 1365 | ¥456,809.05 |
| **`in_transit`（在途未签收）** | **327** | **¥128,443.62** |
| `settled` | 1362 | ¥475,368.33 |

现有 `todaySummary` 把 `delivery` **全部**算进「今日销售」（只标注「未签收 N 张」）。
所以按现有口径，**在途送货算营收**。

但严格说「在途 = 货还没到客户手上」，算营收偏乐观。两条路：

- **甲（与现状一致）**：算，但图上标一句「含未签收 N 张 · ¥X」
- 乙（更保守）：只算 `delivered` / `settled`，在途单列「在路上」

**我倾向甲**（不改变既有口径、避免「图表和概览页对不上」），但这属于产品判断，等你定。

#### ✅ 已定案（2026-10-30 用户裁定）：**甲**

用户原话：*「我倾向于第一阶段保持与现有 `todaySummary` 一致，避免不同页面对同一经营数据
采用两套口径；但最好在界面上明确说明销售额包含未签收送货，或者至少显示未签收数量。」*

⇒ `dailyNetRevenue()` 的口径就是 `status != 'cancelled'`（含在途），
**并且**图表下方必须有一行说明：「含未签收送货 N 张 · ¥X」（没有在途时这行不显示）。

⚠️ 这条**必须在写 `dailyNetRevenue()` 之前定**，因为改口径会让所有历史图跟着变。

---

| 问题 | 建议口径 | 理由 |
|---|---|---|
| 营收算什么 | **`sale + delivery − 「原单有效」的 sale_return`**（见上） | 拒收不能虚减 |
| 在途送货 | **甲：算，并标注**（待你确认） | 与现有 `todaySummary` 一致 |
| 用哪个时间字段 | **`business_day`** | `occurred_at` 依赖查询时区，换机器/跨时区会让历史图**整体平移** |
| 作废单 | 排除（`status != 'cancelled'`） | 与 `todaySummary` 一致 |
| 盘点 / 调拨 | 不计入营收 | 它们不改钱 |
| 采购 | 不计入营收（是成本侧） | 但可以单独画「进货额」 |
| 空白天 | **补 0 并画出来** | 不补的话「三天没卖」会被画成连续的趋势，误导 |

⚠️ **与现有 `todaySummary` 的差异要说明**：它按 `occurred_at` 算「今日」，
而图表按 `business_day`。两者在正常使用时一致（当天录入当天发生），
但**补录昨天的单**时会出现「今日销售」不含它、图上却算在昨天 —— 这是**正确**的，
但要在文档里写清，避免下次有人当成 bug 修。

### English

Revenue = sale + delivery − sale_return; bucket by `business_day` (not `occurred_at`, which shifts with
timezone); exclude cancelled; skip stocktake/transfer; fill empty days with zero. Document the deliberate
difference from `todaySummary`.

## 五·补、第一批落地状态（2026-10-30）

| 项 | 状态 | 实测/说明 |
|---|---|---|
| schema **v7**：`documents(doc_type, business_day)` | ✅ | 只加索引、不碰行；**26.2 万单 / 545 MB 迁移 1.1 s** |
| `QueryDao.dailyRevenue()` | ✅ | 三条 SQL（销售/送货/退货各一条），**近 30 天聚合 4–5 ms** |
| `buildRevenueSeries()` 纯函数 | ✅ | 补零 + 自然周（周一起）+ 自然月 |
| 口径 | ✅ | `销售 + 送货 − 原单仍有效的销售退货`；在途送货计入并单独给张数 |
| 测试 | ✅ | `revenue_series_test` 9 条 + `schema_test` 的 **v3→v7** 专项 |

**三条被实现证实的判断**：

1. **不能一条 SQL `GROUP BY business_day, doc_type`** —— 规划器会放弃
   `(doc_type, business_day)` 索引，实测 143.8 ms vs 6.1 ms。所以拆成三条。
2. **拒收的退货不能再减一次** —— 原送货单已 `cancelled`、本就不计营收，
   再减就是双重冲减（用户实测 458 张、虚减 3.9%）。SQL 里加了
   `JOIN documents o ON o.id = r.ref_doc_id AND o.status != 'cancelled'`。
3. **周不能用 `day ~/ 7`** —— 那是纪元起算每 7 天一刀，边界既非周一也非周日。

**顺手修的一个真问题**：截断的库 `sqlite3.open` 能成功、一读才抛
`database disk image is malformed`，那句英文**直接进了报告**（违反「不许出现
SQL 术语」）。改成打开前先判「头里记的页数 × 页大小 > 实际大小」，
给一句中文；打开失败也不再拼 `error.message`。

**下一批（UI）**：`BarChartPainter` + 概览页接线 + 应收应付横条。
验收标准不变：478 MB 造数库上切页 `settled < 300 ms`，且数字与 `todaySummary` 同口径对得上。
