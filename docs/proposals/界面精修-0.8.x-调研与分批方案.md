# 界面精修（0.8.x）· 调研与分批方案

> 输入：`docs/reply.md`（2026-11-22，9 节要点 + 11 张截图，目录 `docs/界面精修前截图/`）
> 本文件只做**调研**：每条给出「现状 / 根因（代码位置）/ 改法 / 代价与风险」，
> 并按「能不能一批做完」分批。**未动代码**。

---

## 〇、总结论

1. **用户说的现象全部成立**，没有一条是误解。已逐条落到代码位置（见下）。
2. 有 **3 条是「一行改动」级**（库存页按钮分布、流水页导出位置、商品行分隔线）——
   根因都是同一个：**若干元素挤在 `Wrap` / 默认对齐里，没有显式的「谁跟谁靠右」**。
3. 有 **2 条必须先用工具量**（高缩放弹窗溢出、单据行加「商品与数量」的查询成本）——
   不量就动手只能靠猜。
4. 真正的**结构性工程**只有三件：宽屏宽度上限（壳级）、开单页按纸单重排、设置页拆二级页。
   建议分期，不要与「小改」混在一个交付里。

## 一、通用问题

### 1.1 宽屏不设上限（21:9 / 32:9 视线来回跑）

**现状**：所有页面都直接把内容铺满工作区。全仓只有 4 处 `ConstrainedBox`，都在**弹窗/手册**里，
页面层**没有任何最大宽度**。

**根因**：装配点是 `app_shell.dart` 的 `_content()` —— 它把页面直接放进 `Expanded`，
没有任何容器。各页自己也不管宽度。

**改法**（建议）：在 `_content()` 里加一层「读起来舒服的宽度」容器：

| 参数 | 建议值 | 理由 |
|---|---|---|
| 触发阈值 | 工作区 ≥ **720** 逻辑像素 | 与用户提出的一致 |
| 内容最大宽度 | **min(工作区 × 70%, 上限)** | 用户给的规则；再叠一个绝对上限（建议 **1080**）防止 32:9 上仍被拉成一条 |
| 对齐 | **居中** | 左右留白对称，视线不用来回扫 |

⚠️ **两条必须一起考虑**：
- 表格类页面（单据、商品、库存）**行内是左右两端对齐**（名称左、金额右），
  容器变窄后两端距离缩短 —— 这是**好事**，但需要重跑三页的窄屏护栏（264 那批），
  确认没有把「宽屏正常、窄屏溢出」变成「都溢出」。
- 弹窗、抽屉不受影响（它们是 `Dialog` / `push` 的独立路由）。

**代价**：半天；风险低（一处容器 + 护栏复跑）。**但影响全应用，值得单独一批 + 真机看一遍。**

### 1.2 高缩放（1.75 / 2.0）下按钮与弹窗文字快溢出

**现状**：用户描述为「几乎溢出」，说明**还没到画黄黑条纹的程度，但已经很挤**。
全仓 `showDialog` **36 处**，逐个排查靠人眼不现实。

**这条必须先量**（纪律 20）。建议的测量方式（可自动化）：

1. 写一个**只跑测试、不上真机**的探测：遍历每个对话框的「打开方式」，
   在 `textScale = 2.0` 下 pump，断言 `tester.takeException() == null`
   并记录 `RenderFlex` 的剩余宽度（用 `debugDumpRenderTree` 抓 `constraints`）。
2. 产出一张**清单**：哪些弹窗真的溢出、哪些只是「紧」。只有清单里的才改。

**为什么不能直接改**：`AlertDialog` 的按钮区是 `ButtonBar`/`actions`，
它们的 padding 由主题给；盲目加 padding 会让**正常字号下**变得松散。
真正要改的多半是「**按钮里的文字没有 `Flexible`**」这一类（与本仓已踩过三次的坑同源）。

**代价**：探测 0.5 天 + 按清单修 0.5–1 天。**先出清单，再谈改。**

### 1.3 三大开单页没有标题

**现状**：`sale_page.dart:1195` 的 `build` 直接进 `PopScope`，页面内**没有**任何标题；
而单据 / 商品 / 库存 / 往来 / 账户 / 设置都有 `titleLarge` 标题。
（这恰好是「最需要标题」的三页 —— 用户开单前要确认自己在开哪一种单。）

**改法**：三页各在顶部加一行标题（**居中、加粗、字号大一档**），文案用
「店内销售 / 采购入库 / 送货」；**同构三页一起改**（`page_isomorphism_test` 可以加一条 pin）。

⚠️ 开单页是「一屏塞满输入框」的布局，加标题会挤掉约 40 px 垂直空间 ——
窄屏 + 大字号下需要复跑三页的极窄护栏（108 / 160 那批）。

**代价**：0.5 天（含护栏复跑）。

## 二、逐页

### 2.1 概览页 · 压货榜金额位置

**现状**（截图可证）：金额跟着柱子走 —— `¥1,186.81` 在 63% 处、`¥585.00` 在 55% 处，**每行位置都不同**。
数量（80 个 / 45 个）在最右。

**根因**：`stock_top.dart` 的 `_row()` 把金额作为 `Row` 的**弹性子项**放在名字与柱子之间，
宽度随名字长度浮动。

**两个方案**：

| 案 | 做法 | 好处 | 坏处 |
|---|---|---|---|
| **①（我建议）** | 金额**统一右对齐**（与「数量」同列或紧邻其左），柱子占剩下的宽度 | 一眼能纵向比较金额；读数不用追着柱子跑 | 少了「柱子长度 ↔ 金额」的视觉贴合 |
| ② | 金额精确跟在柱子末端 | 视觉上与柱子贴合 | 每行 x 坐标都不同 —— 用户已经指出「容易误解」 |

**代价**：① 半天（含 2.0 倍字号 + 窄屏复跑）；② 1 天（要算文本宽度，且仍有误解风险）。

### 2.2 三大开单页 · 与纸笔单据的版式差异（**本批最大工程**）

**现状**：现在是「卡片式分行录入」（每行一张卡：商品名 / 数量 / 单价 / 金额 / 删除）。

**纸单版式**（用户给的样例 `34414144_093259858109_2.jpg`）：

```
收款收据
客户名称：__________                    2022 年 __ 月 __ 日
┌──────┬────┬────┬────┬──────────┬──────┐
│品名规格│ 单位│ 数量│ 单价│   金额    │ 备注 │
├──────┼────┼────┼────┼──────────┼──────┤
└──────┴────┴────┴────┴──────────┴──────┘
合计：  人民币(大写) 万 仟 佰 拾 元 角 分  ¥____
付款方：__________        收款方：__________
```

**差异清单**（这些不是"美化"，是**录入习惯**）：

| 项 | 现在 | 纸单 |
|---|---|---|
| 结构 | 一单一卡（纵向堆叠） | **一张表格**（列对齐） |
| 表头 | 客户 / 日期分散在卡片里 | 客户名 + 日期**同一行顶部** |
| 金额 | 每行一个 `¥` | 一列金额 + 底部**合计** |
| 大写 | 无 | 人民币**大写** |
| 签名 | 无 | 付款方 / 收款方 |

**建议**：**不要一次重排三页**。先做**一页**（销售，最常用），用「表格化 + 底部合计条」的形态，
真机跑一周；确认用户接受再复制到采购 / 送货（纪律 18：同构一起改，但**先在一页验证版式**）。

⚠️ 三页共用 `_RowCtl` / `_LineCard` 的**逐字复制**结构（`page_isomorphism_test` 守着一部分）。
重排会推翻现在的卡片布局 —— 那批 pin 需要同步重写（**这是本项真正的成本**）。

**代价**：一页 2–3 天；三页 5–6 天。大写金额需要一个纯 Dart 函数（可测）。

### 2.3 商品页 · 行分隔线对比度

**现状**：`products_page.dart:335 / 342` 用默认 `Divider(height: 1)` —— 默认色 `outlineVariant`
在白底上约 **1.2–1.3 : 1**（肉眼几乎不可见，与之前导航分割线 1.63 是同一类问题）。

**改法**：改用 `AppColors` 里已有的强调色（导航分割线用的 `#73777F`，对比度 4.30），
或 `theme.colorScheme.outline`（约 3:1）。建议 **outline（3:1）**：行分隔不需要达到文字级对比度，
太深会让列表看起来像表格。

虚线（用户给的可选项）**建议不做**：中老年用户会把虚线当成「可以拖动的分隔条」。

**代价**：半天（含弱视对比度核对表）。

### 2.4 库存页 · 两个按钮一个在中间、一个在右边

**根因（已定位，与现象完全对上）**：`stock_page.dart` 的头部是一个
`Wrap(alignment: WrapAlignment.spaceBetween)`，里面**三个**子项：
标题「库存」+ `导出库存` + `重新清点` ⇒ `spaceBetween` 把中间那个**摆到了正中间**。

**改法**：把两个按钮收进一个 `Row`（或 `Wrap`）当**同一个子项**，整体靠右：

```
[库存] ............................ [导出库存] [重新清点]
```

**代价**：半小时 + 窄窗复跑（该处已有 160/264 的护栏）。

### 2.5 流水页（往来方 / 账户 / 商品流水，共用 `flow_page_scaffold.dart`）

| 问题 | 根因 | 改法 | 代价 |
|---|---|---|---|
| 导出按钮在中间 | 表头是 `Wrap`，标题与按钮**相邻**，父级居中 ⇒ 看着像按钮居中 | 表头改 `spaceBetween`（标题左、按钮右） | 半小时 |
| 无任何聚合 | 列表只逐行显示 | 见下 | —— |

**聚合怎么加（用户给了三个方向，我的评估）**：

| 案 | 做法 | 评价 |
|---|---|---|
| ① 只在头尾放总数 | 顶部一行「共 N 笔 · 净增减 X · 期末成本 Y」 | **最便宜、最不容易算错**；但用户明确说「中间仍要自己算」，不满足 |
| ② 每行加「累计」列 | 每行右侧显示「截至本行累计数量 / 成本」 | 一次遍历即可（纯 Dart），**能直接回答"算几轮之后是多少"**；列表变宽一列 |
| ③ 悬停图表 | 图上悬停显示到该时刻的累计 | 最直观，但**要新图表 + 交互**，且手机端没有悬停 |

**建议 ②**：用户真正的诉求是「不用自己一条条加」，② 正好；成本是加一列 + 一次累加。
③ 可以作为后续（等 ② 验证用户是否真的会看累计）。

⚠️ ② 需要处理「退货 / 盘点」这些非单调流水 —— 累计语义要写进页面说明，不能只给数字。

### 2.6 单据页

| # | 问题 | 现状/根因 | 改法 | 代价 |
|---|---|---|---|---|
| 1 | 三排筛选没有说明 | `documents_page.dart` 三排 chips 直接铺开 | 每排左侧加「时间：」「类型：」「状态：」 | 1 小时 |
| 2 | 时分秒偶现不显示 | 主单显示 `business_day`（日期），**收付款行**显示到账时刻（带时分秒）⇒ 同一列表两种精度 | 统一：主单也显示 `HH:mm`（`occurred_at` 已有） | 半天（含窄屏） |
| 3 | 条目不显示商品与数量 | `DocumentSummary` **没有明细字段**；为省 N+1 只带 `returnedCents` / `settlementCount` | 新增一次**批量**取明细摘要（`linesSummaryMany(ids)`，200 行一次查），行内显示「牛奶 ×2、面包 ×1 …」 | **1–1.5 天**（含查询成本实测） |
| 4 | 「已收 N 笔」没有金额 | 只有 `settlementCount`，金额在 `document.paidAmount`（缓存列）里**现成** | 行内改「已收 1 笔 · ¥30.00」；「未收 ¥10.00」加粗 | 半天 |
| 5 | 详情页单据号打头 | `document_detail_page.dart` 头部顺序：单号 → 对方·日期 → 录入时间 | 换成：**对方（大）→ 日期 → 单号（小、可复制）** | 半天 |
| 6 | 核销单套娃 | 详情页里的「这笔被哪几笔收付款核销过」可点进收付款单，收付款单里又能回到原单 | 进入时**记录来源**：不是从列表进来 ⇒ 隐藏「核销入口」 | 1 天（要动导航参数 + 三条进入路径各测） |
| 7 | 退货后的金额卡容易误解 | 现在：金额 ¥10 / 已收 ¥10 / 已退货 −¥5 / **多收 ¥5** / 已结清（截图） | 改成两段式：「原单 ¥10.00 − 退货 ¥5.00 = **应收 ¥5.00**」+「已收 ¥10.00（多收 ¥5.00，可退）」 | 半天（文案 + 条件渲染） |

⚠️ 第 3 项要**先量**：200 张单的明细一次取多少毫秒（冷盘）。若超过 100 ms，
改为「只显示第一行商品 + 『等 N 项』」。

### 2.7 往来方页 / 账户页

与库存页第 2.4 同款（按钮分布）+ 通用 1.1。**同一批改**（`flow_page_scaffold` 与页面头部）。
用户说「基本一致，不再赘述」—— 按 2.4 / 2.5 的结论套。

### 2.8 设置页 · 拆二级页面（**中工程**）

**现状**（截图）：一页 6+ 个区块，顺序为 概览图表 / 界面大小 / 店名 / 数据 / 数据刷新 / 多设备同步 / …，
每块带 2–4 行说明文字。用户判词「野蛮生长」是准确的 —— 这不是美化问题，
是**信息架构**问题：所有东西平铺，找一项要滚。

**建议的二级结构**（入口页只保留四类 + 一行说明）：

```
设置
├── 界面            → 界面大小、概览图表（百分数/倍数）
├── 数据与备份      → 数据位置、备份位置、立即备份、数据刷新
├── 手机与同步      → 多设备同步、配对、立即同步、忘记主机
└── 关于            → 版本、许可、第三方组件、手册入口（用户第 3 条：将来加"关于"）
```

**改动面**：`settings_page.dart`（约 1000 行）拆成 1 个入口页 + 4 个子页；
所有 `Key`（约 20 个，被测试引用）必须**原样保留**，否则 20 条测试一起红。

**代价**：2–3 天（拆 + 20 个 key 对齐 + 测试迁移）。**风险中**：`onConfigSaveFailure`、
`hostService` 这些依赖是**逐层传参**的，拆页要把参数一层层带下去（或引入一个 `SettingsScope`）。

⚠️ 这是**唯一会动到大量既有测试**的一项 —— 建议单独一批、单独一次提交。

### 2.9 帮助页 / 用户手册

**现状**（截图）：「目录（共 20 章）」是 `ExpansionTile` 折叠面板 —— 展开时**占据上方 2/3**，
且**不跟随滚动**（它是列表头的一部分）。

**改法**：改为**左侧固定目录 + 右侧内容**（`Row[宽 220 的目录, Expanded(正文)]`），
窗口窄于阈值（建议 720）时**退回现在的顶部折叠**。目录项高亮当前章（滚动联动可后做）。

**代价**：1–1.5 天。⚠️ 手册正文是 HTML（`packaging/用户手册.html` 同源），
左侧目录要复用 `manual_page.dart` 的章节结构，不能另写一份。

## 三、分批建议

| 批 | 内容 | 判断依据 | 估算 |
|---|---|---|---|
| **0 · 先量** | ① 36 个弹窗在 1.75 / 2.0 下的溢出清单；② 单据行取明细的查询耗时；③ 压货榜右对齐在 2.0 下的表现 | 不量就动手只能靠猜（纪律 20） | 1 天 |
| **A · 小改（一批交付）** | 库存页两按钮（2.4）、流水页导出右对齐（2.5-①）、商品行分隔线（2.3）、单据「已收 N 笔·¥X」+ 未收加粗（2.6-4）、单据详情顺序（2.6-5）、退货金额卡（2.6-7）、单据筛选说明（2.6-1） | 全是「位置/文案/颜色」，互不冲突，可一次真机看 | 2–3 天 |
| **B · 需要取舍** | 宽屏 70% 上限（1.1）、开单三页标题（1.3）、流水页累计列（2.5-②）、单据行显示商品（2.6-3）、手册左导航（2.9） | 各自有设计取舍或需要先量 | 3–4 天 |
| **C · 结构工程** | 开单页按纸单重排（2.2）、设置页拆二级页（2.8） | 会推翻现有 pin / 大量测试 | 4–6 天 + 4–6 天 |
| **D · 待单独裁定** | 核销单套娃（2.6-6）、流水图表悬停（2.5-③） | 语义/交互需要你拍板 | —— |

**建议顺序：0 → A → B → C**。A 批最像「用户第二天就能感觉到」的改动，
且风险最低；C 批（尤其开单重排）最好等 0.8.x 走完一轮真实反馈后再动。

## 五、判据与门禁

1. **每一批都必须带「2.0 倍字号 + 窄屏」两条护栏**（现有先例：`#34①`、三页 108/160 那批）。
2. 位置类改动（按钮靠右、标题居中）**不做纯截图验收** —— 加一条断言几何的测试
   （`tester.getRect` 比较左右边界），否则下次改动又会漂。

### 6.1 弹窗在超大缩放下「撑破」——对应 §1.2 的一个实例

**现象**：`return_page.dart:307` 的「确认退货？」弹窗，在超大缩放下标题巨大、

| 按钮区 | `Wrap(spacing: 8, runSpacing: 8, alignment: WrapAlignment.end)`，放不下换行而不是压扁 |

## 七、宽屏上限：**壳层方案作废**，改在页面层做（2026-11-22 超宽屏实测）

用户在 1916×790 的虚拟机实测后指出两条，都成立：

| 现象 | 原因 |
|---|---|
| 滚轮在左右留白上**完全不响应** | 壳层 `ConstrainedBox` 缩窄的是**滚动视口本身** —— 留白在视口之外 |
| 页面标题被一起缩到中间 | 标题是滚动内容的第一个子项，跟着一起被约束 |

**结论：这不是调参问题，是层次选错了。** 宽度上限必须落在**页面内部**：
标题全宽、内容居中、**滚动视口全宽**。壳层那层已撤（`app_shell.dart` 留了注释说明）。

### 7.1 正确形态（每页一致）

```text
┌─ 面包屑（壳层，全宽）──────────────────────────────┐
├─ 页面标题行（全宽）───────────────────────────────┤
│   ┌──────── 内容列（max 1080，居中）────────┐      │
│   │  卡片 / 列表 / 表单                      │      │
│   └─────────────────────────────────────────┘      │
│  ← 这一段左右留白**仍属于滚动视口**（滚轮有效）→   │
└────────────────────────────────────────────────────┘
```

实现要点（每页一处）：
- 滚动体（`ListView` / `CustomScrollView`）**保持全宽**；
- 居中靠**视口内的横向内边距**：`inset = max(16, (可用宽 − 1080) / 2)`（`LayoutBuilder` 算）；
- 页面标题行从滚动内容里**提出来**做成固定行（或留在滚动里但**不受 inset 约束**）；
- 面包屑保持壳层全宽。

### 7.2 代价与顺序

| 项 | 说明 |
|---|---|
| 涉及页面 | 概览 / 单据 / 商品 / 库存 / 往来方 / 账户 / 设置 / 帮助（8 个） |
| 每页改动 | 包一层 `LayoutBuilder` + 算 inset + 标题提出（约 20–40 行） |
| 估算 | 1.5–2 天；风险中（每页都有窄屏护栏要复跑） |
| 建议 | **一次只改一页并给一张超宽屏截图**，别 8 页一起交（这类"看起来都差不多"的改动最容易漏页） |
