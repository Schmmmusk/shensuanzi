# 五页列表骨架 —— 现状与接口设计

> **状态**：🔴 **待裁定，未动实现**（2026-10-23）
> **上游**：`docs/proposals/UI审查落地-分批与决策点.md` 批 3 **第 16 条**
> 「五页共用列表骨架（常驻搜索 + × 清空 + 清空筛选 + **真实总数** + 行箭头）」
> **本文只回答两件事**：五页现在到底差在哪、共用组件该长什么样。**不动代码。**

## 一、为什么要先出这份文档

第 16 条动的是**交互行为**（不是尺寸、不是文案），五个页面的现状又参差不齐。
先动手会出现「改了三页、剩两页半成品」的状态 —— 比不改更糟。
所以先摆事实、定接口，再由人裁定范围。

**English.** This proposal exists because item 16 changes *interaction behaviour*, and the five pages
start from very different states. Starting to code first risks leaving two pages half-migrated,
which is worse than not starting. So: facts first, interface second, scope decided by the human.

**English.** Current state, grep-verified with line numbers. Products is the most complete (search, ×,

## 三、四个缺口，按危害排序

1. **单据页「200 条」会撒谎**（最重）
   `listDocuments(limit: 200)` 拿回最多 200 行，页面又没有任何「还有更多」的提示。
   用户以为「我这个月就 200 单」。**这是数据可信度问题，不是美观问题。**

2. **往来方 / 账户没有搜索**
   开单时选客户靠下拉搜索，但**主数据页本身**翻不到。往来方一多（个体工商户 50–200 个很正常）
   就只能一路滚。

3. **没有「清空筛选」**
   单据页三排筛选可以叠出「一片空白」，用户不知道是自己筛没了 —— 只能逐个点回「全部」。

4. **没有行箭头**
   五页的行都可点（进流水 / 进详情），但长得跟不可点的行一样。
   `ui_principles.md` §1.1：**看不出来能点 = 对目标用户不存在**。

**English.** Four gaps by severity: (1) the documents page silently truncates at 200 rows and never
says so — a *trust* problem; (2) parties/accounts have no list search at all; (3) documents' three
filter rows can be combined into an empty list with no one-tap reset; (4) no row chevron, so tappable
rows look identical to static ones.

## 四、接口设计

### 4.1 三个共用组件（`lib/src/ui/list_scaffold.dart`，新文件）

```dart
/// 列表头：搜索（常驻）+ × 清空 + 额外筛选 + 计数行。
class ListHeader extends StatelessWidget {
  const ListHeader({
    required this.searchKey,          // Key('products-search') —— 各页各自的 key 不变
    required this.controller,
    required this.hintText,
    required this.onChanged,
    this.leading,                     // 额外筛选控件（开关 / chips），各页自摆
    this.countText,                   // 「共 12 种」/「12 条（只显示最近 200 条）」
    this.onClearFilters,              // 非 null ⇒ 右侧显示「清空筛选」
  });
}

/// 行尾箭头。**只给「点了会跳走」的行**（进详情 / 进流水）。
class RowChevron extends StatelessWidget { const RowChevron({super.key}); }

/// 空态：图标 + 一句为什么 + 一条出路（清空搜索 / 清空筛选 / 新建）。
class ListEmptyState extends StatelessWidget {
  const ListEmptyState({required this.icon, required this.title, this.actionLabel, this.onAction});
}
```

**为什么是「头 + 箭头 + 空态」三个，而不是一整块 `ListPage`**：
五页的**行**长得完全不一样（商品有价格列、往来方有角色、单据有状态色），
硬抽一个 `ListPage` 会把行也框死 —— 那是更大的重构，收益不成正比。
**只抽「头 / 尾 / 空态」这三段重复度最高的。**

**English.** Three shared widgets: `ListHeader` (persistent search + × + optional filters + count line),
`RowChevron` (only on rows that navigate away), `ListEmptyState`. Deliberately **not** a whole
`ListPage` — the rows differ fundamentally across the five pages, and forcing them into one widget
would be a much bigger refactor for no proportional gain.

### 4.2 单据页的「真实总数」怎么来

两条路，**要你裁**（见 §六·①）：

- **甲（推荐）**：`DocumentDao.countDocuments(...)` —— 与 `listDocuments` **共用同一个 WHERE 构造器**
  （抽成私有方法，单一来源，防漂移）。页面显示「12 条」或
  「只显示最近 200 条（共 348 条）」。
- **乙**：不动 DAO，超限时显示「200+」。零风险，但**仍不知道真实总数**。

**English.** Two options for the true count: (A) add `DocumentDao.countDocuments(...)` sharing the
same WHERE builder as `listDocuments` — shows "showing 200 of 348"; (B) no DAO change, display "200+".

### 4.3 各页要改的最小集合

| 页 | 改动 |
|---|---|
| 商品 | 换用 `ListHeader`；计数从「显示条数」改成「真实总数」（本来就全量，只需换文案） |
| 库存 | 加 × 清空；加计数；换 `ListHeader` |
| 往来方 | **新增搜索**（按姓名 / 电话）；加计数；换 `ListHeader` |
| 单据 | 加「清空筛选」；加真实总数；换 `ListHeader` |
| 账户 | **新增搜索**（按名称）；加计数；换 `ListHeader` |

**English.** Minimal per-page change set: swap in `ListHeader`, add the missing search/clear/count,
add "clear filters" on documents.

## 五、落地顺序与验证

1. `list_scaffold.dart` + 组件用例（纯 widget，无业务依赖）
2. **商品页**先接（现状最全，风险最低）→ 跑全量门禁
3. 库存 → 账户 → 往来方（每页一次门禁）
4. 单据页（含 DAO 计数 + WHERE 抽取）→ 单独一次门禁
5. 每页补三条用例：**搜索能筛出来 / × 能清空 / 计数与真实条数一致**

**每步都跑四套门禁**；单据页动 DAO，额外跑 core 的 `document_dao_test`。

**English.** Order: build the widgets, then products (lowest risk) → stock → accounts → parties →
documents (DAO change last, isolated). Three assertions per page: search filters, × clears, count
matches reality. Four gates after each step.

## 六、要你裁的三件事

**① 单据页「真实总数」走甲还是乙？**
→ 我推荐 **甲**（COUNT 查询）。理由：现在的 `limit: 200` 已经在撒谎，
乙 只是把谎言说得好听一点。

**② 往来方 / 账户页加搜索，要不要顺带加「按角色 / 按类型」筛？**
→ 我推荐 **只加文本搜索**。角色筛选在开单选择器里已有，主数据页再加一遍是重复入口。

**③ 行箭头加在哪些行上？**
→ 我推荐 **只加在「点了会跳走」的行**（商品→流水、往来方→流水、账户→流水、单据→详情）。
其余行（比如表单里的选项行）不加 —— 箭头是「会跳走」的承诺，滥用会让承诺失效。

**English.** Three decisions: (1) real count via COUNT query (recommended) or "200+"; (2) add text
search only, no role/type filters (recommended); (3) chevrons only on rows that navigate away
(recommended), never on static rows.
