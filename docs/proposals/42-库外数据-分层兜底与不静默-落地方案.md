### ⚠️ 一个必须说清的判断

**只做 L2 + L1，「整页变灰」就已经治好了**（异常不再抛进 build）—— L3 是**第二道防线**（治将来别的
未知抛穿），**L4 是甲里「不静默」的兑现**。
**少了 L4 就等于静默丢数据**（用户看不见那 N 条，也永远不会知道）⇒ 所以 L4 不能省，
且顺序上 **L4 是 L1 的前提**（甲的原话），不是「以后补」。

## 七、风险与边界（诚实说明）

- **跳过行 = 数据看不见** ⇒ L4 必须与 L1 **同批**落地，不许拆到「以后」。
- **不做「自动修复坏数据」**：把兜底值写回库是**另一件事**（改用户数据，需独立裁定）。
- **不做「整库体检」工具**：本次只保证「不再变灰 + 告知」，体检是另一批。
- 手工改库 / 旧备份 / 主机更新 —— 三个触发源都真实存在 ⇒ 这不是防御性编程，是**必现**修复。
