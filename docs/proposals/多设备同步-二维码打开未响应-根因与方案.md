# 多设备同步 · 二维码打开「未响应」—— 根因与方案

> **§BF 提案（2026-10-03）** · 状态：**待裁定**
> 触发：真机测试发现「设置 → 多设备同步」打开二维码界面时窗口频繁「未响应」。
> 应用户要求**文档先行** —— 本文档给出根因取证与方案对比，**未动任何代码**。

## 一、现象

真机（Windows）：打开配对二维码对话框时，窗口频繁出现「**未响应**」。
不是"卡一下"，是 Windows 判定消息泵停了 5 秒以上的那种。

## 二、根因（证据链，全部可复核）

**一句话：每绘制一次二维码，都在 UI 线程上重新做了约两万次完整的二维码编码。**

| # | 证据 | 位置 |
|---|---|---|
| 1 | `paint()` 里构造 `PairingQr(payload)` —— **编码发生在绘制阶段**，而不是打开前算好 | `lib/src/ui/host_service_section.dart:371` |
| 2 | `PairingQr` 的 `code` / `image` / `moduleCount` / `matrix` **全是 getter，每次访问都全量重算** | `packages/shensuanzi_host/lib/src/pairing.dart:87-105` |
| 3 | `matrix` 是双重循环：**内层循环条件 `col < moduleCount` 每次迭代都调一次 getter**；`image.isDark(row, col)` **每个模块都调一次 `image` getter** ⇒ O(n²) 次 getter（n = 49 ⇒ 约 2400 次 `image` + 2450 次 `moduleCount`） | `pairing.dart:100-105` |
| 4 | **`qr` 包的 `QrImage(QrCode)` 构造 = 8 次掩码试算 + 1 次终绘 = 9 次完整编码** —— 这是掩码评分算法的正常成本，不是 `qr` 的 bug | `qr-3.0.2/lib/src/qr_image.dart:17-32` |
| 5 | **实测数字**（见下表） | 附录脚本可复现 |
| 6 | 二维码**没有 `RepaintBoundary`** ⇒ 对话框入场动画的每一帧都重新 paint ⇒ 15 秒的活儿按帧反复做 | `host_service_section.dart:344-351` |

### 实测数字（本机 `dart run`，147 字节真实形状载荷 ⇒ v8 / 49×49 模块）

| 项 | 耗时 | 说明 |
|---|---|---|
| ① `QrCode.fromData`（数据 + 纠错码） | **3.9 ms** | — |
| ② `QrImage(code)` | **24 ms** | = 9 × ① |
| ③ `PairingQr.moduleCount`（访问一次） | **4.3 ms** | = ② 一次（getter 重算） |
| ④ **`PairingQr.matrix`（访问一次）** | **15 408 ms ≈ 15.4 秒** | O(n²) 次 getter × 每次 9 遍编码 |
| ⑤ 修复后形态（编码一次 + 一次 n² 取值） | **3.1 ms** | **差距约 5000 倍** |

**结论**：打开对话框 ⇒ 首帧 `paint` ⇒ **约 15 秒同步计算堵死 UI 线程** ⇒ Windows 判定「未响应」。
这不是"机器慢"能解释的（⑤ 只要 3.1ms）—— 是**结构性的 O(n² × 9) 对 O(1)**，
任何机器都会卡，只有快慢之别；真机性能越差、对话框动画越长，症状越明显。

## 三、方案对比

### 方案 A：`PairingQr` 缓存化（**推荐**）

把「算一次」做进**库**：`code` / `image` / `moduleCount` / `matrix` 改成
构造时（或首次访问）算好并缓存的 `late final` —— **getter 语义不变，调用方零感知**。

- ✅ **治本**：getter 陷阱从库里消失，**任何调用方**（含将来 AH-B Android 端）都不会再踩
- ✅ **零新依赖**：不推翻「二维码自绘、零依赖」的裁定（§BB·三）
- ✅ 纯 Dart 可测：`pairing_test` 可加「重复访问不重算」断言（给 `PairingQr` 加
  `@visibleForTesting int encodeCount`，或时间阈值）
- ✅ 行为**完全不变**：矩阵逐 bit 一致，手机端兼容性零影响；风险极低
- 配套 UI 侧两笔小改：`_QrView` 外包 **`RepaintBoundary`**；`_QrPainter` 持**缓存好的矩阵**
  而非 payload（`paint` 里不再触碰任何 getter）

### 方案 B：换 `qr_flutter`（不推荐）

`QrImageView(data: uri)`。**治标**：它底层就是同一个 `qr` 包（同样 9 次掩码搜索），
只是它自己会缓存 —— 而这恰是方案 A 在**库层**做的事。代价：加依赖 +
`pubspec.lock` 重生成 + **推翻「零新依赖」裁定**（需重裁）。**A 落地后 B 无必要。**

### 方案 C：只在 UI 层算一次、塞进 dialog state（保底，不推荐单独做）

能治住本症状，但**库的 getter 陷阱还在** —— 将来 Android 端 / 任何新调用方再踩一次。

### 推荐：**A**

一个批次做完：库（缓存化）+ UI（`RepaintBoundary` + 持缓存矩阵）+ 测试 + 真机复测。

## 四、修复清单（**已按审查意见落地**，2026-10-03）

| # | 文件 | 改动 |
|---|---|---|
| 1 | `packages/shensuanzi_host/lib/src/pairing.dart` | `code` / `image` / `moduleCount` / `matrix` → **`late final` 缓存**；`@visibleForTesting` 语义改为**公开字段 `encodeCount`**（零依赖：不引 `meta`）；**`uri` 刻意不缓存**（纯字符串拼接，§BF·二 补强 3） |
| 2 | `lib/src/ui/host_service_section.dart` | ⚠️ **`_QrView` 改 `StatefulWidget`，持 `PairingQr` 实例**（不是"持缓存矩阵" —— 审查意见 2.1：哪怕库层缓存了，每帧 paint 构造新实例仍要重新编码）；`RepaintBoundary`；`_QrPainter` → **公开 `PairingQrPainter`**（根层测试要断言 `shouldRepaint`，私有类够不着） |
| 3 | `packages/shensuanzi_host/test/pairing_test.dart` | **+2**：`encodeCount` 三段断言（构造 **0** → 首次访问后**恰好 1** → 重复/跨字段仍 1）· 矩阵与**直接用 qr 包现算**逐 bit 一致 |
| 4 | `test/host_service_section_test.dart` | **+1**：`shouldRepaint`（同一实例 ⇒ **false**；载荷换了 ⇒ **true** —— 见下方"一处偏离"） |
| 5 | 真机复测 | 打开二维码应 < 100ms；`flutter analyze` 0 issues |

**实测（修复后，JIT）**：`matrix` 一次 = **4.38 ms**（修复前 15 408 ms）；
`encodeCount` 三段断言全过；矩阵与现算**逐 bit 一致**。

### 一处偏离（已标注理由）

审查意见 5.2 说 `shouldRepaint` "**必须 `=> false`**"。我实现为
`qr != oldDelegate.qr` —— **同一实例 ⇒ false**（审查的那条断言照过），
**实例不同 ⇒ true**。理由：`CustomPaint` 换 painter 时靠它决定重画与否，
**无条件 false 会把旧码留在屏上**（载荷换了却不重绘）。若你坚持字面的"恒 false"，
需同时把 `_QrViewState.didUpdateWidget` 的换实例逻辑删掉（等于承诺"一个 `_QrView` 永远一个载荷"）。

## 五、风险与明确不做的事

- **不改** QR 内容 / 纠错等级 / 尺寸（矩阵逐 bit 不变）
- **不引入 isolate** —— 修好后全链 3.1ms，上 isolate 属过度设计
- **不删自绘**：quiet zone ≥ 4 模块、模块间 +0.5px 缝补这两条规格的注释都在 `paint` 里，继续有效
- **未来的尺度**（§BF·二 补充）：若将来 QR 内容变长（如把公钥塞进配对码做更高安全等级）、
  或需要**批量生成**（一屏多个配对码），3.1 ms × N 会线性增长 —— **届时再评估 isolate**。
  **是"当前规模不需要"，不是"结构上不需要"**。

## 附录：取证脚本（可复现）

核心逻辑（真实脚本已按惯例用完即删；数字可随时重跑验证）：

```dart
final PairingQr qr = PairingQr(payload);            // payload: 32 字节 base64url 令牌
sw..reset()..start();
final int n = qr.moduleCount;                        // → image → QrImage(code) = 9 次全量编码
print(sw.elapsedMicroseconds / 1000);                // 4.3 ms
sw..reset()..start();
final List<List<bool>> matrix = qr.matrix;           // 双重循环里 moduleCount / image 各被调 O(n²) 次
print(sw.elapsedMicroseconds / 1000);                // 15408.7 ms
```

> ⚠️ 用 `Stopwatch` 取证时**别只 `reset()` 不 `start()`** —— `reset()` 会停表，
> 测出来全是 0.0ms（本次取证自己先踩了一脚，重跑才是真数）。
