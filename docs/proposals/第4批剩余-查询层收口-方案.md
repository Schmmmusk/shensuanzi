> 来源：第 4 批基线 `docs/perf/2026-10-24-v5-migrated.csv`（v5 之后仍慢的那几条）+ 本次实测。
> 状态：**🔴 待裁定，未动实现**。裁定后并入 `docs/reply_review.md`（编号「4c 收口」）。
>
> 前置：索引层已在 §CV·九十八 收口（库存 38.8× / 往来 23×）。本批剩下的**不吃覆盖索引**，

## 零、结论先行（全部实测，26.4 万单 / 37 万流水 / 480 MB）

| # | 查询 | 现状 p50 | 改法 | 改后 | 倍数 | 动 schema？ |
|---|---|---|---|---|---|---|

## 一、单据列表：两段查询（本批最值的一条）

### 1.1 钱花在哪（拆解实测）

| 片段 | p50 |
|---|---|
| 只扫 `documents` + `ORDER BY` 表达式（无 JOIN） | **120 ms** |
| 只 `LIMIT 200`（无排序、无 JOIN） | **0.1 ms** |
| 三个 JOIN、无 `ORDER BY` | **104.7 ms** |
| `rootsOnly` 过滤（关联子查询） | **+7 ms** |
| 全量查询（现状） | **456 ms** |

⇒ 两个大头：**排序 120 ms** + **两个派生表被全量物化 105 ms**（`r` 聚合 26 万行退货、
`s` 聚合 10 万条核销），而真正要的只有 **200 行**。

### 1.2 改法：先拿 id，再只对这 200 个 id 聚合

```sql
-- 第一段：只取 id（不 JOIN、不带派生表）
SELECT d.id FROM documents d
WHERE <筛选条件>
ORDER BY ((d.occurred_at + ?) / 86400000) DESC, d.created_at DESC
LIMIT 200;

-- 第二段：r / s 都加 IN (200 个 id) 限制
SELECT d.*, pa.name AS party_name, COALESCE(r.rsum,0) …, COALESCE(s.psum,0) …
FROM documents d
LEFT JOIN parties pa ON pa.id = d.party_id
LEFT JOIN (SELECT ref_doc_id AS ref, SUM(total_amount) AS rsum, COUNT(*) AS rcnt
             FROM documents WHERE ref_doc_id IN (…) AND doc_type IN (…) GROUP BY ref_doc_id) r
       ON r.ref = d.id
LEFT JOIN (SELECT target_doc_id AS tgt, SUM(amount) AS psum
             FROM settlements WHERE target_doc_id IN (…) GROUP BY target_doc_id) s
       ON s.tgt = d.id
WHERE d.id IN (…);
```

**实测**：第一段 **127 ms** + 第二段 **19.7 ms** ≈ **147 ms**（现状 456 ms，**3.1×**）。

⚠️ **第二段的 `IN` 限制是必需的**：只做「先取 id 再按 id 查」但不限制派生表，
`s` 仍会全量物化 10 万条 —— 那就只省了排序、没省聚合（实测只到 324 ms）。

> Stage 1 costs 127 ms (sort); stage 2 with the derived tables **restricted to the 200 ids**
> costs 19.7 ms (vs 105 ms unrestricted). Total ≈147 ms vs 456 ms today.

### 1.3 可选叠加：日桶表达式索引（要 schema v6，且**与运行时区耦合**）

`ORDER BY ((occurred_at + off)/86400000) DESC, created_at DESC` 的表达式可以用
SQLite 的**表达式索引**接住 —— 但有个硬前提：

| 做法 | 结果 |
|---|---|
| 索引建在 `((occurred_at + 28800000)/86400000) DESC, created_at DESC`，查询里偏移仍是**参数** `?` | **索引用不上**（123.7 ms，仍 `TEMP B-TREE`）—— SQLite 要求表达式**逐字匹配**，参数不匹配字面量 |
| 查询里把偏移写成**字面量** `28800000` | **0.1 ms**（`SCAN d USING INDEX idx_documents_day`） |
| 字面量 + `rootsOnly` 过滤 | 规划器改选 `idx_documents_ref`，**退回 128 ms** ⇒ 必须 `INDEXED BY` 强制 |
| 字面量 + `INDEXED BY` + `rootsOnly` | **0.1 ms** |

**代价与脆弱点**（必须说清楚）：

1. 偏移来自 `DateTime.now().timeZoneOffset`（`document_dao.dart:29`），**运行时可变**。
   索引里必须烘进一个字面量 ⇒ 索引**只在「建索引时的时区」有效**。
2. 所以要么接受「换时区后这个索引变成死重量（20 MB）」并退回排序，
   要么在**索引名里带上偏移**（`idx_documents_day_28800000`）、运行时用
   `PRAGMA index_list` 比对后再决定是否 `INDEXED BY`（约 20 行 + 一次 PRAGMA 缓存）。
3. 新增一个 20 MB 级索引，写入多维护一份。

> An expression index works **only** if the offset is a literal (0.1 ms vs 123.7 ms), and it is
> baked in at creation time while the runtime offset comes from `DateTime.now().timeZoneOffset`.
> Using it safely requires encoding the offset in the index name and checking it at runtime.

## 二、`recent_products`：这是**等价改写**，不是语义收窄

商品选择器的「最近使用」。现状：扫全部 11.2 万张销售单 + 37 万条明细再分组 = **429 ms**。

### 2.1 为什么可以只看最近 K 张

「最近使用的 20 个商品」= 按 `MAX(occurred_at)` 倒序取 20 个商品。
**从最新单据往回走、遇到的第 20 个不同商品，就是答案** —— 一个商品的「最后一次卖出」
必然就是它出现的**最新那张单**。所以只要 K 足够装下 20 个不同商品，结果与全量查询**完全相同**。

### 2.2 实测

| 做法 | p50 | 与全量查询结果 |
|---|---|---|
| 现状（全量扫 + 分组） | **421.6 ms** | — |
| 最近 200 张（`INDEXED BY idx_documents_occurred`） | **1.0 ms** | ✅ **完全一致**（20 行逐个比对） |
| 最近 500 / 2000 张 | 1.0 / 1.9 ms | ✅ 完全一致 |

⚠️ **必须 `INDEXED BY idx_documents_occurred`**：不写的话规划器会选
`idx_documents_type_status` 再排 11.2 万行（实测 122 ms，白瞎了索引）。

### 2.3 保底：不足 20 个就退回全量查询

K = 2000 仍不足 `limit` 个不同商品（商品总数很少、或长期没卖）⇒ 说明数据量本来就小，
**再跑一次全量查询**（此时它必然也很快）。这样「快路径」永远不会改变结果。

> Scanning newest-first and taking the first 20 distinct products is **exactly** the top 20 by
> `MAX(occurred_at)` — verified identical on the real DB at K=200/500/2000. Falls back to the
> full query when fewer than `limit` distinct products are found.

## 三、`doc_search`：本批**不做**（附原因与三个方向）

四路 LIKE 拆开实测（各自单独跑）：

| 分支 | p50 | 说明 |
|---|---|---|
| ① 本单号 `doc_no LIKE '%x%'` | 74 ms | 前后都有 `%`，用不了索引 |
| ② 对方名 `pa.name LIKE` | 52 ms | 同上 |
| ③ 子单号 EXISTS | 119 ms | 走 `idx_documents_ref` |
| ④ **商品名 EXISTS** | **523 ms** | 每个单据上都要探明细 |

试过的改法都不成立：

| 改法 | 结果 |
|---|---|
| 把 ④ 的 `(cd.id = d.id OR cd.ref_doc_id = d.id)` 拆成两个可走索引的子查询 | 479 → **388 ms**（只 19%） |
| CTE 先算「命中商品名」的单据集合再 `IN` | **483 ms**（内层仍要扫 37 万条明细） |
| 先筛商品（300 行）再用 `idx_lines_product` | **1665 ms**（75 个商品 × 明细，`IN` 是逐元素查找，**更慢**） |

**根因**：`products.name LIKE '%x%'` 用不了索引，命中商品名必须**碰一遍 37 万条明细**，
这是 ~400 ms 的硬底。要真正解决只有三条路，**都需要单独裁定**：

1. **FTS5 虚表**（第 4 批已裁「不上」，此处不翻案）；
2. **收窄搜索范围**（只在最近 N 天里搜商品名）—— 语义变化；
3. **接受现状**（搜索是低频动作，且有 200 行上限）。

> Searching by product name inherently touches 370k lines (~400 ms floor). Three rewrites
> tried, all worse or marginal. Deferred; needs a separate ruling (FTS5 / scope narrowing /
> accept).

## 四、两条小项：一个值得、一个不值得

| 查询 | 加覆盖索引 | 结果 | 判断 |
|---|---|---|---|
| `account_balances` | `money_ledger(account_id, amount)` | 64.3 → **9.4 ms**（6.8×） | ✅ 值得（10 万行表，索引约 2–3 MB） |
| `in_transit` | `document_lines(document_id, product_id, quantity)` | 85.7 → 64.1 ms（1.34×） | ❌ **不值得**：`document_lines` 是最大表，三列索引约 40 MB，只换 1.34× |

`in_transit` 的 86 ms 另有解释：种子数据里 **14563 张在途送货单**（占 5.5%），
真实店铺在途单通常个位数 —— 这个数字本身被放大了，不建议为它加索引。

> `account_balances` covering index: 6.8×, worth it. `in_transit`: 1.34× for a ~40 MB index on
> the largest table — not worth it (and the 86 ms is inflated by 14.5k in-transit docs in seed).

## 六、风险

| 风险 | 评估 | 处置 |
|---|---|---|
| 两段查询改变结果（排序/聚合错位） | **中**：两段之间数据可能变（单机单用户，概率极低，但**不是零**） | 第二段用 `WHERE d.id IN (…)` 取回，**按第一段的 id 顺序重排**；测试逐行比对 |
| 两段之间单据被删 | 低 | 第二段少返回几行 ⇒ 页面少一行，不崩；测试覆盖 |
| `recent_products` 快路径结果与全量不一致 | **已实测一致**（K=200/500/2000 三档逐个比对） | 保底分支 + 测试 |
| 表达式索引与时区耦合（1′） | **高**（这是我不推荐它作为默认的原因） | 见 §1.3 的两条出路；或干脆不做 |
| 加索引拖慢写入 | 低（`money_ledger` 10 万行、2–3 MB） | 与 v5 同样的实测方法复核 |

## 七、验收

1. **先红后绿**：先写「两段 == 单段」「快路径 == 全量」的等价性测试 → 红 → 改 → 绿。
2. **反向验证**：把第二段的 `IN` 限制去掉，断言必须红（证明它真的在起作用）。
3. **重跑 `perf_bench`**：`list_documents` 应从 291 ms 落到 **~95 ms**、`recent_products`
   从 429 ms 落到 **< 5 ms**（python 侧实测 456→147 / 429→1.0，perf_bench 侧同比例）。
4. **门禁**：四套测试 + 全部自检 + `analyze` + `format`。

> Red-then-green on equivalence tests, reverse-verify the `IN` restriction, re-run `perf_bench`.

## 八、不做的事

- **不改 `doc_search`**（§三，三条路都要单独裁定）。
- **不给 `document_lines` 加三列覆盖索引**（§四，1.34× 换 40 MB）。
- **不动 `countDocuments`**（`doc_count` 实测 3.7 ms，本来就不慢）。
- **不动导出路径**（无 `LIMIT`，两段查询没有意义）。
- **不为了排序改 `ORDER BY` 语义**（日桶 + 录入时刻是 2026-10-18 的裁定，§CV·六十二）。

> No search rewrite, no big index on document_lines, no export change, no ORDER BY change.

## 九、要你裁的两件

| # | 决策点 | 甲（推荐） | 乙 |
|---|---|---|---|
| ① | 单据列表要不要**日桶表达式索引** | **不要**：只做两段查询，291 → ~95 ms，零 schema、零时区耦合 | 要：291 → ~13 ms，但 schema v6 + 20 MB + **索引绑死建库时区**（要在索引名里带偏移并在运行时比对） |
| ② | `account_balances` 的覆盖索引 | **不加**：账户页是低频页，64 ms 可接受，保持零 schema | 加：64 → 9.4 ms，约 2–3 MB（与 ①乙 一起进 v6） |

**最省事回法：`①甲 ②不加`**（本批零 schema）。

如果你更看重「列表页秒开」，回 **`①乙 ②加`**，我把 v6 一次做完（含时区比对 + 迁移 + 计划断言）。

> Decision: ① expression index (甲 no / 乙 yes), ② money_ledger covering index (甲 no / 乙 yes).
