## 二、为什么是「加宽」而不是「新增」

我上一轮给的是三个**新增**索引。实测之后发现更省的解法：这三个表都已经有一个
**前缀相同但更窄**的索引，直接把需要的列追加在后面即可 —— 索引个数不变。

| 表 | 已有索引 | 加宽成 | 为什么能「一个顶两个」 |
|---|---|---|---|
| `stock_ledger` | `(product_id, seq_no)` | `(product_id, seq_no, quantity, total_cost)` | `GROUP BY product_id` 只需 product_id 是**前缀**；`WHERE product_id=? ORDER BY seq_no` 也完全匹配（`seq_no` 排在第二位，顺序不变） |
| `party_ledger` | `(party_id, seq_no)` | `(party_id, seq_no, amount)` | 同上 |

`seq_no` **必须排在聚合列之前**：聚合不在乎组内顺序，但「按商品看流水」在乎。
实测两种排法（取流水最多的商品，1376 行）：

| 索引 | 聚合（全表） | 按商品查流水 `WHERE product_id=? ORDER BY seq_no` | 计划 |
|---|---|---|---|
| `(product_id, seq_no, quantity, total_cost)` ← **本提案** | 36.9 ms | **6.24 ms** | `SEARCH ... (product_id=?)`，无排序 |
| `(product_id, quantity, total_cost)`（对照） | 34.4 ms | 7.07 ms | 多一步 **`USE TEMP B-TREE FOR ORDER BY`**（文件排序） |
| v4 现状 `(product_id, seq_no)` | 1336 ms | 6.26 ms | 无排序 |

聚合本身两种排法一样快（36.9 vs 34.4，噪声内）；差别在**按商品看流水**：
聚合列在前会让每次「商品流水」多一次 O(n log n) 文件排序，且**行数越多差得越大**
（1376 行时 13%，几千行时会更明显）。本提案的排法在这一点上与 v4 **持平（6.24 vs 6.26）**。

**为什么不保留旧索引 + 新增宽索引**：两个索引都留着，写入要维护两份、
磁盘要装两份（实测这三个新索引共 43.7 MB），而旧的那个已经**没有独立用途**
（宽索引是它的严格超集，前缀查询照样命中）。

> Each of the two tables already has a narrower index with the same prefix — we simply
> append the aggregate columns, so the **index count stays the same**. `seq_no` must stay
> before the aggregate columns: aggregation ignores intra-group order, but per-product
> ledger listing depends on it.

## 三、为什么第三个索引（`documents`）不加

第 4 批基线里 `today_summary` 显示 270 ms，我据此认为 `documents` 也要覆盖索引。
**核实真实调用形态后，这个结论不成立**：

| 场景 | v4 | 加覆盖索引后 |
|---|---|---|
| **单日**（`todaySummary` 的真实用法，取样日 766 单） | **0.23 ms** | 0.15 ms |
| 全区间（0 → 2^62，**生产代码从不这样查**） | 157 ms | 87 ms |

270 ms 是压测脚本为了量级对照而查「全部历史」的结果。生产里 `todaySummary`
永远传当天的零点与次日零点（3c-5 加的上界），0.23 ms 已经不可感知。

加它要 **+4.7 MB**（`documents` 是全库最大表，索引宽 4 列），换来一个
不存在的场景 —— 按项目一贯的「先度量、再决定」原则，**不加**。

> The 270 ms figure came from a full-history range that production never issues.
> Real usage is a single day → **0.23 ms**. The index costs +4.7 MB on the largest table
> for a non-existent query shape. Rejected.

## 四、迁移方案（v5）

### 4.1 `Schema.version` 4 → 5

```dart
static const int version = 5;
```

### 4.2 `migrationStep(4)`（逐版本、单事务、可重入）

```dart
4 => <String>[
  // v4 → v5（2026-10-24，第 4 批基线 §CV·九十七）：把两个窄索引**加宽**成
  // 覆盖索引 —— 库存页 1336 → 37.6 ms、往来余额 648 → 27.7 ms（实测 35× / 23×）。
  // 索引个数不变（换掉不是新增）⇒ 写入代价不变、磁盘 −1.0 MB。
  // `seq_no` 必须排在聚合列之前：「按商品/往来方看流水」依赖它。
  'DROP INDEX IF EXISTS idx_stock_product_seq',
  'CREATE INDEX idx_stock_covering '
      'ON $stockLedger(product_id, seq_no, quantity, total_cost)',
  'DROP INDEX IF EXISTS idx_party_ledger_party_seq',
  'CREATE INDEX idx_party_covering '
      'ON $partyLedger(party_id, seq_no, amount)',
],
```

- **`IF EXISTS` 必须写**：v3→v4 那步的注释已说明「旧库可能被手工清理过」，
  `DROP` 不带 `IF EXISTS` 会因「索引不存在」直接让迁移失败。
- **DDL 在 SQLite 里是事务性的**：四条语句在同一个 `BEGIN … COMMIT` 内，
  中途失败整版回滚（执行器 `database.dart:217-230` 已是这个语义）。
- **耗时**：480 MB 库实测重建 **1.0 s**（一次性、启动时）。用户真实库
  （本机 `D:\神算子数据` 只有 80 单）是**瞬时**。

### 4.3 全新库

`schema.dart` 的建库语句同步替换（`CREATE INDEX` 那两行），
保证「新库」与「迁移上来的库」**结构逐字相同** —— 这是 `schema_test` 的既有断言。

> Version bump 4 → 5 with four DDL statements in one transaction. `IF EXISTS` is
> mandatory (old DBs may have been hand-cleaned). 1.0 s rebuild on 480 MB, instant on
> real customer DBs. Fresh-DB DDL updated identically.

## 六、风险与回退

| 风险 | 评估 | 处置 |
|---|---|---|
| 迁移失败导致启动不了 | **低**：4 条 DDL、单事务、`IF EXISTS`；执行器失败即回滚并 rethrow（启动时暴露，不会带病运行） | 已有 `MissingMigrationException` 兜「改版本忘写迁移」 |
| 迁移耗时阻塞启动 | **低**：480 MB 实测 1.0 s；真实库瞬时 | 无需进度条 |
| 加宽索引让某个查询变慢 | **已实测 7 条**：两条聚合快 23–35×，五条持平 | 计划断言（§五 #3）锁住形态 |
| 写入变慢 | **实测无变化**（15 → 14 µs/组） | 索引个数不变 |
| 磁盘变大 | **实测 −1.0 MB** | — |
| 需要回退 | 本项目无 down migration（与 v2/v3/v4 一致） | 真出问题就发 v6 把窄索引加回来（`CREATE INDEX` 而已，数据无损） |

**数据安全性**：`DROP INDEX` / `CREATE INDEX` **不触碰任何行**。
即使迁移中途断电，最坏情况是「旧索引已删、新索引没建完」→ 事务回滚，
库回到 v4 结构，下次启动重跑。

> Low risk: four DDL statements in one transaction, no row is touched. Worst case is a
> rollback to v4 and a retry on next launch. No down migration (consistent with v2–v4);
> a v6 could re-add narrow indexes if ever needed.

## 七、验收（怎么证明真的有效）

1. **计划断言先红后绿**：改断言 → 跑（旧结构上必须红）→ 上迁移 → 跑（绿）。
2. **反向验证**：把 `idx_stock_covering` 临时改回两列，断言必须红。
3. **重跑 `perf_bench` 对照**：`docs/perf/2026-10-24-baseline.csv`（v4） vs
   新 CSV（v5），同库同参数 `--rounds 20`，两张表并排进台账。
4. **迁移正确性**：`schema_test` 既有的「v4 库迁上来 == 新建库」断言会自动覆盖
   —— 这是本批最重要的回归护栏（结构漂移会让它红）。
5. **门禁**：root / core / host / app 四套 + 全部自检 + `analyze` + `format`。

> Red-then-green on plan assertions, reverse verification, re-run `perf_bench` against the
> v4 CSV, and rely on the existing "migrated == fresh" schema test as the structural guard.

## 八、不做的事（避免范围蔓延）

- **不加 `documents` 覆盖索引**（§三：真实用法 0.23 ms，+4.7 MB 换不存在的场景）。
- **不重构单据列表的 `TEMP B-TREE` 排序**（第 4 批 4c 剩余项：两段查询，独立于本提案）。
- **不加 FTS5**（第 4 批已裁 ②甲）。
- **不改任何查询 SQL** —— 本提案只动索引；查询层优化各自单独提交，便于对照。

> No documents index, no list-sort rewrite, no FTS5, and **no SQL changes** — indexes only,
> so each later query rewrite can be measured against a stable baseline.
