## 二、原语实测：`AlertDialog` 在超高缩放下的内边距

口径：同一段文案（标题「确认退货？」+ 两行正文 + 两个按钮），在 1280×800 下量
**卡片左边 → 标题左边**的距离与标题字号。

| 缩放 | 卡片尺寸 | 标题字号 | **左内边距** | 按钮区占宽 | RenderFlex 溢出 |
|---|---|---|---|---|---|
| 1.00 | 362×248 | 24 | **24 px** | 131 / 167 | 无 |
| 1.75 | 569×320 | 42 | **12 px** | 198 / 231 | 无 |
| 2.00 | 638×344 | 48 | **8 px** | 221 / 253 | 无 |

追加两档：

| 场景 | 结果 |
|---|---|
| 2.0 + **3 个按钮**（取消 / 看看归档 / 开始重建） | 按钮区 329 / 361 = **91%**；再长一点就**纵向堆叠**（框架默认行为，不报错） |
| 2.0 + 长标题「重建本机数据副本？」+ 3 行正文 | 卡片 977×304，内边距同样 **8 px** |

### 结论（比逐项清单更有用）

1. **25 个 `AlertDialog` 不会抛"黄黑条纹"** —— 框架会收窄 `insetPadding`、必要时把按钮
   纵向堆，所以 `Overflow` 异常一次都没有出现。
2. **真正的病是内边距**：字号 24 → 48（**×2**），内边距 24 → **8**（**÷3**）。
   这正是用户说的「标题栏和按钮内文字几乎撑破了对话框」—— 不是溢出，是**字贴边**。
3. 所以**不需要 36 条逐项修**：25 个 `AlertDialog` 是同一条结论，改一个共用入口即可；
   真正要逐个看的是那 **11 个自定义组件**（各自排版、不共用原语）。

### 处置建议（等裁定）

| 对象 | 建议 |
|---|---|
| 25 个 `AlertDialog` | 新增共用 `AppDialog`：`titlePadding` / `contentPadding` 用 `24 * min(scale, 1.4)`（2.0 时约 34 px），按钮区 `Wrap` |
| 11 个自定义组件 | 逐个看（它们自带滚动/分栏，未必有问题）；按实际报障优先级排 |

## 三、「200 张单据取明细」实测（决定 §2.6-3 怎么写）

口径：真实压测库 498 MB / 26.2 万单 / 36.3 万明细行（`perfbench.db`），只读连接。

| 步骤 | 结果 |
|---|---|
| 取最新 200 个单据 id | **18 ms**（列表本来就有 id，可省） |
| `document_lines` 一次取这 200 张单的明细 + 商品名 | **291 行**，p50 **1.1 ms**、p95 **13.8 ms**、max 13.8 ms |
| 对照：`COUNT(documents)` | 168 ms（热态） |

**冷盘折算（估算，非实测）**：291 行散落在 `document_lines` 中，按每行 1–2 页估
≈ 300–600 页 ≈ 1.2–2.4 MB；11 MB/s 的慢盘上 **≈ 0.1–0.2 s**。

⇒ **Q6 的答案：可以全量显示**，不必退成「首行 + 等 N 项」。
慢盘上单据页首屏会多 0.1–0.2 s —— 而这一页本来就在 485 + 377 ms 的量级，**且已挪进工作
isolate**（不冻界面），可接受。
