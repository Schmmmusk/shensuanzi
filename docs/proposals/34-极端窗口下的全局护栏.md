## 一、先把两件事说清（这决定了要不要修）

**① 红黄条纹只在 debug 包里画。** Flutter 的 overflow 指示条由 `kDebugMode` 控制 ——
**release 包不会出现条纹**。你截图里看到的「花屏」是调试构建的产物；
同一处在 release 里的表现是**内容被裁切 / 挤成竖排**（不会花，但也确实不好用）。

**② 但这不代表没问题。** 上面 4 张图里，真正坏掉的是**布局本身**：
`¥28,015.23` 这类**金额不能被截断**的尾部元素，在 480 逻辑宽 + 2.0 倍字号下**自己就比整行还宽**
⇒ 左侧所有内容被压成 0 宽、逐字换行。**这不是某一行的 bug，是「这个尺寸装不下这个字号」。**

### English

**① The yellow/black stripes are debug-only** (`kDebugMode`). Release builds paint nothing —
the same overflow becomes silent clipping. **② But the layout is genuinely broken**: at 480 logical px
with a 2.0 text scale, trailing elements that **must not be truncated** (amounts) are wider than the
whole row, so everything to their left collapses to zero width and wraps character-by-character.
That is not a per-row bug; it is "this size cannot hold this text scale".

## 二、为什么**不再**逐页修

已经按这个思路修了 5 处（§CV·六十九 / 七十 / 七十一）：流水行、账户行、往来方行、导航列。
每一处都是真的 bug，但**它们修完也救不了 480×2.0**：

| 480 逻辑宽 + 2.0 倍 | 数字 |
|---|---|
| 导航列（已夹到 40%） | 192 |
| 剩给工作区 | 288 |
| 行内边距 | 32 |
| 「¥28,015.23」在 2.0 倍下的宽度 | **≈ 300** |

⇒ 光金额就超了。**继续逐页加 `Expanded` 只会让条纹消失、内容变成一列竖字** ——
那是「把报警器拆了」，不是修好。

### English

Five per-page fixes have shipped (§CV·69/70/71) and each was a real bug, but none of them can save
480×2.0: after the nav column (192) there are 288 px left, minus 32 px padding, while a single amount
string at 2.0 is ≈300 px wide. **Adding more `Expanded` would only silence the warning** — the content
would still be a vertical column of characters.

## 三、三个方案

| 案 | 做法 | 代价 | 评 |
|---|---|---|---|
| **甲（推荐）** | **窄窗口自动夹紧字号**：在 `app.dart` 那唯一一处 `textScaler`（`:1487`）按窗口宽度算 `min(用户档位, 可容纳档位)`，并在**页头用一行灰字说明**「窗口较窄，已临时显示为「大」」；窗口拉宽自动恢复 | 一处改；所有页面同时受益；**必须带说明**（不许静默改用户设置） | 480 宽时会降到 ~1.0–1.25，界面**可用**（不是好看，是能用） |
| **乙** | **窄窗口给整页提示**：「窗口太窄了 —— 把窗口拉宽，或在设置里把界面大小调回「标准」」，不渲染页面 | 一处改；**不做**布局适配 | 诚实、零风险；但用户被挡住，什么也做不了 |
| **丙** | **只登记不修**（承认超出目标范围） | 0 | 目标用户（中老年个体户）几乎不会同时开 200% + 超大 + 分屏；但**一旦碰上就是全应用不可用** |

**我推荐甲**，理由：它是**唯一让应用在这种窗口下仍然可用**的选项，且只改一处；
乙虽然诚实但等于「不给用」；丙是把已知的坑留着。

### English

**A (recommended)**: clamp the effective text scale by window width in the single `textScaler` site
(`app.dart:1487`), with a one-line notice in the page header ("窗口较窄，已临时显示为「大」") and
automatic restore when the window widens. **B**: a full-page "window too narrow" notice — honest, zero
risk, but the app refuses to work. **C**: log only. A is the only option that keeps the app usable at
that size, and it is a one-site change.

## 四、如果选甲，落地细节（先摆出来）

1. **夹紧公式**（可调，只此一处）：
   `effective = min(userScale, max(1.0, width / 560))`
   - 480 宽 ⇒ 1.0；700 ⇒ 1.25；900 ⇒ 1.6；1120 以上 ⇒ 用户档位不缩；
2. **必须说明**：页头一行灰字 + 设置页「界面大小」旁一句「窗口较窄时会自动降一档」——
   **不许静默**（`ui_principles.md` 的「说清发生了什么」）；
3. **测试**：`app_shell` 层加一条 —— 480 宽 + 用户选「超大」⇒ 实际 `textScaler == 1.0` 且**页头出现说明**；
   1200 宽 ⇒ `== 2.0` 且**没有说明**（反向灵敏度）；
4. **不碰**：各页的既有布局（已修的 5 处保持），窄屏限幅 1.15 也不动。

### English

Formula: `effective = min(userScale, max(1.0, width / 560))` — one place, tunable. A visible notice is
mandatory (header line + a sentence next to the setting). Tests: 480 + "超大" ⇒ effective 1.0 **and**
the notice appears; 1200 ⇒ 2.0 and **no** notice. No page-level layout changes.
