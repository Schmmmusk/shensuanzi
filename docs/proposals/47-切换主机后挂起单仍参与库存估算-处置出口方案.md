## 一、问题复述与证据链（全部 `文件:行`，可逐条 grep）

**现象（报告 R03）**：切换主机后，旧主机未发送的单**挂起**，但**仍参与库存估算** ⇒ 新主机权威库存 `0`，手机显示 `1`。

| # | 代码事实 | 位置 |
|---|---|---|
| 1 | 切主机 = 对 `queue.unsent()`（`pending` + `failed`）逐条 `markHeld`，原因文案里**明说**「确认要发给现在这台主机，就在「同步队列」里点重试」 | `mobile_sync_service.dart:150-173` |
| 2 | `markHeld` ⇒ `status = failed`、`retry_count = 99`、`last_error = 原因` | `sync_dao.dart:116-120` |
| 3 | `SyncQueueStatus` **只有** `pending` / `sent` / `failed` —— 「挂起」**不是独立状态**，落的就是 `failed` | `sync_queue_entry.dart:28-31` |
| 4 | `unsyncedDelta()` 遍历 `_queue.all()`（**全部状态**）；其文档明写「`pending` + `sent` + `failed` 都算 = 已发生、但权威状态还没包含」 | `stock_delta.dart:73-87` |
| 5 | `stockViewOf()` 的 `contributors` 同源，挂起单也是「未同步影响」的贡献者 | `stock_delta.dart:93-109` |
| 6 | **队列明细页是只读的** —— `failed` 条目只有一行说明文字，**没有任何按钮** | `mobile_shell.dart:345-357` |
| 7 | 既有测试**钉住**了「挂起单保留 + 状态 `failed` + 原因含『上一台主机』」 | `mobile_sync_service_test.dart:377-385` |

**结论**：`unsyncedDelta` 的设计语义**没有错**（这笔销售真实发生过），错在 **#6 —— 没有任何出口**，于是这笔单**永久挂账、永久计入**。

## 二、为什么报告的「排除挂起影响」不能直接采纳

报告方向 = 乙 = **把挂起单从 `delta` 里排除**。这与两条既有事实冲突：

1. **与「重试发给新主机」路径冲突**：用户点重试 ⇒ 单发给新主机 ⇒ 权威变成包含它 ⇒ 若同时又把挂起单排除出 `delta`，**显示会在重试的瞬间跳变**（`0 → 1` 或 `1 → 0`，取决于方向）。
2. **与「主机永远赢」的边界冲突**：手机主库不落业务单（镜像只由 `pull` 写，见 `data_model.md §4.4`）⇒ **队列里的 payload 是这笔销售在手机上的唯一副本**。在客户端**悄悄不算**它，等于让这笔真实发生的生意从估算里消失，**比多显示一笔更危险**（少报 > 多显示，记账 App 第一原则）。

⇒ 报告方向**只有在「先裁清『挂起单还算不算本店生意』」之后才成立**。所以本提案把它列为乙，并给出它的连带裁定项。

## 三、三个选项

| 选项 | 做什么 | 代价 | 评 |
|---|---|---|---|
| **甲（推荐）** | **保持 `delta` 计入**（语义正确、不动既有裁定）；**补处置出口** —— 队列明细页给 `failed` 条目加两个动作：**「重试（发给现在这台主机）」** + **「放弃（不再发送）」**。放弃 ⇒ 条目退出估算；重试 ⇒ 回到 `pending` 参与推送 | 根侧 UI + 1 个 core 动作（`requeue` 已在，**零新增**） | 洞在「没有出口」，甲**正好补在洞里**；`delta` 语义一个字不改 |
| **乙（报告方向）** | 挂起单**不计入** `delta` | 需连带裁「**重试时要不要恢复计入**」 | 与「重试发给新主机」冲突（显示跳变）；等于客户端替用户把真实生意抹掉 |
| **丙** | 甲 + 给「重试 = 发给新主机」加**二次确认**（防误触把旧店的单记到新店账上） | 比甲多一道确认 | 与甲不冲突，是甲的**加固**；可同批，也可后补 |

**⚠️ 三个选项都**、**任何情况下都不做**的事：

- **不自动放弃**（不静默删、不静默排除）—— 只有**用户点了「放弃」**才退出口径。
- **不改「换主机 = 挂起」这条既有裁定**（2026-10-07）—— 挂起本身是对的。
- **不动 `unsyncedDelta` 对 `pending` / `sent` 的计入**（那是它的本职工作）。

## 四、若选甲 —— 「放弃」怎么落（**一个必答的子问题**）

「放弃」= 让这条单**退出估算**，两种做法：

| 子选项 | 做法 | 代价 | 后果 |
|---|---|---|---|
| **甲-删** | 直接 `SyncQueueDao.delete(id)`（**已有**，`sync_dao.dart:212-213`） | **零 schema 改动** | **不可恢复** —— 队列 payload 是这笔单在手机上的**唯一副本**（镜像只读）。删了 = 这笔生意在手机上**彻底没了**（新主机也没收到） |
| **甲-标** | 加一列（如 `discarded_at INTEGER NULL`）或加一个状态，标记「已放弃」 | **动 schema**：`Schema.version 3 → 4` + `migrationStep(3)` + 所有读路径 / `delta` / `triage` / 队列明细都要按它过滤 | **可审计**（留着记录、只是不计入、不出现在待办里） |

> ⚠️ **「加状态」不如「加列」**：`SyncQueueStatus` 是 **wire 枚举**，加值会让**旧版客户端**读到它 ⇒ 走 #42 的 `fromWireOrNull` **跳过该行**（行从旧版界面消失）。加**列**不碰 wire 协议。
>
> ⚠️ 这一列与 **#24**（`sync_queue` 加 `reason_code`）**同表同族** —— 若两条一起做，**一次迁移**即可（但 #24 未裁，不强绑）。

**我的建议**：**甲-删 + 二次确认**起步（零 schema、可当天闭环）；若你要「可审计」，再走甲-标（届时与 #24 合并一次迁移）。判据：**这张单在账上还有没有价值** —— 若用户确认「它属于旧店、不要了」，删比留更干净。

## 八、风险与边界（诚实说明）

- **删 = 丢数据**：队列 payload 是这笔单在手机上的**唯一副本** ⇒ 「放弃」**必须**走二次确认，确认文案要写清「**这张单不会再出现在任何地方**」，不能只说「不再上传」。
- **不做「自动放弃」**：任何静默删除 / 静默排除都违反「不静默」（与 #42 甲 同源）。
- **不修复「旧主机权威里的那笔账」**：本提案只管**手机端估算不再挂账**；旧主机那本账的清理**不在范围**（且手机够不到旧主机）。
- **乙 若被选中**：必须**同时**裁「重试时的恢复口径」，否则显示跳变是必然，等于把 #47 换成一个更隐蔽的 bug。
- **#55 不受影响**：那是更新窗口的大批量边界，与本条无关。
