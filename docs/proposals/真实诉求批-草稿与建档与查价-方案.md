## 零、结论先行

| # | 诉求 | 现状 | 改法 | 风险 |
|---|---|---|---|---|
| 1 | **草稿自动保存**（P0） | 无。关页面 = 全丢 | 编辑时 1.5 s 防抖写 `<数据目录>/drafts/<kind>.json`；进页发现草稿挂**橙条**「恢复 / 放弃」 | **低**（不碰主库、不碰规则） |
| 2 | **开单页无缝建档** | 只能从商品页建档；明细行必须有 `productId` | 明细行允许只填商品名；保存时在**服务层事务内**先建商品再落单 | **中**（改保存路径 + 会写主数据） |
| 3 | **查价** | 只能进「库存」页看（信息量大） | 新页「查价」：大搜索框 + 大字号售价 + 小字库存 | **低**（只读） |

**建议顺序**：1 → 3 → 2。理由：草稿是「救命」，查价是「只读、零风险」，
无缝建档要动保存路径，放最后单独一轮门禁。

> Order: drafts (saves data) → price lookup (read-only) → inline product creation
> (touches the save path and writes master data).

## 一、诉求 1：草稿自动保存（P0）

### 1.1 先说「按 Ctrl+S 被拦截」——**不能照着猜**

我核实了：**Ctrl+S 已经绑在三个页面**上，而且有一段专门修焦点的注释：

```
sale_page.dart:804      SingleActivator(LogicalKeyboardKey.keyS, control: true): _save
purchase_page.dart:650  同上
delivery_page.dart:591  同上
```

`delivery_page.dart:596-600` 还记着 2026-10-14 的 #37甲 修复：`CallbackShortcuts` 内部是
`Focus(canRequestFocus: false)`，点页内空白会把焦点升到路由的 scope ⇒ 快捷键静默失效；
换 `FocusScope` 之后恒生效。

所以「按了没反应」有三种可能，**必须先复现再修**：

| 候选 | 怎么判断 |
|---|---|
| A. 保存被**校验拦住**，而错误摘要滚出了可视区 | 按 Ctrl+S 后看页顶有没有红字；用户说「没反应」时多半是这个（与上一轮 P1「保存失败只标红不定位」同源） |
| B. 焦点在**弹窗里**（商品选择器 / 收款框），快捷键到不了页面 | 关掉弹窗再按一次 |
| C. 保存**抛异常**（磁盘/库），只弹了一次 SnackBar 就没了 | 看日志 |

⚠️ **本提案不假设是哪一种**。但无论哪一种，**草稿自动保存都能兜住**——这正是它该做 P0 的理由。

> Ctrl+S is already bound on three pages (with a documented focus fix). The "no response"
> symptom needs reproduction first; the draft feature makes the data loss impossible regardless.

### 1.2 存哪里：**数据目录下的 `drafts/`**，不进主库

```
<数据目录>/
  shensuanzi.db
  .shensuanzi-data          ← 现有标记
  drafts/                   ← 新增
    sale.json
    purchase.json
    delivery.json
```

为什么是这里（而不是 `%APPDATA%` 或 SharedPreferences）：

1. **草稿属于这份数据** —— 用户换数据目录（换店/换电脑）时草稿应该跟着走；
2. **不进主库**（家人明确要求）：草稿是脏数据，进 `documents` 会污染流水与对账，
   而且 `RuleEngine` 的每一条不变量都不该为「没提交的东西」开口子；
3. **不进 `%APPDATA%`**：那是「这台机器」的配置，与「这家店的账」不是一个生命周期；
4. 备份**不打包 drafts**（备份只拷 `shensuanzi.db`）—— 草稿不该被当成账。

⚠️ 目录不可写时**静默跳过**（草稿是尽力而为，不能因为存不了草稿就让开单报错）。

### 1.3 存什么：字段**全用原文**，不做任何金额/数量换算

```json
{
  "v": 1,
  "savedAt": 1761300000000,
  "kind": "sale",
  "partyId": "…",
  "partyName": "王老板",
  "date": "2026-10-24",
  "remark": "…",
  "lines": [
    {"productId": "…", "productName": "蒙牛纯牛奶", "quantity": "3",
     "unitPrice": "5.00", "entryUnit": "", "discountAmount": "",
     "baseUnit": "瓶", "packageUnit": "箱", "packageSize": 24}
  ],
  "payments": [{"accountId": "…", "amount": "15.00"}]
}
```

- **一律存字符串原文**：`SaleDraft` / `PurchaseDraft` / `DeliveryDraft` 里的数量与金额
  本来就是 `String`（用户输入原文）—— 存原文 = 恢复后**一字不差**，不引入二次换算误差；
- `v` 是草稿格式版本：将来加字段时旧草稿能识别（不认识的 `v` ⇒ 忽略并提示「草稿来自更新版本」）；
- `savedAt` 用于橙条文案（「今天 14:32 的草稿」）。

**序列化放哪**：`core` 的 draft 类上加 `toJson()` / `fromJson()`（纯值对象、无 IO），
**文件读写放 app 层**（`drafts_store.dart`）。这样序列化能被纯 Dart 测试覆盖。

### 1.4 触发与清除

| 时机 | 动作 |
|---|---|
| 任一输入变化 | 起 **1.5 s 防抖**，到期写文件（家人建议 1~2 s，取中） |
| 保存成功 | **删草稿** |
| 点「放弃」（橙条） | **删草稿** |
| 点「取消」并确认放弃 | **删草稿**（`_cancel` 已有二次确认） |
| 页面 dispose（用户直接关窗口） | **立刻写一次**（不删）—— 这正是要救的场景 |
| 恢复后继续编辑 | 照常防抖覆盖 |

⚠️ **不要**在 dispose 时判断「有没有实质内容」——空表单也会写，但那只是一行 JSON，
下次进页橙条会说「上次的草稿是空的」？⇒ **写之前先判空**：`lines` 全空且无备注/客户 ⇒ 删草稿而不是写。

### 1.5 恢复交互：橙条，**不自动填**

```
┌─────────────────────────────────────────────┐
│ 发现 10月24日 14:32 未提交的草稿（3 行）      │
│                        [恢复]  [放弃]        │
└─────────────────────────────────────────────┘
```

- **不自动填**（家人明确要求）：用户可能是想开一张新单，自动填会让他以为软件出错了；
- 「恢复」⇒ 填进表单 + 收起橙条 + **保留草稿**（继续编辑时防抖覆盖）；
- 「放弃」⇒ 删草稿 + 收起橙条 + 表单保持当前状态（不动）；
- 草稿与当前表单都有内容时点「恢复」⇒ 二次确认「会覆盖你现在填的」。

### 1.6 边界（每条都要有测试）

| # | 情况 | 期望 |
|---|---|---|
| 1 | 草稿里的商品**已被删/停用** | 恢复后照常显示名字，保存时按现有校验报错（不静默丢行） |
| 2 | 草稿日期是**昨天** | 恢复后日期仍是昨天（草稿存了 `date`） |
| 3 | 草稿 JSON **损坏** | 忽略 + 删掉 + 日志（不崩、不弹红） |
| 4 | `drafts/` **不可写** | 静默跳过；开单照常 |
| 5 | 同一 kind 的草稿被**另一台设备**同步过来 | 不适用（草稿不进库、不同步） |
| 6 | 两个页面（销售/采购）都有草稿 | 互不影响（按 kind 分文件） |

### 1.7 测试

- **纯 Dart**：`SaleDraft.toJson → fromJson` 往返等价（含空行、含包装单位、含让价）；
  损坏 JSON ⇒ `null`；版本不认识 ⇒ `null`。
- **widget**：进页有草稿 ⇒ 橙条出现且**表单是空的**；点「恢复」⇒ 表单被填；
  点「放弃」⇒ 文件被删。
- **反向验证**：把防抖时长改成 0 并删掉 `cancel`，橙条用例应红（证明防抖真的在起作用）。

> Serialization is pure value objects (core, testable); file IO is app-layer. Drafts live
> beside the DB, never inside it; restore is opt-in via an orange banner.

## 二、诉求 2：开单页无缝建档

### 2.1 现状比想象的近：`SaleLineDraft` **已经**允许没有商品

```dart
class SaleLineDraft {
  const SaleLineDraft({
    this.productId = '',      // ← 已经是「可空」的形态
    this.productName = '',
    ...
```

所以「手打商品名」**不需要改数据模型**，只需要：
1. UI 允许提交一行 `productId == '' && productName != ''`；
2. 保存时把它解析成真实商品。

### 2.2 落点：**服务层的事务内**，不是 UI、也不是 `RuleEngine`

家人说「在 ServiceSink 里拦截」，方向对（不能在前端调建库），但精确位置要再往里一层：

| 位置 | 能不能做 | 原因 |
|---|---|---|
| UI | ❌ | 违反「同步落库必须走 RuleEngine/服务层」的纪律 |
| `RuleEngine` | ❌ | 引擎拿到的是 `List<DocumentLine>`，里面的 `productId` 已经是**主键**；引擎不知道「商品名」，也不该知道 |
| **`SaleService.create` / `PurchaseService.create`** | ✅ | 它负责把 draft 变成 `DocumentLine`（`document_build.dart`），**建商品与建单在同一个 `db.transaction` 里** |

**事务可行性已核实**：`Db.transaction` 是**可重入**的（`database.dart:266` 用 `_depth` 计数，
`if (_depth > 0)` 直接复用外层事务）⇒ `ProductService.create()`（它自己也开事务）
在服务层的事务内调用**会加入同一事务**，不会出现「商品建了、单没落」。

```
SaleService.create(draft)
  └─ db.transaction(() {
       ① 解析缺档行：productId == '' 且有名字
          → 先按**名字精确匹配**现有商品（避免重复建档）
          → 匹配不到 ⇒ ProductService.create(ProductDraft(name: 名字, unit: '件',
                                                          costPrice/sellPrice: 见 §2.3))
       ② 用解析后的 productId 构造 DocumentLine
       ③ RuleEngine.dispatch(document, lines)   ← 落单（引擎自己不开事务，因为已在事务内）
     })
```

⚠️ **必须先匹配再新建**：用户手打的名字很可能与已有商品**一字不差**（他只是没从选择器点）。
不匹配就建档 ⇒ 商品列表里出现两个「蒙牛纯牛奶」，库存被拆成两半。这是本项**最大的坑**。

### 2.3 建商品时填什么

| 字段 | 销售单 | 采购单 | 理由 |
|---|---|---|---|
| `name` | 用户输入 | 用户输入 | — |
| `unit` | `'件'` | `'件'` | 与 `ProductDraft` 的默认值一致（**已经是「件」**，不是新造） |
| `sellPrice` | **= 行单价** | 留空 | 销售单填的单价就是售价 |
| `costPrice` | 留空 | **= 行单价** | 采购单填的单价就是进价 |
| `barcode` | 空 | 空 | 有码的话用户会扫码，不会手打 |

⚠️ **留空 = 0，不是「未知」**。这一点要在对话框里说清楚：**「先建档、价格以后再改」**，
否则用户会以为系统记住了他的进价（其实只是这一单的）。

### 2.4 交互（家人给的两个按钮，我建议改成三个）

```
┌──────────────────────────────────────────────┐
│ 「蒙牛纯牛奶」还没建档。                        │
│                                              │
│ [先建档再保存]  [去商品页填详细信息]  [取消]    │
└──────────────────────────────────────────────┘
```

- **先建档再保存**（默认，回车即走）：按 §2.3 建 + 落单，一步完成；
- **去商品页填详细信息**：跳到商品页、名字预填，本单不保存（用户回来重开）；
- **取消**：什么都不做，回到表单（**不关页面、不丢输入**）。

⚠️ 一次保存里**多个**缺档行 ⇒ 一个对话框列出全部（「这 3 个还没建档」），
不要弹三次。

### 2.5 风险与护栏

| 风险 | 护栏 |
|---|---|
| 同名重复建档 | §2.2 的「先精确匹配」；测试：已存在同名 ⇒ **不新建**、直接绑定 |
| 错别字被固化成商品 | 对话框把名字**加引号原样显示**；「去商品页」这条路给愿意改的人 |
| 进价污染商品档 | 采购单只写 `costPrice`、销售单只写 `sellPrice`；留空不写 0 到「已有值」上（新建才有值，不改已有商品） |
| 建档成功但落单失败 | **同一事务** ⇒ 一起回滚（这是选服务层而不是 UI 的唯一理由） |
| 手机端（同步）也走这条路 | 手机端不建档（`MasterDataPolicy` 手机可建商品 —— 但**本批不动手机端**，只做桌面） |

> Resolution happens inside `SaleService.create`'s transaction (reentrant `Db.transaction`),
> matching by exact name first to avoid duplicates. Never in the UI, never in the engine.

## 三、诉求 3：查价

### 3.1 页面

```
┌────────────────────────────────┐
│  ← 查价                        │
│  ┌──────────────────────────┐  │
│  │ 🔍 输入商品名或条码        │  │
│  └──────────────────────────┘  │
│                                │
│   蒙牛纯牛奶 500ml              │
│   ¥ 5.00          ← 48pt 大字  │
│   库存 36 瓶                    │  ← 小字
└────────────────────────────────┘
```

- **只显示**：名称 / 售价 / 库存。**不显示**成本、编码、条码、预警值（家人明确要求）；
- 输入即筛（300 ms 防抖，复用 `ListHeader` 的既有实现），结果**列表化**（多个命中时）；
- 条码：键盘式扫码枪直接往输入框打字 + 回车 ⇒ 命中唯一时直接显示大字号；
- 数据：`ProductDao.findAll(query: …)` 与 `findByBarcode(…)`（**两个 API 都已存在**，不用新写查询）。

### 3.2 入口

概览页放一个明显入口（与「开单」「库存」同级），**不动库存页**（家人明确说库存页做得好）。

### 3.3 库存口径

「库存 36 瓶」用 `stockByProduct()`（账面）还是 `availableInStore()`（在店可售）？

- **用账面**（`stockByProduct`）：查价的人问的是「店里有几瓶」；
- 在店可售是给「低库存告警」用的（扣掉在途），对查价的人是噪音。

⇒ 用账面，并在小字里只说「库存」（不说「可售」，避免与库存页口径打架）。

## 七、验收

1. **草稿**：断网/杀进程后重开页面 ⇒ 橙条在、点恢复后**一字不差**；保存成功后文件消失。
2. **无缝建档**：手打一个新名字 ⇒ 保存后商品列表**多一个**、单据**一条**、库存流水**一条**；
   手打一个**已存在**的名字 ⇒ 商品数**不变**、单据正常。
3. **查价**：输入「牛奶」⇒ 大字售价 + 小字库存；扫条码 ⇒ 唯一命中直接显示。
4. **门禁**：四套测试 + 全部自检 + `analyze` + `format`（与每批同）。
5. **真机**：在家人那台机器上按「填一半 → 直接关窗口 → 重开」走一遍。

> Acceptance: kill the app mid-edit and restore; inline creation must add exactly one
> product and one document; price lookup shows only name/price/stock.
