# 服务绑定收紧（TM-1 甲）—— 落地方案（🔴 待裁定，未动实现）

> 来源：`docs/threat_model.md` §七 **TM-1**。
> 2026-11-10 用户裁定「本次走**乙**（只改文案）」；2026-11-11 用户要求「一并出甲的方案」。
> 本文只讲**甲**：让「只绑局域网网卡」这句话成真。

## 一、现状（三处证据，逐条对齐）

| 位置 | 现状 |
|---|---|
| `service_controller.dart` `_startRaw()` 调 `HostHttpServer.start(...)` | **没传 `address`** |
| `http_server.dart` | `final InternetAddress bind = address ?? InternetAddress.anyIPv4;` ⇒ **绑 `0.0.0.0`** |
| `service_controller.dart` `selectAddress()` 的注释 | 「换地址**不用重启服务**：服务绑的是 `0.0.0.0`，地址只影响二维码内容」 |

⇒ 探测出来的局域网地址（`_address`）**只用于二维码与界面提示**，与绑定无关。
这就是为什么文档里那句「只监听局域网网卡」在 2026-11-09 的审查里被判为**假话**。

## 二、好消息：地址选择逻辑已经很健壮，不用重写

`LocalIp.rank()` 已经把该做的都做了（2026-10-25 的 `natpierce` 事故之后加固过）：

1. 排除 loopback / link-local
2. **真网卡名优先**（`WLAN` / `Wi-Fi` / `以太网` / `Ethernet` / `本地连接`）
3. 优先私有网段（`192.168/16`、`10/8`、`172.16~31/12`）
4. **跳过虚拟网卡**（VirtualBox / VMware / WSL / Hyper-V / VPN / 穿透工具）
5. 都挑不出来 ⇒ 退回第一个非 loopback；一个都没有 ⇒ `null`

而且 `host_service_section.dart` **已经有「换一个地址」的 UI**
（`host-address-option-<ip>`，列出全部候选让用户挑）。

⇒ **甲的工作量不在「怎么挑地址」，在「绑定之后那些路径怎么办」。**

## 三、核心代价：三处行为会变，每一处都必须处理

### 代价 1：`selectAddress()` 从「只重画二维码」变成「**必须重启服务**」

现在换地址是同步、无副作用、必然成功。绑定收紧之后：

- 绑定发生在 `serve()` 那一刻 ⇒ 换地址**必须**停掉旧 server、用新地址重绑
- 重启会**短暂断连**（手机正在同步时可能失败一次）
- 重启**可能失败**（端口被别的程序抢了）⇒ `selectAddress` 从 `bool` 变成 `Future<...>`

⚠️ 这一条会波及 UI：对话框里点另一个地址，现在 `setState` 就完事；之后要显示「正在重启服务…」。

### 代价 2：探测不到地址时，「服务起不来」还是「回退 `0.0.0.0`」

| 选项 | 行为 | 后果 |
|---|---|---|
| 甲 | **直接失败**，状态 `failed` + 提示「没找到局域网地址，请先连上 WiFi」 | 语义诚实；但**用户拔了网线时连本地都连不上**（虽然本来也没用） |
| **乙（推荐）** | 回退 `0.0.0.0`，但**在 `snapshot` 里标出 `bindFallback = true`**，界面上明说「当前监听全部网卡（没找到局域网地址）」 | 不损失可用性；且**不留假话** —— 文档可以写「正常情况只绑局域网网卡，探测失败时回退并显式告知」 |

否决甲的理由：`0.0.0.0` 在「找不到局域网地址」时是**唯一能用**的绑定，
而那种情况下用户本来就该先连网 —— 但让他看到「服务启动失败」比「能起但连不上」更容易误解。

### 代价 3：多网卡选错 > 现在更严重

现在选错只影响二维码（重扫一次就能改）。收紧后选错 = **绑到错误网卡 = 手机根本连不上**，
而且用户不知道要回来改。

缓解（推荐都做）：
1. 对话框里的地址列表**标注推荐项**（`rank()` 已经排好序，第一个标「推荐」）
2. 选中虚拟网卡地址时给一句提示：「这个地址可能是虚拟网卡，手机多半连不上」
3. 「服务正在运行但手机连不上」时，设置页给一个明确的**排查入口**（现在已有类似的提示文案）

## 四、实现范围

| 层 | 文件 | 改动 |
|---|---|---|
| host | `service_controller.dart` | `_startRaw()`：`start(address: InternetAddress.tryParse(_address))`；`selectAddress()` 改为 **async + 重启**；新增 `bindFallback` 状态 |
| host | `http_server.dart` | 无需改动（`address` 参数本来就有） |
| host | `service_controller.dart` | `_address` 为 `null` 时按 §三 代价 2 的裁定处理 |
| ui | `host_service_section.dart` | 换地址时显示「正在重启服务…」；地址列表标「推荐」；虚拟网卡提示 |
| ui | `settings_page.dart` | 若 `bindFallback`，在服务状态行显示「当前监听全部网卡」 |
| doc | `threat_model.md` §2.1 / §七 | 甲落地后把「只监听局域网网卡」改成真话，TM-1 标 `✅ 已落地` |

**不改**：`local_ip.dart`（选择逻辑已够用）。

## 六、风险与建议

| 风险 | 影响 | 缓解 |
|---|---|---|
| 用户选了虚拟网卡地址 | 手机连不上，且很难自查 | 列表标推荐 + 虚拟网卡提示 |
| 换地址重启时正在同步 | 一次同步失败（客户端有退避重试） | 提示「正在重启服务」；重试逻辑已存在 |
| 探测不到地址 | 按裁定回退或失败 | 见 §三 代价 2 |
| **用户换网卡（拔网线切 WiFi）** | 绑定失效：服务显示 `running` 但不可达 | 这**不是新增风险**（现在换网卡后二维码里的地址也过期了），但收紧后更隐蔽 ⇒ 建议状态行提示「网络变化后请重启服务」 |

## 七、我的建议

**先做甲的最小版**（只改 `_startRaw` + `bindFallback` + 测试 1/2/7），
**`selectAddress` 的异步化单独一刀**。

理由：前者是「让文档那句话成真」，风险集中在启动路径，好测；
后者会改一个被 UI 直接调用的同步方法，波及对话框交互与一处 `setState`，
混在一起做的话，出问题时不容易判断是哪一半引起的。

## 八、需要你裁定的三件

1. **§三 代价 2**：探测不到地址时，失败 还是 回退并显式告知（我推荐后者）
2. **§七**：是否接受「分两刀」（先绑定、后 selectAddress）
3. **§六 最后一条**：要不要加「网络变化后请重启服务」的提示（这需要监听网卡变化，成本比前两件高）
