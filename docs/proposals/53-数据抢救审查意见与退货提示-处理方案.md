## 一、① 抢救没带 `-wal` —— **实测丢 17%**

### 实验（120 单的库，其中 20 单只在 wal 里）

造法：先写 100 单并 `wal_checkpoint(TRUNCATE)`（进主文件），再写 20 单**不 checkpoint**
（只在 `-wal` 里），然后复制文件当「崩溃现场」。

| 情形 | 读出单据数 |
|---|---|
| 现场快照（主文件 + wal） | 120 |
| **只拷主文件（不带 wal）** | **100（丢 20，17%）** |
| 连 wal 一起拷 | **120** ✓ |
| 主文件**头坏** + wal（借头后） | **120** ✓ |
| 主文件**坏页** + wal | **120** ✓ |

三条要点：

1. **用户说的「可能漏」是确定的漏**：只要崩溃前有未 checkpoint 的已提交事务，就一定丢。
2. **wal 里的页能覆盖主文件的坏页** —— 所以连头坏、坏页都能靠 wal 救回来。
3. **`-shm` 不用复制**（共享内存索引，SQLite 打开时重建）。

### 修法

```dart
source.copySync(copy);
final File wal = File('$sourcePath-wal');
if (wal.existsSync()) wal.copySync('$copy-wal');   // ← 就这一句
```

- 抢救用的已经是**可写连接**（P1 落地时为了 `DROP INDEX` 改的），它打开副本时会自动应用 wal。

#### 🆕 裁定补充：必须先保证「源文件在复制期间没变」

分两次 `copySync`（`db` 然后 `-wal`），如果另一进程正在写库，两次复制之间 wal 可能变了
⇒ 拿到的是**主文件 + 另一个时刻的 wal**，组合起来可能比「只拷主文件」更糟（会应用半截事务）。

做法（按可靠性递增）：

| 方案 | 做法 | 评价 |
|---|---|---|
| **甲（推荐）** | 复制前后各取一次「文件大小 + 修改时间 + wal 的 salt」，不一致就**明确失败**并让用户重试 | 简单、诚实；抢救本来就不该在「库还开着」时做 |
| 乙 | 抢一个独占锁（`flock` / Windows 共享模式）再复制 | 更彻底，但 Dart 没有跨平台文件锁 API，要 `Process.run` 绕 |
| 丙 | 复制到副本后，**用 `PRAGMA integrity_check` 验副本**，不过就重来 | 补救而非预防，且慢 |

**判据（测试要钉住）**：复制期间改动源文件 ⇒ 抢救必须**返回失败**并说「文件正在被别的程序写，
请关掉软件再试」，而不是默默产出一份可能不一致的结果。

> 现实约束：能走到抢救这一步，用户通常已经打不开软件了（没有进程在写）。所以甲案的
> 「检测到变化就失败」在真实场景里几乎不会触发 —— 但**必须存在**，否则「抢救」会变成
> 「碰运气」。
- 报告加一个字段 `walCopied`，界面上说一句「用上了还没落盘的最新数据」（让用户知道救的是「最后一刻」）。
- **顺序很重要**：复制 wal 必须在**借头之前**（借头会改主文件头，但 wal 的盐值校验依赖主文件头——
  实测借头后仍能应用，因为盐值存在 wal 头里，与主文件头无关；但先复制更安全）。

### 测试设计（**先红后改**）

1. 造库 → 写 100 单 → checkpoint → 再写 20 单 → **不 close**，直接复制 `db` + `-wal` 到另一处
2. 抢救副本，断言 `totalDocuments == 120`
3. **反向灵敏度**：把 `wal.copySync` 那行注释掉 ⇒ 必须红（变成 100）

> ⚠️ 造「未 checkpoint 的 wal」有个坑：Dart 的 `Database.dispose()` **会 checkpoint**。
> 所以要在 dispose **之前**复制文件（Windows 上 SQLite 不是独占打开，可以复制）。

### English

Measured: a 120-document database with 20 documents only in `-wal` yields **100 documents** if only the
main file is copied (17% loss). Copying `-wal` alongside gives all 120 — including when the main file's
header or pages are damaged (WAL pages overwrite the damaged ones). Fix is one line; test must go red first.

## 二、② 完整性判定偏粗 —— 判据可以精确化

### 现状为什么不够

```dart
final bool expectsLedger = myStock.isNotEmpty || myMoney.isNotEmpty || myParty.isNotEmpty;
```

一张 5 行的销售单，5 条库存流水只救回 1 条 ⇒ `isNotEmpty` 为真 ⇒ 判「完整」并导入。
库存少减 4 行，账就错了 —— 这恰好是抢救功能最该防的事。

### 好消息：判据本来就有精确答案

看 `rule_engine.dart`：库存流水是**逐条明细生成的**

```dart
for (final DocumentLine line in lines) { _insertStock(productId: line.productId, ...) }
```

所以「应有几条」不是猜的，是**可以算的**。

### 判据表（按业务类型）

| 类型 | 明细 | 库存流水 | 资金流水 | 往来流水 |
|---|---|---|---|---|
| `sale` / `delivery` | ≥1 | **条数 = 明细条数**，且每个 `product_id` 都有 | 立即收款才有 | 有往来方才有 |
| `purchase` | ≥1 | 同上 | 立即付款才有 | 有往来方才有 |
| `sale_return` / `purchase_return` | ≥1 | 同上（数量符号相反） | 退款才有 | 有往来方才有 |
| `stocktake` | ≥1 | **只对「数量有变化」的明细要求**（无差额不产生流水） | 无 | 无 |
| `receipt` / `payment` | 无 | 无 | **≥1** | 有往来方才有 |

#### 🆕 裁定补充：`Set<product_id>` 不够 —— 必须按商品核对**行数与数量**

用户举的反例（成立）：

| 明细行 | 商品 | 数量 |
|---|---|---|
| 第 1 行 | 可乐 | 10 |
| 第 2 行 | 可乐 | 20 |

规则层**逐条明细**生成流水（两行 ⇒ 两条）。丢了一条之后，`stockProducts` 里**仍有「可乐」**
⇒ 集合判据照样通过。**集合只记「有没有」，不记「几次、多少」。**

改成按商品聚合核对：

```dart
// 明细侧：每个商品的「行数」与「数量合计」
final Map<String, ({int rows, int qty})> lineAgg = ...;
// 流水侧：同一商品的行数与数量合计（流水数量带符号，销售是负）
final Map<String, ({int rows, int qty})> stockAgg = ...;
// 判据：行数相等 且 数量绝对值相等
```

三条判据（按严格程度，取前两条就够）：

1. **行数相等**：明细里某商品有 N 行 ⇒ 库存流水里同一商品也有 N 行
2. **数量相符**：`|SUM(明细数量)| == |SUM(流水数量)|`（流水带符号，销售为负）
3. 金额相符（可选）：`SUM(明细 amount) == |SUM(流水 total_cost)|` —— 但让价/折扣会让两者不等，
   **不建议**作为判据（会误报）

**盘点的例外**：数量无变化的明细不产生流水 ⇒ 盘点单按「有变化的行」比对，
不能要求「每行都有流水」。

#### 🆕 裁定补充：核销关系也要查（当前是漏的）

`_firstMissingRef()` 收了 `settle` 参数**但一次都没用**。后果：

- 一张收付款单如果它的 `settlements` 行丢了 ⇒ 那张单看起来「完整」，但账上少了这笔核销
- 一张退货单的退款核销丢了 ⇒ 与 ⑥ 的退款上限判断直接相关

判据：

| 单据类型 | 核销要求 |
|---|---|
| `receipt` / `payment` | `SUM(settlements.amount where receipt_doc_id = 本单)` **必须等于** `documents.total_amount` |
| 其它类型 | 若 `settlements` 里有指向它的行，那些行的 `receipt_doc_id` **必须也在**（否则核销悬空） |

核销是「钱和货的对应关系」，丢了它 = 账面上钱和货对不上，比缺一条流水更难查。

### 判定不了的，进待确认

如果一张单据的类型不认识（`DocType.fromWireOrNull` 返回 null），或者规则表里没有它的行
⇒ **默认判「不完整」**，进待确认列表。宁可疑，不可放。

### 测试设计（**先红后改**）

现有测试都是「删光一张单的全部流水」，钉不住部分缺失。补：

1. 5 条明细的销售单，**删掉其中 2 条**库存流水 ⇒ 必须判不完整
2. 同上，删掉 1 条明细对应的**全部**流水（其余完好）⇒ 必须判不完整
3. 盘点单，数量无变化的明细**不产生流水** ⇒ 必须判**完整**（反例，防过度严格）
4. 收付款单只有资金流水 ⇒ 完整

### English

Current check passes if *any* ledger row exists — a 5-line sale with 4 lost stock rows still looks complete.
But `rule_engine` generates one stock row per line, so the expected count is computable. Replace
`isNotEmpty` with a per-`product_id` coverage check; unknown doc types default to "incomplete".

## 三、③ 备份后台复制 —— 风险真实，但要先测

### 现在的流程

1. 主线程 `PRAGMA wal_checkpoint(TRUNCATE)`（wal 清空、数据落进主文件）
2. `Isolate.run` 复制主文件
3. 复制期间应用继续跑，业务写入进新的 wal

### 风险点（用户指出的，成立）

第 2 步期间如果有写入，wal 涨到阈值（默认 1000 页）会触发 **auto-checkpoint** ——
那时主文件正在被复制，**可能拷到撕裂的快照**。而 `quick_check` 只验结构，验不出「少了几笔」。

### 先测，不先改

测试设计：备份进行中持续提交业务写入（用一个慢速文件系统或大库拉长复制窗口），
备份完成后对比「备份里的事务数」与「checkpoint 时刻的事务数」。

**这个测试有一个前提要先验证**：能不能稳定复现。如果复现不了（复制太快），
就要人为拉长窗口（例如注入一个「复制前 sleep」的钩子）。

### 如果确认不安全，两条路

| 方案 | 做法 | 代价 |
|---|---|---|
| **甲：SQLite backup API** | `sqlite3_backup_*` 做一致性快照（不锁业务） | 要先确认 Dart 的 `sqlite3` 包暴露了这个 API；不暴露就得走 FFI 或换方案 |
| 乙：备份期间禁写 | 备份开始时拦业务写入 | 用户体验差（备份几百 MB 要几秒），不推荐 |

**甲是正解**：`sqlite3_backup_step` 是 SQLite 官方为「在线备份」设计的，
它内部持有读锁、按页拷贝，**不需要停业务**。

> ⚠️ 待验证：`package:sqlite3` 是否暴露 `backup` API。若没有，看它的 `Database` 有没有
> `prepare` 之外的原生入口；再不行就 `DynamicLibrary` 直接调 `sqlite3_backup_init/step/finish`
> （三个函数，参数简单）。

### English

Risk is real: a checkpoint triggered by concurrent writes during the isolate copy can tear the snapshot,
and `quick_check` cannot detect missing transactions. Test first (needs a way to reliably reproduce the
window). If confirmed, use the SQLite backup API (`sqlite3_backup_*`) — verify whether `package:sqlite3`
exposes it.

## 四、④ 抢救阻塞 UI —— 该搬 isolate，但要单独提交

### 现状

`rescueDatabase` 声明 `async`，但内部是 `copySync` / `readAsBytesSync` / `writeAsBytesSync`
+ 大量同步 SQLite 调用。`async` 只让「等待」不阻塞，**同步计算照样占住事件循环**。
478 MB 库的抢救可能几十秒，界面会完全冻住，进度条也不动 —— 用户分不清「在抢救」和「卡死」。

### 方案：整体搬进 `Isolate.run`

好消息：**`rescueDatabase` 的参数和返回值都是纯数据**（String 路径 + `RescueReport`），
不持有 `Database`（它自己在里面开），所以可以直接 `Isolate.run`。

进度要靠 `SendPort`（`Isolate.run` 不支持回调）：

```dart
final ReceivePort progress = ReceivePort();
await Isolate.run(() => _rescueInIsolate(..., progress.sendPort));
```

### 代价与取舍

- `_repairHeader` 那条路径会把整个库读进内存（478 MB ⇒ 478 MB `Uint8List`）。
  搬进 isolate 之后，这份内存不在 UI isolate 上，**反而更安全**。
- 进度消息是「发一条丢一条」的语义，UI 端要做节流（否则几十条消息刷爆帧）。
- 这块改动碰的是**执行模型**，不是业务逻辑 —— 按用户要求**单独一次提交**。

### English

`async` does not move synchronous work off the UI isolate. `rescueDatabase` takes and returns plain data,
so `Isolate.run` works directly; progress via `SendPort` with UI-side throttling. Separate commit.

## 五、⑤ 销售退货「不退钱」后，欠款结论不够明显

### 现状（取证）

`return_page.dart` 提交成功后直接 `Navigator.pop()` —— **退货页关掉就结束了**，没有任何「现在欠多少」的结论。
用户回到销售单详情页，只能看到「已退货 −¥30」，然后自己去想「原来欠 100，退了 30，那现在欠 70？」
—— 而那个 70 要跨「金额 / 已收 / 已退货 / 未收」四行心算。

这正是用户说的「必须去难以逐行计算的流水中找到真正的欠款」。

### 建议

**退货提交成功后，回原单详情页并给一条明确的结论**（不是关窗走人）：

| 情形 | 提示 |
|---|---|
| 退完还欠 | 「已退货 ¥30。这张单现在客户还欠 **¥70**。」 |
| 退完不欠不欠他 | 「已退货 ¥30。这张单已经两清（客户不欠你，你也不欠客户）。」 |
| 退成「我们欠客户」 | 「已退货 ¥30。这张单现在**你欠客户 ¥20**（退得比收得多）。」 |

三种情形都要**明确说出方向**（客户欠我 / 我欠客户 / 两清）——「未收 ¥-20」这种写法
用户读不懂，也容易当成错账（详情页已有 `unsettled < 0 ⇒ 多收 ¥X` 的口径，这里要一致）。

### 具体位置

- `return_page.dart` 的 `_submit` 成功分支：`Navigator.pop()` 改成 `Navigator.pop(结果)`
- 调用方（详情页的 `_returnDocument`）拿到结果后 `showSnack` + 刷新
- 文案里的三个数字（退货额 / 当前欠款 / 方向）都从**服务层算**，不在 UI 里拼

### English

After a return is submitted the page just closes — no "what do I owe now" conclusion. Add a result
returned to the caller: "Returned ¥30. This order now owes you ¥70." Must state the direction
(customer owes you / you owe customer / settled), not a negative number.

## 六、⑥ 送货「已签收未收款」退货时，不该展示退款卡片

### 现状（取证）

`return_page.dart` 的退款卡片只判断「有没有选账户」，**不看原单收过钱没有**。
一张已签收、一分钱没收到货的送货单，退货时照样弹出「退款金额 / 退款账户」——
用户填了、提交，才发现根本没这笔钱可退（或者更糟：真生成了一张付款单，账上凭空多出一笔支出）。

用户原话：「这种问题发生了后果更难收拾」—— 对，它不是显示问题，是**会造出错账**的入口。

### 建议

**退货页按原单的「已收金额」决定卡片形态**：

| 原单已收 | 退款卡片 |
|---|---|
| = 0 | **不显示金额与账户**，改为一句说明：「这张单还没收到钱，所以没有可退的。退货后会直接冲减欠款。」 |
| > 0 但 < 退货额 | 显示卡片，但金额上限 = 已收金额，并说明「最多退 ¥X（这张单只收到这么多）」 |
| ≥ 退货额 | 正常显示 |

**同时**在服务层加一道闸：`ReturnDraft` 带退款时，如果原单已收为 0 ⇒ `RuleRejected`
（不只靠 UI 拦 —— UI 可以绕过，规则层不行）。

#### 🆕 裁定补充：上限必须基于「真实收款」与「累计已退款」

用户指出的三点，逐条确认：

**① `paid_amount` 是缓存，不是真相。** `Agents.md` §二·4 明确：真相在流水，
`documents.paid_amount` 是派生缓存。判「原单收过多少钱」要用
`SUM(settlements.amount WHERE target_doc_id = 原单)`。

**② 要扣掉以前退过的钱。** 反例（成立）：原单实收 100 → 第一次退货退了 80 → 第二次又退货。
此时不能再按「原单收过 100」允许退 80，因为已经退出去 80 了。

判据：

```
累计实际退款（含本次） ≤ 原单真实收款
且 本次退款 ≤ 本次退货应退金额
```

**③ 顺带发现一个既有实现的问题**：`SettlementService.refundedAgainstCentsOf()`
用的是 `SELECT SUM(paid_amount) FROM documents WHERE ref_doc_id = ? AND doc_type IN ('sale_return', ...)`
—— **读的还是缓存字段**。它算「已退款」时同样应该走 `settlements`。

> 这一条会动到既有方法，影响详情页「还欠客户退款」的显示。改动要**单独一轮 + 对拍**
> （同一批数据下新旧算法结果必须一致，不一致就说明某处缓存与真相漂了 —— 那本身是另一个 bug）。

**落地位置**：`RuleEngine` 里退货/退款的前置校验（与「核销五道门槛」同一层），
不在 UI。UI 只负责「不显示不该显示的入口」。

### 测试（**先红后改**）

1. 送货单已签收、`paid_amount = 0` ⇒ 退货页**不出现**退款金额输入框
2. 同上，直接构造带退款的 `ReturnDraft` 提交 ⇒ `RuleRejected`，文案说清「这张单还没收到钱」
3. 已收 50、退货 80 ⇒ 退款上限 50，超出被拦

#### 🆕 裁定补充：不只送货 —— **所有可全额赊账的单据**都要这样

用户指出：能全额赊账的不只 `delivery`，`sale`（挂账销售）与 `purchase`（挂账采购）同样会
「一分钱没付就退货」。所以修法不能只加在送货分支上。

**做法**（用户建议）：先把送货这条流程做对，再**同构**到其它类型 —— 而不是一次改三处
（`Agents.md` 纪律 18：同构代码是漏改高发区，所以要有机械保证）。

判据：`ReturnPage` 与规则层的退款校验**只读「原单真实收款」这一个数**，不按 `docType` 分支写死
—— 这样新增单据类型时不会漏。测试要对 `sale` / `delivery` / `purchase` **各跑一遍同样的用例**。

### English

The refund card only checks whether an account is selected — not whether the original order ever received
money. A signed-but-unpaid delivery lets the user "refund" money that never arrived, creating a phantom
payment. Fix: hide the card when received = 0, cap at received amount, and enforce the same rule in
`RuleEngine` (UI can be bypassed). **This applies to every fully-credit doc type (`sale` / `delivery` /
`purchase`), not just delivery** — the check reads "real received amount" and must not branch on doc type.

## 七、优先级与批次

| 批次 | 内容 | 理由 | 预估 |
|---|---|---|---|
| **第一批** | ① WAL 复制 + ② 完整性判定 + ⑤ 退货欠款结论 + ⑥ 送货未收款不退款 | 都是**数据正确性**（①②⑥）或**明确的产品缺陷**（⑤）；改动集中在两个文件；都能先写红测试 | 半天 |
| **第二批** | ③ 备份并发（先测后改）+ ④ 抢救搬 isolate | ③ 要先定案，④ 是执行模型改造；用户明确要求分开提交 | 各半天 |

**①②⑥ 的共性**：都是「静默地少了一点东西」—— 少 20 张单、少 4 条流水、多一笔假退款。
这类 bug 用户不会报「坏了」，只会觉得「账怎么对不上」，所以优先级最高。

**建议明天开工顺序**：①（最快、实验已备）→ ⑥（有造错账风险）→ ②（要改判据，测试多）→ ⑤（纯文案）。
③④ 放到确认 ①②⑥ 之后再动。

### English

Batch 1: ① ② ⑤ ⑥ — all data-correctness or clear product defects, red-testable, two files. Batch 2:
③ (test first) and ④ (isolate refactor), separate commits. Start with ① (fastest, experiment ready),
then ⑥ (can create phantom payments), then ②, then ⑤.
