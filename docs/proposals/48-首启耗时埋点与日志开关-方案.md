# 48 · 首启耗时埋点与日志开关（附「最近 30 天 vs 全部」调查结论）

> **本文双语**：每节先中文，紧随 `English` 段。两段内容等价；若有出入，**以中文为准**。
>
> ✅ **已裁定「甲」并落地（2026-10-28）**：编译期 `--dart-define=SSZ_STARTUP_TRACE`，
> 6 个点位（T0/T1/T2/T3/T4 + 每次切页），**只存内存、首帧后异步落盘**。
> 双向验证：正式包里 `startup-trace` / `T0_main` **搜不到**；埋点包里**搜得到**。

---

## 零、结论速览

1. **「最近 30 天比全部慢」不成立** —— 是我测量时把 `?` 的实参顺序排反了。
   用命名参数重测：**全部 128 ms、最近 30 天 57.6 ms、最近 7 天 55.7 ms**，默认档本来就快。
2. **这一层已经没有可优化项**：默认视图的 SQL 合计 ≈142 ms，占真机切页 1.3 秒的 **11%**。
   继续在 SQL 上抠，收益上限就是那 142 ms。
3. **剩下的 ~1.1 秒必须靠应用侧埋点才能定案**，本文给出埋点设计与开关选型（推荐 **甲：编译期开关**）。

### English

1. **"Last 30 days is slower than All" is false** — I had passed the `?` arguments in the wrong order.
   Re-measured with named parameters: **All 128 ms, last 30 days 57.6 ms, last 7 days 55.7 ms** — the default range is already the faster one.
2. **Nothing left to optimize at this layer**: the default view's SQL totals ≈142 ms, i.e. **11%** of the 1.3 s median page switch on real hardware.
3. **The remaining ~1.1 s can only be attributed with in-app instrumentation.** This document specifies the trace points and the switch design (recommended: **Option A, compile-time flag**).

## 一、调查：我为什么会得出「30 天更慢」

我最初的测量 SQL 是拼出来的，`?` 的顺序是「`occurred_at` 下界 → 排序偏移 → LIMIT」，
但我传的实参是 `(偏移, 200, 下界)` —— **第一个 `?` 拿到了 28800000（偏移量）当时间下界，
LIMIT 拿到了一个 13 位的毫秒时间戳**。

后果：那条「30 天」的查询实际返回 **161,722 行**（不是 200），耗时 216 ms。
它测的根本不是我要测的东西。

**怎么发现的**：把「返回行数」也打出来，看到 161,722 这个数才意识到 LIMIT 没生效。
（教训：**性能测量必须同时断言返回行数** —— 只报时间，测错了也看不出来。）

### English

My first measurement passed the parameters in the wrong order: the `occurred_at` bound received the sort offset,
and `LIMIT` received a 13-digit millisecond timestamp. That "30-day" query actually returned **161,722 rows**
instead of 200, and cost 216 ms. I caught it only after printing the row count.
**Lesson: a timing benchmark must also assert the row count** — otherwise a wrong query looks like a slow one.

## 二、修正后的真实成本（478 MB / 26.2 万单，真实 DAO 实测）

| 段 | 全部 | 最近 30 天（默认） |
|---|---|---|
| 计数 `countDocuments(rootsOnly)` | 64 ms | 64 ms |
| 列表第一段（取 200 个 id） | **128 ms** | **57.6 ms** |
| 列表第二段（这 200 行的聚合） | 20 ms | 20 ms |
| **合计 / 次页面重建** | **212 ms** | **142 ms** |

对照真机数据（第二次，68 个自动事件）：切页中位 **1.34 秒**。
⇒ 默认视图的 SQL 只占 **11%**；即使用户在搜索（自动切「全部」），也只占 **16%**。

**结论：在这一层继续优化，最多再省 142 ms，动不了那 1.1 秒。**

### English

| Segment | All | Last 30 days (default) |
|---|---|---|
| `countDocuments(rootsOnly)` | 64 ms | 64 ms |
| List stage 1 (fetch 200 ids) | **128 ms** | **57.6 ms** |
| List stage 2 (aggregate those 200) | 20 ms | 20 ms |
| **Total per page rebuild** | **212 ms** | **142 ms** |

Against real-hardware data (median 1.34 s per page switch), the default view's SQL is **11%** of it.
**Conclusion: further SQL work can save at most 142 ms and cannot touch the remaining 1.1 s.**

## 三、埋点方案（要回答的问题）

首启 4 秒、切页 1.1 秒，到底花在哪？需要在**应用侧**打 6 个时间戳：

| # | 位置 | 回答什么 |
|---|---|---|
| T0 | `main()` 第一行 | 进程起来到 `main` 的延迟（引擎/加载器） |
| T1 | `bootstrap` 开始 | —— |
| T2 | `Db.open` 返回（含迁移） | 开库 + 迁移 |
| T3 | 主数据/快照预加载完成 | 启动期的查询 |
| T4 | 第一帧 `WidgetsBinding.instance.addPostFrameCallback` | **首帧构建 + 布局 + 光栅** |
| T5 | 每次切页：`appShellPage` 进入 / 首帧回调 | **切页的页面构建耗时** |

输出：一行一条 JSON，落到 `%LOCALAPPDATA%\神算子\startup-trace.jsonl`（**只追加、不覆盖**），
同时 `debugPrint` 一份方便当场看。

**只打时间戳，不采集任何业务数据**（不含单号、金额、客户名）。

### English

Six timestamps: `main()` entry, bootstrap start, `Db.open` return, preload done, first frame callback,
and per-page-switch enter/first-frame. Output is one JSON line per event to `startup-trace.jsonl`
(append-only) plus a `debugPrint`. **Only timestamps — no business data.**

## 四、开关选型（**请你选一个**）

| 案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **甲（推荐）** | 编译期常量：`const bool kStartupTrace = bool.fromEnvironment('SSZ_STARTUP_TRACE');` 打包时 `flutter build windows --release --dart-define=SSZ_STARTUP_TRACE=true` | **默认构建里代码被完全消除**（const 折叠 + tree shaking），运行时零成本、零分支；不用改配置、不用读环境变量 | 要专门打一个「带埋点的包」；和正式包**不是同一个二进制** |
| **乙** | 运行时读环境变量（`Platform.environment['SSZ_STARTUP_TRACE']`） | 同一个二进制，改环境变量就能开 | 读环境变量的代码**永远在包里**；Windows 上给 GUI 程序设环境变量对普通用户不友好（要改快捷方式或用命令行启动） |
| **丙** | 只在 `kDebugMode` 下埋点 | 绝不影响发布包 | **debug 构建的性能特性与 release 差一个量级**（JIT vs AOT），测出来的数不能用来解释真机 |

**推荐甲**，理由：要测的是**发布包**的启动耗时，而 debug 的数不能用（丙出局）；
乙虽然同一个二进制，但读环境变量这件事对「双击 exe 的用户」根本用不上，还永久留一段代码在包里。

甲的代价是「要打一个专门的包」，而这个包**除了多几行时间戳，与正式包逐字相同**（同一份源码、同一个 `--release`）。

### English

**Option A (recommended)**: a compile-time constant via `--dart-define`; in a normal build the code is
eliminated entirely (const folding + tree shaking), so production has zero runtime cost.
**Option B**: read an environment variable at runtime — same binary, but the code always ships, and
setting env vars for a GUI app on Windows is awkward for end users.
**Option C**: `kDebugMode` only — rejected, because debug (JIT) performance differs from release (AOT)
by an order of magnitude; its numbers cannot explain real-hardware behaviour.

## 五、验收（做完怎么算成功）

1. **默认包**：`flutter build windows --release` 后，产物里搜不到 `startup-trace` 字样
   （证明甲真的把它消除掉了）。
2. **埋点包**：`--dart-define=SSZ_STARTUP_TRACE=true` 打包，跑一次，`startup-trace.jsonl` 里
   6 个时间戳齐全，且 `T4 - T0` 与 `perf_monitor` 测到的首启时长对得上（±0.3 秒）。
3. 切页埋点：连点 5 个页面各两次，**第一次与第二次的差值**直接回答「是不是每次都要重建」。

### English

1. A normal release build must not contain the string `startup-trace` (proves elimination).
2. A traced build must produce all six timestamps, with `T4 - T0` matching `perf_monitor`'s cold-start
   measurement within ±0.3 s.
3. Switching to each page twice reveals whether the cost is paid on every visit.

## 六、明确不做的事

- **不做列表懒加载 / 页面保活**：已实测「20 行 vs 200 行」没有信号，没有证据指向它们。
  等埋点数据出来再谈。
- **不动 schema**：本次调查里试过给 `settlements` 加 `(receipt_doc_id, target_doc_id)` 复合索引，
  它确实消掉了每行的 `TEMP B-TREE FOR count(DISTINCT)`，但**耗时没变**（215.7 → 218.0 ms），
  所以不加。

### English

- **No lazy list / page keep-alive**: measured "20 rows vs 200 rows" shows no signal; no evidence.
- **No schema change**: a composite index on `settlements(receipt_doc_id, target_doc_id)` did remove the
  per-row temp B-tree but changed timing by nothing (215.7 → 218.0 ms), so it is not worth a migration.
