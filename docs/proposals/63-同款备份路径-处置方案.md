# 同款「checkpoint + 拷文件」路径 —— 处置方案（✅ 已落地 2026-11-12）

> grep 全仓 `wal_checkpoint`，发现**还有 3 处**同类写法。
> 上一轮口头汇报说「2 处」，本文件更正为 **3 处**（漏了手机导出那条），
> 并说明 `data_migrator` 为什么**不算**。

## 一、清点结果（4 处命中，1 处误判）

| # | 位置 | 用途 | 并发写者 | 失败语义 |
|---|---|---|---|---|
| 1 | `packages/shensuanzi_core/lib/src/db/database.dart:294` `_backupBeforeMigration` | 迁移前自动备份 `<db>.before-v{N}` | **无**（`Db.open` 内，服务未起、UI 未建） | **抛** ⇒ 打不开 |
| 2 | `packages/shensuanzi_app/lib/src/mirror_archive.dart:56` `snapshot` | 换主机时归档旧镜像 | **可能有**（pull 正在提交） | 返回 `null` ⇒ 配对继续 |
| 3 | `lib/src/app.dart:2005` `_exportBackupMobile` | 手机「导出本机数据」（分享给微信/文件） | **可能有**（同步引擎） | **吞掉异常继续**（只写日志） |
| 4 | `packages/shensuanzi_app/lib/src/data_migrator.dart:352` `_copyTree` | 换数据目录（整个目录搬家） | **无** | 中止并回滚 |

### 为什么第 4 处不算同款（有证据，不是估计）

- 搬家前的顺序是：`host.stop()`（等在途收尾）→ **`openingDb.close()`** → isolate 里搬
  （`lib/src/app.dart:1664-1688`）⇒ 库已关闭，**没有写者**。
- 它拷的是**整个目录**，`-wal` / `-shm` 一起过去 ⇒ 目标目录是一对自洽的
  db + wal，SQLite 打开时自行恢复。**只有 `_skipOnMove` 跳过运行态锁文件**
  （`data_migrator.dart:377`），那是必须跳的。
- 所以它既不需要 checkpoint，也不需要快照 —— **本次不动**。

## 二、共同的缺陷（3 处都有）

| 缺陷 | 后果 |
|---|---|
| `PRAGMA wal_checkpoint(TRUNCATE)` **返回值没人看** | 它返回 `(busy, log, checkpointed)`。有读者在时可能只做了一部分，主库仍缺最新事务，而代码照拷 |
| 直接写**最终文件名**（非 tmp + rename） | 中途失败（磁盘满 / 断电 / 被中断）留下**半份文件，名字却像退路** |
| 没有完整性校验 | 半份文件唯一能被发现的方式是「用户真去恢复时发现打不开」 |

但**三处的前提完全不同，不能一刀切**：

| | #1 迁移前备份 | #2 镜像归档 | #3 手机导出 |
|---|---|---|---|
| 数据量 | 全量库（实测 498 MB） | 镜像 9 表（几十 MB 级） | 镜像 + 空壳主库 |
| 库可能是**坏的**吗 | **可能**（正是要留退路） | 可能（正是要留证据） | 可能（正是要带走现场） |
| 是否需要**字节保真** | **要**——文件名里带 `before-v{N}`，`PRAGMA user_version` 必须是迁移前那个 | 不要，逻辑完整即可 | 不要 |
| 能否接受「库读不出 ⇒ 备份失败」 | **不能**（等于没有退路） | 能（尽力而为） | 能，但**必须告诉用户** |
| 失败代价 | 打不开软件 | 少一份归档，用户不知道 | **用户以为单带走了，其实没带** |

> 关键差异一句话：**`VACUUM INTO` 要求库可读。** 它的语义是「读出来重写一遍」，
> 遇到结构损坏直接失败。而迁移前备份存在的**唯一理由**就是「库可能有问题」——
> 用 VACUUM 等于把安全网绑在它要保护的对象上。

## 三、方案 A（第 1 处）：推荐**甲** —— 保留字节拷贝，补三件

### 甲：字节拷贝 + 三处加固（推荐）

```
1. 检查 checkpoint 返回值
     busy != 0 || log != checkpointed  ⇒  抛（沿用现有「备份失败就抛」策略）
     此时说明有别的连接在写；宁可这次打不开，也不在没有退路时改用户数据
2. 先写 <db>.before-v{N}.tmp，成功后 rename 成正式名
     同目录 rename 是原子的；失败时删 tmp，不留假退路
3. copySync 之后比对源与副本的 lengthSync()；不一致 ⇒ 删 tmp 并抛
```

### 乙：改用 `VACUUM INTO`（不推荐）

| 反对理由 | 说明 |
|---|---|
| 库损坏时备份不出来 | 正是最需要备份的时候失效 |
| 丢掉 `user_version` 之外的字节特征 | 文件名承诺「这是 v7 的原样」，VACUUM 出来的是「v7 内容的重新排版」。`user_version` 大概率保留，但**要额外验证**，而字节拷贝不用验 |
| 慢 | 读 498 MB + 写 498 MB ≈ 2–4 s，而它发生在**首帧之前**，用户看到的是「打不开」 |
| 无收益 | 这一处**没有并发写者**，checkpoint 本来就够 |

### 不做的（写明理由，免得日后被当成遗漏）

- **不加 `quick_check`**：实测 850 ms，且在启动路径上。这份备份的用途是
  **字节级还原**，不是「证明库是好的」—— 要校验也应在**恢复时**做，不是备份时。
- **不动 `foreignKeys` / 迁移链**：与本次缺陷无关。

## 四、方案 B（第 2 处镜像归档）：推荐**乙** —— 改用 `VACUUM INTO`

### 为什么这次反过来选 VACUUM

1. **确实有并发写者**：换主机发生在手机端，pull 可能正在提交事务 ——
   checkpoint 与复制之间的窗口是真实的，不是理论。
2. **不需要字节保真**：归档是冷证据，只要「打开能看到当时的 9 张表 + 队列」。
3. **不需要新开连接**：手头**就有** `Db`（`snapshot({required Db db, ...})`）。
   但**不能就地同步跑** —— 见下面的更正。
4. **失败语义天然兼容**：外层已经有 `try → return null`，配对照常继续。

> ### ⚠️ 更正（2026-11-12 用户审查）：这里**必须**进 isolate
>
> 初版写「不需要 isolate」，理由是「不需要跨 isolate 传连接」——**这个推论是错的**：
> 「要不要 isolate」取决于**这段工作会不会堵住 UI 线程**，与「要不要传连接」无关。
> `VACUUM INTO` 要读整个库再写一份，是**纯同步重活**；而 `snapshot()` 现在是**同步方法**，
> 调用点在手机换主机流程上。照初版做，就是换主机时界面长时间不动、
> 用户以为手机死机，镜像库越大越明显 —— 与本轮把大库工作移出 UI isolate 的原则相冲突。
>
> **改成**：`snapshot()` 改 `Future<Directory?>`，在独立 isolate 里**按路径**打开镜像
> （不传连接）再 `VACUUM INTO`；调用层显示「正在归档旧主机的数据…」的忙碌状态。

### 要一并处理的细节

| 项 | 处理 |
|---|---|
| 目标文件必须不存在 | 现有代码已 `target.existsSync() ⇒ deleteSync(recursive: true)` 再 `createSync`，✔ 满足 |
| 路径转义 | 单引号双写（SQL 字符串字面量规则）；反斜杠不是转义字符，统一正斜杠 |
| `-wal` / `-shm` 残留 | `VACUUM INTO` 直写新文件，目标侧不会产生，✔ 无需清理 |
| **归档失败要清整个目录** | 现在失败只留一个空目录（`target.createSync` 之后才做事）。VACUUM 中途失败 / 进程停在写 `manifest.json` 之前，都会留下**没有 manifest 的目录** ⇒ `list()` 会把它当成一条「未知主机 · 1970 年」的归档 |
| **`list()` 必须跳过缺 manifest 的目录** | ⚠️ **初版这里写错了**。我写「现有实现已跳过读不懂的目录，✔」——**不成立**。实际代码：`manifest.existsSync()` 为 false ⇒ `decoded = null` ⇒ `json = {}` ⇒ **仍然 `out.add(...)`**，于是显示「未知主机」「1970-01-01」。见下一节 |

### 更正：`list()` 现在**不会**跳过坏目录（附代码依据）

```dart
final Object? decoded = manifest.existsSync()
    ? jsonDecode(manifest.readAsStringSync())
    : null;
final Map<String, Object?> json = decoded is Map ? ... : const <String, Object?>{};
out.add(MirrorArchiveEntry(
  hostId: (json['host_id'] as String?) ?? '未知主机',
  archivedAt: DateTime.fromMillisecondsSinceEpoch(at is int ? at : 0),   // 0 ⇒ 1970
));
```

只有 `jsonDecode` **抛异常**时才会被 `catch` 跳过；「文件不存在」根本不抛。
⇒ 一个空的 / 半截的归档目录会像真归档一样出现在设置页的「历史主机数据」里，
用户点进去看到「未知主机 · 1970 年」，这正是本次改造后**更容易**制造出来的状态。

**改法**（三条一起做，否则只堵一半）：
1. `list()`：`manifest.json` 不存在、解析失败、或 `host_id` / `archived_at` 字段不合法 ⇒ **跳过该目录**（不 add）；
2. `snapshot()`：整个归档失败（任一环节）⇒ **删掉刚建的目标目录**，不留空壳；
3. 测试覆盖两种失败：**数据库快照失败**、**manifest 写入失败**。

## 五、方案 C（第 3 处手机导出）：推荐**乙 + 失败必须告知**

### 为什么这处最严重

```dart
void _checkpoint(Db db) {
  try { db.raw.execute('PRAGMA wal_checkpoint(TRUNCATE)'); }
  catch (error) { _log.write('导出前 checkpoint 失败（$error）—— 继续导出，可能缺最新几笔'); }
}
```

- **失败静默继续**，只有日志里一句话；
- 而这个功能的**唯一目的**就是「把还没推给电脑的单带走」（文件头注释原话：
  「真正会丢的只有一样东西：`sync_queue` 里还没推给主机的单」）；
- 缺的恰好是它存在的理由 ⇒ 用户以为带走了，换机后**单没了**；
- 而且 `_copyForExport` 是 `readAsBytes + writeAsBytes`，**无 tmp、无校验**。

### 做法

| 项 | 现在 | 改成 |
|---|---|---|
| 镜像 | checkpoint（吞异常）+ `readAsBytes` | **`VACUUM INTO`**（一致性快照） |
| 主库（空壳） | **完全没有 checkpoint**，直接拷 | 同样 `VACUUM INTO`（统一一条路） |
| 失败 | 日志 + 照常分享 | **返回一句人话拒绝分享**（「没能把数据整理出来，请重启软件后再试」），
不要给一个可能缺单的包 |
| 连接 | `sync.openMirror()` 拿到的 `Db` | **不要关** —— `openMirror()` 是**幂等且缓存**的（`mobile_sync_service.dart:141` 的 `_mirror`），那是服务持有的长连接，关掉会打断同步。`VACUUM INTO` 直接用这条连接即可 |

### ⚠️ 更正（2026-11-12 用户审查）：清单与库副本**必须同一个时间边界**

初版只讲了「库要一致」，**漏了那份人话清单**。现在的顺序是：

```
查 unsent 队列 → 生成「未同步单据.txt」 → 等复制库 → 交给分享面板
```

手机端同步队列**是活的**：查到 3 条之后，其中 1 条推送成功、或又新开了 1 单，
等数据库快照生成时库里的队列已经不是那 3 条了。于是分享包里会出现：

- `未同步单据.txt` 写 **3 条**，`shensuanzi_mirror.db` 里只有 **2 条**；
- 或反过来：库里有 4 条，清单只写 3 条。

对这份文件来说这是最糟的一类错误 —— **它的用途就是「照着清单核对哪些单没传上去」**，
清单和库对不上，用户就没法判断到底丢没丢。

**改成**（顺序是重点）：

1. 先 `VACUUM INTO` 出镜像快照；
2. **从这份快照里**读 `sync_queue`（新开只读连接读快照文件，不读活库）；
3. 用第 2 步的结果生成 `未同步单据.txt`；
4. 最后把三样一起交给分享面板。

⇒ 清单与库副本来自**同一个快照**，不可能再互相矛盾。

⚠️ 这一处的取舍要你点头：**「宁可导不出，也不给一个可能缺单的包」**
与现在「尽力导出」相反。我认为对「用户要拿它换机」的场景，前者才对。

## 六、要不要抽一个共用原语（推荐：要）

三处各写一遍，必然漂移（这次的 3 处就是漂移的产物）。建议在 core 加两个对称的原语，
**名字直说语义，让人不可能选错**：

| 原语 | 语句 | 用在 |
|---|---|---|
| `snapshotDatabaseTo({required String source, required String target})` | 只读打开源 → `VACUUM INTO` → **只读**校验 → 失败删半成品 | 镜像归档 · 手机导出 · 备份（**已在用同一套逻辑**） |
| `Db.snapshotTo(String target)` | 上面那个的薄包装（手头已有连接时省一次打开） | 只给「确定不会堵 UI」的路径用 |
| `Db.copyAsIs(String target, {required String forVersion})` | 检查 checkpoint 返回值 → `copySync` 到 `.tmp` → 比大小 → `rename` | **只有**迁移前备份（字节保真 + 可能损坏 + 无并发写者） |

- **主原语按「路径」而不是「连接」设计**，理由直接来自这次的教训：
  它要能在 isolate 里跑（备份已经是这样，镜像归档也要这样）。按连接设计的原语
  天生进不了 isolate，最后必然被就地同步调用 —— 那就是 §四 更正里说的那个坑。
- 校验一律**只读连接**跑 `PRAGMA quick_check`，**不要 `Db.open`**：
  `Db.open` 会跑迁移链并把库切成 WAL ⇒ 「检查一份旧版本副本」等于顺手升级它。
  这条纪律 `pubspec.yaml` 里 `sqlite3` 那条依赖注释已经写过（数据抢救体检同款），
  本轮的 `backupAndVerifyInIsolate` 已按它改（2026-11-12）。
- `copyAsIs` 内部用 `Database`（raw），因为 `_migrate` 阶段拿到的还不是 `Db`。
- `BackupService` 已经实现了这套逻辑（`backupAndVerifyInIsolate`），
  抽原语时可以**直接把那段搬进 core**，别重写一遍。
  ⚠️ **但不强求它改调 `Db.snapshotTo`**（审查意见）：它已经在独立 isolate 里工作，
  为了「复用同一个入口」而让它依赖主 isolate 的 `Db` 对象，是把好的结构换成一个统一的名字。
  **共用的是语义与可靠性约束，不一定是同一个底层入口。** 允许两处各有一份实现，
  但必须共用同一套**验收测试**（下面 6 条）。

### `snapshotTo` 必须满足的 6 条（审查指定，比抽象本身更重要）

| # | 要求 | 为什么 |
|---|---|---|
| 1 | 写到**目标临时文件**，成功后**原子替换** | 中断不留半份「看起来有效」的副本 |
| 2 | 校验用**只读连接** + `quick_check` | 校验不许改动被校验的文件 |
| 3 | **失败清理**：临时文件、`-wal` / `-shm` 一并删 | 提示说「已删除」就必须真删 |
| 4 | **目标路径不能覆盖源库**（同路径 / 同文件句柄要拒绝） | 否则等于把源库自己写坏 |
| 5 | **Windows 下目标已存在时的替换行为要明确** | `rename` 到已存在的文件在 Windows 上会失败（POSIX 是覆盖），必须先删或先改名 |
| 6 | 源库**只读打开**（`OpenMode.readOnly`） | 默认 `readWriteCreate` 会在源文件消失时凭空建空库 |

> 第 4 条尤其要注意：`VACUUM INTO` 的参数是**字符串路径**，如果目标与源相同，
> SQLite 会直接报错（还好），但如果只是**同一文件的不同写法**（正斜杠 / 短路径 / 大小写），
> 就不一定拦得住。实现时应在**拼 SQL 之前**用 `p.equals` 之类规范化后比较。

### 顺带更正一条：`wal_checkpoint` 的 `busy` 不只是「有写者」

初版只写了「busy ≠ 0 ⇒ 有别的连接在写」。更准确：**持有读事务的连接也会让 checkpoint
做不完整**（WAL 模式下读事务会钉住 read-mark）。所以判据必须是**返回值三列一起看**
（`busy` / `log` / `checkpointed`），不是「没抛异常就算成功」——
`wal_checkpoint` 在多数失败情形下**根本不抛**。

### 「复制期间没有新写入者」要靠**调用顺序 + 测试**固定，不只靠注释

审查指出：迁移前备份的前提是「此刻没有别的写者」，而这个前提现在是**隐含**的。
落地时必须：

1. **调用顺序写死**：`host.stop()` → `openingDb.close()` → 备份 → 迁移（与
   `data_migrator` 当前顺序一致，见 `app.dart:1664-1688`）；
2. **加一条测试**：在备份前后断言「没有第二条连接持有该库」（可用 `sqlite3` 尝试独占打开，
   失败即说明还有连接）；
3. 在 `_backupBeforeMigration` 的注释里**指向那个顺序**，而不是只写「此时没有写者」。

> 这一条不是形式主义：`Db.open` 内部是「打开 → configure → migrate」，备份发生在
> migrate 里；如果将来有人在 `open` 之前又开了一条连接（比如预热、体检），
> 这个前提就破了，而代码本身不会报错 —— 只会悄悄产出一份可能不一致的备份。

## 七、测试计划（先说清哪些**测不出**）

沿用 P1 的教训：这三处的核心缺陷**很难写出有区分度的单测**（旧实现在小数据量下
往往也能过）。所以只承诺**能真的红**的那几条：

| # | 用例 | 能红吗 |
|---|---|---|
| 1 | 第二条连接持读事务时，`copyAsIs` 的 checkpoint 返回 `busy=1` ⇒ **抛**（不是照拷） | ✅ 能（P1 那条测试已证明可构造） |
| 2 | 拷贝中途失败 ⇒ 目录里**没有** `.before-v{N}`（只有 `.tmp` 或什么都没有） | ✅ 能（用 `debugFailCopyFor` 同款注入钩子，`data_migrator` 已有先例） |
| 3 | `copyAsIs` 产物的 `PRAGMA user_version` == 迁移前版本 | ✅ 能 |
| 4 | `snapshotTo` 产物能被打开、行数与源库一致、无 `-wal`/`-shm` 残留 | ✅ 能（正向） |
| 5 | 镜像损坏时 `snapshot` 返回 `null` 且**配对仍继续** | ✅ 能 |
| 6 | 手机导出失败时**不**调用分享、返回人话 | ✅ 能（注入失败钩子） |
| 7 | ~~「旧实现会丢事务」~~ | ❌ **测不出**（与 P1 同因：小数据量下 checkpoint 通常仍会写回主库）。不要假装能测 |
| 8 | **数据库快照失败 ⇒ 归档目录整个被删**（不留空壳） | ✅ 能（源库换成垃圾文件即可） |

> 第 2 条要补一句这次的实测教训：`backupAndVerifyInIsolate` 的「失败删 `.tmp`」
> 我写了用例，但**撤掉修复后它仍然通过** —— 垃圾源库在创建目标**之前**就失败了，
> 没有半成品可删。真正会残留的是「VACUUM 写到一半被打断」（磁盘满 / 进程被杀），
> 单元测试造不出来。所以那条用例只锁**不变量**，注释里已写明，不冒充判别器。
> 第 2 条之所以说「能红」，靠的是**注入钩子**（模拟「已经写了一部分再抛」），
> 不是靠真实的磁盘满。
