# 换网卡后提示「地址变了」—— 处置方案（✅ 已落地 2026-11-17）

> 起因：`docs/reply_review.md` §九十·⑥ 登记的第一件欠账 ——
> **提案 62 第一刀收紧绑定之后，换 WiFi / 插拔网线会让服务仍听在旧网卡上**，
> 而界面显示「已开启」。用户当时裁定「提示先不加」，第二刀之后这条更值得提示了。
> 2026-11-17 用户选定「换网卡提示（62 收尾）」。

## 一、问题是什么（先取证）

| 项 | 事实 |
|---|---|
| 绑定形态 | 服务**只绑探测到的那一个地址**（`_startRaw` 的 `address: bind`，提案 62 第一刀） |
| 换 WiFi 后 | 新网卡拿到新 IP，**监听套接字仍挂在旧 IP 上**（重新 bind 不会自己发生） |
| 用户看到的 | 状态「已开启」；二维码里写着一个**已经不存在**的 IP；手机连不上 |
| 为什么会这样 | 第一刀之前绑 `0.0.0.0`，换网卡照样能连 —— 收紧绑定降低了攻击面，**代价就是这个** |
| 判定成本 | 重新枚举网卡只需一次 `LocalIp.detectAll()`（几百毫秒，纯读取） |

⇒ 这是**收紧绑定的必然代价**，必须由界面说出来（纪律 17：能力变了，说明也要跟着变）。

## 二、四个决策点（全部按推荐落地）

| # | 决策点 | 取 | 理由 |
|---|---|---|---|
| 64-① | **只提示 + 用户点一下换**，还是**自动重绑**？ | **只提示** | 自动重绑会让手机里存的 `ip:port` **静默失效**，而此刻用户可能正在推送单据；换绑还要停服务（断连一瞬间）。**改变用户可见的连接参数，必须是他自己的动作** |
| 64-② | 什么时候重新探测？ | **打开设置页 + 打开二维码 / 短码对话框之前** | 那两处正是「手机要扫码」的时刻。**不做定时轮询**：桌面常驻，几百毫秒的枚举换来的只是「早几十秒知道」，噪音大于收益 |
| 64-③ | 判据放哪？ | **控制器**（`HostServiceSnapshot.staleAddress`），UI 只取值 | 与 `bindFallback` 同款。两个零散字段之间**不许各算各的判据**（§CV 同源教训） |
| 64-④ | 提示放哪、说什么 | 设置页运行区块**一行红字** + 二维码对话框**码上方**同一句；文案由领域层给 | 二维码那屏是用户真正会看到「扫了连不上」的地方，只在设置页说等于让他先失败一次 |

### 明确**不做**的（写清理由，别日后当遗漏）

- **不自动重绑**（见 64-①）。
- **不定时轮询**（见 64-②）。换 WiFi 后如果用户一直停在设置页不动，提示不会自己冒出来 ——
  下次打开/刷新才会。**已知且接受**。
- **不自动改二维码里的地址**：码必须与绑定同源（`pairingPayload` 从 `_address` 取），
  在没重绑的情况下改码就是**撒谎**。
- **不在概览页加红卡**：那是「要不要打扰」的另一层设计，本轮不动。

## 三、语义边界（三条，写在 `recheckAddress` 的注释里）

| # | 边界 | 不守的后果 |
|---|---|---|
| 1 | **探不到 ≠ 地址失效**：探测抛异常 / 一块网卡都没有 ⇒ 不写 stale | 凭空吓唬人，比不提示更糟（与 `needsBackupAttention` 宁可少报同一立场） |
| 2 | **探测期间状态变了就作废**（停了 / 换过地址）⇒ 本次结果不写 | 拿旧状态算新结论，会报出一个不存在的失效 |
| 3 | **只判断、不重绑**，且**不抛** | 抛到界面 ⇒ 面板卡在「忙」 |

## 四、落地清单

| 层 | 文件 | 改动 |
|---|---|---|
| host | `service_controller.dart` | 新字段 `_staleAddress` / `HostServiceSnapshot.staleAddress` / `staleAddressHint`（文案单一出处）；新方法 `recheckAddress()`；启动 / 停服 / 换地址成功都会清掉 |
| ui | `host_service_section.dart` | `initState` 与 `_showQr` / `_showShortCode` 各重探一次；设置页一行红字（`host-service-address-stale`）；二维码对话框顶部同一句（`host-qr-address-stale`） |
| test | `test/service_controller_test.dart` | 新增「地址失效提示（提案 64）」**5 条** |
| test | `tool/selfcheck_service.dart` | 同款镜像 **14 条**（118 → 128 + 6 条既有… 见台账实测数字） |
| test | `test/host_service_section_test.dart` | 新增 1 条：面板红字 → 二维码对话框红字 → 换到新地址后撤掉 |

## 五、反向灵敏度（落定时两次验过）

| 破坏点 | 结果 |
|---|---|
| 把 `latest.any(...) ? null : bound` 的三元写反 | 「换了网卡 ⇒ 报失效」等 **3 条红** |
| 不写 `_addressOptions = latest` | 「候选表要换成新的」等 **2 条红** |

两次都已回滚并复绿。

## 六、仍然欠着的（与本案相关，但不在本轮范围）

- **端口不变**仍只是实测事实，不是契约（§九十·⑥ 第二件）。
- 提案 62 §四 的「地址列表标『推荐』」「虚拟网卡提示」未做。
- 换 WiFi 后**若用户始终不开设置页**，提示不会主动出现（本方案的已知取舍）。
