## 一、实测与代码核实（哪些是量的、哪些是读的）

### 1.1 量的

| 项目 | 环境 | 结果 |
|---|---|---|
| 拷贝 100 MB 文件（= `File.copySync` 同语义，同盘顺序拷贝） | 本机 SSD | **42 ms** |
| 拷贝 480 MB 文件 | 本机 SSD | **168 ms** |
| 写 1.2 MB CSV（2 万行，含 `fsync`） | 本机 SSD | **3–5 ms** |

**外推**：报告给的目标机是「2 核 / 4 GB / **机械硬盘**」。机械盘顺序写 80–120 MB/s
⇒ 100 MB ≈ **0.9–1.3 s**，加上杀毒软件实时扫描（报告实测 1.5–3 s）⇒ **主线程冻结 1–3 秒**。
这期间界面完全不动，用户会连点或强杀 —— 这正是本批要修的头号问题。

⚠️ **本机是 SSD，上面的 42 ms / 168 ms 不能代表目标机**。所以本批的验收必须包含
真机（见 §五），不能只靠桌面数字。

### 1.2 读代码核实的（不用跑就知道的固定成本）

**① 店名每敲一键 = 2 次同步写盘 + 一次全应用 setState**

```
settings_page.dart:350  onChanged: _updateShopName
  → _updateShopName()  → _apply()
      → configStore.save(newConfig)      ← 第 1 次写
      → widget.onChanged(newConfig)
          → app.dart:1881  _configStore.save(config)   ← 第 2 次写
          → setState(() => _config = config)           ← 整个 AppShell 重建
```

报告说「每键 3 次 IO（含 app_shell 每 build 读一次）」—— **写是 2 次（已核实）**，
第 3 次「读」我没核实到（`app_shell.dart` 那处可能已改），提案里只按 **2 次写** 计。

**② 每单保存末尾为一句 SnackBar 扫全表 `party_ledger`**

`sale_service` / `purchase_service` / `delivery_service` 保存成功后，为了在提示里说
「对方现在欠多少」，调用的是全表聚合（`partyBalances()`）再取其中一个 —— 明明只需要
`WHERE party_id = ?`。26 万行 `party_ledger` 上这一下是**每单固定成本**，与这单无关。

**③ 单据列表一次性建 200 行**

`documents_page` 是 `SingleChildScrollView` + `Column`，200 行 `Card` 全部一次性 build/layout。
200% 缩放下每行更高，可见行更少，但**构建量不变**。

> Measured on SSD: 100 MB copy = 42 ms (HDD extrapolates to 1–3 s), 1.2 MB CSV = 3–5 ms.
> Verified by reading: 2 sync writes per keystroke, a full `party_ledger` scan per save,
> 200 `Card`s built eagerly.

## 二、5a 主线程阻塞：备份与导出移出主线程

### 2.1 备份（必须保留「同步拷贝」语义）

`Agents.md` §4.5 明确「备份是**同步拷贝**」—— 语义是「拷出来的是一个**一致的**库文件」，
不是「不许用后台线程」。所以：

```dart
// 主线程：先 checkpoint，把 WAL 落进主库（这一步必须与写事务同一线程）
db.raw.execute('PRAGMA wal_checkpoint(TRUNCATE)');
// 再交给 isolate 纯文件拷贝（不需要数据库连接）
final bool ok = await Isolate.run(() => _copyFile(source.path, tmpPath));
```

**为什么必须在主线程 checkpoint**：`wal_checkpoint` 需要数据库连接，而
`sqlite3` 的 `Database` 对象**不能跨 isolate 传**（本仓 2026-10 已踩过
「object is unsendable: _AsyncCompleter」，见 `app.dart:1975` 的注释）。所以：
**连接相关的工作留在主线程（checkpoint 是毫秒级），纯文件 IO 进 isolate**。

**现成写法**：`app.dart:1981` 的 `_runMigrationInIsolate` 就是同一个模式（顶层函数 +
只捕获可发送的字段）。照抄即可，不需要发明新机制。

### 2.2 导出

`writeAsBytesSync` 改成在 isolate 里写。导出**不碰数据库**（`ExportTable` 已经是算好的
行），所以整个「拼 CSV 字节 + 写文件」都可以搬走，比备份更简单。

收益小（SSD 3–5 ms），但**低配 + 杀软扫描下是 50–300 ms 的主线程冻结**，而且
「导出中…」这个提示在阻塞期间**根本画不出来** —— 现在的反馈是假的。

### 2.3 ⚠️ 这条改动要动一条**写下来的规则**（代价在这）

`export.dart:15` 有一段明确注释：

> ⚠️ **文件读写一律用同步 API**（`writeAsBytesSync`）：与 `BackupService`
> 同一个理由 —— 数据量是几百 KB 级，而**异步 IO 在 widget 测试里不会自己完成**
> （`testWidgets` 的 fake async 不推真实事件循环），会让测试必须套 `runAsync`，
> 测出来的东西更远。

**规则的理由是「测试方便」，不是「必须同步」** —— 数据量那条判断现在也不成立了
（低配 + 杀软下 300 ms，用户能感知）。所以可以改，但要**如实承担代价**：

| 受影响 | 情况 | 处置 |
|---|---|---|
| `packages/shensuanzi_app/test/backup_test.dart`（34 条）、`export_test.dart`（19 条） | 全是普通 `test()`，本来就 `await` 结果 | **不用改**（已核实：`testWidgets` 计数为 0） |
| `test/startup_test.dart` 场景 6/7/8 | `testWidgets` 里跑**真实备份**（启动时 `unawaited(_autoBackup())`，断言备份文件/目录状态） | **必须改**：套 `tester.runAsync`，或给 `App` 注入可替换的 `BackupService`（后者更干净但改动面更大） |
| 各页导出按钮的 widget 测试 | 传的是假 `ExportSink`，不走真实写盘 | 不用改 |

⚠️ **这是本批唯一「会连带改测试」的项**，也是我把 ① 标成「中风险」的原因。
若你不希望动 `startup_test`，回 `①丙`（只改设置页 + 保存点查 + 反馈，备份导出留到有真机数字之后）。

### 2.4 不改的

- **不改成流式/分块备份**：备份文件必须是单文件快照，分块只会引入「半份备份」的风险。
- **不动 `autoBackup` 的触发时机**（启动时 `unawaited`）—— 移出主线程之后它不再阻塞首屏。

> Backup: checkpoint on the main thread (needs the connection), then copy the file inside
> `Isolate.run` — the existing `_runMigrationInIsolate` pattern. Export: move the whole
> byte-building + write into the isolate.

## 三、5b 每键固定成本：设置页与保存提示

### 3.1 设置页店名：防抖 300 ms + 失焦立即落盘

```dart
// 现状：每键 → save + save + 全应用 setState
// 改为：每键只更新 controller 与「超长提示」；300 ms 无输入或失焦时才 _apply
```

**「修改立即生效」的承诺不破**：用户看到的店名在概览页，300 ms 不可感知；
失焦时**立即**落盘，所以「改完就去点别处」不会丢。缩放档位是**离散选择**（点一下），
保持立即生效不变。

### 3.2 保存末尾的 `party_ledger` 全表扫 → 点查

三个 service 里的「对方现在欠多少」改成 `partyBalanceOf(partyId)`（`WHERE party_id = ?`，
走 `idx_party_covering` 前缀）。**结果一模一样**，只是不再扫全表。

⚠️ 这一条要**逐个核对**三个 service 的文案口径：如果提示里说的是「全部往来方合计」
就不能点查 —— 先读代码确认语义再改（纪律 17）。

> Debounce settings writes (300 ms + blur), and replace the per-save full scan with a
> point query — after verifying the message actually means "this party".

## 四、5c 三处反馈（「慢的时候要说话」）

| # | 现状 | 改法 |
|---|---|---|
| 1 | 备份无进度（启动时静默跑） | 备份开始时置状态；**超过 300 ms** 才在概览页显示「正在备份…」，完成后显示「上次备份：今天 09:05」 |
| 2 | 导出成功文案只活 6 秒 | 在页面上留一行小字「上次导出：单据.csv（今天 09:12）」，SnackBar 保留 |
| 3 | 保存失败只标红不定位 | 保存期间 `enabled: !_saving` 锁住输入（低配保存慢，用户更容易在等待中改输入） |

> Three feedback points: backup progress after 300 ms, persistent "last export" line,
> lock inputs while saving.

## 七、不做的事

- **不改 `ListView` 结构**（除非真机 > 300 ms，见 §六）。

> No list rewrite unless measured, no opening-stock controller rewrite, no font shrinking,

## 八、要你裁的四件

| # | 决策点 | 甲（推荐） | 乙 |

| ① | 备份与导出移出主线程 | **都移**（备份 checkpoint 留主线程 + isolate 拷文件；导出整体进 isolate）。代价：`startup_test` 场景 6/7/8 要套 `runAsync` 或注入假 `BackupService` | 只移备份（导出 SSD 上只有 3–5 ms，但低配+杀软会到 300 ms）—— 测试代价**一样**，因为问题出在备份那侧 |
