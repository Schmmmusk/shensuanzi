## 〇、诉求原文（拆成 6 条可验收行为）

> 「3 个开单页面的商品明细卡片中，输入商品名称的输入框能否添加自动补全功能？
> 具体实现：用户输入部分名称，输入框弹出下拉框给出完全匹配或相近的商品内容（具体内容视所处页面而定），
> 按上下方向键选择候选项，按回车键一键填好选中内容。若相关内容输入框已有内容则提醒用户是否要覆盖。
> 若用户输入的内容没有匹配项，则询问用户是否立刻创建新商品，此时选是，则可将之前的无缝建档直接拿过来用。」

| # | 行为 | 验收方式 |
|---|---|---|
| 1 | 三个开单页（销售 / 采购 / 送货）的商品名输入框都能补全 | 三页各 1 条 widget 测试 |
| 2 | 输入部分名称 ⇒ 下拉给出**完全匹配或相近**的商品 | 匹配排序测试 |
| 3 | ↑ / ↓ 选候选项，**回车**填入 | 键盘导航测试（不是鼠标点击） |
| 4 | 候选内容**随页面而变**（采购看进价、销售/送货看售价与库存） | 三页副标题断言 |
| 5 | 输入框**已有内容**时选候选 ⇒ 先问要不要覆盖 | 确认框测试 |
| 6 | 无匹配 ⇒ 问「要不要立刻建新商品」，选是 ⇒ 复用**无缝建档** | 建档流程测试 |

### English

Six acceptance behaviours: completion on all three order pages; fuzzy + exact matching; arrow-key
selection with Enter to fill; per-page candidate detail (cost on purchase, price/stock on sale and
delivery); overwrite confirmation when the field already has content; and "no match → create now"
reusing the existing seamless product creation flow.

## 二、方案：一个共用组件，三页各接一次

新建 `lib/src/ui/product_name_autocomplete.dart`：

```dart
ProductNameAutocomplete(
  controller: row.name,          // 复用行卡现有的 controller（不新建）
  focusNode: row.nameFocus,
  enabled: enabled,
  products: widget.productService.list(),
  pageKind: ProductPageKind.purchase,   // 决定副标题显示进价 / 售价 / 库存
  currentProduct: row.product,          // 用于"覆盖确认"
  onPicked: (Product p) { row.bind(p); onChanged(); },
  onCreateRequested: (String typedName) async { … },  // 见 §四·B
  errorText: errors?[SaleLineField.product],
)
```

内部用 `RawAutocomplete<Product>`：

| 部件 | 做法 |
|---|---|
| `optionsBuilder` | 见 §三 的匹配与排序；空输入 ⇒ 返回空（不弹） |
| `optionsViewBuilder` | 一张 `Material` 卡片 + 最多 8 行；高亮行用主题色底；每行两行文字（名称 + 副标题） |
| `fieldViewBuilder` | 直接返回现有 `TextField`（保留 `suffixIcon` 列表按钮、`errorText`、`textInputAction`） |
| `onSelected` | 绑定商品 + 重算 + 触发覆盖确认（§四·A） |
| 键盘 | `RawAutocomplete` 内置；**但要补一条测试**：overlay 打开时回车=选中、overlay 关闭时回车=跳下一格（保留现有 `onSubmitted` 行为） |

**三页各自只改一行**：把 `TextField(...)` 换成 `ProductNameAutocomplete(...)`，
**不复制三份匹配逻辑**（纪律 18：全仓同款模式必须一处定义）。

### English

One shared widget, three call sites. `RawAutocomplete` supplies the overlay and the keyboard intents;
the field view keeps the existing `TextField` (suffix picker icon, error text, `textInputAction`).
No matching logic is duplicated across pages.

## 三、匹配与排序（"完全匹配或相近"的具体定义）

| 优先级 | 规则 | 例（输入 `大米`） |
|---|---|---|
| 1 | **名称完全相同**（`TRIM` + 忽略大小写） | `大米` |
| 2 | **名称前缀**匹配 | `大米（东北）` |
| 3 | **名称包含** | `优质大米` |
| 4 | **编码 / 条码**命中 | 输入 `P0002` 命中 `测试大米` |
| 5 | 同分按 `code` 升序（**稳定排序**，避免每次按键顺序抖动） | — |

- 上限 **8 条**；超出按上面顺序截断。
- **停用商品**默认不出现；但若输入的是它的**完整名称**，仍然给出并标「（已停用）」——
  与 `findByExactName`（不过滤 `is_active`）保持一致，否则用户会"建出一个重名商品"。
- **空输入不弹**（避免一进页面就糊一屏候选）。

**候选副标题（"内容视所处页面而定"）**：

| 页面 | 副标题 |
|---|---|
| 采购入库 | `P0002 · 进价 ¥18.00` |
| 店内销售 / 送货 | `P0002 · 售价 ¥25.00 · 可售 2 袋` |

### English

Ranking: exact name → name prefix → name contains → code/barcode hit, ties broken by `code` for
stable ordering, capped at 8. Inactive products are hidden unless the typed text equals their full
name (mirrors `findByExactName`, which ignores `is_active`). Empty input shows nothing. The subtitle
is page-specific: cost on purchase, price + available stock on sale/delivery.

## 四、三个交互细节

### A · 覆盖确认（诉求 5）

| 情形 | 行为 |
|---|---|
| 输入框为空 | 直接填入并绑定，**不问** |
| 输入框内容与候选**等价**（名称或编码相同） | 直接绑定，**不问** |
| 其他 | 弹「换掉这一行的商品？」——「原来是「X」，要换成「Y」吗？」[取消 / 换掉] |

**✅ 裁定：乙（前缀豁免）**（2026-10-25）—— 用户原话：「用户输入『大』想选『大米』，
如果每次都弹『要覆盖吗』会把人烦死。只有当输入框里的词**完全不是候选词的前缀**
（比如本来是『可口可乐』，非要换成『大米』）才弹窗。」

| 选项 | 规则 | 状态 |
|---|---|---|
| 甲（严格） | 只要输入框非空且与候选不同就问 | ❌ 未采纳 |
| **乙（前缀豁免）** | 仅当输入框内容**不是候选的前缀**时才问（前缀 = 用户正在搜索，不问） | ✅ **采用** |

### B · 无匹配 ⇒ 立刻建档（诉求 6）

**触发**：`Enter` 且无候选，或输入框**失焦**，且文本非空、无同名商品、且**尚未弹过**（防重复）。

**对话框**：「没找到「**X**」，现在建一个吗？」[先不建 / 建档]

- 选「建档」⇒ `showProductFormDialog(initialName: X)`（**直接复用无缝建档**）→
  保存成功后该行绑定新商品、单价按页面预填（采购=进价 / 销售·送货=售价）。
- 选「先不建」⇒ 行保持"只有名字"的状态（与现在手打后不建档的语义一致），保存时仍由
  `missing_product_dialog` 兜底 —— **两条路互不替代**。

⚠️ **能力门**：`sink.canCreateProducts == false` 时（如某些装配下的 `QueueSink`），
**不给「建档」按钮**，改成「先去商品页建一个，再回来开单」+ 一个跳转按钮 ——
否则就是"点了建档，单子却传不到电脑"的假承诺（手机端历史教训）。

### C · 与保存时兜底的关系

补全只解决"录入时选得准"，**不改变保存语义**：
- 选中候选 ⇒ 绑定 `productId` ⇒ 保存直接用 id；
- 只有名字没绑定 ⇒ 保存时按 `findByExactName` 重新匹配（现有逻辑，含自动绑定）；
- 仍匹配不到 ⇒ `missing_product_dialog`（现有逻辑，一次列全）。

### English

A: overwrite confirmation — silent when empty or equivalent; otherwise ask. **Decision D1′**: strict
(always ask) vs prefix-exempt (recommended, since typing-to-search would otherwise prompt constantly).
B: no match → offer to create, reusing `showProductFormDialog(initialName:)`; when the sink cannot
create products, offer a jump instead of a false promise. C: completion does not change save
semantics — the existing exact-match and missing-product fallbacks stay.

## 五、手机端要不要一起开（决策点 D2′）

现状：手机行卡是「点此选商品」单元格（因为 `QueueSink.canCreateProducts = false`），
但手机**能**建档（选择器里的「新建商品」走 `QueueMasterSink`）。

| 选项 | 做法 | 代价 | 状态 |
|---|---|---|---|
| **甲** | **只做桌面**；手机保持「点此选商品」，但给**选择器加一个搜索框**（手机没有方向键，补全的价值主要在桌面） | 小 | ✅ **采用** |
| 乙 | 手机也开手打 + 补全 | 需要先把 `QueueSink.canCreateProducts` 接到 `QueueMasterSink`（建档要能进队列），否则"无匹配→建档"在手机上是假承诺；工作量与风险都大 | ❌ 留待下一轮 |

**裁定（2026-10-25）**：甲。用户原话：「手机端目前是『点此选商品』的单元格，如果要改成手打+补全，
还得把 `QueueSink` 改造支持无缝建档，风险太大。先给手机选择器加个搜索框，足以解决痛点。」

### English

The phone's row card is a picker cell, not a text field. Recommendation: **desktop only** for now,
plus a search box inside the phone's product picker; enabling typed names on the phone requires
wiring `QueueSink` to `QueueMasterSink` first, otherwise "create product" would be a false promise.

## 六、风险与对策

| 风险 | 对策 |
|---|---|
| **中文输入法组合期**（拼音未上屏）每次 `onChanged` 都重建候选，会打断 IME | `if (value.composing.isValid) return;` —— 组合期不更新候选 |
| **回车冲突**：有候选时应"选中"，无候选时应"跳下一格" | overlay 打开时由 `RawAutocomplete` 的 Actions 吃掉回车；补一条测试钉住两种情形 |
| 商品量大时每次按键全表过滤 | 几百条线性过滤 < 1 ms（实测再定）；**先不做索引**，超过 2000 条再谈 |
| 覆盖确认打断连续录入 | 决策 D1′ 的乙口径 |
| 三页各写一份导致漂移 | 组件一处定义 + 三页各 1 条测试；`grep` 断言三页都只有一次 `ProductNameAutocomplete(` |
| 补全与 `suffixIcon` 列表按钮抢焦点 | 选中候选后 `FocusScope.of(context).nextFocus()`，保持现在的录入节奏 |

### English

Watch the IME composing state (do not rebuild candidates mid-composition), the Enter conflict
(select when the overlay is open, advance focus when not), and per-page drift (one widget, three
call sites, a grep assertion).
