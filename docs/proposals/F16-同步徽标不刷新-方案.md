# F16 同步徽标不刷新 —— 方案

> ✅ **已裁定「乙+丙」并落地（2026-10-27）。** 取证定案见 §四点五，落地记录见 §四点六。
> **真因：一次推送丢了响应 ⇒ 队列条目停在 `pending`；而**没有任何自动重试**，
> 只有「回到开单页 / 再点立即同步 / 再开一单 / 应用恢复」才重试 ⇒ 徽标长时间（实测 **≥2 分 40 秒**）
> 停在「待同步 N 条」，而单据其实**早就到了电脑**。徽标说的是真话。

>
> **来源**：0.6.5 复跑（F16，P3）+ 2026-10-26 真机**两次复现**。

## 一、现象（真机两次）

| 时间 | 操作 | 结果 |
|---|---|---|
| 2026-10-25 | 手机离线开单 → 连 Wi-Fi → 点「立即同步」 | 「上次同步 20:24」已更新、电脑也收到了单，但**徽标仍写「待同步 1 条」**；切到别的标签再回来才变「已同步」 |

## 二、原假设（**已被反证，留档**）：被 push 的整屏页把 `shell` 钉在了 push 那一刻

### 2.1 徽标的刷新机制

`mobile_shell.dart` 的三态条靠**实例身份**判断要不要重查：

```dart
// _SyncStatusBarState
void didUpdateWidget(_SyncStatusBar oldWidget) {
  super.didUpdateWidget(oldWidget);
  if (!identical(oldWidget.version, widget.version)) _load();   // ← 只有换了实例才重查
}
```

`version` 传的是 `widget.shell`（`AppShell` 实例，由 `app.dart` 每次 `build` **新建**）。
⇒ 在 **tab 内**（徽标由 `_MobileShellState.build` 直接构造）这条链路是通的：
`app.setState` → 新 `AppShell` → `didUpdateWidget` 看到新实例 → `_load()` → 徽标更新。

### 2.2 断在哪：`_openFull` 推的整屏页

```dart
// mobile_shell.dart:65
void _openFull(NavDestination destination) {
  Navigator.of(context).push(MaterialPageRoute<void>(
    builder: (BuildContext context) => Scaffold(
      appBar: AppBar(title: Text(destination.label)),
      body: Column(children: <Widget>[
        _SyncStatusBar(sync: widget.shell.mobileSync, version: widget.shell),  // ← 闭包捕获
        ...
```

`builder` 里的 `widget.shell` 是**push 那一刻**的实例。而 Flutter 的
`_ModalScopeState` 会把路由内容**缓存在 `_page` 字段**里 ——
祖先 `setState` 只会重建 `Overlay` 的壳，**不会重新执行这个 `builder`**
（只有路由自己 `changedInternalState` 时才清 `_page`）。

⇒ `_SyncStatusBar` 一直拿着**旧的** `version`：
`identical(old, new)` 恒为 `true` ⇒ `_load()` **一次都不会跑** ⇒ 徽标永远是 push 时的快照。
返回上一页再进来（重新 push）才会拿到新实例 —— 这正是"切走再回来才刷新"。

### 2.3 当时以为的影响面（**随假设一起作废**）

`_openFull` 用在：**设置**、**帮助**、以及**概览页的快捷入口推出来的开单页**。
最后这条要紧 —— 代码注释自己写着：

> 「三态条也挂在整屏页上 —— 用户是在**这里**开单的（裁定 ②：
> 保存后三态条要**立即**可见地更新），只在 tab 底下挂会看不见。」

⇒ 从概览的「销售开单」按钮进去开单、保存后，**徽标不会变成「待同步 N 条」**，
直到用户退出去再进来。这不是配色问题，是**裁定 ② 在这条路径上没兑现**。

### 2.4 为什么这个判断**错了**（2026-10-26 22:00 反证）

按提案自己定的规矩，先写 T1 让它红。**T1 绿了**：

```
DEBUG 已同步(onstage)=1  已同步(all)=2  待同步(onstage)=0  待同步(all)=0
```

`skipOffstage: false` 数到**两个**「已同步」（tab 一个、整屏页一个），「待同步」零个
⇒ 整屏页上的徽标**当场**就刷新了。护栏测试留下：`test/mobile_shell_test.dart`
「F16 反证：整屏页（设置）上的徽标会跟着壳刷新」。

错在哪：

- 闭包捕获的是 **`_MobileShellState` 这个 `State` 对象**，不是 `widget.shell` 的**值**；
- 而 `widget` 是 `State` 上的**可变字段**，`didUpdateWidget` 之后已指向新的 `MobileShell`
  ⇒ `widget.shell` 读到的是**当前**实例；
- `_ModalScopeState._page` 缓存确实存在（`routes.dart:1085`），但换根/换主题会触发
  `didChangeDependencies`（`routes.dart:1116`）把它清掉，路由随之重建。

⇒ 真机那条现象的根因**仍未找到**。这正是「先红」纪律的价值：它拦住了一次
"照着错根因写一堆代码"。

### English

The "stale instance" theory is **refuted**: the reproduction test came out green — both
badges (tab and pushed page) updated immediately. The closure captures the `State`, not
the value of `widget.shell`, and `widget` is a mutable field on `State`. The three options
(甲/乙/丙) are therefore void.

### English

excluded by the reproduction test. H1 — "that particular tap did not actually push

## 四、取证（改判据：**不用人眼截图**，用主机侧时间戳）

### 4.1 为什么不能靠截图

用户 2026-10-26 22:14 的原话：

> 「这件事手动完成难度很高。在网络连接稳定的情况下，这件事几乎不可能完成：
> 点击后，按钮应会立刻变为"已同步"，切换时长远短于人类极限反应时长；
> 即使使用快捷截屏手势（三指下滑）也很难做到。只有在网络连接不太稳定的情况下才有可能。」

**这个反驳成立** —— 网络正常时徽标是毫秒级翻的，人眼/手势根本追不上。
所以判据必须换成**带秒级时间戳的客观记录**。

### 4.2 更好的判据：主机库的 `documents.created_at`

`sync_server.dart:597` 写着「`created_at` / `updated_at` / `sync_version` **由主机写**」
（纪律 10 + §七），第 609 行 `'created_at': now` 用的是**主机收到那一刻的时钟**。
而 `documentCreatePayload()` 明确把 `created_at` / `updated_at` 从 payload 里剔掉
（host-only 列）。

⇒ **主机 `documents.created_at` = 这张单真正被主机收下的秒级时刻**，
手机上不需要任何操作、不需要截图。

### 4.3 已经拿到的第一组数据（2026-10-26）

| 单号 | 主机收到（`created_at`） | 当时我看到的 |
|---|---|---|
| `XS20261026-001` + `SK…-001` | **20:24:53** | 点完「立即同步」后 8 秒截图（约 20:24:44-50）：**待同步 1 条** |
| `XS20261026-002` + `SK…-002` | 20:50:14 | 切回库存页已是「已同步」 |

**初步读数**：截图时刻（≤20:24:50）**早于**主机收到时刻（20:24:53）
⇒ 那一刻队列里**确实还有**这条单，**徽标说的是真话** ⇒ 支持 **H1**，不支持"UI 不刷新"。

⚠️ 但这组数据**不足以下结论**：截图与主机收到只差约 3-9 秒，
而 `adb screencap` 本身就要 3-5 秒 —— 时间分辨率不够。**必须再做一次秒级复现。**

### 4.4 秒级复现步骤（一次就够）

1. 手机上开一单（保持离线）→ 连 Wi-Fi → **记下点「立即同步」的秒级时刻**
   （用电脑看时钟即可，点之前看一眼）；
2. 等 10 秒，**不要切标签**，看徽标当时写什么（一条静态观察，不需要抢拍）；
3. 到电脑上查：

```sql
SELECT doc_no, datetime(created_at/1000, 'unixepoch') FROM documents ORDER BY created_at DESC LIMIT 3;
```

**判据**：

| 主机收到时刻 vs 你点同步的时刻 | 徽标当时写什么 | 结论 |
|---|---|---|
| 晚 5 秒以上 | 待同步 | **H1** —— 徽标是对的，问题在"那次推送为什么慢/失败"，与 UI 无关 ⇒ **F16 关闭** |
| 早于你看到「待同步」的时刻 | 待同步 | **H2** —— 真 bug（`counts()` 时序），再上临时日志 |
| 同一秒内 | 已同步 | **H3** —— 正常，F16 关闭 |

**仍然不建议先改代码。** 但这次不需要"抢拍"，只要**一条静态观察 + 一条 SQL**。

### English

Manual screenshots cannot work: with a healthy network the badge flips within
milliseconds. Use the host instead — `documents.created_at` is written by the host at
apply time (`sync_server.dart:597/609`), so it gives a second-precision record of when the
document actually arrived, with no interaction on the phone. The first data point
(`XS20261026-001` arrived 20:24:53, screenshot ≈20:24:44-50 showed "pending 1") supports H1,
but the resolution is too coarse to conclude; one more run with second-precision timing
settles it.

## 四点五、真机取证定案（2026-10-27）

### 4.5.1 实验（可复现）

1. 手机断网 → 开一单（可乐 ×1，全款）⇒ 徽标「待同步 1 条」；
2. **先等网络彻底稳定**（WiFi 开 20s，`ping 电脑` 通）再进设置页；
3. 点「立即同步」；
4. 记录三样东西：**主机 `documents.created_at`**（主机收到那一刻，秒级）·
   **「上次同步」时间**（= `syncNow` 真正完成的时刻）· **徽标**（截图，不用抢拍）。

### 4.5.2 实测时间线（2026-10-27）

| 时刻 | 事件 | 证据 |
|---|---|---|
| **11:39:21** | 主机收到 `XS20261027-002` + `SK20261027-002` | 主机库 `created_at` |
| **11:39** | `syncNow` **完成**（不是卡住） | 设置页「上次同步：2026-10-27 11:39」 |
| 11:39:22 → **11:42:05** | 徽标一直是「**待同步 1 条**」（≥ **2 分 40 秒**） | 11:41:02 / 11:41:41 / 11:42:05 三张截图 |
| **11:42:32** | **回到「开单」页** ⇒ 徽标变「已同步」 | 截图 |

前一轮（11:30:40）现象相同，且「切到概览再切回我的」**不会**恢复 —— 只有回**开单**页才恢复。

### 4.5.3 结论：**徽标没撒谎，是队列里真的还有那条**

- `counts()` 只统计 `status != 'sent'`；徽标显示「待同步 1 条」⇒ 那行**仍是 `pending`**。
- `syncNow` 完成（`上次同步` 已更新）⇒ 不是"卡在同步里"，也不是"UI 没重建"
  （`build()` → `_buildHome()` 每次都新建 `AppShell`，`didUpdateWidget` 必然重查 —— 已核对代码）。
- 主机在 11:39:21 就落库了，客户端却没把它记为成功
  ⇒ **只能是这次推送的响应丢了 / 超时**（主机已提交，客户端没收到回执）。
  这是**推断**，直接证据（客户端日志）在 release 包上取不到 —— 如实标注。

### 4.5.4 真正的缺口：**没有自动重试**

- 全仓 `Timer.periodic` = **0**；`autoPush()` 的调用点只有四处：
  提交单据后 · 提交主数据后 · 回**开单页**时（开单页那句提示自己写着「回到这个界面时再自动试一次」）·
  应用恢复（`app.dart:364`）。
- ⇒ 一旦某次推送丢了响应，那行 `pending` **只能等用户碰巧触发上面某个动作**才会重试。
  用户看到的就是「一直待同步，切走再回来才变」—— 与 F16 原报告逐字吻合，
  但**根因不是刷新，是重试**。

### 4.5.5 修法（三选一，**待裁定，本轮不动代码**）

| # | 做法 | 代价 / 风险 |
|---|---|---|
| **甲** | **后台退避重试**：前台时按 `nextRetryAt` 起一个轻量定时器（如 30s 一次），到点自动 `autoPush` | 要小心「打字每键查全库」那类性能坑；只在有 pending 时起，空了就停 |
| **乙** | **推送后对账**：`pushAll` 结束后若 `remaining > 0`，拉一次 pull，并把「主机已有、本地仍 `pending`」的条目**直接标记 `sent`**（幂等键就是实体 `id`） | 改动小、直击要害；但要在 `clearConfirmed` 旁边加一条「按实体 id 匹配 pending 行」的逻辑，得想清"主机返回的是否够全" |
| **丙** | 只做 UI 兜底：三态条点开时给「重试」按钮（现在点开是解释文案） | 最省事，但用户仍要自己发现"卡住了" |

**推荐 乙 + 丙**：乙治病（响应丢了也能自愈），丙兜底（万一还有别的路走不到）。
**甲** 单独用不够 —— 它只是让重试更快发生，不解决"主机已有但本地 pending"的对账问题。

### 4.5.6 附带更正

- 2026-10-26 那轮「原根因假设被反证」**是对的**（不是 UI 实例过期）。
- 本轮同时确认：**`build()` → `_buildHome()` 每次重建 `AppShell`**，所以
  「`identical(version)` 判断失效」这条路可以彻底排除。

## 四点六、落地记录（2026-10-27，裁定「乙+丙」）

### 4.6.1 乙：推送后对账

| # | 改动 | 位置 |
|---|---|---|
| 1 | `SyncQueueDao.due(now, {limit, **ignoreBackoff**})` —— 不看 `next_retry_at`，把所有 `pending` 拿出来 | `sync_dao.dart` |
| 2 | `SyncClient.push({maxEntries, **ignoreBackoff**})` 透传 | `sync_client.dart` |
| 3 | `SyncClient.reconcilePending()` = `push(ignoreBackoff: true)` | 同上 |
| 4 | `syncNow` 在 `pushAll` 之后：**若 `remaining > 0` 就补问一次**（不循环） | `mobile_sync_service.dart` |

**为什么是「再推一次」而不是新加一个「主机你有没有这些 id」的接口**（用户提的坑 ① 的落地）：

1. 推送本来就幂等（`同步幂等键 = 实体 id`，已存在回 `already_exists`）⇒ 再推一次**就是**
   在问「你有这笔吗」，答案还是机读的；
2. 新接口是**协议变更**：旧电脑 + 新手机 = 404 ⇒ 对账直接失效，而「电脑上跑的是上一版」
   在真实用户那里是常态；
3. **不拉全量**：只碰 `pending` 那几条，**完全不调 `pull`**。

**不循环**：弱网下循环重试会把界面拖住（用户否决「甲」的理由之一就是"一直转圈"）。

### 4.6.2 丙：三态条点开后的「立即重试」

- `mobile_shell.dart` 的队列面板，在**有待同步**时给一个 `FilledButton`
  （`Key('sync-retry-now')`）→ `MobileSyncService.reconcilePending()` → 关面板 →
  **`_load()` 当场刷徽标** → `showNotice` 说结果（D4 甲：统一入口、先清队列）。
- `MobileSyncService.reconcilePending()` 是**只推不拉**的轻量版：不比对 schema、
  不弹遮罩 —— 用户点它的诉求是「再试一下」，不是再跑一遍完整同步。
- 用户提的坑 ②（对账后必须刷 UI）：丙走 `_load()`；乙走 `syncNow` 末尾既有的
  `setState`（`build()` → `_buildHome()` 每次新建 `AppShell` ⇒ 徽标必然重查）。

### 4.6.3 测试（+6，全部先红后改）

| 层 | 用例 | 造的是什么 |
|---|---|---|
| core | 响应丢了 ⇒ 停 pending；对账 ⇒ 转 sent | `replyThrow`（响应丢）→ `replyJson(already_exists)` |
| core | 普通 push 被退避挡住、对账不会 | 失败一次后 `push()` 的 `attempts == 0`，对账 `== 1` |
| core | 主机真没有 ⇒ 对账重推会 `applied`（不是只查不推） | 护栏 |
| app | `syncNow` 推完还剩 pending ⇒ **自动对账** | `FakeHost.pushBodies` 脚本化：第一次空 results、第二次 already_exists；断言 `pushRequests == 2` |
| app | 队列本来就空 ⇒ 不发多余的对账请求 | 护栏（`pushRequests == 0`） |
| widget | 三态条点开有「立即重试」，点完徽标当场变 | 注入假 `Transport`（不能真联网） |

**用户提的坑 ③**（测试必须造出「响应丢了」）：core 用假 `Transport` 的
「抛异常 + 下一次答 `already_exists`」组合；服务层用 `FakeHost` 的脚本化回执。
**没有拔网线、没有真等超时**。

**反向灵敏度（三轮，都精确命中）**：

1. 撤掉 `syncNow` 里的对账接线 ⇒ app 测试红（`Expected: <2> / Actual: <1>`）；
2. `reconcilePending` 不再忽略退避 ⇒ core 两条红（`Expected: <1> / Actual: <0>`）；
3. 撤掉「立即重试」按钮 ⇒ widget 测试红（`Found 0 widgets with key [sync-retry-now]`）。

### 4.6.4 诚实边界
