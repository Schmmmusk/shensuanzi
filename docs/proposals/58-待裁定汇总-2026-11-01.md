### A2 schema v8：把主机身份搬进库（提案 56 ④，当时按裁定暂缓）

**背景**：提案 56 裁定 ④ 写的是「**暂缓**（等诊断与 L2 实测结果）」。现在两件都完了 ——
L2 在真实 Windows 上实测通过，根因也结案了（**进程跑在 Low 完整性**，不是代码 bug）。

**它想做什么**：把 `host.json`（`host_id` + `token_hash` + DPAPI 密文）搬进 `shensuanzi.db`

**但有一条关键事实必须先摆出来**：根因是 **Low 完整性 ⇒ 库也写不进去**。
所以 v8 **不能**解决那类故障，它只让「身份」不再单独占一个文件。

| 选项 | 做法 | 代价 |

| 甲 | 做 schema v8（身份进库） | 一次 schema 迁移（迁移链 +1）+ 双端读写改造 |

**推荐乙**：收益只是「少一个文件」，成本是一次 schema 迁移 + 双端改造；
而真正的故障源（进程完整性）v8 治不了。等以后真有别的理由动 schema 时顺手带上更划算。

**最省事回法：`A2 乙`**

English: schema v8 would move the host identity from `host.json` into a table. It was deferred

write fallback + diagnostics.

### A4 手机「手动填地址」的误导（2026-11-01 你点名）

**你遇到的四件事**：

1. 入口叫「**扫不了码 / 连不上？手动填地址**」—— 名字就在说「填地址」；
2. 输入框 label「**电脑地址**」、hint `192.168.1.5:17890` —— 更加强调「只填地址」；
3. 没配对过时只填地址被拦，这时才说「还缺配对令牌，请扫二维码或把配对码整段粘进来」；
4. 真正的配对码是 `shensuanzi://pair?host_id=…&ip=…&port=…&token=…&v=1`（**约 100 字符**），
   没人愿意手输 —— 连你自己都被误导，以为输 IP 就行。

> 值得记一笔：全角字符（中文输入法打的 `。` `：`）**成功转义**了，这条是好设计，保留。

| 选项 | 做法 | 代价 |
|---|---|---|
| 甲 | **只改文案与入口名**：入口 →「扫不了码？粘贴配对码」；输入框说明「两种都能粘：整段配对码 / 光一个地址（限已配对过的手机）」；错误文案指向电脑上的「复制配对码」按钮 | 小，半天内 |
| **乙** | 甲 **+ 6 位数字短码**：电脑端显示 `482913`（5 分钟有效、一次性），手机输 6 位数字，电脑点「确认」 | 中；主机端要加「待确认配对」状态机 + 手机端一个输入页 |
| 丙 | 只做乙（不改文案） | 不推荐：短码上线前的那段仍然误导 |

**推荐乙**：甲治不了「又臭又长」这个根 —— 只要还需要用户抄 100 个字符，中老年用户就走不通。
6 位短码是行业标准做法（蓝牙配对、微信登录、AirPlay 都是），而且**电脑端已经有人看着屏幕**，
「电脑上点确认」这一步天然可做。

**最省事回法：`A4 乙`**

English: The manual-entry dialog is mislabelled — the entry says "manually enter address",
the field says "PC address", and only after failing does it explain that a full pairing code is
required. The real pairing code is ~100 characters, so nobody will type it. Option 甲 fixes only
the wording; **乙 (recommended)** also adds a **6-digit short code** (PC shows `482913` for five
minutes, phone types six digits, PC confirms) — the industry-standard flow, and the PC user is
already looking at the screen.

### A5 ⚠️ 大库全量同步**拉不完**（2026-11-01 实测，26.4 万单）

**现象**（真机实测三次，库 26.4 万单 / 546 MB）：

| 次 | 结果 |
|---|---|
| 1 | **10 万条**（镜像 214 MB，约 2.5 分钟） |
| 2 | **还是 10 万**（「历史主机数据」1 份 → 2 份） |
| 3 | **23.3 万**（还差 3.1 万） |

**两个根因**：

1. **页数上限**：`maxPullPages = 200` × 服务端每页 500 = **10 万条/次**。超限时如实报
   「只同步了一部分，请再点一次」，但在真实大库上它是一堵**硬墙**。
2. ⭐ **新镜像从不写 `mirror_meta.host_id`** ⇒ 第二次同步判定「身份不符」⇒
   **归档重建 + 从头拉**。小库无感（80 条重拉 1 秒），**大库致命**（每次点都回到起点）。
   证据：第一次的镜像**没有 `mirror_meta` 表**，第二次之后有了。

| 选项 | 做法 | 代价 |
|---|---|---|
| 甲 | **只修 host_id**（新镜像建好就写） | 一行 + 回归测试；但 10 万/次的上限还在，26 万单要点 3 次 |
| **乙** | 甲 **+ 页数上限提到 2000 页**（=100 万条，够用 10 年） | 小；单次同步时间变长，但本来就该一次拉完 |
| 丙 | 乙 **+ 把「没拉完」改成对话框**（SnackBar 几分钟后用户已离开那一屏） | 小；体验最好 |

**推荐乙**：host_id 是**必修的 bug**（不修就永远前进不了），页数上限必须一起提
（否则用户要手动点 3 次，还会以为卡住了）。丙的对话框可以顺手做，也可以等下次。

**最省事回法：`A5 乙`**

English: On a 264k-document database the phone can only pull **100k rows per sync**
(200 pages × 500 rows), and worse — **a freshly created mirror never writes
`mirror_meta.host_id`**, so the *second* sync sees "identity mismatch", archives and rebuilds,
and starts over from row 1. Small databases hide it (re-pulling 80 rows is instant);
large ones can never finish. **Recommended 乙**: always write `host_id` on mirror creation
(a one-line bug fix) **and** raise the page cap to 2000 (≈1M rows). 丙 additionally turns
"not finished" into a dialog instead of a SnackBar.
