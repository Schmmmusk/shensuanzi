# 待定方案：P1-1（盘点原文落库） vs §2.8（设置页拆二级）

> 2026-11-27。用户要求先出方案再决定方向。
> 两项的**共同点**：都不是"顺手能改"的小事。**不同点**：一个动数据写入路径，一个动信息架构。

---

## A. P1-1 盘点单丢失「录入原文单位」

### A.1 事实（已核对代码，不是推测）

| 环节 | 现状 | 位置 |
|---|---|---|
| 开单（销售/采购/送货） | `DocumentLine.create(... entryQuantity:, entryUnit:)` —— 两列都写 | `documents/document_build.dart:74-84 / 120-130 / 168-178` |
| 盘点草稿 | `StocktakeLineDraft` **只有** `productId / productName / quantity` | `documents/stocktake_draft.dart:32-47` |
| 盘点落库 | `RuleEngine._stocktake()` 用 `actualByProduct` 映射**重建** `DocumentLine`，只给 `quantity` | `rules/rule_engine.dart:1000-1020` |
| Schema | `document_lines.entry_quantity` / `entry_unit` **早已存在**（v8） | `db/schema.dart:269-270` |

⚠️ **关键**：光在草稿里加字段还不够 —— 引擎在 `_stocktake` 里**丢弃**了原始的 `DocumentLine`，
用 `Map<productId, 实际数量>` 重造。所以**改点有两个**，不是一个。

### A.2 改法（三处 + 测试）

| # | 文件 | 改动 |
|---|---|---|
| 1 | `stocktake_draft.dart` | `StocktakeLineDraft` 加 `entryQuantity`（String，空=同 `quantity`）/ `entryUnit`（String?）；`copyWith` / `fromProduct` / 校验同步 |
| 2 | `document_build.dart`（盘点的 build） | 构造行时带 `entryQuantity` / `entryUnit`（与开单同款） |
| 3 | `rule_engine.dart::_stocktake` | **保留原文**：签名改为接收原始 `List<DocumentLine>`（或 `Map<productId, (entryQty, entryUnit)>`），重建行时回填两列 |
| 4 | 测试 | core：按箱盘点 2 箱 ⇒ 断言 `entry_quantity=2`、`entry_unit='箱'`、`quantity=48`；再加一条「没切单位 ⇒ entry 两列为 null」 |

### A.3 风险与对策

| 风险 | 说明 | 对策 |
|---|---|---|
| **写入路径回归** | `_stocktake` 是权威落库路径；改错 = 库存错 | 先写**能红的测试**（当前行为：entry 列为 null），改完保留为护栏；`dart test` 全量 + 手工 `adb`/真机各盘一次 |
| 语义混淆 | `quantity` 仍是「最小单位实际数量」，不可改 | 断言 `quantity` 不变，只多两列 |
| 手机端链路 | `stocktake` 单据由手机入队 → 主机 `RuleEngine` 落地 | 手机侧草稿构造需同步（`QueueSink`），否则手机盘的点仍丢原文 |
| 旧数据 | 既有盘点单两列为 NULL | 显示层已能处理（`entryUnit` 可空），不做回填 |

### A.4 代价与判据

- **代价**：0.5 天（改 + core 测试）＋ 0.5 天（手机链路 + 回归）≈ **1 天**
- **验收**：按箱盘点 2 箱 → 详情页显示「2 箱（= 48 瓶）」；库里 `entry_quantity=2` / `entry_unit='箱'` / `quantity=48`

## B. §2.8 设置页拆二级页面

### B.1 规模（实测）

| 指标 | 值 |
|---|---|
| `settings_page.dart` | **1087 行** |
| 区块 | 6 个（概览图表 / 界面大小 / 店名 / 数据 / 数据刷新 / 多设备同步） |
| 被测试引用的 `Key` | **11 个** |
| `settings_page_test.dart` | 561 行 / **19 条用例** |
| 构造参数 | **11 个**（config / configStore / backupDirectory / backupStatusLine / backupNeedsAttention / onBackupNow / hostService / onChangeBackupLocation / onConfigSaveFailure / onRefreshNow …） |

### B.2 目标结构

```
设置
├── 界面            → 界面大小、概览图表（百分数/倍数）
├── 数据与备份      → 数据位置、备份位置、立即备份、数据刷新
├── 手机与同步      → 多设备同步、配对、立即同步、忘记主机
└── 关于            → 版本、许可、第三方组件、手册入口
```

### B.3 两种拆法

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **甲：入口页 + 4 个子页（全量）** | 一次性拆完 | 结构一次到位 | 19 条用例要跟着改页面层级；11 个参数要逐层传或引入 `SettingsScope`；**一次大改** |
| **乙：先拆「关于」一页（渐进）** | 只搬走「关于/版本/许可/手册」 | 验证 `Key` 保留策略与参数传递方式；风险小；可先在真机看结构是否被接受 | 入口页仍旧偏长；两次收尾 |

⚠️ 拆页会把「一页里的 19 条用例」变成「入口页跳转 + 子页断言」；**测试迁移量 = 主要成本**，
比写子页本身更费时。

### B.4 代价与判据

| 方案 | 代价 | 风险 |
|---|---|---|
| 甲 | 2–3 天 | 中高（11 Key + 19 用例 + 11 参数） |
| 乙 | 0.5–1 天（含一次真机确认） | 低 |

**共同判据**：所有既有 `Key` 仍能被 `find.byKey` 找到（从入口页点进子页后）；
设置项保存后 `AppConfig` 的写盘行为与失败提示**一条不变**。

## C. 对比与建议

| 维度 | P1-1 | §2.8 |
|---|---|---|
| 影响 | **数据可追溯性**（用户回看单据对不上自己的纸质单） | **找东西的速度**（滚一屏找一项） |
| 动到哪 | core 写入路径（`RuleEngine`） | 纯 UI + 测试结构 |
| 出错后果 | **库存数据错**（最坏情况） | 某个设置项暂时找不到（可回滚） |
| 能否取证 | 能：一条 core 测试先红 | 能：几何/跳转断言 |
| 代价 | ≈ 1 天 | 甲 2–3 天 / 乙 0.5–1 天 |

**我的建议：先做 P1-1，但严格按"先红后修"** ——
它是已登记的 **P1**、影响真实记账可追溯性，且范围边界清楚（三处 + 测试）。
设置页拆分建议走**乙案**（先拆「关于」），用一次真机确认结构方向后再做全量，
避免一次性动 11 个 Key / 19 条用例。

**若你认为"记账没错、只是看不到原文"可以延后**，那就先做 §2.8 乙案 —— 它不碰数据路径。
