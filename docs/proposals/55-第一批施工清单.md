### 盘点为什么判不了「该有的流水丢了」

`_stocktake` 的写法：明细 `quantity` 存**实际数量**，差额 `实际 − 账面` 只写在
流水里，`diff == 0` **不写流水**。所以「某条本该存在的盘点流水丢了」单凭单据
**判断不出来** —— 要判它得知道当时的账面数，而账面数只能从（可能已损坏的）
流水反推，等于用被怀疑的数据验证它自己。

- **不做**：不假装查过，也不恢复「每条盘点明细都必须有流水」（零差额会误杀）。
- **做**：一条明细最多产生一条流水 ⇒「流水条数 > 明细条数」一定是坏的。
- 测试：零差额通过 / 有差额且流水完整通过 / 流水条数多于明细 ⇒ 不完整。

> 如果以后确实要判「盘点流水丢失」，需要引入**独立于流水**的账面快照
> （比如每次盘点把账面数一并存进单据），那是 schema 层的事，不在抢救器里解决。

**四条施工前提被审查推翻并已改正**（详见 `docs/reply_review.md` §CV·四十七）：

1. **资金流水不能一律比 `paid_amount`** —— 真实收款单的 `paid_amount` **恒为 0**，
   钱挂在它自己的 `money_ledger` 上；主单反过来**不写** `money_ledger`。
2. **「往来流水为空」不等于「不适用」** —— 只有 `party_id` 为空才是散客/散采。
3. **核销必须双端处理** —— 只过滤关系会让两端的单据各自导入，账能打开但对不上。
4. **库存只比行数不够** —— 还要比数量合计，并查「流水里有、明细里没有」的商品。

## 一、⑥ 退款上限

### 现状（已取证）

| 事实 | 位置 |
|---|---|
| `documents.paid_amount` 是**派生缓存**，真相在 `settlements` | `Agents.md` §二·4 |
| `SettlementService.refundedAgainstCentsOf()` 读的是 **`SUM(documents.paid_amount)`** | `settlement_service.dart:210` |
| `SettlementDao.settledAmountOf(id)` 才是从 `settlements` 算的（已在 `unsettledCentsOf` 里用） | `settlement_service.dart:130` |
| 退款卡片只看「有没有选账户」，不看原单收过钱没有 | `return_page.dart` |

### 三条判据（落在 `RuleEngine`）

```
① 本次退款 ≤ 本次退货应退金额
② 累计实际退款（含本次） ≤ 原单真实收款
③ 原单真实收款 == 0 ⇒ 任何退款请求直接拒绝
```

「原单真实收款」= `SettlementDao.settledAmountOf(原单id)`（走 `settlements`，不是缓存）。
「累计实际退款」= 该原单下所有退货单的 `settledAmountOf` 之和（同样走 `settlements`）。

### 要改的三处

| # | 位置 | 改什么 | 风险 |
|---|---|---|---|
| 1 | `RuleEngine` 退货/退款前置校验 | 加上述三条 | 低（新校验） |
| 2 | `SettlementService.refundedAgainstCentsOf()` | 从 `paid_amount` 改走 `settlements` | **中**：详情页「还欠客户退款」会跟着变 |
| 3 | `ReturnPage` 退款卡片 | 原单真实收款 = 0 时隐藏金额与账户，改成一句说明；> 0 时上限 = 真实收款 | 低 |

> **第 2 项必须单独一轮 + 对拍**：同一批数据下新旧算法结果必须一致。不一致说明某处缓存与真相
> 漂了 —— 那本身是另一个 bug，要先查清再改，不能顺手抹平。

### 测试（先红后改）

| # | 场景 | 期望 |
|---|---|---|
| 1 | 送货已签收、真实收款 0，退货带退款 | `RuleRejected`，文案含「这张单还没收到钱」 |
| 2 | 真实收款 100，第一次退 80（已退）⇒ 第二次想退 80 | 拒绝（累计 160 > 100） |
| 3 | 真实收款 100，退货应退 30，想退 40 | 拒绝（本次超应退） |
| 4 | `sale` / `delivery` / `purchase` **各跑一遍 #1** | 三个类型都拒绝（不只送货） |
| 5 | 对拍：`refundedAgainstCentsOf` 新旧算法 | 同一批数据结果相同 |

**反向灵敏度**：撤掉规则层校验 ⇒ #1 必须红（而不是只靠 UI 隐藏）。

### English

Three rules in `RuleEngine`: refund ≤ this return's amount; cumulative refunds ≤ real receipts; zero
receipts ⇒ reject. Change `refundedAgainstCentsOf` to read `settlements` (with a cross-check against the
old algorithm in a separate round). Tests must cover `sale`/`delivery`/`purchase`, plus cumulative overflow.

## 二、② 完整性判定

### 现状（已取证）

```dart
final bool expectsLedger = myStock.isNotEmpty || myMoney.isNotEmpty || myParty.isNotEmpty;
```

一条流水就放行。`Set<product_id>` 也不够（用户举的反例：可乐 10 + 可乐 20，丢一条仍含「可乐」）。

**而规则层是逐条明细生成流水的**（`rule_engine.dart`：`for (line in lines) _insertStock(...)`），
所以「应有几条」是可算的，不必猜。

### 判据（按业务类型）

| 类型 | 库存流水 | 资金流水 | 往来流水 | 核销 |
|---|---|---|---|---|
| `sale` / `delivery` / `purchase` | **每个商品的行数 = 明细行数**，且 `|SUM(数量)|` 相符 | 金额相符（见下） | **金额 = 单据金额** | 有核销行则两端必须都在 |
| `sale_return` / `purchase_return` | 同上（符号相反） | 同上 | 同上（符号相反） | 同上 |
| `stocktake` | **只对数量有变化的明细**要求（零差额不产生流水） | 无 | 无 | 无 |
| `receipt` / `payment` | 无 | **金额 = 本单金额** | 有往来方才有 | **`SUM(settlements.amount) == total_amount`** |

#### 🆕 金额检查的边界（用户裁定补充「补金额」，但**不能乱比**）

用户要求「补金额、往来流水、资金流水检查」。照做，但必须分清**哪两个金额本来就该相等**：

| 比什么 | 能比？ | 为什么 |
|---|---|---|
| 明细 `amount` ↔ 库存流水 `total_cost` | ❌ **不能** | `total_cost` 是**成本**，明细 `amount` 是**售价**。两者本来就不等（毛利就在这个差里） |
| 明细 `amount` ↔ 单据 `total_amount` | ✅ 能 | 明细金额之和 = 单据金额（退货让价已直接改小 `amount`） |
| 往来流水 `amount` ↔ 单据金额 | ✅ 能 | 挂账时往来冲减的就是这张单的金额 |
| 资金流水 `amount` ↔ 实收/实付金额 | ✅ 能 | 立即收付款的金额就是流水金额 |
| 收付款单 `total_amount` ↔ `SUM(settlements.amount)` | ✅ 能 | 一张收付款单的金额就是它核销出去的钱 |

> ⚠️ 我最初在提案里写「金额不比，让价会误报」—— 那句话**理由错了**：让价已经体现在
> 明细 `amount` 里（`discount_amount` 恒 0，见 `return_service`）。真正不能比的是
> **成本 vs 售价**。这里改正，避免实现时照着错误理由砍掉该有的检查。

### 实现要点

1. 明细侧与流水侧各聚合一次：`Map<productId, (行数, 数量合计)>`
2. 判据：`行数相等 && 数量绝对值相等`
3. **不用金额比对**：让价/折扣会让两者不等，会误报
4. 核销：`receipt`/`payment` 单的 `settlements` 合计必须等于本单金额；其它类型若有指向它的核销行，
   那些行的 `receipt_doc_id` 必须也在
5. 类型不认识 ⇒ **默认不完整**

### 测试（先红后改）

| # | 场景 | 期望 |
|---|---|---|
| 1 | 5 行明细的销售单，删 2 条流水 | 不完整（现有代码会判完整 ⇒ **先红**） |
| 2 | 同商品 2 行（10 + 20），删 1 条流水 | 不完整（`Set` 方案会漏 ⇒ 这是用户的反例） |
| 3 | 盘点单，某明细数量无变化 | **完整**（反例，防过度严格） |
| 4 | 收付款单，核销合计 ≠ 本单金额 | 不完整 |
| 5 | 一张单的核销行丢了 | 不完整 |

### English

Replace "any ledger row exists" with per-product `(rowCount, quantitySum)` equality against detail lines.
Skip amount comparison (discounts cause false positives). Stocktake only requires rows for changed
quantities. `receipt`/`payment` must have settlements summing to their amount. Unknown types ⇒ incomplete.

## 三、54 第一批：查询层

### 3.1 schema v7：一条索引

```sql
CREATE INDEX idx_docs_type_bday ON documents(doc_type, business_day);
```

- 迁移：`migrationStep(6)`（`ALTER`/`CREATE INDEX` 不需要重建表）
- 实测：26.2 万单上建索引 **184 ms**；按类型查 30 天从 **108–144 ms → 3.7–6.1 ms**
- 写成本：每插一单多维护一个索引，< 1 ms

### 3.2 营收口径（**必须按裁定的公式**）

```
营收 = SUM(total_amount) WHERE doc_type IN ('sale','delivery') AND status != 'cancelled'
     − SUM(total_amount) WHERE doc_type = 'sale_return' AND status != 'cancelled'
                            AND 原单(ref_doc_id) 存在且 status != 'cancelled'
```

- 拒收（原送货单 `cancelled`）**不冲减**：实测 458 张、虚减 ¥45.8 万
- 原单读不到 ⇒ 保守按冲减处理
- 待用户定：**在途送货算不算营收**（现有 `todaySummary` 算）

### 3.3 聚合 API（`QueryDao`）

| 方法 | 签名 | 说明 |
|---|---|---|
| `dailySales` | `List<({int businessDay, int cents})> dailySales({required int fromDay, required int toDay, Set<DocType>? types})` | 一条 SQL 一个指标 |
| `dailyNetRevenue` | 同上，内部 = 销售 − 有效退货 | 图表主口径 |

**性能纪律**：按类型过滤时**不要一条 SQL 里 `GROUP BY business_day, doc_type`**（实测 143.8 ms，
因为规划器走 `idx_documents_type_status`）。要**按类型拆开查再在 Dart 里合并**（各 3.7–6.1 ms）。

### 3.4 纯函数 `buildDailySeries`

```dart
/// 把稀疏的 (day, cents) 补成连续的日序列，并可聚合成周
List<DailyBucket> buildDailySeries({
  required List<({int day, int cents})> rows,
  required int fromDay,
  required int toDay,
  BucketGranularity granularity = BucketGranularity.day,
});
```

四条必须单测的规则：

1. **空白日补 0**（不补会把「三天没卖」画成连续趋势）
2. **自然周**：按**周一**为起点（`business_day` 是 1970-01-01 起的日序号，
   直接 `/7` 得到的是「从纪元起每 7 天」，**不是日历周**）
3. 周标签要能显示范围（`10/21–10/27`）
4. 求和 / 平均 / 最大值都能从结果算（不要重复扫）

### 3.5 测试

| # | 场景 | 期望 |
|---|---|---|
| 1 | 3 天有单、中间 2 天空 | 5 个 bucket，空的补 0 |
| 2 | 跨周（周三到下周周二） | 两个周 bucket，周一是分界 |
| 3 | 正常退货 | 净额 = 销售 − 退货 |
| 4 | **拒收**（原单作废 + 退货） | 净额 **不减**那笔退货 |
| 5 | 补录昨天的单 | 落在昨天（`business_day`），不是今天 |
| 6 | 索引在（`EXPLAIN QUERY PLAN` 不许出现 `TEMP B-TREE`） | — |

### English

v7 adds `(doc_type, business_day)`. Revenue = sales − returns whose original doc is still valid (rejection
must not subtract). Query per doc type separately, never `GROUP BY` two dimensions in one statement
(143.8 ms vs 6.1 ms). `buildDailySeries` fills empty days with zero and buckets by **calendar week starting
Monday**, not `business_day / 7`.
