## 零、结论先行：**本批不需要动 schema**

你说「要动 schema，算大更新」—— 我上一轮那句「#4 加列」说得不严谨，**核对后是本批零 schema 变更**：

| 候选 | 报告原话 | 核对结果 |
|---|---|---|
| P2 #4 `SettlementView.occurredAt` 装的是 `created_at` | 「改字段名或加列」 | **两条都不用**：`_views` 已经 `LEFT JOIN documents d`（`settlement_dao.dart:104-107`），直接把 `s.created_at` 换成 `d.occurred_at` 即可 —— 收款单的 `occurred_at` 本来就是那笔钱真正发生的时间 |
| 未收额要不要落一列 | （报告没提，但直觉会想） | **不能落**，见 §五：它是派生值，落列等于把不变量 B4 复制一份，必须双写 + 回填 + 处理历史脏数据 |

⇒ 本批是**纯代码 + 文案**：core 纯函数、DAO 一处 SELECT、UI 一处显示、导出结果一个字段。
**没有 v5 迁移、没有 `Schema.version` 变更、没有回填脚本。**

> **No schema change in this batch.** The one item the report flagged as "add a column or rename"
> (P2 #4) already has a zero-cost fix: the view query already joins `documents`, so it can read
> `d.occurred_at` directly. Storing an "unsettled amount" column would duplicate invariant B4 and
> require dual writes, backfill, and dirty-data handling — explicitly rejected in §五.

## 一、子批 3a：未收统一来源（本批的核心）

### 1.1 现状：四处计算、两套公式

| 位置 | 公式 | 含退货冲减？ |
|---|---|---|
| `document_dao.dart:404`（未结清筛选，SQL） | `total − paid − COALESCE(rsum,0)` | ✅ |
| `settlement_service.dart:130-131`（`unsettledCentsOf`） | `total − settled − returnedAgainst` | ✅ |
| `sale_service.dart:182`（保存后提示「还差多少」） | `total − paid` | ❌ |
| `purchase_service.dart:181` | `total − paid` | ❌ |
| `rule_engine.dart:1201`（校验文案里的金额） | `total − settled` | ❌ |

后果：**部分退货 + 部分收款**的单，保存提示与列表筛选会给出**不同的欠款数字**。
（例：销售 100、退 30、收 50 ⇒ 列表说欠 20，保存提示说欠 50。）

> Four call sites, two formulas. A doc with a partial return and a partial payment shows
> different "still owed" numbers in the list filter vs. the save toast.

### 1.2 方案：一个纯函数，四处调用

在 core 加一个**纯函数**（不查库，输入是三个已算好的数）：

```dart
/// 真实未收/未付 = 总额 − 已核销 − 该单累计退货冲减（`§审查 BUG-04`）。
/// ⚠️ 唯一口径：DAO 的 SQL、服务层提示、规则层文案都必须用它（或与它逐字同形）。
int unsettledCentsOf({
  required int totalAmount,
  required int paidAmount,
  required int returnedAmount,
  required DocType docType,
  required DocStatus status,
});
```

- 退货单 / 收付款单 / 盘点单 ⇒ **恒 0**（不产生债权债务）；作废单 ⇒ **0**。
- 返回值**可以为负**（退货超过已收），**不夹 0** —— 负未收是真实业务信号（见 3a-2）。
- SQL 侧：把 `document_dao.dart:404` 的表达式抽成 `String unsettledSql(...)`（同一文件、
  紧挨函数），并在注释里写「改一处必须改另一处」+ 一条**对拍测试**（同一批数据，
  SQL 结果与函数结果逐个相等）。

> One pure function + one SQL fragment, next to each other, with a parity test over the same
> fixtures. Negative values are allowed (they are a real signal), not clamped to zero.

### 1.3 3a-2 负未收显式显示

- 详情页金额卡：未收为负 ⇒ 显示「**多收 ¥X**」（而不是「未收 −¥X」）。
- 列表行：`未收` 列为负时同样显示「多收」。
- 规则层文案（`rule_engine.dart:1201`）改用新函数，避免「存在未结清金额（-500）」这种句子。

> Negative unsettled renders as "over-collected ¥X", never as "unsettled −¥X".

### 1.4 3a-3 顺带：`#1` 已在更早的批次修好

报告 P2 #1 说「未结清筛选拿 `paid_amount` 缓存当真相」—— 核对当前代码，
`document_dao.dart:391-405` **已经** JOIN 了 settlements 汇总（`r.rsum`）并按三项相减。
**该条已失效**（报告快照后由 BUG-04 修过），本批只需把公式抽成 1.2 的函数。

> P2 #1 is already fixed (the filter joins settlements and subtracts returns). Only the
> extraction in 1.2 remains.

## 四、子批 3d：导出完整性自曝（P2 #2）

现状：导出遇到「跳过坏行」（`read_failures` 解码失败）照样落一份**缺行** CSV，
用户拿文件对账会与屏幕不符，且**没有任何提示**。

修法：导出结果类型加两个字段（**不落库**）：

```dart
class ExportResult {
  final String path;
  final int rowsWritten;
  final int skippedBadRows;   // 解码失败被跳过的行数
  bool get isComplete => skippedBadRows == 0;
}
```

- 四个导出入口（单据 / 商品 / 往来 / 账户）都在完成提示里说：
  「已导出 N 行；**有 M 行读不出来被跳过**，这份文件不完整」。
- 客户端库存估算同理：`StockDelta` 已经统计 `readFailures`，导出时必须把它带出来。

> Export must report `skippedBadRows`; the completion toast says the file is incomplete
> when it is. No schema, no new table — a field on the result type.

## 五、为什么「未收额」不能落列（schema 讨论，结论 = 不做）

直觉方案：给 `documents` 加 `unsettled_amount`，筛选/排序直接读它。**四条理由否掉**：

1. **它是派生值**：`total − paid − returned`，三项都在库里，落列 = 同一事实存两份。
2. **会与不变量 B4 打架**：`paid_amount` 本来就要与 `settlements` 对账；再加一列，
   不变量从 1 条变 3 条（`unsettled == total − paid − returned`），每处写入都要维护。
3. **回填与历史脏数据**：迁移要给所有历史单算一遍；任何一处漏写就永久不一致，
   而**没有任何查询能发现它**（除非再写一条对拍）。
4. **收益为零**：未结清筛选已经走索引 + JOIN 聚合（`idx_settlements_*`），
   2 万单量级是毫秒级 —— 第 4 批的性能度量会验证这一点，**先度量再优化**。

⇒ 若将来确实需要「按未收额排序」，走**物化视图/缓存表 + 明确失效点**，
那是独立提案，不在本批。

> Storing the unsettled amount is rejected: it duplicates a derived value, triples invariant B4,
> needs a backfill with no way to detect drift, and buys nothing measurable. If sorting by it is
> ever needed, that is a separate proposal (materialized cache with explicit invalidation).

## 七、风险与顺序

| 风险 | 说明 |
|---|---|
| 3a 改「未收」口径会**改变用户看到的数字** | 只影响「有退货且部分收款」的单；改完要跑 `settlement_view_test` / `overview` / 导出三处回归 |
| 3b-1 部分核销改严 | 同步直推的历史客户端可能被拒 —— 但 v1 客户端从不发部分分配（UI 封顶），风险≈0 |
| 3b-2 单号无条件重生成 | 客户端本地显示的单号会与主机不同（本来就该以主机为准；pull 会覆盖） |
| 3c-4 `occurredAt` 换源 | 排序/展示会变（收款单从「录入时刻」变成「业务时刻」）—— 这正是修复目标 |

**建议顺序**：3a（核心，独立可发）→ 3c（机械项，一次提交）→ 3b（规则/协议，含 ⑥甲）→ 3d（导出）。
每步单独跑门禁，**任何一步红了就停在那一步**。

> Order: 3a → 3c → 3b → 3d, each with a full gate run. 3a is the only one that changes
> numbers users see; the rest are mechanical or additive.
