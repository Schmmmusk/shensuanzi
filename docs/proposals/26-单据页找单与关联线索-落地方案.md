## 二、根因（①）：同一列存着两种口径，而列表按「看不见的那个」排

### 中文

**三个事实，全部 `文件:行` 可查：**

| # | 事实 | 依据 |
|---|---|---|
| **A** | **主单**的 `occurred_at` = **当天 00:00**（开单页只能选到「日」，§BG 方案甲） | `sale_draft.dart:493`：`int get occurredAt => DateTime.parse(date.trim()).millisecondsSinceEpoch;`（注释：「当天 00:00（本地时区）」） |
| **B** | **退货单 / 手记收付款单**的 `occurred_at` = **精确时刻** | `return_service.dart:252` `occurredAt: stamp`；`settlement_service.dart:343` 同款 |
| **C** | 列表排序 = `ORDER BY occurred_at DESC, created_at DESC` | `document_dao.dart:308` |

A + B + C 的合成结果：**同一天里，所有派生单据（退货 / 手记收款）的 `occurred_at` 都 > 主单的 00:00**
⇒ 它们**全部压在主单上面**，`created_at` 那一段兜底排序**根本没机会生效**。
用户那 5 张单正是这个形状：18:06 / 16:53 / 16:50 / 16:48 都 > 00:00，而 21:11 的主单 `occurred_at` 是 00:00 ⇒ 排最后。

**更难看的一层（这才是「不信任」的来源）**：

- 列表页自己写的文案是**对的**（`documents_page.dart:254-255`）：
  「最新的排在最上面：先按「单据日期」，同一天里按「录入时间」倒序。」
- 详情页**同时**显示两个时间（`document_detail_page.dart:293` 单据日期、`:300`「录入于 21:11」）。
- ⇒ **文案承诺的是「录入时间」，实现用的是 `occurred_at`，用户点开后看到的是 `created_at`。三个东西，只有用户看到的那个是对的。**

按纪律 17 判：**文本对、实现偏 ⇒ 改实现**（不是改文案）。改文案等于把「按日期排、同一天内乱序」写成规则，
用户的下一句会是「那你们为什么不按时间排」。

**补充一处**：自动生成的收付款单 `occurred_at` **继承主单**（`rule_engine.dart:864` `occurredAt: mainDoc.occurredAt`）
⇒ 它们也是 00:00。所以「立即收款」的销售单不会出现 A/B 错位；**只有手记收款与退货**会。

### English

**Three facts, each grep-able:**

| # | Fact | Evidence |
|---|---|---|
| **A** | A **main document's** `occurred_at` = **local midnight** (the form only accepts a date; §BG option A) | `sale_draft.dart:493` |
| **B** | **Return / manual receipt** docs use the **exact instant** | `return_service.dart:252`, `settlement_service.dart:343` |
| **C** | List ordering = `ORDER BY occurred_at DESC, created_at DESC` | `document_dao.dart:308` |

A+B+C ⇒ **every derived document on a given day sorts above the main document**, and the `created_at`
tiebreaker never fires. The user's five rows are exactly that shape.

**The worse layer (the actual source of distrust)**: the list's own help text promises
"same day ⇒ by **entry time**, descending" (`documents_page.dart:254-255`), the detail page shows
"录入于 21:11" (`document_detail_page.dart:300`), but the SQL sorts by `occurred_at`. **Three different
notions of time; only the one the user sees is right.** Per discipline 17: **text is right, implementation
is wrong ⇒ fix the implementation.**

**One more fact**: auto-generated receipts inherit the main doc's `occurred_at` (`rule_engine.dart:864`)
⇒ they are also midnight. So "immediate payment" sales don't show the mismatch; **only manual receipts
and returns do.**

## 三、① 修法：按「日」分桶，日内按 `created_at` 倒序

### 中文

```sql
-- 落地时的最终写法（见下方「一处偏离」）
ORDER BY ((d.occurred_at + ?) / 86400000) DESC,   -- ? = 本地时区偏移（毫秒）
         d.created_at DESC
```

| 要点 | 说明 |
|---|---|
| 为什么按「日」分桶 | 主单是 00:00、派生单是时刻 —— 只有**抹掉日内差异**，两者才回到同一个可比维度 |
| 为什么加本地偏移 | `occurred_at` 存的是本地零点；按 UTC 整除一天会把东八区的 00:00 算到前一天 |
| 为什么不改 `occurred_at` 语义 | 纪律 15：语义变更 = 新字段。把主单改成「日期 + 保存时刻」是**篡改业务日期**，且要迁移历史数据 ⇒ 否决 |
| 索引 | `idx_documents_occurred` 用不上（表达式 + 全表排序）。个体户年单据几千条，不为此加函数索引（SQLite 也不支持表达式索引） |
| 跨时区 | 中国无夏令时；多时区同步已在 #32 登记为待办，本批不碰 |

**⚠️ 一处偏离（落地时发现，已登记）**：本文原写
`date(d.occurred_at / 1000, 'unixepoch', 'localtime')`，**实测返回 `NULL`** ——
本仓打包的 SQLite 编译时带了 `SQLITE_OMIT_LOCALTIME`（Python 自带的 SQLite 有这个修饰符，
所以早先那次验证是**假绿**）。`NULL` 会让排序**静默退化**成只看 `created_at`，跨天顺序直接错。
⇒ 改成「**加本地偏移后整除一天**」：纯整数运算，不依赖 TZ 数据库、也不依赖修饰符。
偏移由 `DocumentDao` 用 `DateTime.now().timeZoneOffset` 取（单一时区前提，与 `Agents.md` §一 一致）。

**落地实测（2026-10-18，`documents_list_test.dart` 4 条全绿）**：
`00:00` / `16:48` / `21:11` 三个时刻分桶相同；原值比较下 `00:00 < 16:48` 为真（复现了 bug）。

**改完后那 5 张单的顺序**（与用户逐张点开的时刻完全一致）：

```
XS20261012-008  21:11  →  SK20261012-006  18:06  →  SK20261012-003  16:53
                →  XT20261012-002  16:50  →  XT20261012-001  16:48
```

**文案不动**（`:254-255` 本来就对）。**但要加一句**（纪律 17：能力变了就说清）：
「同一天里，退货和收款按**记账时刻**排」——因为主单没有时刻，用户需要一个解释为什么同一行只写日期。

### English

```sql
-- Final form used in the implementation (see "one deviation" below)
ORDER BY ((d.occurred_at + ?) / 86400000) DESC,   -- ? = local UTC offset in ms
         d.created_at DESC
```

| Point | Why |
|---|---|
| Day bucketing | Main docs are midnight, derived docs carry an instant — only by **erasing the intra-day difference** do they become comparable |
| Adding the local offset | `occurred_at` stores local midnight; UTC day bucketing shifts 00:00 to the previous day in UTC+8 |
| Not changing `occurred_at` semantics | Discipline 15; it would also rewrite the business date and need a backfill — rejected |
| Index | `idx_documents_occurred` is unusable (expression + full sort). A few thousand docs/year; no functional index (SQLite doesn't support them) |
| Time zones | No DST in China; multi-TZ is already a #32 follow-up, out of scope |

**⚠️ One deviation found during implementation (recorded)**: the original
`date(d.occurred_at / 1000, 'unixepoch', 'localtime')` **returns `NULL` here** — the bundled SQLite is
compiled with `SQLITE_OMIT_LOCALTIME` (Python's SQLite supports the modifier, which made the earlier
verification a **false green**). `NULL` silently degrades ordering to `created_at` only, breaking
cross-day order. Replaced with **integer day bucketing after adding the local offset** — pure integer
math, no TZ database and no modifier. The offset comes from `DateTime.now().timeZoneOffset` inside
`DocumentDao` (single-timezone premise, consistent with `Agents.md` §1).

Resulting order matches the user's five timestamps exactly. The help text stays; **one clause was added**:
"same day, returns and receipts sort by **posting time**" — main docs have no time, and the user deserves
to know why one line shows only a date.

## 四、② 展示层级：把「单号」从第一位拿下来

### 中文

用户的原话：**「中老年用户最关心的数据是：交易金额，交易时间，交易状态，交易对象。单据编号？……这部分内容确实应当显示，但没必要像现在这样提到这么重要的位置上来。」**

**现状**（`documents_page.dart:442-509`）：单号是**第一行、加粗（`w600`）**，类型跟在后面；对方名与日期挤在**第二行**；
金额 / 状态 / 未收在右列。⇒ 用户第一眼扫到的是**一串他从来不用的编号**。

**改后布局**（行高不变，仍是 3 行；单号降级但**不隐藏**）：

```
┌────────────────────────────────────────────────────────────┐
│ 王老板                                          ¥240.00    │  ← 交易对象 + 交易金额（最大字号）
│ 店内销售 · 2026-10-12 · XS20261012-008            已结清    │  ← 类型 · 时间 · 单号（灰小字，可换行）+ 状态
│ 已退 2 次 ¥240.00 · 已收 1 笔                              │  ← 仅当有关联时出现（见 §五）
└────────────────────────────────────────────────────────────┘
```

| 位置 | 内容 | 依据 |
|---|---|---|
| 左·第 1 行 | **对方名**（`w600`，15–16sp，**单行 + 省略号**） | 交易对象 |
| 右·第 1 行 | **金额**（`w700`，`tabularFigures`，千分位） | 交易金额（用户列的第一位） |
| 左·第 2 行 | `类型 · 日期 · 单号`（`bodySmall` 灰，`Wrap` 可换行） | 单号在此**仍完整可见**，只是不再抢第一行 |
| 右·第 2 行 | **状态**（`docStatusLabel(displayStatus(...))`） | 交易状态 |
| 右·第 3 行 | 未收 / 未付（橙色，仅 > 0） | 现状保留 |
| 左·第 3 行 | 关联摘要（§五） | 生命周期进度 |

**两处顺带修掉的真问题（截图第 5 行实证）**：

1. **长对方名把行撑成 3 行**：`1111…（一长串）` 让左列换行 3 次、金额被挤到最右。⇒ 对方名 `maxLines: 1` + `TextOverflow.ellipsis`，
   完整名字在详情页（那里有空间）。**这是可证缺陷，不是审美**。
2. **日期只到「日」时，同一天多张单无法区分**（用户就是靠点开才发现的）。⇒ 见下方「时间显示」。

**时间显示**（需要你裁，见 Q3）：

| 方案 | 行为 |
|---|---|
| **甲** 维持现状：一律 `formatDate` | 与 `format.dart:19-21` 的既有注释一致（「单据的 `occurred_at` 不用带时分 —— 真机踩过 00:00」） |
| **乙（推荐）** 按数据如实：`occurred_at` 落在零点 ⇒ 只显示日期；否则显示到分 | 主单印 `2026-10-12`，退货/收款印 `2026-10-12 16:48`。**不印假的 00:00**，也不抹掉真实时刻 |
| 丙 | 全部显示到分 ⇒ 主单会印 `00:00`，**已被 §BG 真机否决过**，不建议 |

选乙要**同时改 `format.dart:19-21` 的注释**（那段话会变成错的）——纪律 17 的判据是 grep 能力词，不是凭印象。

### English

The user's words: older users care about **amount, time, status, party**; the doc number should be
**visible but not top-billed**. Today the doc no is **line 1, bold** (`w600`), with the party/date squeezed
into line 2 (`:442-509`) — the first thing the eye hits is an identifier they never use.

**New layout** (same 3-line height; doc no demoted, **not hidden**): party (bold, line 1 left) + amount
(bold, line 1 right); `type · date · doc no` as grey `bodySmall` on line 2 left, status on line 2 right;
unsettled on line 3 right; relation summary on line 3 left.

**Two real defects fixed on the way (evidenced by row 5 of the screenshot)**:

1. A long party name wraps three times and squeezes the amount to the far right ⇒ `maxLines: 1` +
   ellipsis; the full name lives in the detail page. **This is a provable defect, not taste.**
2. Date-only rendering makes same-day documents indistinguishable (the user had to open each one).

**Time display** (needs a ruling, Q3): **A** keep date-only (matches `format.dart:19-21`), **B (recommended)**
render truthfully — midnight ⇒ date only, otherwise to the minute (no fake `00:00`, no erasing real instants),
**C** always to the minute (prints `00:00`, already rejected on a real device in §BG). Choosing B requires
updating the comment at `format.dart:19-21`, which would otherwise become false.

## 五、③ 生命周期聚合：一笔生意一行（**纯展示投影，零 schema 变更**）

### 中文

用户的原话：**「底层仍按原有架构组织数据，展示时将同一张单子在生命周期内不同进度聚合在一张单子内。」**
—— 这正是本方案的做法：**数据层一个字不动**，只在**读侧**做投影。

**数据层已经天然支持这个投影**（`documents.ref_doc_id` + `settlements`）：

```
销售单 XS-008（root，ref = NULL）
├── 收款单 SK-006（ref = XS-008，自动生成）  ── settlements 里 1 笔
├── 收款单 SK-003（ref = XS-008，自动生成）  ── settlements 里 1 笔
└── 退货单 XT-002（ref = XS-008）
      └── 退款单 FK-00x（ref = XT-002）
```

**判定规则**（全部是既有字段，不需要新列）：

| 概念 | 判定 |
|---|---|
| **根**（一笔生意） | `ref_doc_id IS NULL`，**且**：收付款单必须**不是「只核销了一张单」**（那说明它是那笔生意的已收/已付） |
| **⚠️ 手记收付款单的归属** | `SettlementService.settle` 生成的收款单 `ref_doc_id` 是 **NULL** —— 关联只在 `settlements` 里 ⇒ 判据 = `COUNT(DISTINCT target_doc_id)`：**1 ⇒ 折进被核销单；0（客户直接给钱）/ ≥2（一收多单）⇒ 自己当根**。这是**用户复跑抓出的缺口**（§CV·六十六） |
| **子**（这笔生意的进度） | `ref_doc_id = 根.id`（自动收付款、退货） |
| **孙**（退款） | `ref_doc_id = 退货单.id` ⇒ 归到同一个根下 |
| 何时**不**聚合 | 用户**明确筛了**子类型（收款 / 付款 / 销售退货 / 采购退货）⇒ 平铺，否则一片空白（既有 `_includeDerived` 语义，`documents_page.dart:108-115`） |

**一个漂亮的简化**：现有那段复杂的「折叠派生单据」条件（`document_dao.dart:260-285`，用 `EXISTS` 判原单是否作废）
在「只列根」下**退化成** `d.ref_doc_id IS NULL` + 手记收付款单的 `settlements` 判据（见上）。⇒ 代码更短，语义更准。

**行内摘要**（第三行，只在有内容时出现）：

```
已退 2 次 ¥240.00 · 已收 2 笔
```

| 段 | 口径 | 数据源 |
|---|---|---|
| 已退 N 次 ¥X | 该根下所有 `sale_return` / `purchase_return` 的 **条数** 与 `SUM(total_amount)` | 一次 `GROUP BY ref_doc_id`（`returnedAgainstMany` 的既有形状，`document_dao.dart:41-62`） |
| 已收 / 已付 N 笔 | 该根单**自身**的 `settlements` 行数（退款不算「已收」，它在「已退」里） | 一次 `GROUP BY target_doc_id`（`idx_settle_target` 已存在，`schema.dart:310`） |

**为什么不在行内展开**（不做 `ExpansionTile`）：列表已经 200 行、首屏被筛选项占满（§六）；
行内展开会让行高跳动，中老年用户会「找不到刚才那行」。**关联单据的入口 = 点行进详情**，
详情页已有「退货记录」（`document_detail_page.dart:758`）与「核销去向」（`:113-121`）。

**⚠️ 这会推翻一条既有裁定，必须你点头**：

> `§审查 2026-10-05` 定过：**正常部分退货单仍然必须显示**（它是独立交易），只折叠「原单已作废」的整单退货。

聚合后，**部分退货单不再单独占行**（折进根行 + 「已退 1 次」）。好处是用户要的「一笔生意一行」；
代价是**列表里看不到退货单本身**，退款入口要走「根单详情 → 退货记录 → 点退货单」两步。
**我的判断**：可以推翻，但要**同时**给两个补偿——① 行内「已退 N 次」必须显眼（不是可选装饰）；
② 根单详情页把「退货记录」区块**上移**到金额区下方（现在在页面靠下）。若你认为退货单必须保持独立行，
就走 **乙：缩进从属**（子单仍在列表里，但缩进 + `↳` 前缀，视觉上挂在根行下）。

**导出**（AF-5：不许撒谎）：列表聚合了，导出**不能装作没聚合**。两个选项：

| 方案 | 做法 | 代价 |
|---|---|---|
| **甲（推荐）** 导出保持**平铺**（逐条记录）+ 按钮文案改成「导出当前筛选的单据（退货、收付款各占一行）」 | 会计拿到的是完整账，一行一条记录 | 屏幕与文件**行数不一致**，但**文案说明了** |
| 乙 导出也聚合 + 加两列「已退次数 / 已收笔数」 | 与屏幕 1:1 | 收付款/退货记录**从导出里消失**——会计会缺凭证 |

**推荐甲**：导出是**给会计的凭证**，不是屏幕截图；AF-5 要的是「说到做到」，不是「长得一样」。

### English

The user's ask: **keep the storage architecture, aggregate a document's lifecycle stages into one row on
screen.** This proposal does exactly that — **zero schema change, zero data migration, zero write-path
change**; only a read-side projection.

The data already supports it via `documents.ref_doc_id` + `settlements`:

| Concept | Rule |
|---|---|
| **Root** (one deal) | `ref_doc_id IS NULL`, **and** a receipt/payment must **not** settle exactly one document (if it does, it *is* that deal's "paid" record) |
| **⚠️ Manual receipts** | `SettlementService.settle` creates receipts with **`ref_doc_id = NULL`** — the link lives in `settlements` ⇒ rule = `COUNT(DISTINCT target_doc_id)`: **1 ⇒ fold into that doc; 0 (cash with no invoice) / ≥2 (one receipt, several invoices) ⇒ stays a root**. This gap was found on user re-test (§CV·66) |
| **Child** (progress) | `ref_doc_id = root.id` (auto receipts/payments, returns) |
| **Grandchild** (refund) | `ref_doc_id = return.id` ⇒ same root |
| When **not** to aggregate | The user explicitly filters by a child type (receipt / payment / sales return / purchase return) ⇒ flat list, otherwise it would be empty (existing `_includeDerived` semantics) |

**A neat simplification**: the current convoluted "fold derived docs" predicate (`document_dao.dart:260-285`,
with an `EXISTS` on the original's status) collapses to `d.ref_doc_id IS NULL` plus the manual-receipt `settlements` rule above under roots-only.

**Row summary** (line 3, only when non-empty): `已退 2 次 ¥240.00 · 已收 2 笔` — one `GROUP BY ref_doc_id`
for returns, one `GROUP BY target_doc_id` for settlement counts (index already exists).

**No in-row expansion**: 200 rows, a crowded first screen, and jumping row heights make older users lose
their place. The entry point to related docs stays "tap the row ⇒ detail", where both blocks already exist.

**⚠️ This overturns an existing ruling** (2026-10-05: normal partial returns must stay visible as independent
transactions). Aggregation removes them from the list. My view: acceptable **only with two compensations** —
① the "已退 N 次" hint must be prominent; ② the detail page's "退货记录" block moves up. Alternative **B**:
keep child rows but indent them under the root with a `↳` prefix.

**Export** (AF-5: no lying): **A (recommended)** keep export **flat** (one row per record) and rename the
button to "导出当前筛选的单据（退货、收付款各占一行）" — the accountant gets the full ledger, and the label
tells the truth. **B** aggregate the export too (screen parity) — but then receipts/returns vanish from the
file, and the accountant loses vouchers.

## 六、搜索：按内容 + 按时间

### 中文

用户要求：**「考虑在单据页面内添加搜索功能，同时支持按时间搜索和按内容搜索」**。

我的解读（若不对，Q5 里改）：

| 维度 | 现状 | 本批做法 |
|---|---|---|
| **按时间** | **已有**：今天 / 本周 / 本月 / 最近 30 天 / 自定义 / 全部（`:264-294`） | **保留**，把「自定义」提到更显眼（它是唯一能精确定位的）；**不做**「输入 `10-12` 当日期」的词法解析（歧义：`10-12` 也可能是单号片段、金额） |
| **按内容** | **零** | 新增搜索框，匹配 **单号 / 对方名 / 商品名** |

**实现要点**：

- 落点 = `_summaries` 新增 `String? query`，条件（与既有筛选 AND）：
  ```sql
  AND (
    d.doc_no LIKE ? ESCAPE '\'
    OR pa.name LIKE ? ESCAPE '\'
    OR EXISTS (SELECT 1 FROM documents c WHERE c.ref_doc_id = d.id
               AND c.doc_no LIKE ? ESCAPE '\')          -- 聚合后仍能按退货单号搜到那笔生意
    OR EXISTS (SELECT 1 FROM document_lines l
               JOIN products p ON p.id = l.product_id
               WHERE l.document_id = d.id AND p.name LIKE ? ESCAPE '\')
  )
  ```
- **必须转义** `\` `%` `_` 并**显式写 `ESCAPE '\'`**：否则用户搜「50%」= 全表（`LIKE` 的通配符）。
- **输入即筛**（`onChanged` → `setState`），不做防抖：本地 SQLite + 200 行，防抖只会制造「我打了字但列表没动」。
- **搜索时自动切「全部」范围并明说**：默认档是「最近 30 天」（`:80`），搜三个月前的单会 0 结果。
  三个选项——甲 保持范围（搜索基本失效）/ 乙 静默跨范围（**UI 撒谎**）/ **丙（推荐）自动切「全部」+ 一行说明**
  「已切到「全部」来找（原来只显示最近 30 天）」，清空输入**不自动切回**。
- **导出必须同口径**：`listDocumentsForExport` 传同一个 `query`，否则「导出当前筛选」当场变谎话。

### English

Requirement: search by **time** and by **content**. My reading (correct it in Q5 if wrong):

| Dimension | Today | This batch |
|---|---|---|
| **Time** | **Exists**: today / this week / this month / last 30 days / custom / all | **Keep**; surface "自定义" more; **no** free-text date parsing (`10-12` is ambiguous — doc-no fragment or amount) |
| **Content** | **None** | New search box matching **doc no / party name / product name** |

Implementation: one optional `query` in `_summaries`, ANDed with existing filters; four `LIKE`s covering root
doc no, party name, **child doc no** (so a return's number still finds the deal after aggregation), and
product names via `document_lines` join. **Escape** `\ % _` and write `ESCAPE '\'` explicitly, or typing
`50%` becomes a wildcard. Filter as you type, no debounce. **Auto-switch the range to "全部" and say so**
when the user starts typing (silent widening would make the UI lie). Export must pass the same `query`.
