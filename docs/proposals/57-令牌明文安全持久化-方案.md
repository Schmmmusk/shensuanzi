# 57 · 令牌明文的安全持久化（重启后还能画同一个二维码）—— 方案

> **本文双语**：每节先中文，紧随 `English` 段。两段内容等价；若有出入，**以中文为准**。
>
> **性质**：待裁定提案。**不占主台账 §编号**，裁定后按常规并入 `docs/reply_review.md`。
>
> **由来**：提案 56 的裁定 ③ 明确指出 —— 「当前只持久化令牌哈希，重启后无法恢复二维码明文。
> L2 成功不等于重启后能够显示原二维码……若要实现重启后直接显示原二维码，
> 应另行设计令牌明文的安全持久化机制。」本文就是那份「另行设计」。
>
> **它治的是什么**：不是写盘失败，而是**每天开机都要重新生成配对码**。
> 重新生成 = 轮换令牌 = 已配对的手机全部失效、必须重扫 —— 这才是用户真正的痛点。

---

## 零、结论速览

1. **推荐方案 A：用 Windows DPAPI（当前用户作用域）把明文加密后存回 `host.json`**，
   新增字段 `token_protected`，`token_hash` 保留不动。
2. 这不是「把明文写盘」——**加密后的密文 + 操作系统的用户密钥**；而且**威胁模型没有变差**：
   神算子的库本来就是**未加密的 SQLite 文件**，能读到 `host.json` 的人早就能读到全部账目。
3. 失败路径必须**明确且不静默**：解不开（换了 Windows 用户 / 换了机器）⇒ 当作「没有明文」，
   界面说「这台电脑换了用户或换了机器，需要重新生成一次配对码」——**绝不悄悄换令牌**。
4. 老文件（只有哈希）行为**完全不变**：升级后第一次「重新生成」才写入 `token_protected`。
5. **不做**：不做跨机器可解密（那等于把密钥也存盘）、不做 `CRYPTPROTECT_LOCAL_MACHINE`
   （任何本机用户都能解，等于没加密）、不做「把明文写进配置文件」。
6. 与提案 56 的关系：**互补，不互相替代**。写不进 `host.json` 时 DPAPI 也救不了；
   但 DPAPI 成功之后，「每次开机重扫」这个真实痛点就消失了 —— 即使写盘偶发失败，
   也只需要重试一次而不是重新配对全部手机。

### English

Recommended: **Windows DPAPI (current-user scope)**, encrypting the plaintext token into a new
`token_protected` field in `host.json`, keeping `token_hash` as-is. This is not "plaintext on disk":
it is ciphertext bound to the OS user key, and the threat model does not get worse — the database
itself is an unencrypted SQLite file, so anyone who can read `host.json` can already read every
ledger entry. Failure must be loud, never silent: if decryption fails (different Windows user or
machine) treat it as "no plaintext" and tell the user to regenerate once. Old hash-only files keep
today's behavior exactly. Explicitly not doing: cross-machine decryption (that means storing the
key), `CRYPTPROTECT_LOCAL_MACHINE` (any local user could decrypt), or plaintext in a config file.

## ✅ 可行性已实测（2026-11-01，`tool/probe_dpapi.dart`）

**结论：Dart 直调 `crypt32.dll` 可行，7 条检查全过。** 不是纸上方案。

```
OK   CryptProtectData 成功
OK   CryptUnprotectData 成功
OK   往返字节一致
OK   密文不含明文
OK   熵不符 ⇒ 解密失败
OK   篡改 1 字节 ⇒ 解密失败
OK   不带熵：往返一致
通过 7，失败 0
```

### 实测踩到的两个坑（实现时必须知道）

| 坑 | 现象 | 真相 |
|---|---|---|
| **`DATA_BLOB` 字段顺序** | `CryptProtectData` 返回 0，`GetLastError = 998 (ERROR_NOACCESS)`，四种参数组合全都一样 | 结构体是 **`cbData` 在前、`pbData` 在后**（`CRYPTOAPI_BLOB { DWORD cbData; BYTE *pbData; }`）。写反了 Windows 把「指针的低 4 字节」当长度去读 |
| **`LocalFree` 不在 `crypt32`** | `Failed to lookup symbol 'LocalFree'`（错误 127） | 它在 **kernel32**；DPAPI 的输出缓冲区由系统分配，必须还回去 |

> 第一条尤其值得记：**类型系统完全不报错**，只能靠 `GetLastError` 看出是「内存访问无效」。
> 用 `package:win32` 可以绕开这个坑，但本仓不想为一个函数引一整个包 ——
> 直调 + 探针脚本（`tool/probe_dpapi.dart`）已经证明够用，且探针可复跑。

## 一、现在为什么画不出码（事实）

| 事实 | 出处 |
|---|---|
| 主机只持久化 `sha256(明文)` | `HostIdentity.toJson()` 只写 `host_id` / `token_hash` / `created_at` |
| `load()` 读回的 `plaintextToken` 恒为 `null` | `HostIdentity` 的字段注释与实现 |
| `canShowQr` 据此判断，重启后必为 `false` | `HostIdentity.canShowQr` |
| 要再画码只能 `reset()` | `HostIdentityStore.reset`（轮换令牌，旧令牌立刻失效） |
| 后果 | 已配对手机全部要重扫；用户每天开机一次 |

> 注意：**校验不需要明文**（哈希足够），所以「手机还能连」这件事**今天已经成立**；
> 画不出码只是「没法再给新手机扫码」，以及 UI 逼着用户点「重新生成」——
> **而那个按钮才是把手机踢下线的元凶**。

### English

The host persists only `sha256(token)`; `load()` always returns `plaintextToken == null`, so
`canShowQr` is false after restart. Verifying a client never needs the plaintext (the hash suffices),
so "paired phones still work" is already true today — what is missing is the ability to *show* the
QR again. The real damage is the UI pushing the user to press "regenerate", which rotates the token
and kicks every paired phone offline.

## 二、目标与非目标

**目标**

1. 重启后**能画出与上次完全相同的令牌**（同一个 `host_id` + 同一个明文）。
2. 已配对手机**不需要重扫**，重启后仍能 pull / push。
3. 解不开时**说清楚**，且**不静默换令牌**。

**非目标**

1. 不解决「`host.json` 写不进去」（那是提案 56；两者互补）。
2. 不做跨机器可解密（换机器就该重新配对一次，这是**正确**的安全语义）。
3. 不改变令牌轮换的语义（「重新生成」仍然会作废旧令牌 —— 那是它的职责）。

### English

Goals: the same QR after restart; paired phones keep working without re-scanning; loud, non-silent
failure. Non-goals: fixing the write failure (proposal 56), cross-machine decryption (re-pairing on a
new machine is the *correct* semantic), and changing what "regenerate" means.

## 三、四个方案对比

| # | 方案 | 重启后能画码 | 明文落盘 | 换机器 | 成本 | 结论 |
|---|---|---|---|---|---|---|
| **A** | **DPAPI（当前用户）加密后存 `token_protected`** | ✅ | 密文 | 解不开 ⇒ 要求重生成一次 | 中（一次 FFI + 迁移） | **推荐** |
| B | 明文直接写进 `host.json`（或另存 `token.txt`） | ✅ | **明文** | 能用（跟着文件走） | 低 | ❌ 等于取消「只存哈希」的设计 |
| C | 只存哈希 + 保留「上一代哈希」宽限期 | ❌ 画不出码，但旧手机不会掉线 | 无 | — | 低 | 🟡 可作为 A 的补充（见 §七） |
| D | 不改（现状） | ❌ | 无 | — | 0 | 每天重扫，痛点持续 |

> **为什么 C 不够**：它解决「手机掉线」，但不解决「给新手机扫码」——
> 而用户之所以每天点「重新生成」，正是因为**界面上没有码**。
> C 可以作为 A 的兜底（A 解不开时用 C 的宽限期少伤一次），但单独用不解决问题。

### English

Four options compared: A DPAPI-encrypted blob (recommended), B plaintext on disk (defeats the
hash-only design), C previous-hash grace window (keeps phones online but still cannot *show* a QR),
D no change. C alone does not solve the user's problem; it can complement A as a fallback.

## 四、方案 A 的实现细节

### 4.1 文件格式（`host.json` v2，**向后兼容**）

```json
{
  "version": 2,
  "host_id": "01a1572b-…",
  "token_hash": "…",
  "created_at": 1730000000000,
  "token_protected": {
    "scheme": "dpapi-user-v1",
    "blob": "<base64 of DATA_BLOB>"
  }
}
```

- `version` 从 1 → 2；**读的时候不认版本号**（有 `token_protected` 就试，没有就走今天的老路），
  这样「老程序读新文件」也不会崩（只是忽略新字段 —— 与「字段只增不删」一致）。
- `token_hash` **必须继续写**：它是校验的唯一来源，也是解不开时的降级依据。

### 4.2 加密

- API：`CryptProtectData` / `CryptUnprotectData`（`crypt32.dll`，`dart:ffi` 直调；
  `package:ffi` 已在 lock 里，只需在 `shensuanzi_host` 的依赖里显式声明）。
- 作用域：**当前用户**（不加 `CRYPTPROTECT_LOCAL_MACHINE`）——
  加了它任何本机用户都能解密，等于没加密。
- 附加熵（optional entropy）：`sha256(host_id)` 的字节。
  ⇒ 密文与这个 `host_id` 绑定，**把 blob 挪到另一个 `host.json` 里解不出来**。
- 标志：`CRYPTPROTECT_UI_FORBIDDEN`（后台进程不许弹系统对话框）。
- 明文只在内存里出现，**不进日志、不进备份清单、不进错误信息**。

### 4.3 写 / 读 / 失败

| 时机 | 行为 |
|---|---|
| 生成 / 重置令牌 | 先算哈希，再加密；两者都成功才写文件。加密失败 ⇒ **只写哈希**（= 今天的行为）+ 日志 `protect=failed:<errno>` |
| 启动读取 | 有 `token_protected` ⇒ 解密 ⇒ `plaintextToken` 有值 ⇒ 能画码；解密失败 ⇒ `plaintextToken=null` + `lastReadProblem` 记原因 |
| 界面 | 能画码 ⇒ 照常显示二维码；解不开 ⇒ 一屏说明「这台电脑换了用户或换了机器，需要**重新生成一次**配对码（手机会需要重扫一次）」，**不自动重置** |
| 老文件（v1） | 行为与今天完全一致；下一次「重新生成」才升级到 v2 |

> ⚠️ **绝不自动重置**：自动重置会把「手机掉线」变成用户完全没预期的事故
> （与 `resetForNewHost` 的处置口径一致 —— 宁可停下来问，也不替用户决定）。

### English

File format v2 adds `token_protected` (scheme + base64 blob) and keeps `token_hash`. Encryption uses
`CryptProtectData` in current-user scope with optional entropy `sha256(host_id)` (binds the blob to
that host id) and `CRYPTPROTECT_UI_FORBIDDEN`. On write: hash + encrypt, both must succeed; if
encryption fails, fall back to hash-only (today's behavior) and log it. On read: try decrypt; on
failure record the reason and show "this PC changed user or machine — regenerate once", never
auto-reset. v1 files behave exactly as today until the next regeneration.

## 五、安全论证（为什么这不让情况变坏）

| 攻击者能力 | 现在 | 方案 A 之后 |
|---|---|---|
| 能读数据目录（同用户） | 能读全部账目（明文 SQLite）+ 哈希 | 同上，且能解密出令牌 —— **但令牌本来就在他手里能用** |
| 能读数据目录（**另一个** Windows 用户） | 能读全部账目 | 同上，**解不出令牌**（DPAPI 绑用户） |
| 拿到备份文件（拷到别的机器） | 有账目 | 有账目，**解不出令牌** |
| 只拿到 `host.json` 一个文件 | 只有哈希（无明文） | 有密文（无用户密钥 ⇒ 打不开） |

结论：**「同用户能读数据目录」这个前提下，安全边界没有变化** ——
库是明文，令牌只是「再多一个能用的凭据」，而那个凭据的**签发者就是这台机器上的这个用户**。
真正的收益是：**用户不再被迫每天轮换令牌**（轮换会让所有手机掉线，那是可用性事故）。

> 若将来要给库上加密（SQLCipher 之类），那时的威胁模型会变，本文需要重新评估 ——
> 记在这里，避免以后有人误以为「DPAPI 已经保护了令牌，所以库也可以明文」。

### English

Threat-model table: for an attacker who can already read the data directory as the same user, nothing
changes — the SQLite database is unencrypted, and the token is a credential issued by that very user.
For a *different* Windows user, or for a backup copied to another machine, the blob does not decrypt
at all. If the database is ever encrypted (SQLCipher etc.), this proposal must be revisited.

## 六、测试与验收

| # | 用例 | 判据 |
|---|---|---|
| 1 | 生成令牌 ⇒ 读回 | `load().plaintextToken` 与生成时相同；`authorizes()` 为真 |
| 2 | 加密 → 解密往返（纯函数层） | 字节一致；篡改 1 字节 ⇒ 解密失败（不返回垃圾） |
| 3 | 解密失败（blob 被换 / 熵不符） | `plaintextToken == null`、`canShowQr == false`、`lastReadProblem` 有值、**不重置令牌** |
| 4 | 老文件（无 `token_protected`） | 行为与今天完全一致 |
| 5 | 加密 API 不可用（模拟 FFI 失败） | 只写哈希 + 日志 `protect=failed`，功能不退化 |
| 6 | 明文不落日志 | 生成后 grep 日志文件，**不含**明文令牌 |
| 7 | 端到端（真机） | 连续两次重启，二维码里的令牌**逐字相同**；已配对手机重启后仍能同步 |

**总验收**：同一台机器连续重启两次，二维码内容不变、手机不用重扫；
把 `host.json` 拷到另一个 Windows 用户下，界面说「需要重新生成一次」而不是崩或静默换令牌。

### English

Seven cases: round-trip, tamper detection, decrypt failure (no auto-reset), legacy file unchanged,
encryption unavailable (degrade to hash-only), no plaintext in logs, and an end-to-end restart test
where the QR content is byte-identical and paired phones keep syncing.

## 七、风险与可选的补充

| 风险 | 处理 |
|---|---|
| 用户换了 Windows 账户 / 重装系统 | 解不开 ⇒ 说明 + 重生成一次（**手机要重扫**，一次性的） |
| 数据目录被拷到另一台电脑 | 同上（这是**期望**行为：换机器该重新配对） |
| DPAPI 在极老系统上不可用 | 降级为只写哈希（今天的行为），日志记一次 |
| 用户把整个目录发给别人排障 | 对方解不开令牌，但仍能看到账目 —— **与今天一样**，不新增泄露面 |

**可选补充（方案 C 的一部分）**：在 `host.json` 里再留一个 `token_hash_previous`（上一代哈希），
校验时两个都认，**有效期 30 天**。这样即使 A 失败、用户被迫重置一次，手机也有一个缓冲窗口
（重置后旧手机还能连 30 天，用户有空再扫码）。**这一条独立于 A，可单独裁。**

> 但要注意：`token_hash_previous` 会让「作废旧令牌」不再即时生效 ——
> 若某台手机是**被偷了**，用户点「重新生成」时期望它立刻失效。所以宽限期必须**可关**
> （例如「重新生成」时给一个勾选「让旧设备立即失效」）。

### English

Risks and mitigations: changed Windows account or reinstall → decrypt fails → one-time regeneration
(expected, re-pair once); directory copied elsewhere → same; very old systems → degrade to hash-only.
Optional add-on (part of option C): keep `token_hash_previous` accepted for 30 days so a forced reset
does not instantly disconnect phones — but this weakens "revoke immediately", so it must be
opt-out-able when the user regenerates after losing a phone.
