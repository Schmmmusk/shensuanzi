# 图表大库测试 + 启动耗时实测报告（2026-11-01）

> 起因：用户 2026-11-01 提出「图表没参与大库测试，如果严重失真则考虑引入对数刻度」，
> 并在随后的真机联调里报了两件事：**库存页搜索框被压货榜挤下去**、**启动黑屏 10 秒**。
> 本报告给这三件事的实测数据与结论。**都不需要改产品逻辑**（一处 UI 已改，见 §3）。

## 一、方法

| 项 | 做法 |
|---|---|
| 数据 | `D:/perf-data/mirror-v7.db`（26.4 万单 / 37.0 万明细 / 300 商品 / 200 往来方 / **546 MB**），与性能基线同一份 |
| 图表 | 新增探针 `tool/chart_scale_probe.dart`：**不画图，只算像素** —— 用真库算出原始数字，再按真实渲染规则（`RatioBar`：比例照实算、最少 4px；营收柱：高度 = 金额 × 单位、无下限）换算，统计「有多少条看不出差别」 |
| 启动 | `adb shell am start -W`（到首帧）+ `SSZ_STARTUP_TRACE` 分段埋点（T0/T1/T4/T2/T3） |
| 真机 | Redmi 2312DRA50C / Android 14；网络＝**手机开热点给电脑**（电脑 WLAN `192.168.45.56`） |

## 二、图表：**没有失真，不建议上对数刻度**

| 图 | 真实数据 | 手机端像素 | 判断 |
|---|---|---|---|
| 近 30 天营收（按周，5 桶） | ¥418,982 / 1,622,078 / 2,409,220 / 4,115,090 / 0 | 柱高 **10.6 / 41.0 / 60.9 / 104 / 0** px | 没有 <1px 的柱；最大/最小非零 ≈ 9.8:1 |
| 压货榜 Top10 | ¥12,964 ~ ¥17,600（**1.36:1**） | 241 ~ 328 px | **没有一条触底 4px**，长度差肉眼可辨 |
| 应收 / 应付 | ¥9,255.57 vs ¥24,454,744.60（**2643:1**） | 应收 **0.1px → 触底 4px**，应付 328px | 唯一严重失真处，但**它是诚实的** |

真机截图复核：营收图金额标签自动退让（去千分位 → 去 `¥`）**没有重叠**；
压货榜 10 行条形长度差异可辨。

**结论：不上对数刻度。** 三条理由：

1. 三张图上每根柱、每行**都写着金额**（规则 1：不让人从高度反推）—— 长度只是「一眼感」；
2. 对数刻度会让「两倍金额 ≠ 两倍长度」，与本仓已经踩过**两次**的「抬 4% 下限」是同一类错误（图会暗示一个不存在的比例）；
3. 压货榜取的是分布**最高端**（Top10），天然不会极端；营收图 5 根柱都 >10px。

> 唯一值得盯的是欠款横条那种 2643:1（真实店铺也会出现）。但它只有两条、数字并排，
> 目前判断「不该为极端情况牺牲可比性」。若日后要动，**只动这一处**，别碰营收图与压货榜。

## 三、压货榜：默认收起（用户当场指出，已改）

A1 把完整压货榜放库存页最上面之后，10 行榜有半屏高 ⇒ **搜索框被顶到榜下面**，
而库存页 95% 的用法是「搜一个商品」。现在默认**收起成一行摘要**：

```
⌄ 压货最多的 10 个商品                    最多 ¥17600.17
  洗洁精（5）10卷 · 按占用资金排，点开看全部
```

点开才是完整卡 + 「收起压货榜」。「从概览跳过来定位压货榜」仍然成立（那一行就是榜）。

顺手修掉一个自己写出来的崩溃：`_stockTop.isEmpty` 是「行 + 待校准 + 负成本」三者皆空，
所以「非空但一行都没有」是可能的 —— 收起态取 `rows.first` 直接 `Bad state: No element`。
现在那种情况直接展开完整卡。测试 +1（库存页 30 条）。

## 四、启动耗时：**不是回归，是冷缓存**

| 场景 | 结果 |
|---|---|
| **release + 546 MB 库（热缓存）** | **1708 / 1541 ms** —— 与性能基线（1.34~1.55 s）一致 |
| debug + 546 MB 库（热缓存） | 5.4 s（其中 Dart 侧只有 1.6 s） |
| debug + 空镜像 | 4.7 / 5.1 / 4.9 s |
| 冷缓存（刚把 546 MB 拷进手机） | ~10 s |

debug 包分段（`SSZ_STARTUP_TRACE`）：

| 点位 | 时刻 |
|---|---|
| T0_main | 0 ms |
| T1_run_app | 219 ms |
| **T4_first_frame** | **1502 ms** |
| T2_db_open | 1592 ms |
| T3_services / T3b | 1600 / 1608 ms |
| overview 首帧 / 稳定 | 735 / 1790 ms |

**结论：启动没有退化，不做优化。** 用户看到的 10 秒＝我刚把 546 MB 库拷进手机、
页缓存全冷，同时还在一边截图一边轮询。热起来就是 1.5~1.7 s。
要留的护栏：**别在刚拷完大库后测启动**。

### 顺带修掉：埋点在 Android 上一直是哑的

`SSZ_STARTUP_TRACE` 编进去了，但 `startup-trace.jsonl` 一行都没有。
根因：`defaultFile()` 读 `Platform.environment['APPDATA']`（Windows 写法），
Android 上为空 ⇒ 退回 `Directory.systemTemp`（Android 上是 `/tmp`，不存在也不可写）
⇒ 写盘抛异常被 catch 吞掉 ⇒ **静默失效**。
改成「跟着数据库走」：`<数据目录>/日志/startup-trace.jsonl`
（`StartupTrace.traceFileFor`，纯函数 + 测试）。

## 五、⚠️ 联调纪律（本轮教训）

用户手动测试期间我在跑启动耗时循环（`am force-stop` + `am start`），
把他两次启动**当场掐掉**（`ApplicationExitInfo` 证据：22:18:05 / 22:18:18 两条
`reason=10 USER REQUESTED / subreason=21 FORCE STOP`），他看到的是「黑屏后直接退出」。

⇒ **真机联调时双方先说一声谁在用**；抓数据的一方不许在对方点的时候反复 force-stop。
