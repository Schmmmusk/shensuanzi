## 三、「7.1 秒」这笔账拆开看

`samples.csv` 有 `fg_title` 列（前台窗口），这一列在本轮是决定性的：

| 时刻 | CPU | 读累计 | 前台窗口 | 说明 |
|---|---|---|---|---|
| 22:23:08–22:23:29 | 35–44% | 111.6 MB | 神算子 | 启动 → 概览（事件 #1/#2） |
| 22:23:29 | — | — | **切到控制台** | 用户去看监控输出 |
| 22:23:30–22:24:03 | **0.0%（34 秒）** | **238.6 MB 不动** | **控制台** | 应用完全静止 |
| 22:24:03 | 0.0% | 238.6 | 控制台 | `e` 记下「7.1 s」 |
| 22:24:04 | 71.3% | **450.0 MB（+212）** | **神算子** | 活从这一刻才开始 |
| 22:24:05–07 | 14–29% | 462.1 MB | 神算子 | 事件 #3，实测 **2.02 s** |

⇒ **只能认 2.02 s。** 那 34 秒里应用既没有 CPU 也没有 IO，连前台都不是它。

同一形状在三处重复：

| 用户记录 | 应用实测 | 记录时刻的前台 |
|---|---|---|
| 库存页 7.1 s | 2.02 s | 控制台 |
| 看商品单据 3 s | 1.03 s | 控制台 |
| 切单据页 0.9 s | 0.44 s | 控制台 |

⚠️ **注意别读反了**：三条记录的前台都是控制台，是因为**人要敲 `e` 才能记**。
它不是「应用一直不在前台」的证据。真正能用的只有 22:23:30–22:24:04 这一段
（连续 34 秒、跨 170 个采样点，应用零活动）。

**两种解释，现有数据分不开**：
① 点击没有及时送达 / 窗口激活延迟 7 s（VM 输入与显示管线）；
② 用户先看监控输出，22:24:03 才点回去，2.02 s 就是全部代价。

## 四、2.02 s 本身也不是 SQL 慢

| 事实 | 值 | 出处 |
|---|---|---|
| `stock_group` p50 | **39.1 ms** | `baseline-after.csv`（本机、20 轮、缓存热） |
| `in_transit` p50 | **70.1 ms** | 同上 |
| 库存页**一次进入**的读量 | **212 MB** | 22:24:04 一秒内累计读跳变 |
| 单据页/库存页大读事件 | 244.8 MB / 245.1 MB | 事件 #15（7.13 s）/ #20（3.71 s） |

39 ms 与「秒级」差的不是算法，是**页缓存**：39 ms 是在库全热时量的；
冷缓存下同一批扫描要从虚拟 SATA 读几百 MB。用户 22:31:46 的原话
——「page cache 感觉起来了，切页不卡了」—— 与这条完全吻合。

**读放大从哪来**（代码事实，`lib/src/ui/stock_page.dart`）：

```dart
void initState() { _stockTop = widget.queries.stockTop(); }   // :170  ✅ 算一次
Widget build(...) {
  final agg = widget.queries.stockAggregates();               // :286  ❌ 每次重建都全表聚合
  final inTransit = widget.queries.inTransitByProduct();      // :299  ❌ 同上
}
```

同一页三条全表聚合，**一条在 `initState`、两条在 `build`** —— 这是同构漂移
（纪律 18 的同款形状）。覆盖索引 `idx_stock_covering(product_id, seq_no, quantity, total_cost)`
已经在（v5），所以问题是**扫了几遍**，不是「没有索引」。

⚠️ 这仍是**假设**：一次 `build()` = 2 次索引全扫 ≈ 120 MB 读，要凑到 212–245 MB
需要 2–4 次重建。重建次数没有测过 —— 见 §六 第 3 条。

## 六、下一轮只需要改三件小事（都是测试方法，不动生产代码）

1. **构建必须 bump 版本号**：`pubspec.yaml` 仍是 `0.7.5+12`，两个**不同**的构建
   在日志里都自称 `v0.7.5` ⇒ 事后无法分辨谁是谁。本次就靠 `app.so` 时间戳
   才把这条补上。建议每次「要拿去实测」的构建至少 `0.7.5+N+1`。
2. **监控控制台别和被测窗口抢前台**：把 cmd 最小化，或输出重定向到文件
   （`perf_monitor.py run ... > out\log.txt`），让「点页面 → 上屏」这一段不被
   焦点切换污染。本轮 34 秒的空白就是被它吃掉的。
3. **给库存页加一条重建计数**（临时埋点即可）：`build()` 跑了多少次、
   `stockAggregates()` 被调了多少次。这是判定 §四 假设的**唯一**一条测量，
   而且比再跑一整轮 10 分钟便宜。→ **已落地，见 §八**

## 七、没做的

### 开关与代价

```bash
flutter build windows --release --dart-define=SSZ_PAGE_COST_TRACE=true
```

`kPageCostTrace` 是 `const bool.fromEnvironment` ⇒ **不传这个 define 时，
`_cost` 恒 `null`、Stopwatch 恒 `null`，三处调用被常量折叠掉**，正式包行为不变
（与 `SSZ_STARTUP_TRACE` 同一套机制，同一套「埋点不许拖慢被埋的东西」的约束）。

计数期间**不碰磁盘**，只在**离开库存页**时追加一行 JSONL：

```json
{"kind":"pagecost","ts":"2026-11-09T22:24:03.120","page":"stock",
 "builds":3,"spanMs":2010,"aggMs":118,"transitMs":211,
 "perBuild":[[0,39,70],[812,40,71],[1600,39,70]]}
```

落点：`<数据目录>\日志\page-cost.jsonl`（与 `startup-trace.jsonl` 同目录，用户只拷一个文件夹）。

### 判据（跑完直接看这几个数）

| `builds` | `aggMs` | 结论 |
|---|---|---|
| 1–2 | 几十毫秒 | §四 假设**作废** —— 读放大另有来源（要找 SQL / 索引） |
| ≥ 5 | 上百毫秒 | §四 假设**成立** —— 该把两条聚合挪出 `build()` |
| 任意 | 单次 ≥ 500 ms | **单条聚合本身就慢**（冷缓存）—— 那是磁盘问题，不是重建次数问题 |

⚠️ `perBuild[i][0]` 是「第 i 次重建距进入多久」，可以拿它对齐 `samples.csv` 的
时间轴，看那 212 MB 读量落在第几次重建上。

`_cost` 的三处调用、以及 `SSZ_PAGE_COST_TRACE` 一起删掉
（一个常开的诊断层留在生产里，迟早会有人拿它当功能用）。
