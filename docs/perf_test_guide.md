# 长时间使用性能实测 —— 测试手册

> 面向**外部测试人员**：一台与开发无关的机器、一份可随时丢掉的数据。
> 目标不是「找 bug」，是回答三个问题：
> **① 数据涨到 10 万行/表以后，软件还能不能用？②卡在哪一步？③卡的原因是库、是界面、还是机器？**
>
> 配套脚本（`tool/` 下，Python 3.8+，**只用标准库**）：
> `perf_seed.py`（造数）· `perf_bench.py`（库侧基线）· `perf_monitor.py`（人工实测记录）

---

## 〇、先说红线（违反了这一轮就白测）

1. **这份数据不是业务数据，不能用来验收「账对不对」。**
   造数脚本直写 SQL（测试机上没有 Dart 跑 RuleEngine），它按规则的口径拼出了自洽的账，
   但不执行任何业务校验。**功能验收看 `docs/desktop_acceptance.md`，不要用这批数据判对错。**
2. **必须用一份独立的数据目录**（例如 `D:\perf-data`）。
   它会写 10 万行以上的单据与流水、库可能到几百 MB；**绝不要指向正在用的正式账套**。
3. **脚本不会启动、也不会结束软件进程。** 软件由你开、你关。
4. **一轮测试期间，别同时做大数据量拷贝/杀毒全盘扫描/系统更新** —— 那些会把 I/O 抢走，
   测出来的数字不能归因给软件。真发生了就在备注里写清楚。

---

## 一、交付物与摆放

把下面 4 个文件放在**同一个目录**（例如 `D:\perf-tools\`）：

```
perf_seed.py          造数（写 10 万+/表）
perf_bench.py         库侧查询基线（只读）
perf_monitor.py       人工实测实时记录（只读）
seed_test_data.py     被上面复用：加载 schema / 指纹校验（别删）
schema_snapshot.json  离线 schema（测试机上没有源码时靠它）
```

> 为什么必须带上后两个：`perf_seed.py` **不内嵌建表语句**，它从 `schema.dart`（开发机）
> 或 `schema_snapshot.json`（测试机）读，并且校验指纹 —— 这是为了防止「用旧结构建了新库」。

## 二、环境准备（10 分钟）

| 项 | 要求 | 为什么要管 |
|---|---|---|
| 系统 | Windows 10 / 11 目标机（就是你要测的那台） | — |
| Python | 3.8+（`python --version` 能打印即可） | 脚本只用标准库，不装任何包 |
| 磁盘 | 准备 **≥ 3 GB 空闲**（造数 + 备份 + 导出） | 单表 10 万行后库约 300–500 MB；每次启动还会自动备份一份 |
| 电源 | **「高性能」**，不要「节能」 | 节能会把 CPU 降频，测出来是电源策略的锅 |
| 缩放 | 记录系统的显示缩放（100% / 125% / 150%）与软件里的「界面大小」档位 | 这两者叠加会显著影响界面耗时 |
| 杀毒 | 记录是否开启实时防护；**建议造数时临时关闭**，人工实测时按真实环境（开着） | 造数慢是杀软在扫，不是软件慢 |
| 其它 | 关掉浏览器大页签、微信大文件传输、Windows 更新 | 抢 I/O 与 CPU |

**记下这台机器的三件事**（写进报告）：CPU 型号与核数、内存大小、**磁盘是机械还是固态**。
这三个决定了「这台机器该有多快」。

## 三、五步流程

```
① 让软件自己建一次数据目录          （1 分钟）
② perf_seed.py 造数 + 自检           （3–10 分钟）
③ perf_bench.py 基线（前）            （1 分钟）
④ perf_monitor.py + 人工点一遍        （20–40 分钟）
⑤ perf_bench.py 基线（后）+ 交回文件  （1 分钟）
```

### 第 ① 步：先让软件建目录

1. 打开神算子 → 选一个**新的**数据目录（如 `D:\perf-data`）→ 「开始使用」；
2. 看到主界面后**关掉软件**。

> 这一步的作用：拿到软件的标记文件、配置、备份目录，以及一份**与软件同版本**的库结构。
> 有了它，第 ② 步不依赖 `schema_snapshot.json` 也不会出错。

### 第 ② 步：造数

```bat
cd /d D:\perf-tools
python perf_seed.py --data-dir "D:\perf-data" --dry-run
```
先看计划：会打印「预计需要单据约 N 张、全部行约 M 条、库约 X MB、耗时约 T 秒」。
确认目标目录是那个测试目录后，去掉 `--dry-run` 正式跑：

```bat
python perf_seed.py --data-dir "D:\perf-data"
```

预期（默认参数，**开发机 NVMe 实测**；测试机按磁盘类型外推）：

| 项 | 量级 |
|---|---|
| 每张流水表（明细/库存/资金/往来/核销） | **≥ 100 000 行**（`settlements` / `money_ledger` 刚好压线，其余远超） |
| 单据 | 约 **26 万**张（含自动生成的收付款单） |
| 明细 / 库存流水 | 各约 **37 万**行 |
| 往来流水 | 约 **26 万**行 |
| 商品 / 往来方 / 账户 | 300 / 200 / 4 |
| 时间轴 | 2 年；最近 7 天有加密的单 |
| 全部行数 | 约 **146 万**行 |
| 库文件 | 实测 **476 MB**（约 343 字节/行） |
| 耗时 | 开发机 **57 秒**；机械盘预计 **5–15 分钟** |

跑完会打印一张**自检表**（B4/B5、seq_no 无洞无重、单号唯一、收付款必有账户……）。
看到 `✅ 自检全过，可以用作性能基线。` 才算成功；出现 `❌` 就把输出整段留下交回。

可选开关：

| 开关 | 用途 |
|---|---|
| `--min-rows 200000` | 每表 20 万行（更接近 5 年老店） |
| `--days 1095` | 时间轴 3 年（默认 730 天） |
| `--products 800` | 商品数（测「商品多时库存页/选择器」） |
| `--stress-docno` | **最后一天故意造 >999 张同类型单**，用来复现「单号第 1000 单撞号」的已知缺陷 —— 这一轮**不要**加，单独跑一轮再用 |
| `--allow-nonempty --confirm-wipe` | 在同一目录重造（清空六张业务表，主数据保留） |

### 第 ③ 步：库侧基线（造完立刻跑，软件不要开）

```bat
python perf_bench.py --data-dir "D:\perf-data" --csv before.csv --explain
```

它会跑 15 条「界面背后真正执行的查询」，给出 p50/p95，并把 `EXPLAIN QUERY PLAN` 打出来。
**这一步的数字是「软件没开时的库」**，用来和人工实测期间的探针对照。

> `--explain` 的输出请一起交回 —— 它能直接回答「索引有没有用上」。
> 例如 `pull_window` 应该走 `idx_documents_updated`；如果显示 `SCAN documents`，就是缺陷。

### 第 ④ 步：人工实测（核心）

> 开测前先跑一次 `python perf_monitor.py selftest`（两秒钟，不需要软件）：
> 它用合成数据检查「进程发现」和「动作识别」的逻辑没被改坏。不过就别测了 ——
> 识别逻辑坏了的话，一整轮数据都是废的。


**开两个窗口**：一个开软件（建议最大化，别最小化——最小化会停掉绘制），另一个跑记录器。

```bat
python perf_monitor.py run --data-dir "D:\perf-data" --out D:\perf-run1 ^
  --label "老机器-机械盘-第1轮" --app-version 0.6.4 ^
  --session-note "Win10/4GB/机械盘/杀软开着/系统缩放125%/应用150%"
```

### ⭐ 这一版**不用按键**（2026-10-27 改）

脚本自己找进程、自己识别操作。你只管照清单用软件。

| | 以前 | 现在 |
|---|---|---|
| 找进程 | 要 `--process shensuanzi.exe`，改过名就找不到 | **按窗口标题「神算子」自动找**，改名也认 |
| 记动作 | 每个动作前敲 `s 库存页`、做完敲 `e` | **什么都不用敲** |
| 耗时来源 | 人按秒表（误差 0.3–0.5 秒） | 脚本按 0.2–0.5 秒采样自己算，**误差 = 采样间隔** |
| 漏记 | 忘了按就少一条 | 有读写就会记，漏不了 |

**它认的是「机器在忙」这一段**（CPU / 读库 / 写库），不是「你点了哪个页面」——
软件窗口标题是固定的，脚本看不到页面。所以报告里写的是
「**读库/界面重建**」或「**写库**」，**不冒充**页面名。这是刻意的：
宁可说"我不知道你在哪页"，也不编一个像真的的标签。

判据（都能调）：

| 信号 | 默认阈值 | 含义 |
|---|---|---|
| CPU | ≥ 25%（单核=100%） | 在算 |
| 读 | 单次采样 ≥ 2048 KB | 在读库 |
| 写 | 单次采样 ≥ 256 KB | 在写库 |

低配机跑不动大查询、阈值偏严时，加 `--busy-cpu 10 --busy-read-kb 512` 重测。

**想给它贴名字**（可选，做了报告会给出「自动 vs 人工」的偏差，顺便验证识别准不准）：

```
s 库存页                ← 点「库存」之前按回车（开始计时）
（在软件里点「库存」，等列表出来）
e 3 列表出来前有半秒白屏   ← 结束计时；3=卡顿，后面是备注
```

**观感（1–5）只能人给** —— 脚本能测「用了 1.8 秒」，测不出「你觉得能不能忍」。
所以清单里至少**挑 3–5 个关键动作**按一次 `e` 填观感，其余交给自动识别。

**观感定义（必须统一，否则跨机器不可比）**：

| 分值 | 含义 | 参考 |
|---|---|---|
| 1 顺畅 | 点下去立刻有反应 | < 0.3 s |
| 2 一般 | 有短暂等待，但不影响操作 | 0.3–1 s |
| 3 卡顿 | 明显等一下，能察觉 | 1–3 s |
| 4 明显卡顿 | 等到怀疑没点上 | 3–10 s |
| 5 无响应 | 出现「未响应」/转圈很久 | > 10 s |

**如果软件占满全屏、不方便切窗口**（只想贴名字时用；不贴就不用管）：另开一个命令行，
用 `mark` 往同一个 spool 写（`run` 要带 `--spool D:\perf-run1\events.jsonl`）：

```bat
python perf_monitor.py mark --spool D:\perf-run1\events.jsonl --action 库存页 --start
python perf_monitor.py mark --spool D:\perf-run1\events.jsonl --action 库存页 --end --duration 1.8 --feel 3 --note "半秒白屏"
```

记录器那边的 `run` 会自动读到（每次采样轮询一次）。

**做清单时注意**：

- 每次动作**只测一件事**（别「一边导出一边开单」）；
- 同一动作**做 3 次**，取最差的一次记 `e`（数据只记一条，备注写「第 2 次最差 4.2s」）；
- 冷启动要**真的关掉软件**再开（第一次 page cache 是空的，第二次是热的，两者都要测）；
- 出问题时**先按 `m` 记一句**（时间点 + 现象），再决定要不要继续。

结束时按 `q` → 自动生成：

```
D:\perf-run1\
  report.md        汇总与判读（先看这个）
  samples.csv      逐采样点（Excel 直接开）
  events.csv       人工动作与备注
  session.json     会话元信息
```

### 第 ⑤ 步：收尾

1. **关掉软件**，再跑一次基线：
   ```bat
   python perf_bench.py --data-dir "D:\perf-data" --csv after.csv --explain
   ```
2. 把下面五样交回（见「六、交回清单」）。

## 四、结果怎么读

### 4.1 `report.md` 的六节

| 节 | 看什么 |
|---|---|
| 一、会话 | 机器/版本/时长/库大小 —— **先确认这轮的条件**，否则数字没法比 |
| 二、人工动作 | 每个动作的用时（脚本计时）+ 你的观感 + 判定（超过门槛会标 ⚠️） |
| 三、采样摘要 | CPU/内存/句柄/库体积/WAL 的 min-p50-p95-max 与首末变化 |
| 四、探针 | 库当时有多快（p50/p95） |
| 五、自动判读 | 脚本给出的线索（**不是结论**）：超过 2 秒的动作、持续高 CPU、内存上涨、WAL 偏大、采样缺口 |
| 六、覆盖 | 18 项标准动作做了几项（没做的会列出来） |

### 4.2 `samples.csv` 列含义（挑常用的）

| 列 | 含义 | 怎么用 |
|---|---|---|
| `interval_ms` / `gap_ms` | 与上次采样的间隔 / 超出预期的部分 | `gap_ms > 0` = 那一刻整机被压住（客观证据） |
| `cpu_pct` | CPU，**单核 = 100%**（12 核全满 ≈ 1200%） | 持续 > 100% 说明在算；接近 0 却卡 = 在等 I/O |
| `rss_mb` / `private_mb` | 工作集 / 私有内存 | 长时间单调上涨 = 疑似泄漏 |
| `handles` / `threads` | 句柄数 / 线程数 | 只涨不落 = 资源没释放 |
| `db_mb` / `wal_mb` | 库与 WAL 体积 | WAL 长期几百 MB 不回落 = checkpoint 有问题 |
| `probe_*_ms` | 三条只读查询耗时 | 与 `before.csv` 对比，判断「库变慢了」还是「界面变慢了」 |

### 4.3 判读门槛（本轮建议值，可在命令里改）

| 场景 | 门槛 | 说明 |
|---|---|---|
| 人工动作 | > 2 s 标 ⚠️ | `--slow-action 2` |
| 持续高 CPU | 连续 3 个点 ≥ 85% | `--cpu-busy 85` |
| 内存 | 首末涨 ≥ 30% 且 > 100 MB | `--rss-growth 30` |
| 采样缺口 | 间隔 > 2.5 倍 | 说明整机被压住 |
| 库侧探针 | 与 `before.csv` 比 p95 涨 ≥ 2 倍 | 需要两份 CSV 对照 |
| **`perf_bench` 门禁** | `count_roots` p95 > 120 ms 或 `list_roots` p95 > 200 ms ⇒ **退出码 4** | 这两条是单据页每帧真正跑的；调参时加 `--no-gate` |

> 门槛可以按机器放宽（老机器 4 秒也许算正常），**但同一轮里必须统一**，
> 并在 `--session-note` 里写清。

### 4.4 什么算「可复现的退化」

同时满足三条才算：

1. **同一动作、同一数据量、同一档缩放**下，用时比参照机高 ≥ 2 倍；
2. `samples.csv` 里那一刻有对应的客观信号（CPU 打满 / I/O 等待 / gap）；
3. 换一次会话还能重现。

只有第 1 条没有 2、3 的，先记成「观察」，别急着报缺陷。

### 4.5 参考基线（开发机实测，只用来判断「量级对不对」）

下面这份是用**默认参数**造的库（26 万单 / 36.6 万流水 / 476 MB）在开发机（NVMe、12 核）上
跑出来的。测试机的数字**本来就会更差**，它只用来回答一个问题：
**「我这边的数字是不是离谱？」**

| 查询 | p50 | 说明 |
|---|---|---|
| `stock_group`（库存合计） | **1346 ms** | 库存页「账面」、开单页库存快照 |
| `stock_cost`（成本余值） | **1346 ms** | 库存页「成本（均价）」 |
| `party_balances`（往来余额） | **620 ms** | 往来方页、概览「应收合计」 |
| `recent_products` | 417 ms | 开单页商品选择器（最近使用） |
| `doc_search` | 356 ms | 单据页搜索（四路 LIKE） |
| `list_documents` | 303 ms | 单据列表首屏 |
| `today_summary` | 269 ms | 概览「今日销售」 |
| `in_transit` | 87 ms | 库存页「在途」 |
| `account_balances` | 64 ms | 账户页余额 |
| `pull_stock` / `pull_documents` / `pull_window` | **< 1 ms** | 同步分页与窗口（索引对得上） |
| `lines_of_page` / `settled_counts` | < 1 ms | 本页明细、本页核销笔数（批量形状正确） |

> ✅ **前两条 1.3 秒已于 2026-10-24 修掉（schema v5，§CV·九十八）**：`stock_ledger` 的聚合
> 当时走 `idx_stock_product_seq` 但**不覆盖** `quantity` / `total_cost`，每行都要回表。
> v5 把它加宽成 `idx_stock_covering(product_id, seq_no, quantity, total_cost)`、
> `party_ledger` 同理加宽成 `idx_party_covering` ⇒ **1336 → 35 ms（38×）**、
> **648 → 27 ms（23×）**，索引个数不变（换掉不是新增）。
> 在新库上重跑本脚本，`stock_group` / `stock_cost` 应在 **30–40 ms** 量级；
> 若又回到几百毫秒，先查 `--explain` 是不是**退化成了非 covering**（`query_plan_test` 会拦）。
>
> 反过来：如果你的 `pull_*` 也到了几十毫秒、`lines_of_page` 到了秒级，那说明**索引没被用上** ——
> 把 `--explain` 的输出一起交回。

## 五、常见问题

| 现象 | 原因与处理 |
|---|---|
| `⛔ 这个库里已经有 N 行业务数据` | 脚本在保护你。确认是测试目录后加 `--allow-nonempty`；要重造再加 `--confirm-wipe` |
| `⛔ 库的 schema 版本是 4，脚本支持 3` | 脚本与软件版本不匹配。两种情况：① 分发时忘了带上最新的 `schema_snapshot.json`（让开发跑 `python tool/gen_schema_snapshot.py` 重新生成）；② 你混用了新旧脚本 |
| `⚠️ 随脚本分发的 schema 快照已过期` | 开发机上会出现：脚本改用 `schema.dart` 解析，能继续跑；但**分发前必须重生成快照**。测试机上不会出现（没有源码） |
| `数据库操作失败（可能是库被软件占用 / 磁盘满）` | 关掉软件再跑。SQLite 同一时刻只允许一个写者 |
| 造数很慢 | 杀软在扫 → 临时关闭；机械盘 → 正常，10 万行/表可能要 10 分钟 |
| 每次启动很慢、磁盘占用翻倍 | **自动备份**在拷贝整库（这是已知设计：备份是同步拷贝，且 **距上次超过 24 小时**才会再备一次）。库 400 MB 时那一天的首启会多拷 400 MB —— 这正是本轮要量的东西，记进备注 |
| 库里全红（负库存） | 不应该发生。造数脚本会「出库前自动补货」；如果出现，把 `--verify` 的输出交回 |
| 库存页要好幾秒、开单页打字卡 | **这是本轮要量的已知缺陷**，不是测试环境问题：`stock_ledger` 聚合不覆盖列 ⇒ 36.6 万行时单次约 1.3 秒（见 §4.5）。照实记录，别归因给机器 |
| `perf_seed.py` 报「schema 快照已过期」 | 开发机上会出现（脚本改用 `schema.dart`，能继续）；**测试机上不会**，因为它没有源码、只用快照。分发前让开发跑 `python tool/gen_schema_snapshot.py` |
| 同类型单号到 1000 就报错 | **已知缺陷**（`latestDocNo` 按字典序取最大值）。用 `--stress-docno` 可以稳定复现，单独跑一轮，别混进干净基线 |
| Python 报中文乱码 | 用 `chcp 65001` 或在 PowerShell 里先 `$env:PYTHONIOENCODING='utf-8'` |
| `没找到进程 shensuanzi.exe` | 软件没开或进程名不同（看任务管理器）。也可以 `--pid <数字>` 指定；找不到时进程指标显示 `—`，其余照常记 |
| 记录器打不开进程（权限） | 用管理员权限运行命令行；或只测文件+探针（进程指标为 `—`） |
| `--duration` 没停 | 单位是**分钟**；`0.5` = 30 秒。默认 0 = 一直跑到你按 `q` |

## 七、启动埋点包（量「用户实际等多久」）

> **什么时候用它**：`perf_monitor` 量的是「进程忙了多久」，说不清「点一个页面到底等多久」。
> 要回答后者，打一个**埋点包**（编译期开关，正式包不含这些代码）。

### 7.1 打包

```bash
flutter build windows --release --dart-define=SSZ_STARTUP_TRACE=true
```

⚠️ **两次构建不要同时跑**（都写 `build/` 目录）：2026-10-28 就因此出现过一次「图标全没了」。
上一次构建结束再开始下一次。

### 7.2 跑什么（约 1 分钟）

1. 启动，**数据目录选造数库**（大库才有意义；小库全是 20 ms，看不出问题）
2. 等首屏出来，**停 3 秒**
3. 依次点：库存 → 单据 → 往来方 → 账户 → 商品 → **再回单据**
4. 每页**等它出来再点下一个**（连点会把两页的成本混在一起）
5. **商品页停住不动鼠标 3 秒**（这一条专门用来区分「真动画」与「鼠标 hover 重绘」）
6. 关掉软件

### 7.3 交回

```
%APPDATA%\神算子\日志\startup-trace.jsonl
```

每行一个 JSON，**不要手工改**（改过的数据不能用来下结论）。

### 7.4 字段怎么读

启动行（每次启动一行）：

| 字段 | 含义 | 正常量级 |
|---|---|---|
| `T0_main` | 进程进 `main` | 恒 0（计时器从这开始） |
| `T1_run_app` | `runApp` 之前 | 几 ms |
| `T4_first_frame` | **窗口出现** | 个位数 ms |
| `T2_db_open` | 开库 + 迁移完成 | 十几 ms |
| `T3_services` | 服务装配完 | 十几 ms |
| `T3b_backup_status` | 备份状态读完（含一次磁盘访问） | 正常几 ms；**几百 ms 以上 = 在等盘** |
| `db` / `dbMb` / `host` | **测的是哪个库、哪台机器** | 先看这三项，否则数据没法比对 |

切页行（每页两行）：

| 字段 | 含义 |
|---|---|
| `firstMs` | 第一帧画完（**下限**） |
| `settledMs` | 静默 500 ms / 到 10 秒硬上限（**用户体感对应这个**） |
| `frames` | 这段时间画了几帧。`settledMs ≈ firstMs` 且 `frames≈1` ⇒ 第一帧就是最终画面 |
| `timedOut` | `true` = 一直在动（转圈/动画），被 10 秒截断 |

**判读要点**：`settledMs` 才是「用户等了多久」；`firstMs` 只是下限，别拿它下结论。

### 7.5 跑完记得重打正式包

埋点包里带着时间戳代码（虽然只在 `--dart-define` 打开时编译进去）。
**交回数据后请重打一次不带开关的正式包**，否则 `packaging/make_release.py` 会把埋点包发出去。

### 7.6 怎么确认「正式包真的没有埋点代码」

```bash
grep -c "startup-trace" build/windows/x64/runner/Release/data/app.so    # 应为 0
grep -c "shensuanzi.db"  build/windows/x64/runner/Release/data/app.so   # 应为 1（对照，证明 grep 有效）
```

对照组必须有命中 —— 否则「搜不到」可能只是搜错了文件。

## 八、迁移测试（schema 变更必看）

> **前提**：测试机房的机器**离开后会被还原**（2026-10-29 用户说明）。
> 所以每一轮都要从零准备，**没有「昨天那个库还在」这回事**。

### 8.1 两条路，优先用甲

| 路径 | 做法 | 代价 |
|---|---|---|
| **甲（推荐）** | 先造一个**当前版本**的库 → 用 `tool/downgrade_to_v5.py` 降级成旧版本 → **用新包打开**它 | 不需要分发任何旧安装包；走的还是同一条迁移代码 |
| 乙 | 先装**旧预览版**建出旧库 → 造数 → 再装新包覆盖 | 要发旧包，且**旧库造数没有现成脚本**（造数脚本只认当前版本的快照） |

**为什么甲更好**：降级脚本做的三件事（删索引 → 删列 → 改 `user_version`）与 v6 迁移**严格互逆**，
得到的形状与真旧库逐字一致（`business_day` 在 `documents` 末列，删掉后列顺序不变）。
实测往返：v5 → v6 迁移 3.3 s、26.2 万行数据完整、回填 0 行错误、外键 0 违例。

### 8.2 甲路径的完整步骤

```bash
# ① 造一个当前版本的库（造数脚本原生支持）
python tool/perf_seed.py --data-dir "D:\ssz" --confirm-wipe

# ② 降级成旧版本（先 dry-run 看它要做什么）
python tool/downgrade_to_v5.py --db "D:\ssz\shensuanzi.db" --dry-run
python tool/downgrade_to_v5.py --db "D:\ssz\shensuanzi.db" --yes
#    ⇒ 应打印「降级完成：v5；business_day 已移除；idx_docs_bday_created 已移除」

# ③ 装新包、打开这个库 ⇒ 触发 v5→v6 迁移
```

### 8.3 验收判据（四条，缺一条都算没过）

| # | 看什么 | 期望 |
|---|---|---|
| 1 | 软件能正常打开、单据页能进 | 不弹错误边界、不白屏 |
| 2 | 数据目录里有 `shensuanzi.db.before-v5` | **必须有** —— 它是迁移失败时唯一的人工退路 |
| 3 | 单据数、单据行数与迁移前一致 | 用 `perf_bench --db ...` 打印的 `documents` / `document_lines` 对照 |
| 4 | 单据页排序仍对（今天的最新单在最上面） | 抽查两张：一张今天、一张补录的老单 |

**第 2 条特别重要**：迁移前会自动把库拷一份成 `.before-v5`（放在数据目录里，不是备份目录）。
**没有它就别往下测** —— 一旦迁移中途失败，没有退路。

### 8.4 迁移失败了怎么办

- 软件会**停在旧版本**（迁移逐版本、每版一个事务，失败的这一版整条回滚）；
- 下次启动会**从断点继续**，不是从头重来；
- 真要退回去：把 `shensuanzi.db.before-v5` 改回 `shensuanzi.db`（先删掉当前的）。
- **把当时的错误原文发回来** —— 迁移失败几乎总是某条 SQL 与真实老库形状不符，
  没有原文就只能猜。

### 8.5 为什么不再发「旧预览版」

- 旧包只能建出旧库，**造数还是要解决**（造数脚本读的是随仓的 `schema_snapshot.json`，
  它跟着当前版本走；给旧库造数会因为「版本不符」被拒）；
- 降级脚本只动结构、不写业务值，且**只作用于测试库**（有数据时会要求 `--yes`）；
- 少分发一个安装包，就少一个「装错版本」的变量。
