# 安全性测试

神算子的架构有几个**罕见特点**，它们直接决定了测试策略的形状：

| 特点 | 对测试的影响 |
|---|---|
| **离线优先，无中心服务器** | 没有服务端可测；安全性测试主战场在**本地存储 + 局域网 HTTP + 安装包供应链** |
| **Windows 主机即权威数据源** | 主机崩溃 = 全店数据不可用 → **稳定性测试的权重远高于普通桌面应用** |
| **SQLite 单文件 + WAL 模式** | 崩溃一致性、断电安全、文件句柄泄漏是**高发故障面** |
| **目标用户为技术弱势群体** | 用户不会上报 Bug，稳定性问题**只能靠自动化发现** |
| **局域网 HTTP（无 TLS）** | 信任边界明确但窄；测试重点在**未授权访问**与**端口暴露面** |
| **AGPL-3.0 开源** | 审计需要覆盖**第三方依赖的许可证合规性** |

### 安全性测试

**层次一：静态分析（每次提交前）**

- `flutter analyze` 已是项目唯一全仓 lint 门禁——保持 0 issues 是**第一道安全防线**（未使用导入、类型错误都可能掩盖真实问题）
- **密钥与凭证扫描**：全仓不能出现硬编码令牌、密钥、密码。当前 `HostIdentity` 只存 sha256、明文不进持久化文件，但**需要一条自动化断言持续守住**——已有断言在 `auth_test.dart`，但只测了“生成时正确”，没测“全仓没有其他硬编码密钥”。建议增加一个纯 Dart 扫描脚本（类似已有的 `import_guard.dart` 模式）
- **依赖漏洞扫描**：定期跑 `dart pub outdated` 和 `dart pub deps`，关注 `sqlite3` / `shelf` / `file_selector` 的 CVE。不引入自动化 CI 的前提下，**在 `README` 里记录依赖清单与最后核查日期**，每次发版前手动核对

**层次二：本地数据安全（每次发版前）**

这是神算子**最独特的测试面**——数据在用户自己的文件系统里：

| 测试项 | 具体断言 |
|---|---|
| **SQLite 文件权限** | Windows 上数据库文件不应被同机其他用户可读写（NTFS ACL） |
| **备份文件完整性** | 已有 `PRAGMA integrity_check`（§AE-1 加固），**但缺一条**：备份文件被篡改后恢复应当失败——当前 `integrity_check` 能查出结构损坏，但**加密场景下篡改检测**未覆盖（v1 不做加密，记在案） |
| **日志脱敏** | `AppLog` 是否记录了**经营数据**（商品名/金额/往来方）？当前设计声明“不记经营数据”，需要一条**自动化扫描**：用含敏感关键词的夹具跑一遍启动，检查日志文件里没有这些词 |
| **标记文件不可篡改** | `.shensuanzi-data` 被手改后，系统行为是否安全（当前是“读回 null 走向导”，安全） |

**层次三：局域网攻击面（仅在 AH-A 落地后需要）**

一旦 `shelf` 服务接通（批次 2）：

- **未授权访问**：无 Token / 错 Token → 401。已有测试，**但需要补充**：暴力穷举 Token 的速率限制（当前无速率限制——局域网内可信，但 AH-A 落地后值得加一个简单的延迟或锁定）
- **端口扫描面**：服务只监听局域网网卡（`data_model` 已声明），**需要一条断言**确认不会绑定 `0.0.0.0`（在 Windows 上绑定 `0.0.0.0` 会同时暴露给公网）
- **二维码泄露**：二维码含 Token 明文，**物理接触 = 泄露**。已在 `threat_model` 声明“不防”，但**UI 上应有“配对完成后隐藏二维码”的逻辑**，并测试

**层次四：安装包供应链**

- `LICENSE` + `THIRD_PARTY.md` 已存在，**但缺一条自动校验**：`make_release.py` 的 `EXTRA` 清单只检查文件存在，**不检查内容完整性**。建议增加“LICENSE 文件 sha256 与仓库内一致”的断言
- **构建可复现性**：`pubspec.lock` 已入库，`third_party/sqlite3` 需手动预置——**当前没有自动化校验**“新机器上的构建产物与旧机器一致”。v1 接受，但记在案
