
# 稳定性测试

**核心原则：神算子是“生意的基础设施”——它崩了，店里就做不了生意。稳定性测试的目标不是“找 Bug”，是“证明它不会在不该崩的时候崩”。**

**第一层：崩溃一致性（最高优先）**

- **WAL checkpoint 后的断电模拟**：已有测试覆盖“备份前 checkpoint”，但**缺一条**：模拟“正常写入过程中进程被杀”后重新打开数据库，数据是否一致。可以在 `selfcheck` 里加一个场景：写入一批单据 → 不关闭 Db → 直接 `Db.open` 同一文件（模拟崩溃恢复）
- **迁移失败的恢复**：已有测试覆盖（§AQ），但**缺一条**：迁移失败后，`before-v{N}` 备份**确实能用来恢复**的端到端测试（当前测的是“备份文件存在”，没测“恢复后数据可用”）
- **文件句柄泄漏**：已有 `Db.open` 失败后 dispose 的修复（§AN），但**缺一条**：连续 100 次打开-关闭数据库后，Windows 句柄数不增长。可以用 `Process.runSync('handle.exe')` 或纯 Dart 的 `File.open` 计数来验证

**第二层：长时间运行（“30 天法则”）**

行业实践表明，**在真实工作环境下连续运行 30 天**能暴露任何脚本测试都找不到的粗糙边缘。神算子不需要完整的 30 天 soak test，但可以做**一个最小的等价物**：

- **模拟连续 30 天的单据写入**：用脚本连续写入 1000 张采购单 + 1000 张销售单 + 500 次核销，观察内存增长、数据库文件增长、查询响应时间变化
- **重复启动-关闭循环**：连续启动应用 200 次，每次做完一笔业务，确认启动时间不退化、日志不无限膨胀
- **备份目录长期运行**：连续 40 天的自动备份（用 `shouldAutoBackup` 的时间注入模拟），确认保留策略正确清理

**第三层：环境鲁棒性（已部分覆盖，需扩展）**

§AT 修复了“离线映射盘导致崩溃”，但**同类环境问题还有**：

| 场景 | 当前状态 | 需要的测试 |
|---|---|---|
| 数据目录在 U 盘上，运行中拔盘 | 未测 | 写入时拔盘 → 是否优雅报错而非崩溃 |
| 磁盘满 | 备份失败已处理，**主库写入未测** | 写入大单据时磁盘满 → 是否回滚而非留下半条记录 |
| 系统时钟跳变 | `shouldAutoBackup` 有容错 | 主库 `occurred_at` 是否受影响（已有架构保证：`seq_no` 主导） |
| 防病毒软件锁文件 | 未测 | SQLite 文件被锁时是否重试而非崩溃 |
| 多用户同时登录同一台 Windows | 未测 | 两个用户会话同时打开同一数据目录 → 是否检测到冲突 |

**第四层：UI 稳定性**

- **长时间开单页不释放控制器**：`TextEditingController` 的泄漏。已有“500 商品级别会慢”的记录在案，**需要一条**：连续开 100 张单后，内存不线性增长
- **导航切换 100 次**：页面状态是否正确释放
- **200% 缩放下所有页面可操作**：已有对话框的溢出测试（§AG 场景 9），**需要扩展到所有页面**——不是测试用例覆盖（widget 测试很难测布局溢出），是**真机走一遍**
