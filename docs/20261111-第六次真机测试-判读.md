## 一、⭐ P2 定案（但不是我预想的那个原因）：**与库大小无关，绑定"首次创建"**

`dbprobe` 这次终于写出来了（串行化修复已随 0.7.8 生效）。**三组启动并排**：

| 时刻 | 场景 | 主库 | `-wal` | `T2p_sqlite_open` |
|---|---|---|---|---|
| 18:27:14 | **安装后首次**（新建库） | **4096 B** | 238,992 B | **19261 ms** |
| 18:56:12 | 造数后首次（**498 MB**） | 498.0 MB | — | **22 ms** |
| 19:33:06 | 不清缓存二次（**498 MB**） | 498.0 MB | — | **22 ms** |

`dbprobe` 原文（18:27 那次）：

```json
{"kind":"dbprobe","db":"F:/神算子数据/shensuanzi.db",
 "lengthSync":4096,"statBytes":4096,"statType":"file",
 "head":[83,81,76,105,116,101,32,102,111,114,109,97,116,32,51,0],
 "siblings":["shensuanzi.db-shm:32768","shensuanzi.db-wal:238992","shensuanzi.db:4096"]}
```

**四条结论：**

1. **`dbMb: 0.0` 不是测量错误** —— 主库**真的是 4096 字节**（`lengthSync` 与 `statBytes` 两条途径一致），
   `head` 是合法 SQLite 魔数，所以"打开的是真库，只是它只有 1 页"。
2. **那一次走的是"新建库"路径**：4096 B 是 SQLite 的空库头，`-wal` 里 233 KB 是建 12 张表 + 索引。
3. **同一个 `sqlite3.open()`，空库要 19.3 秒，498 MB 的库只要 22 ms** ——
   **与数据量完全相反**。⇒ **"读得多所以慢"这条线彻底排除。**
4. ⇒ **慢的是「首次创建这个文件」这个动作**，不是"打开已有文件"。

**横向对照（三台机器、同一份应用）**：

| 环境 | 打开**已存在**的 498 MB 库 |
|---|---|
| L13（本次） | **22 ms** |
| 虚拟机 | 83 ms |
| L51（机房，`F:` 6 层过滤） | 9822–14692 ms |

**⇒ L13 上"打开 498 MB 库"只要 22 ms —— 说明过滤栈对这一步影响有限。**
**L51 那 9.8 秒的成因仍未定**（它与 L13 差在"每次重启后"，而 L13 这三次没有重启间隔）。

### 对"19.3 秒"的最强候选

**还原保护（`DFFilter`）在 F: 上"首次创建文件"的登记成本。**
理由：19.3 秒只出现在「这个文件还不存在、要新建」的那一次；同一台机器、
同一个目录、同一个应用，文件建好之后只要 22 ms。

**判据（下一次即可验）**：拿一个新目录放应用（或删掉库让它重建），
如果又是十几秒 ⇒ 坐实"创建"；如果是毫秒 ⇒ 是别的东西。

## 二、两个真缺陷（都已修，带回归护栏）

### 2.1 从库存流水点进送货单详情 ⇒ **签收入口消失**

截图：`送货页面问题.png`。单号 `SH20241125-023`，状态**在途**，
但底部只有一句灰字「**签收入口暂时用不了（数据还没就绪）**」。

**根因**：`stock_page.dart` 构造 `DocumentDetailPage` 时**漏传 `deliveries`**：

```dart
builder: (context) => DocumentDetailPage(
  documentId: documentId,
  settlements: widget.settlements!,
  products: widget.products,
  // ← 少了 deliveries
),
```

`document_detail_page.dart` 里 `deliveries == null` 就走降级分支。

**⚠️ 同款构造点共 4 处**（`account_page` / `documents_page` / `document_detail_page` 自己 / `stock_page`），
**只有这一处漏** —— 典型「同构代码漏改」（纪律 18）。

**修法**：`StockPage` 加 `deliveries` 参数 → `app_shell` 传 `shell.deliveries` → 透传给详情页。

**回归护栏**：`test/stock_page_test.dart` 的 `#27` 用例加断言
`DocumentDetailPage.deliveries != null`。
**反向灵敏度已验证**：把 `deliveries:` 那一行删掉，测试立刻红，报的正是那句 reason。

### 2.2 用户手册正文里印着内部审查编号

截图：`用户手册里出现了不该出现的审查标记.png`。原文：

> 只填一格保存时软件会提示你补齐（**§审查 OBS-06**）。

**根因两层**：

1. `manual_content.dart` 里就写着这句（是写文案时顺手把台账编号带进去了）；
2. **门禁没拦住** —— `forbiddenDevTermsInUserText` 只有技术词汇（`Dart` / `schema` / `SQL` …），

（加这两个而不是加「审查」——「审查」太宽，而这两个在本项目里只可能出现在内部文档与注释里）。

**连带**：`packaging/用户手册.html` 已重新生成，`§`/`OBS-` **0 处**；
core 848 / app 503 / 根 531 全过（说明加词没误伤既有文案）。

## 三、⚠️ 乙方案的效果要**向下修正**

`page-cost.jsonl`（19:14 那次，停留 279 秒）：

```json
{"builds":11,"spanMs":279527,"aggMs":710,"transitMs":1160,
 "perBuild":[[201,57,93],[14163,58,94],[40502,66,104],[45709,58,94],
             [83383,57,96],[84105,58,103],[243831,58,94],[247530,65,106],
             [247708,56,90],[249729,57,95],[279419,0,0]]}
```

**`builds: 11`、`aggMs: 710`（≈ 11 × 65 ms）⇒ `_loadAggregates()` 被调了 11 次。**

**这说明 `didUpdateWidget` 与"父级重建"同频**，而父级重建的次数 ≈ 原来的 build 次数。
⇒ **乙方案只省掉「本页 `setState`」那部分（搜索 / 展开 / 筛选），
对「切页回来」没有收益** —— 因为那本来就该重算。

**另一个副作用（埋点语义漂移）**：`perBuild` 的第 2/3 项现在记的是
「**最近一次** `_loadAggregates` 的耗时」，不是「本次 build 内的聚合耗时」。
所以看这两个数不再能判断"这一帧为什么慢"——**要看 `frame-cost` 的 p99**。

**`frame-cost` 仍有尖刺**（这台机器 19:10–19:19 的窗口）：

| 窗口 | `build` p99 |
|---|---|
| 18:56:26 | **322.7 ms** |
| 19:10:43 | **172.5 ms** |
| 19:14:09 | **151.9 ms** |
| 19:16:58 | **147.8 ms** |
| 19:18:29 | **271.8 ms** |

⇒ **乙方案没有消除 build 尖刺**。原因：`didUpdateWidget` 里的
`stockTop`（~35 ms）+ `_loadAggregates`（~65 ms）**同步执行，仍在那一帧里**。

**⇒ 真正的解法还是"先出骨架、再异步填"**（上一轮 §四 待办 1），不是搬位置。
