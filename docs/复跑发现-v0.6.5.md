## 二、逐条详情

### F1（P1）草稿只活一次导航

**现象**（用户 A1 期间实测）：在采购页填了内容 → 切到别的页面 → 切回来（没点"恢复草稿"）→ 再切走 →
**草稿没了**。用户原话：「草稿只保留到下一次切换页面，再切换回来就没了」。

**根因**：`lib/src/ui/purchase_page.dart` 的 `_writeDraftNow()` 在 `dispose()` 里被调用，
它把「当前表单是空的」直接当成「用户把草稿清空了」：

```dart
if (!purchaseDraftHasContent(draft)) {
  store.delete(DraftKind.purchase);   // ← 这里把还没恢复的草稿删了
  return;
}
```

第一次离开页面：表单有内容 ⇒ 写盘（草稿在）。
第二次进页面：草稿只是被读进 `_restoreRaw` 等用户点"恢复"，**表单仍是空的**。
第二次离开页面：当前表单空 ⇒ `delete()` ⇒ **上一份草稿被抹掉**。

**修法**：`_restoreRaw != null`（存在待恢复草稿）时**一律不许删**。
三页同款：`sale_page.dart` / `purchase_page.dart` / `delivery_page.dart`。

**待确认**：`_restoreRaw` 只在 `initState` 设置，若用户恢复后再清空表单，删除行为仍应保留。

### F2（P2）保存后必留假草稿

**现象**：保存成功后按 P-3 裁定**保留供应商**（连续录单更快），但 `purchaseDraftHasContent`
把 `partyId != null` 算作"有内容" ⇒ 离开页面必写一份「只有李哥、明细全空」的草稿；
下次进页面弹"恢复草稿"，恢复出来是空表单。

**证据**：实测文件 `D:\SSZ-Rerun-065\data\drafts\purchase.json`：

```json
{"v":1,"kind":"purchase","partyId":"…","partyName":"李哥","remark":"",
 "lines":[{"productId":"","productName":"","quantity":"","unitPrice":"", …}],
 "payments":[{"accountId":"…","accountName":"现金","amount":""}]}
```

**修法（择一）**：
- 甲：`*DraftHasContent` 不再把"只有往来方"算内容（但往来方 + 明细才算）；
- 乙：保存成功后把草稿状态标记为"已消费"，下次进页面不弹。

### F3（P2）退货选"不退钱"后没有待退款提醒

**现象**（用户 D7）：退货时如果当时没退钱，之后单据上**看不到"还欠客户多少退款"**，
让人以为已经结清了。

**证据**：`XT20261025-003`（退 3 瓶 ¥10.50）`paid_amount = 0`，但销售单详情卡片只写
「已退货 −¥14.00 / 已全部退清 / 状态 已结清」——**没有一个字说还欠客户 10.50**。
（退款完成后 D7 验证：现金确实 −10.50，卡片上也不会再多一行，说明这条信息全程都不露出。）

**代码里已是悬案**：`document_detail_page.dart:341` 原注释
「⚠️ 这**不是**口径修复：那笔退款该不该露出，是 #38 第二步的裁定对象」。

**待裁定**：
- 甲：全退时卡片显示「**还欠客户退款 ¥10.50**」，状态行不再写「已结清」（货都退了，"结清"没意义）；
- 乙：只删「已全部退清」那行，退款只在退货单上看。

### F4（P2）详情页互相跳转成环

**现象**（用户原话）：「单据的聚合仅发生在根页面，点进某一张单后，再点底下的单子按钮，
就会跳转到对应单据（这里选择 SK20261025-001），再点击里面的核销按钮，就会再次跳转……
如此往复，导致用户被困在单据具体页面里很难出来」。

**根因（信息架构）**：根列表做了聚合（「已退 2 次 ¥14.00 · 已收 1 笔」把退货/收款折进原单），
但详情页把每条关联单都做成**可点的入口**（退货记录 → 退货单 → 核销 → 收付款单 → …），
且每层都是 push，**没有"回到原单"的捷径**，返回键要一层层退。

**待裁定**（方向，不是实现）：
- 甲：关联单**不再跳转**，就地展开摘要（详情页只作为"终点"，不做中转站）；
- 乙：保留跳转，但顶部加面包屑 / 「回到原单 XS…」按钮；
- 丙：只允许"单向"跳转（原单 → 关联单），关联单里的入口不再下钻。

### F5（P3）详情页不显示单价与录入原文

明细行只渲染 `测试可乐 × 24 ¥48.00`（`document_detail_page.dart:714` 只取了 `quantity` 和 `amount`），
库里 `entry_quantity=2 / entry_unit=箱`、`unit_price=200` 都有值但没画出来。
用户想核对"我当初是按箱录的"就看不到。

### F6（P3）库存页成本标签与金额被拆散

成本那一行是 `Wrap(alignment: WrapAlignment.spaceBetween)`，但里面有 **4 个**子项：
`账面·在途` 文字、`成本（均价）ⓘ`、4px 间隔、金额列 ⇒ `spaceBetween` 把 4 项**均摊**，
标签被推到行中间、金额贴最右，看起来像错位。

代码注释写的是"宽屏两项两端对齐"，与实际的 4 子项不符。

### F7（P3）流水页的金额没有口径说明

桌面端只显示裸 `¥-6.00`（`stock_flow_page.dart:274`）；窄屏（手机）写的是
「成本 ¥-6.00（每件 ¥2.00）」。同一个页面两套文案。
`-6.00` 是**出库成本**（3 瓶 × 均价 2.00），不是单据金额 ¥10.50 —— 桌面用户无从判断。

### F8（P3）明细顺序

详情页顺序：金额卡 → 退货记录 → 核销 → 灰字结论 → 明细。
用户建议：**明细提到退货记录上方**（"这单卖的是什么"是最基本信息，退货/核销是后续动作）。

### F9（P3）状态「已确认」看不出未结清

**现象**（E2）：`XS20261025-002` 金额 ¥50.00 / 已收 ¥30.00 / 未收 ¥20.00，而**状态写「已确认」**。
用户建议改成「**已确认但未结清**」。

**分析**：`status` 是单据生命周期（`confirmed` / `settled` / `cancelled`），
"结清"是**派生**事实（`paid_amount` 与 `金额 − 退货` 的比较）。两者现在只显示前者，
所以「已确认」读起来像"完事了"，而实际上还差 ¥20。

**修法方向**：状态行在 `confirmed` 且未收 > 0 时显示「已确认 · 未结清」；
`settled` 仍显示「已结清」；作废仍「已作废」。**不要**新增枚举值（否则老库/同步要迁移），
只在展示层组合。

### F10（P2）单据 CSV 导出漏了 5 张单

**现象**：单据页筛「今天」→ 点「导出当前筛选的单据（不做合并：退货单独一行）」，
导出 **13 行**，而库里同一天有 **18 张单**。

| 漏掉的单 | 类型 | 状态 | 为什么值得关心 |
|---|---|---|---|
| `FK20261025-001` | payment | settled | 采购 20 元时的**自动付款单** |
| `FK20261025-002` | payment | settled | 采购 48 元时的自动付款单 |
| `FK20261025-003` | payment | settled | 退给王姐的 ¥3.50 退款 |
| `SK20261025-001` | receipt | settled | 销售 ¥14 的自动收款单 |
| `XT20261025-001` | sale_return | confirmed | 拒收产生的**整单退货** |

**根因**：`_summaries()` 里有一段 `if (!includeDerived && !rootsOnly)` 的排除逻辑
（派生收付款单 + 原单已作废的全额退货单不进列表）。导出传的是
`rootsOnly: false, includeDerived: _includeDerived`（界面那个开关的当前值，默认 false）
⇒ **排除逻辑照样生效**。

而 `document_dao.dart:256` 的注释写的是：
「⚠️ 导出是「把数据带走」（AF-12）⇒ **恒全量**，不跟随 includeDerived」。

⇒ **注释与实现不一致**（纪律 17）。两种修法二选一，需裁定：
- 甲：按注释办 —— 导出恒全量（传 `includeDerived: true`），文件里 18 行；
- 乙：按实现办 —— 改注释与按钮文案，明说"派生单不导出"（但对账会少 5 张，不推荐）。

**影响**：拿这份 CSV 对账，"单据数"和软件里对不上，且少掉的正是**收付款**（对账最关键的行）。

### F11（P3）流水时间混着两种精度

账户流水导出里：

```
FK20261025-001  付款  -20.00  2026-10-25 00:00    ← 开单时"全款"自动生成的付款单
SK20261025-002  收款   30.00  2026-10-25 20:46    ← 手工核销
```

自动生成的收付款单 `occurred_at` = **单据日期（当天 00:00）**，手工核销 = **真实时刻**。
同一列里两种精度，`00:00` 会被读成"半夜记的账"。
建议：日期型（`time_estimated` 或 occurred_at 为整日）只显示 `2026-10-25`，不补 `00:00`。

**顺带**：流水类导出（商品流水 / 账户流水）的表头是「单号 / 单据类型 / 数量 / 成本 / 日期」，
**没有「序号」列**（清单原稿写的是"含序号"）。`seq_no` 在库里是有的，导不导需要一并定。

### F12（P2）SnackBar 久不消退

**现象**（用户复跑反馈）：「现有的 SnackBar 存在久不消退的问题」。

**根因（两个叠加）**：

1. **不清理上一条**：全仓 39 处 `showSnackBar`，只有 **1 处**（`export_button.dart:63`）先
   `removeCurrentSnackBar()`。其余 38 处直接入队 ⇒ Flutter 的 SnackBar 是**串行排队**的，
   连续操作（比如连点两次保存、保存后立刻收款）会排成队，一条播完才播下一条。
2. **时长偏长**：`Duration(seconds: 6)` 出现 13 次、`8` 出现 7 次、`4` 出现 4 次、`3` 出现 3 次。
   两条 8 秒的就够把提示压 16 秒，中老年用户不会主动划掉，只能干等。

**建议（待裁定）**：
- 抽一个 `showNotice(context, text, {long})`：**先 `removeCurrentSnackBar()` 再 show**，
  默认 **3 秒**，只有"含怎么办"的长文案才 6 秒；
- 39 处统一改走它（一次性，别一处一处改，否则下次又漂移）；
- 或者干脆换形态：这类"已保存"的确认更适合**页内一行淡出**，不占底部。

### F13（P2）「要留心」只看应收，不看应付

**现象**（用户复跑）：概览页「要留心」只写「应收合计 ¥10.50（1 家未结）· 其中 王姐 ¥10.50」，
而库里 **李哥 应付 ¥72.00**（往来方页红字「应付 ¥72.00」），卡片里一个字都没有。
更糟的边界：若某天只有应付、没有应收、也没有负库存，卡片会显示
「**目前没有要留心的事。**」—— 而实际上欠着供应商的钱。

**证据**：
- `overview_page.dart:394` 起的 `careCard` 只有两路：`receivables.totalCents > 0`、`negativeStock > 0`；
- `query_dao.dart:484` 的 `ReceivablesSummary` **只有应收口径**（`totalCents` = 正余额之和），
  全仓 grep 不到 `PayablesSummary` / `payablesSummary`。

**顺带发现（纪律 17）**：`docs/reply_review.md:11915` 的设计表把「**未签收送货单 K 张**」
列为「要留心」的内容之一，但实现里它在「今日销售」的送货行（`transitCount`），
`careCard` 没有这一项。要么是有意挪走（那就改设计稿），要么是漏了（那就补）。

**建议（待裁定）**：
- 加一行「**应付合计 ¥B（N 家未结）· 其中 <供应商> ¥x**」，与应收并列；
- 顺序上应付放**前面**（要还出去的钱比要收进来的更急）；
- 同时把「未签收送货单 K 张」补回或从设计稿删掉。

### F14（P1）"忘记主机 → 扫新主机"后同步永久失败

**现象**（2026-10-25 21:10，真机）：手机端「忘记这台主机」→「扫码连接主机」→ 扫码成功
（相机确实读到了电脑屏幕上的二维码）→ **首次同步立刻报红**：

```
同步时出错（Bad state: 落库 products 的行（id=01a17289-2674-…）失败：
UNIQUE constraint failed: products.code
若为 UNIQUE 冲突：主机侧 doc_no 唯一，正常同步不会撞 —— 大概率是本地镜像损坏
（本地占位单号与主机单号相同）。修复路径是重建镜像 + 全量重新拉取（游标清空即从头拉）。
）—— 请重试；一直这样请把这句话告诉技术支持
```

**根因（两处叠加，缺一不可）**：

1. `mobile_sync_service.dart:428` 的 `pairFromCode`：

```dart
lastHostSwitchHeldEntries =
    previous != null && previous.hostId != info.hostId   // ← 关键
    ? resetForNewHost(previousHostId: previous.hostId)
    : 0;
```

**「忘记这台主机」会把 `pairing.json` 删掉** ⇒ 再扫码时 `previous == null`
⇒ **`resetForNewHost()` 不执行 ⇒ 镜像不重建**。

2. 另一条重建路径（`syncNow` 里 `hostSchema > mirror.schemaVersion`）也不成立：
   **旧主机和新主机都是 schema 5**，版本相同 ⇒ 不重建。

⇒ 手机镜像里还留着**旧主机**的 `P0001 / P0002`，新主机全量拉取时插入同 `code` ⇒ UNIQUE 冲突。
**每一次重试都必然失败**，而错误文案让人"请重试"。

**为什么严重**：换电脑 / 重装系统 / 换一家店，都是「先忘记、再扫新机」——
**这恰好是产品自己引导的顺序**（忘记对话框写着"之后可以重新扫码连接"）。
用户会卡死在同步页，唯一自救是卸载重装（会丢本机未同步的单）。

**修法建议**：
- **镜像库自己记 hostId**（`mirror_meta` 表或 `PRAGMA application_id`），配对/同步时与
  `payload.hostId` 比对，不同就 `rebuildMirror()` —— **不要依赖 `pairing.json` 是否还在**
  （用户点"忘记"是正常路径，不是异常）；
- 顺带给一个手动出口：设置 → 多设备同步 → 「**重建本机数据副本**」（错误文案里都写了
  "重建镜像"，界面上却没有这个按钮）；
- 补一条测试：`pairFromCode` 在 `previous == null` 但镜像非空时也必须重建。

**用户裁定（2026-10-25）——补救措施**：
「手机扫码时，发现换了主机，**自动将之前连接的主机及其数据全部归档**，然后再执行现有内容。」

含义（落地时要守住的点）：
- **归档 ≠ 删除**：旧主机的镜像 + 未同步队列要留在本机（比如
  `<私有目录>/archive/<旧 hostId>-<时间>/`），并给一个"看归档"的入口；
- 判定不能用 `pairing.json` 是否存在（用户点"忘记"就没了）—— 必须由**镜像自己记 hostId**；
- 归档完再 `rebuildMirror()` + 全量拉取；
- 归档是**可恢复**的：用户换回旧主机时，数据还在。

### F15（P2）原始异常字符串直接甩给用户

**现象**：上面那条红字把 `Bad state: …`、`UNIQUE constraint failed: products.code`、
甚至内部修复指引（"游标清空即从头拉"）**原样**印在界面上。

**根因**：`mobile_sync_service.dart:258` 的兜底分支
`'同步时出错（$error）—— 请重试；一直这样请把这句话告诉技术支持'` 把 `error.toString()` 拼进了文案。

**为什么违反自家纪律**：项目里 `M15 两通道`（原始异常进日志、界面给分类文案）在详情页、
启动页都执行了（`widget.onStorageFailure?.call(...)` + 分类文案），**唯独同步这条漏了**。
用户看到的是"源码"，不是"我该怎么办"。

**修法**：按异常类型分类（网络 / 鉴权 / 数据冲突 / 其他），每类给一句人话 + 一个动作；
原始 `toString()` 只进日志（`_log.crash`）。"数据冲突"这一类可以直接指向 F14 的
「重建本机数据副本」按钮。

### F16（P3）同步成功后徽标不刷新

设置页点「立即同步」→ 21:27 同步完成（`上次同步` 已变成 21:27、桌面库收到单），
但**顶部徽标仍写着「待同步 1 条」**；切到「概览」再回来才变「已同步」。
⇒ 徽标读的是页面打开时的一份快照，没跟着同步结果重建。

### F17（P2）离线单不影响手机库存显示

**现象**：手机断网开单（大米 1 袋，`待同步-730450129`）→ 进「库存」页：
大米仍是 **1**、账面 1、在途 0，**没有**任何「≈ 估算」行或"含未同步"的标注。
（清单 H4-4 的期望是"库存显示估算"。）

**代码里本来有这条路**：`stock_page.dart:229` 取 `stockDelta.unsyncedDelta()`，
`:740` 在 `unsynced != 0` 时渲染「≈ 台账 + 未同步 = 合计」的叠加行。
`StockDelta.deltaOf()` 对 `sale` 记 −quantity，`unsyncedDelta()` 统计队列全部条目
（`pending`/`sent`/`failed` 都算）—— 口径看着没问题。

**⇒ 现象确凿，根因待查**（三个待验证方向）：
1. 手机壳里 `stockDelta` 是否为 `null`（`app.dart:1742` 的 `mirror == null` 分支）；
2. 队列条目的 `payload` 结构是否与 `deltaOf` 期望的一致
   （`{'document': {...}, 'lines': [{'product_id','quantity'}]}`）；
3. `quantity` 在 payload 里是不是 `int`（`deltaOf` 用 `quantity is! int` 直接跳过）。

复跑时没能在手机上读到队列内容（release 包 `run-as` 不可用，
「导出本机数据文件」走的是系统分享面板，拿不到路径）—— 下一轮要么用 debug 包，
要么给设置页加"导出到固定路径"。
