这次审计已经挖出一个比最后两个抢救边界更重要的问题：神算子的业务规则和数据恢复体系已经相当成熟，但主机网络服务的实际监听范围，与项目声明的安全边界不一致。

我先把结论摆出来：神算子已经不是一个“AI 帮忙拼出来的进销存 Demo”，而是一款具备完整领域模型、离线同步、迁移、备份与故障恢复机制的真实业务软件。它已经走得很远；但我还不会把它评为可以毫无保留地托付经营数据的成熟产品。

最主要的原因不是功能缺失，而是网络暴露、数据文件机密性和备份一致性这三项基础保障仍有重要缺口。

## 前言、先说最严重的发现：主机服务并没有按文档所说限制在局域网网卡

`HostHttpServer.start()` 的默认绑定地址是 `InternetAddress.anyIPv4`，也就是 `0.0.0.0`。而真正启动主机服务的 `HostServiceController` 调用它时，没有传入特定网卡地址。

这意味着服务会监听本机所有 IPv4 网络接口，而不是只监听某个局域网地址。

项目文档却声称服务只监听局域网网卡，以此防御外部网络访问。两者并不一致。

这里不能直接推断公网一定能够访问——Windows 防火墙、路由器和网络环境仍然可能挡住连接。但当前代码本身没有兑现“只监听局域网”的承诺。

这项我会列为全仓最高优先级之一。建议在实现上明确绑定策略，并增加自动化测试，验证实际监听地址，而不是只验证二维码里显示的 IP。

相关代码：[http_server.dart](packages/shensuanzi_host/lib/src/http_server.dart) · [service_controller.dart](packages/shensuanzi_host/lib/src/service_controller.dart) · [threat_model.md](docs/threat_model.md)

# 一、项目整体：已经具备完整软件系统的骨架

我认为神算子最值得肯定的，不是功能数量，而是它已经形成了一套比较清楚的工程体系。

## 1. 架构：拆分有实际意义，不是为了好看

目前的四层结构：

> Flutter 应用层：Windows / Android 用户界面与应用协调

> core：业务规则、数据库、DAO、同步协议、SyncClient

> host：HTTP、鉴权、配对、SyncServer

> app：数据目录、备份、恢复、日志、配置

三个业务包都是纯 Dart，不依赖 Flutter。

我很认可这条架构路线。

`core` 不知道自己运行在 Windows 还是 Android；`host` 不负责重新实现业务规则；`app` 不把文件管理逻辑散落在页面里。Flutter 负责把这些能力组合起来。

它带来了三个实际好处：

- 业务规则可以独立测试，不需要启动 Flutter。
- 主机端和桌面单机端共享同一个规则引擎。
- Android 不必复制库存、金额和核销规则，只负责提交业务请求并同步权威结果。

这三点直接降低了业务规则漂移的风险。

相关入口：[README 架构说明](README.md) · [Agents.md](Agents.md)

我的评价：架构方向正确，抽象基本服务于实际业务，没有明显的过度设计。

不过，根 Flutter 应用的 `lib/src/app.dart` 已经承担了相当多的装配和生命周期协调工作。以后继续加功能时，建议把启动流程、主机服务生命周期、同步协调和备份状态等职责逐渐拆开。现在不必为了拆分而重构，但要防止它变成新的“万能文件”。

## 2. 领域模型：已经不是简单的进销存 CRUD

我认为这是神算子真正的技术核心。

它不只是维护：

```text
商品 → 库存数量
客户 → 欠款金额
账户 → 余额
```

而是建立了四类流水与业务单据之间的关系：

- `stock_ledger`：库存变化事实。
- `money_ledger`：资金变化事实。
- `party_ledger`：往来余额变化事实。
- `settlements`：收付款与业务单据之间的核销关系。

再加上不可随意修改的业务单据、`seq_no` 排序、派生缓存与 `RuleEngine` 统一落库，整体模型已经能够解释很多实际经营场景。

特别是最近几轮，你们逐渐把重要业务规则变成可复用的不变量：

- 退款不能超过原单实际结算金额。
- 多张退货单要按原单累计退款额度。
- 退货退款方向与原交易方向相反。
- 明细金额必须与单据总额一致。
- 流水方向是业务含义，不能只比较绝对值。
- 一条核销关系的两端必须一起处理。

这已经是一个有明确领域边界的业务系统，而不是把若干表拼在一起的记账软件。

我还特别认可 `ledger_signs.dart` 的演进：从单纯的正负符号，发展成 `absent / either / positive / negative` 三态。这是一个很小的类型设计，却解决了真正的业务歧义。

# 二、最需要认真处理的四项问题

下面是我认为真正影响长期可靠性的事项。按严重程度排序。

## 1. P0 · 网络安全边界 · 主机服务监听所有 IPv4 接口

前面已经指出，这次全仓审计再次确认。

`HostHttpServer.start()`：

```dart
final InternetAddress bind =
    address ?? InternetAddress.anyIPv4;
```

而 `HostServiceController` 启动时没有传入特定地址，因此实际监听 `0.0.0.0`。

这与威胁模型里“只监听局域网网卡”的防御承诺不符。

需要区分两个事实：

监听所有接口，不等于公网一定可以访问。 Windows 防火墙、路由器配置和网络环境仍可能阻止外部连接。

但现在项目并没有通过监听地址实现“只接受局域网连接”。不能把防御责任留给未验证的系统默认行为。

我的建议是：明确制定主机监听策略，并验证：

1. 服务是否只绑定允许的局域网接口。
2. VPN、虚拟网卡和隧道网卡不会意外成为监听入口。
3. 没有可用局域网地址时，服务采取明确行为。
4. 测试能检查实际监听地址，而不只是二维码中的 IP。

另外，当前 HTTP 无 TLS，项目已经承认不防局域网中间人攻击。这是可以选择的 v1 取舍，但它与监听范围必须一起评估，不能一边扩大监听面，一边继续沿用原来的安全承诺。

## 2. P0 · 数据机密性 · 加密承诺与实际实现不一致

这是第二个比较严重的问题。

README 明确说明：

- 数据库是普通 SQLite。
- 备份可以用 SQLite 工具直接打开。
- 当前暂不提供加密。

这个产品决策本身没有问题。对目标用户而言，忘记密码导致无法找回经营数据，确实是需要认真考虑的代价。

但 `docs/threat_model.md` 和 README 的威胁模型又声称：

- 数据文件被拷走可以防御。
- 备份文件泄露可以防御。
- 可选 SQLCipher。
- 备份包可使用 AES-256。

我检查了依赖、数据打开路径和备份实现，没有发现与这些承诺对应的 SQLCipher / AES 数据加密机制。

这就不是文案小错误了。

没有加密的 SQLite 文件一旦被别人拿到，数据库里的经营数据就可以被直接读取。 Token 鉴权只保护应用的网络入口，不能保护已经被复制出去的数据文件。

我建议现在就把威胁模型分成三种：

| 威胁       | 当前实际能力     |
| -------- | ---------- |
| 未授权网络请求  | 有 Token 鉴权 |
| 数据文件被复制走 | 没有文件级加密保护  |
| 备份文件泄露   | 没有加密保护     |

你们可以继续坚持默认不加密，但必须诚实地写明保护边界。将来如果增加可选加密，再将其列为已经实现的能力。

相关文档：[README](README.md) · [threat_model.md](docs/threat_model.md)

## 3. P1 · 数据耐久性

SQLite 当前使用 `synchronous=NORMAL`

在 `Db._configure()` 中，我看到：

```dart
db.execute('PRAGMA synchronous = NORMAL');
db.execute('PRAGMA busy_timeout = 3000');
```

`busy_timeout = 3000` 是合理的：遇到短暂写锁时，不要立刻让业务操作失败。

但 `synchronous = NORMAL` 有一个必须让产品负责人了解的后果。

在 WAL 模式下，SQLite 使用 `NORMAL` 时可以保持数据库一致性，但已经提交的事务在突然断电或操作系统崩溃后，仍有可能回滚；普通应用进程崩溃与断电是不同的情况。SQLite 官方文档对此有明确说明。

[image](https://www.google.com/s2/favicons?domain=https://www.sqlite.org\&sz=32)

这意味着：

用户刚刚看到“保存成功”的一笔单据，在某些断电场景下仍可能消失。

这不意味着数据库一定会损坏，也不意味着 `NORMAL` 是错误配置。SQLite 官方也将它视为 WAL 模式下一个常见的性能与安全平衡选择。

[image](https://www.google.com/s2/favicons?domain=https://www.sqlite.org\&sz=32)

但神算子不是一个可以随意丢失最后几秒数据的临时工具。它存的是经营记录。

我建议把这个问题正式列为数据耐久性决策：

- Windows 主机权威数据库是否应使用 `FULL`，优先保证已确认事务的持久性？
- Android 本地镜像是否可以继续使用 `NORMAL`？
- `FULL` 在目标低配置电脑上的写入延迟究竟增加多少？

不要凭感觉决定。拿家里的目标硬件和较大的真实测试库测一次，再裁定。

## 4. P1 · 备份一致性 · checkpoint 后直接复制文件，仍需解决并发写入问题

当前 `BackupService` 的核心流程是：

```text
WAL checkpoint(TRUNCATE)
       ↓
Isolate.run()
       ↓
复制 shensuanzi.db 到 .tmp
       ↓
quick_check
       ↓
rename 为正式备份
```

把文件复制放进 isolate 是正确的性能优化，原子改名也很好。

但还有一个尚未彻底解决的问题：

checkpoint 完成，不代表从 checkpoint 返回到复制结束期间，数据库不会继续变化。

当前主程序仍然可以接受新的业务写入；文件复制期间 SQLite 也可能执行自动 checkpoint，修改主数据库文件。

因此，直接复制主文件并不天然等于获得一个一致的时间点快照。

SQLite 官方专门提供了 Online Backup API。它可以在数据库继续被使用时完成一致性快照，并且允许其他连接继续工作。官方文档也说明了传统文件复制方式需要对数据库持有共享锁，使写入者等待，否则就应使用更合适的在线备份机制。

[image](https://www.google.com/s2/favicons?domain=https://www.sqlite.org\&sz=32)

`quick_check` 通过只能说明副本通过了相应结构检查，不能证明它包含了所有应当进入该备份时间点的已提交业务数据。

我建议第二批备份施工正式定案时，优先评估 SQLite Online Backup API 或等效的一致性快照方案。并且必须做一项专门验收：

备份过程中持续写入订单、收付款与退货，恢复备份后验证账本是否对应一个完整、可解释的时间点。

这一项比单纯检查备份文件能否打开重要得多。

# 三、同步系统：设计相当完整，但输入验证还可加强

我对同步架构的整体评价是正面的。

Windows 主机持有权威数据库和 `RuleEngine`；Android 维护镜像与队列，通过 `SyncClient` 推送单据，再通过 pull 拉取权威状态。

你们已经处理了不少实际容易出错的事情：

- 幂等键使用实体 ID。
- 主数据冲突采用 host-wins。
- 队列状态区分 pending、sent、failed。
- push 成功不代表本地镜像已经确认更新。
- pull 需要拉到最后一页才清理已确认队列。
- 断网与业务拒绝分开处理。
- 最近修改过的主单通过更新窗口补拉。

这套同步机制已经明显超出了普通的 HTTP 上传下载。

不过，我发现一个值得补上的协议防线。

## SyncClient 对服务端返回的行列没有完整的列白名单检查

`SyncPullResult.fromJson()` 只把顶层实体限制在已知的九张表中，但每行的字段目前基本只是转换成 `Map`。

随后 `SyncClient._upsertRow()` 会直接使用：

```dart
final List<String> columns = row.keys.toList();

_raw.execute(
  'INSERT INTO $table (${columns.join(', ')}) VALUES ($marks) '
  'ON CONFLICT(id) DO UPDATE SET $assignments',
  values,
);
```

这里的表名是白名单内的，但列名来自 HTTP 响应，却被直接拼接成 SQL 标识符。

参数绑定可以保护值，但不能自动保护动态列名。

正常主机代码生成的响应当然是可信的，但网络响应没有 TLS 保护，且项目明确把中间人攻击列为不防御范围。因此这一点至少应该有独立的输入校验，不能让解析器无条件相信每个服务端返回的字段名。

建议为每张同步实体建立明确的可读取列白名单，在写入镜像之前完成：

- 列名检查；
- 必填列检查；
- 字段类型检查；
- 不允许的主机字段检查。

现有 `SyncWhitelist` 有写入列白名单，但它主要用于客户端推送到主机的路径，不能直接认为已经覆盖了客户端 pull 的返回字段。

相关代码：[sync_pull.dart](packages/shensuanzi_core/lib/src/sync/sync_pull.dart) · [sync_client.dart](packages/shensuanzi_core/lib/src/sync/sync_client.dart) · [whitelist.dart](packages/shensuanzi_core/lib/src/sync/whitelist.dart)

# 四、数据库、迁移、恢复：这是目前项目最有竞争力的部分

这一部分我给出比较高的评价。

## 1. 数据库迁移的结构很好

`Db.open()` 不只是打开一个 SQLite 文件：

- 启用 WAL。
- 设置外键。
- 设置锁等待时间。
- 检查 Schema 版本。
- 逐版本执行迁移。
- 迁移前创建 `.before-vN` 备份。
- 对需要重建父表的迁移临时关闭外键。
- 最后执行 `foreign_key_check`。

每一版迁移独立事务，不会让长迁移链全部变成一个不可恢复的大事务。

尤其是迁移前备份失败就拒绝升级，这个原则是对的：

宁可暂时打不开，也不要在没有退路的情况下改用户的数据。

## 2. 数据抢救已经形成了业务层恢复机制

你们最近几轮对 rescue 的改造，我认为是整个项目里最有价值的工程成果之一。

它不只是通过 SQLite 打开损坏文件，而是：

- 保留原件，不在原件上直接修复。
- 复制工作副本并尝试恢复数据库结构。
- 分批读取 rowid，失败后继续二分。
- 检查明细、库存、往来、资金、核销之间的业务关系。
- 对不完整或未知类型的单据不擅自认定完整。
- 将可以恢复的业务与待确认数据分开报告。

特别是你们接受了盘点单有一类损坏无法仅凭现有数据判定，这比为了追求“恢复率”而强行猜测更可靠。

我仍然认为本轮正在补的 NULL 引用和 `transfer` 类型是最后必要的边界之一。完成后应当按照完整混合账本再跑一遍验收。

## 3. 离线镜像的库存估算思路正确

Android 不拥有权威业务状态，所以把镜像库存和未同步队列的 delta 分开显示，并明确标记估算值，这是正确的产品选择。

它没有假装手机在离线期间已经知道主机的最终库存。

这种对“真实状态”和“估算状态”的区分，与整个项目的可靠性目标是一致的。

这部分应当是下一阶段的主要质量工作之一。

## 构建和发布还有两个容易被忽视的地方

第一，Windows 构建依赖本地预置的 `third_party/sqlite3/`，但这个目录被 `.gitignore` 排除。换机器克隆仓库后，不能直接保证离线构建。文档已经解释了手工准备方式，但没有对 SQLite 源码内容做完整哈希验证。

第二，`make_release.py` 会防止使用过期构建产物，并生成发布包 SHA-256，这很好；但它对随包 `LICENSE`、`THIRD_PARTY.md` 等文件主要检查是否存在，并没有核对内容是否正确。

这些不阻碍当前功能，但影响以后稳定维护和发布供应链。
