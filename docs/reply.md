# 二、新发现：不应该存在的流水，仍可能被抢救器放行

建议补充后再验收

这是本轮最重要的发现。

你们现在明确规定：

> `0` 表示某类单据不产生这张表的流水。

但我对照 `_assemble()`、`_stockProblem()`、`_partyProblem()` 和 `_moneyProblem()` 后发现，当前并没有在所有情况下贯彻这条规则。

具体有三个场景。

## 1. 普通销售单可能被塞入额外资金流水

`_moneyProblem()` 对普通业务单据只做：

```dart
if (settledCents != paidCents) {
  return ...;
}
return null;
```

它没有检查 `money` 列表是否为空。

可是销售、采购、送货和退货主单不直接写 `money_ledger`，实际资金流水属于独立的收付款单。

假设：

- 一张正常销售单；
- 已有正确的库存、往来和核销；
- 损坏又额外留下了一条 `money_ledger`；
- 这条流水引用了一个真实存在的账户。

那么其他检查可能全部通过，额外资金流水也会被写进恢复后的数据库。

结果：账户余额平白多出一笔钱。

建议：对于 `moneySignOf(type) == 0` 的单据，应明确要求对应的资金流水不存在。

## 2. 散客销售可能被挂上不属于自己的往来流水

`_partyProblem()` 当前第一条判断是：

```dart
if (partyId is! String || partyId.isEmpty) return null;
```

这意味着没有 `party_id` 的单据直接跳过往来流水检查。

而 `_ledgerRefProblem()` 只有在单据的 `docParty` 非空时，才要求流水往来方与单据一致。

因此可以构造：

- 一张没有往来方的散客销售；
- 损坏后多出一条 `party_ledger`；
- 这条流水引用另一个真实存在的客户；
- 金额、外键都有效。

目前它可能通过检查。

恢复后，这笔本来不应该存在的欠款却被记到某个真实客户名下。

建议：如果单据没有往来方，就必须要求它没有往来流水。

这同样适用于不产生往来流水的盘点单。

## 3. 收款单和付款单也可能带着库存流水进入新库

`_stockProblem()` 只在 `expectsLines` 为真时调用。

而收付款单没有商品明细，`expectsLines` 为假，因此它们完全跳过库存完整性检查。

但是 `stockSignOf(receipt/payment)` 返回 0，意味着它们不应产生库存流水。

如果损坏导致某条库存流水挂到了收款单或付款单上，只要主数据引用还有效，这条流水就可能未经检查被写入新库。

结果：收款或付款操作可能意外改变商品库存。

这与前面两个问题是同一类缺陷。

## 我建议怎么修？

不需要引入复杂的新机制，只需要让符号表的零值语义真正成为抢救器的约束：

| 情况                                  | 应当处理        |
| ----------------------------------- | ----------- |
| `moneySignOf(type) == 0`            | 对应单据不得有资金流水 |
| `partySignOf(type) == 0`            | 对应单据不得有往来流水 |
| 单据没有 `party_id`                     | 不得有往来流水     |
| `stockSignOf(receipt/payment) == 0` | 收付款单不得有库存流水 |

这里有一条例外必须保留：盘点虽然没有固定库存方向，却可以产生库存流水。 不能因为符号表返回 0 就把盘点的库存流水全部禁止。

建议用明确的类型判断或单独的适用性定义处理这一例外。

新增测试可以直接通过现有真实业务夹具注入额外流水，再确认这些单据进入待确认列表，而不是导入新库。

# 三、符号表还有一个小小的语义问题

[ledger_signs.dart](packages/shensuanzi_core/lib/src/models/ledger_signs.dart) 顶部写道：

> 返回 0 表示这类单据不产生这张表的流水。

但 `stockSignOf(DocType.stocktake)` 返回 0，是因为盘点差额可能为正、也可能为负，而不是因为盘点一定没有库存流水。

这两个意思不同：

- 收付款单的库存方向为 0：不应产生库存流水。
- 盘点单的库存方向为 0：允许产生库存流水，但无法预先确定方向。

当前抢救器用 `_stockProblem()` 单独处理了盘点，因此暂时没有因为这个问题误判。

不过，未来其他模块直接调用 `stockSignOf(stocktake)` 时，很容易把 0 理解成“不允许任何库存流水”。

我建议将来把这两种状态分开表达，例如：

- 不产生流水；
- 流水存在，但方向不固定；
- 流水存在，方向固定。

不一定现在就要引入复杂类型，至少先修正公共注释和测试辅助函数的约定。

# 四、`ledger_signs_test` 有一个测试细节值得完善

目前 `expectSigns()` 对于符号为 0 的情况，检查的是：

```dart
expect(sum, 0);
```

但合计为零不代表没有流水记录。

举例：

| 流水  | 金额   |
| --- | ---- |
| 第一条 | +100 |
| 第二条 | −100 |
| 合计  | 0    |

测试仍然会通过。

这意味着，如果未来某类本来不应该生成流水的业务错误地生成了两条相互抵消的流水，测试可能发现不了。

建议在零值分支直接检查：

```sql
SELECT COUNT(*) FROM ...
WHERE document_id = ?
```

要求记录数为零，而不是只要求 `SUM()` 为零。

对于盘点的库存流水，则不要调用这个“必须无记录”的分支。
