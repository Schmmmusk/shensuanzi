# §Z 审查意见

## 总评

方向和分层都对，与 §X 同构。**5 个待裁定项都同意**。但有 **3 处需要修改**（其中 1 处涉及数据语义），以及 **7 项遗漏**——其中 **退货入口**和**折扣/抹零**是**主路径上绕不开**的。

---

## 一、逐条对 Z-1 ~ Z-5

### Z-1 范围：A+B 一起做 ✅

同意。理由充分——真机已经撞到「没账户存不了全款」，A 是 B 的**硬前置**。分成两阶段反而要在 B 阶段再切一次。

### Z-2 负库存行内提示 ✅，但**判断时机**要写清

同意"行内红色提示，不拦人"。但提案没写清**"当前库存"是什么时候取的**——这是个真问题：

| 时机 | 问题 |
|---|---|
| 每次输入数量时查 | 性能差，且一次开单要查几十次 |
| 页面加载时查一次 | 用户开单期间库存可能变了（另一台设备在卖） |

**建议**：**页面加载时批量查一次快照**（`QueryDao.stockByProduct`），输入时用这个快照判断。**不重查**——因为这**只是提示，不是校验**：负库存本来就允许，保存必然放行。

UI 上要**明确说明这是快照**：

```
当前库存 10（打开本页时）
```

而不是含糊的"当前库存 10"——用户看到数字变了不会以为是 bug。

### Z-3 编辑期初余额二次确认 ✅，但**语义比确认更重要**

二次确认是**表面**。真正的风险在 `data_model.md §2.3` 已经写明的话：**修改会重算全部历史余额**。也就是说，用户改一下期初余额，**三个月前的账户余额数字跟着变**——这在会计上叫"重述历史"。

对个体工商户，最真实的场景是"**我当时填错了**"，不是"我改变主意了"。**两者在 UI 上应该是同一件事**——都是修正，不是撤销。

**建议（三选一，按推荐度排序）**：

| 方案 | 内容 | 代价 |
|---|---|---|
| **A（推荐）** | **v1 不允许编辑**：期初余额建时填对；要修就「新建一个账户 + 把老账户停用」 | UI 简单，历史不可篡改；代价是用户要重建账户 |
| B | 允许编辑，但**二次确认里明说「X 月 X 日至今的余额都会跟着变」**（不只是"重算"两个字） | 一句话的事，但用户**不会真的理解**——直到某天发现三个月前对不上 |
| C | **产生一张"期初调整"收付款单**（`doc_type=receipt/payment` + 特殊 `ref_doc_id`），`initial_balance` 只读 | 历史不动，语义干净；但要引入新语义，core 要改 |

**推荐 A**。理由：账户建档本来就是低频动作，用户不会频繁改；真改错了，重建账户 30 秒的事。**B 看起来温和，实际上是把风险推给用户**——他看不懂警告文案。

### Z-4 客户建档最小入口 ✅，但**要处理"同一人既是客户又是供应商"**

`parties` 表的 `roles` 是 JSON 数组，就是为了这个场景。但 §Z 写的是"最小入口（名称 + 电话可选，role=customer）"——**只说了新建**，没说"这个人已经是供应商怎么办"。

**问题**：个体工商户最常见的场景之一——老王既供货给你，也从你这里进货。

如果客户选择器只提供"新建"，用户点下去会**建一条同名 party**，而系统里已经有一条 `roles=["supplier"]` 的老王。`parties` 表没有 `name` 唯一约束，所以**能建**——但从此有两条老王，`party_ledger` 分流，**对账时分不清哪个是哪个**。

**建议**：客户选择器的"新建"入口，**输入名称时先查已有 party**：

| 匹配情况 | 行为 |
|---|---|
| 无匹配 | 正常新建 |
| 匹配到已有 party（无 customer role） | 提示「已有同名往来方『老王』，要加为你的客户吗？」→ 用户确认后**追加 role**，不新建 |
| 匹配到已有 party（已有 customer role） | 直接选中，无需新建 |

**代价**：多一次查询 + 一段文案。**收益**：避免将来**最麻烦的一类数据问题**（同名往来方）。

`SupplierService.createSupplier` 那边也要同步处理。这两处**共用**一个"新增 or 追加 role"的逻辑。

### Z-5 `recentlyPurchased` 泛化 ✅

同意。`recentProducts({List<DocType> docs})` 一处 SQL 采购销售共用。参数化比平行方法好。

## 二、遗漏项（按重要性）

### 遗漏 1：**退货入口**——主路径上的黑洞

§Z 只说"开新单"，没提**退货**。但个体工商户天天遇到退货：

```
用户卖出去 → 客户第二天说"不要了"→ 怎么办？
```

core 层 **RULE-007 / RULE-008 已经实现**（`sale_return` / `purchase_return`），但 UI 上**没有任何入口**。用户唯一的办法是"再开一张负数销售单"——这会**绕开 RULE-007 的成本回退逻辑**，**库存成本算错**。

**必须在 §Z 里明确**：

| 方案 | 内容 |
|---|---|
| **A（推荐）** | **v1 UI 不做退货**，但**明说**：用户开不了退货单，需要退货请等 v1.1 |
| B | v1 做**最小退货**：单据列表 → 找到原销售单 → 「退货」按钮 → 弹对话框选商品和数量 |

**推荐 A 还是 B 要看时间预算**。如果 B 只要半天，就做——因为**没有退货入口的销售模块是不完整的**。如果 B 要两天，先 A。

**但不管是 A 还是 B，都要在 `docs/ui_principles.md` 或 §Z 里写明**——这是**有意识地不做**，不是忘掉了。

### 遗漏 2：**折扣 / 抹零**——个体工商户的日常

个体工商户的销售最常见的是**抹零**：

```
合计 ¥123.45 → "算了，给 120 吧"
```

v1 没有折扣模块。用户会怎么处理？

**建议**：**v1 不做折扣**，用户在**最后一行单价上手动调整**（比如把单价从 12.345 改成 12）。

**但要在开单页 UI 上留一个提示位**——当用户改单价改得离谱（比如最后一行单价从 12 改成 0.5）时，不提示（信任用户）。

**真正的问题**：如果用户想"整单打 9 折"，他得逐行改单价，**很麻烦**。这个需求真实存在，但**v1 可以接受**——个体工商户的折扣多数是整数抹零，改最后一行就够了。

**记录在案**：折扣/整单优惠是 v1.2 的候选功能。

### 遗漏 3：**"最近客户"**——客户选择器也需要

采购页的商品选择器有"最近采购"，销售页的客户选择器**也需要"最近销售"**——个体工商户的客户群是稳定的，一开店就能点到常客。

**建议**：与商品选择器同构——空查询显示"最近往来的客户"（20 条）。

### 遗漏 4：**单价预填售价，但用户会改**——要写清

采购预填进价是合理的（进价相对固定）。销售预填售价，**用户会改**——**议价是常态**。

提案提到"售价 `sellingPrice`"预填，但没说这是**默认值而非约束**。要在实现说明里写清：

- 预填售价 → 用户**可改** → 改后的单价是这一行的真相
- **不回写** `products.sell_price`（这次卖便宜了，不代表下次也便宜）

### 遗漏 5：**送货单不做**——v1 的所有销售都是"当场提货"

`delivery` 规则 core 已实现，但 §Z 只做 `sale`。

**建议明确**：v1 UI 只有"店内销售"，不提供"送货单"。要送货只能开 sale 单 + 备注里写"送货"。**送货单 UI 留 v1.1**。

这不是大问题，但**要在 §Z 里说清**——否则用户会问"我送货上门了怎么记？"

### 遗漏 6：**利润显示**——先不做，但留位置

个体工商户最关心"这笔赚了多少"。但精确利润需要出库成本——**`stock_ledger.total_cost` 已经精确记录**，理论上可以算。

**但**：

- 计算成本需要查 `stock_ledger`（有 I/O）
- 显示利润会让开单页更复杂
- 首次使用的用户看到"利润 ¥5.20"可能困惑"这数怎么来的"

**建议**：**v1 开单页不显示利润**。但**保存成功的 SnackBar 可以显示**：

```
单号 XS20260927-001 已保存 ¥120.00
```

不加利润。**留给 v1.2**——在单据详情页显示，用户主动点击才看。

### 遗漏 7：**开单页的"必填项"视觉标记**

采购页没提，销售页也没提。但**中老年用户需要明确的视觉引导**：

- 必填项标 **红色星号**（`名称 *`）
- 选填项不标

这是 UI 层面的基础——**建议加进 `ui_principles.md` §四（数字输入）之后，作为新的一小节**。

## 三、一个实现建议（不是裁定项，但值得采纳）

### `SaleDraft` 与 `PurchaseDraft` 应该**共用抽象**

`PurchaseDraft` / `SaleDraft` 的字段结构几乎一样：

```
供应商 / 客户     → counterparty
明细行             → lines
立即付款 / 收款    → immediatePayments
日期               → occurredAt
```

**建议**：抽一个**内部基类或 mixin**——`DocumentDraft`——包含：

- `lines` / `payments` / `occurredAt` 的公共部分
- `validateLines()` / `validatePayments()` 的公共逻辑
- `counterpartyId` 抽象字段（`PurchaseDraft` 是供应商，`SaleDraft` 是客户）

`PurchaseDraft` 和 `SaleDraft` 各自实现 `direction`（采购 vs 销售）的差异。

**收益**：
- 明细行校验、付款行校验、金额格式化，只写一份
- `PurchaseLineDraft` / `SaleLineDraft` 合并成一个
- 将来的 `DeliveryDraft` / `ReturnDraft` 也能复用

**成本**：需要现在多花半天设计这个抽象。但**第二次出现的重复就是重构的时机**——现在正是。

**如果不想现在做**，也至少在 §Z 里**留一个注释**：`SaleDraft` 与 `PurchaseDraft` 有 80% 重复，等第三个单据（`DeliveryDraft`）出现时抽 `DocumentDraft` 基类。

## 四、结论与建议

**同意 Z-1 ~ Z-5**，其中：

- **Z-3 改为方案 A**（不允许编辑期初余额）——比二次确认更干净
- **Z-4 补充"同名 party 追加 role"逻辑**——与采购页共用

**补充 7 项遗漏**，其中**遗漏 1（退货入口）**必须落地或在文档里明确声明不做。

**新增两条实现建议**：
- `SaleDraft` / `PurchaseDraft` 共用 `DocumentDraft` 抽象（或至少留注释）
- 负库存提示的"库存快照"语义要写清

**我的总体判断**：这份提案**骨架完全对**，问题都在"用户会撞到什么"这一层——同名 party、没有退货入口、抹零、最近客户。这些**不是设计缺陷，是覆盖缺口**。补完之后可以直接进入实现。
