## 一、对四个决策点的确认

| # | 决策点 | 意见与理由 |

| **①** | 备份与导出移出主线程 | **选甲（都移）。** 机械硬盘上 1-3 秒的冻结是灾难性的。虽然会改 `startup_test`，但为了免于用户强杀进程，这点测试重构的代价绝对值得。 |

## 二、落地时极易踩的 3 个工程暗坑

虽然方案逻辑完美，但在写 Dart 代码时，这些地方极易翻车：

### 1. 备份的 Isolate 陷阱
`Isolate.run` 里执行的闭包**不能捕获任何不可发送的对象**（比如 `Database` 连接）。
- 绝不能写成：`Isolate.run(() => backupService.doBackup())`（因为 `backupService` 里含有 Database 实例）。
- **正确做法**：就像方案里说的，主线程执行完 `wal_checkpoint`，然后通过**顶层函数**把 `sourcePath` 和 `targetPath` 传进 isolate，在 isolate 里只做 `File.copySync`。

### 2. `startup_test` 的修改策略
如果用 `tester.runAsync` 来包真实的备份测试，很容易导致超时或者测试不稳定（因为 `runAsync` 会强制推真实事件循环）。
- **强烈建议**：与其改 `runAsync`，不如**给 `App` 注入一个假的 `BackupService`**。在 widget 测试中，只验证“调用了备份服务并传入了正确的参数”，真实的备份逻辑在纯 Dart 的 `backup_test.dart` 里去测。这样更符合“UI 只摆放，逻辑在纯 Dart”的原则。

### 3. `party_ledger` 的点查验证
服务层那句“对方累计欠款 ¥xx”，现在用的是全表聚合，改成点查（`WHERE party_id = ?`）后，**务必确保原来保存后的 SnackBar 测试断言依然能过**。因为全表聚合如果遇到“散客（无往来方 ID）”，行为可能和点查不同，需要仔细核对一下 `party_id` 为空时的分支。
