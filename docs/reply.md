# 裁定审查：文件属性用英文

## 一、结论

**保持英文。** 用户建议的判断对——**但理由里有一处事实不够精确，值得纠正**；另有一处建议可以再优化。

---

## 二、事实层面：一处需要修正

原提案说"**rc.exe 没有 `/utf-8`**"——这个判断**不完整**。

**准确的事实**：MSVC 2019（16.x）起的 `rc.exe` **支持 `/utf-8`**，前提是 Windows SDK 10.0.17763 或更新。所以"方案 C 不可行"是**结论对、理由不对**。

真正的完整图景是：

| 方案 | 技术上可行？ | 真实代价 |
|---|---|---|
| A 保持英文 | ✅ | 与裁定有差异（零成本） |
| B UTF-16 LE with BOM | ✅ | 仓库里唯一的异类文件；将来第一次编辑它的合作者会困惑 |
| C `/utf-8` + CMake 传参 | ⚠️ **看工具链** | ① 依赖 SDK 版本 ≥ 10.0.17763；② 需要在 Flutter 生成的 CMake 配置里找到 rc.exe 的参数入口（不是"改一行"）；③ **所有构建者**必须满足 SDK 版本——一个人本地能建、另一个人建不了，是最难查的那种 bug |

**所以裁定不变，但理由要换**：不是"做不到"，而是"**代价远超收益**"。

---

## 三、判断层面：为什么"保持英文"是对的

真正的原则不是"能不能做"，而是：

> **构建输入的编码一致性 > 一个几乎没人看的属性页。**

拆开看这条原则的两边：

**左边的分量**：

- `Runner.rc` 是**仓库里唯一的构建资源文件**。它如果变成 UTF-16，就成了孤例——不是"另一个选择"，是"唯一一个需要单独理由的文件"
- 一旦有一处例外，下一处（`manifest`？`app.manifest`？）就会被引用为例外
- 这种"例外扩散"在项目生命周期里是**单向的**——很难回收

**右边的分量**：

用户真正会看到的界面路径，与属性页的对比：

| 界面 | 编码 | 用户看到什么 |
|---|---|---|
| 窗口标题 | 中文 ✅（`main.cpp` 用 `\u` 转义） | 每次打开软件 |
| 任务栏 / Alt+Tab | 走**窗口标题** | 每次切换 |
| 开始菜单 | 走 exe 文件名 + 图标 | 每次启动 |
| 帮助页「关于」 | 中文 ✅ | 用户主动查 |
| **exe 文件属性页** | **英文** | **用户几乎不看** |

**用户感知路径 100% 是中文。属性页是唯一例外——而且是那个"用户几乎不会打开"的地方。**

---

## 四、两处可以优化的细节

### 优化 1：`FileDescription` 改用 `&`

当前：`Shensuanzi - inventory and bookkeeping`

建议：`Shensuanzi - Inventory & Bookkeeping`

理由：

- **属性页那一栏宽度有限**（Windows 属性对话框约 40 字符），`and` 占 3 字符换成 `&` 是纯收益
- **首字母大写**是 Windows 资源字符串的惯例——`Inventory & Bookkeeping` 比 `inventory and bookkeeping` 更符合属性页的观感

### 优化 2：`shensuanzi.exe` 的**文件名**也要明确保持英文

**这一点提案里没提，但它是同一个问题**。

exe 文件名决定了什么：

| 界面 | 名称来源 |
|---|---|
| 开始菜单 | exe 文件名去扩展名 |
| 任务栏悬停提示 | exe 文件名 |
| 进程名（任务管理器） | exe 文件名 |
| zip 解压后的文件列表 | exe 文件名 |

**如果把 exe 改成 `神算子.exe`**：

- ✅ 开始菜单会显示「神算子」——比 `shensuanzi` 好看
- ❌ **zip 解压时可能乱码** —— zip 格式的 UTF-8 flag 不一定被设置，Windows 自带解压器按 GBK 解
- ❌ **命令行 / 批处理 / 脚本场景出问题** —— `.bat` 里写中文路径需要代码页配合
- ❌ **未来如果有构建脚本引用它** —— 又要面对编码问题

**所以**：`shensuanzi.exe` 保持英文，**是与 `Runner.rc` 保持英文一致的策略**——不是"两个独立的决定"，是**同一条原则的两个落点**。

**用户看不到"文件名是英文"的损失**——因为开始菜单里显示的是 **exe 文件名 + 图标**，用户靠**图标**认应用，名字是 `shensuanzi` 反而显得**稳**（不像"半成品"）。

## 五、一处"记下来但不做"的观察

**真的没有"能进中文"的路径吗？**

有，但是**独立的、不冲突的方案**——不是"绕过编码问题"，而是"用另一个机制"：

| 机制 | 能不能进中文 | v1 做不做 |
|---|---|---|
| `Runner.rc` 的字符串表 | 看编码 | 不做（本裁定） |
| **exe 内嵌 manifest** | manifest 本身支持 UTF-8 | **不做**——manifest 里没有 `ProductName` / `FileDescription` 这两个字段 |
| **Windows 10+ 的 `appxmanifest`** | 打包成 MSIX 时可用 | 不做（v1 用便携 zip） |

**结论**：v1 没有"既保持文件编码一致又能进中文"的路径。**记下来**——将来如果做 MSIX 安装包，属性可以走 `appxmanifest`（那是 UTF-8 的 XML），届时中文属性**会自然出现**，与现在的 `Runner.rc` 英文属性**不冲突**（MSIX 属性页会覆盖 exe 属性页）。

**这是"将来有，但不急"**——写进 `windows_build.md` 的"未来扩展"段，比遗忘好。

## 七、一句话

**保持英文。** 用户建议的方向对——但理由要换：不是"做不到中文"，而是"**为了一行几乎没人看的属性，把仓库里唯一的构建资源文件改成异类，不划算**"。

补两点：`FileDescription` 用 `&` 更紧凑；`shensuanzi.exe` 的**文件名**保持英文是与 `Runner.rc` **同一条原则**的落点，不是独立决定。

**用户感知路径 100% 是中文**——属性页是唯一的例外，而它恰好是那个"没人看"的地方。
