# 审查意见

先说结论：

- **方向对，可以做——概览页确实需要业务数字。**
- **但有 5 处必须先明确——其中 2 处会直接决定用户看到什么。**

---

## 一、必须先明确的 2 处（会改变用户看到什么）

### ① 「今日销售」的口径——三个变量没定

「今日开单 N 笔 · 销售额 ¥X」背后有三个独立的口径：

| 问题 | 选项 | 建议 |
|---|---|---|
| 按什么日期算「今日」 | `occurred_at`（业务日期）/ `created_at`（录入时刻） | **`occurred_at`**——单据日期是用户填的，不是系统录入时刻 |
| 含赊账吗 | 含 / 不含 | **含**——「销售额」是业务发生额，不是实收款 |
| 含送货吗 | 含 / 不含 | **不含 `delivery`**——送货和销售单是两种业务（虽然都是出库），混在一起会让「开单 N 笔」变成「开了 N+送货 M 笔」 |

**但「不含 `delivery`」有一个后果**：用户在**送货模式**下用得多（你之前真机测试提到过「手机用户送货场景」），如果概览只算 `sale` 不算 `delivery`，用户会觉得「我明明今天送了不少单，怎么显示 0 笔」。

**建议**：

- 「今日经营」卡分两行：
  - 「店内销售 N 笔 · ¥X」
  - 「送货 M 笔 · ¥Y（未签收 K 张）」
- 如果嫌两行太复杂，**至少把送货笔数**也放进数字

### ② 「今日销售」会漏补录的单——文案要说清

`occurred_at` 是业务日期。用户**昨晚忘了录，今天补录一张昨天的单** ⇒ 这张单不进「今日销售」。

**技术上正确，但用户会困惑**：「我今天明明录了 5 张单，怎么显示 3 笔？」

**两种解法**：

| 解法 | 做法 |
|---|---|
| **甲（推荐）** | 文案明确：「**今日销售（按单据日期）**」——加三个字「按单据日期」，用户能懂 |
| 乙 | 增加「今日录入」的独立数字——但那是两个概念，会让卡片更复杂 |

**建议甲**——文案加限制条件，比增加数字简单。

## 二、快捷入口——**建议重选按钮**

提案说：

> 单据 / 库存 / 往来 / 账户 四按钮（跳转现有导航）

**但项目左侧导航已经把这四项列为「数据查询组」**——用户在导航里随时能点，概览页再放一遍**没有新价值**。

**概览页的快捷入口应该放「用户每开张要做的第一件事」**——看导航结构：

| 组 | 项 | 是否该进概览 |
|---|---|---|
| **高频动作** | 销售开单 · 采购入库 · 送货 | ✅ **这才是用户每天开工的入口** |
| 数据查询 | 单据 · 库存 · 往来方 · 账户 | ❌ 导航已有，无新增价值 |

**建议**：快捷入口放「销售开单 / 采购入库 / 送货」——这是用户打开软件后最想立刻做的事。

**如果用户诉求里明确说要「单据 / 库存 / 往来 / 账户」**——那也可以，但要知道这是**对导航的重复**，不是新增价值。**优先问用户想要哪种。**

## 三、其他要明确的

### ③ dayStart 由 UI 传——提案说的对，但要写清「UI 怎么算」

提案说：

> `todaySummary(DateTime dayStart)`（occurred_at ≥ 当日零点，dayStart 由调用方传入）

**好的设计——core 不做时间判断。** 但要明确：

- **UI 层怎么算 dayStart**：`DateTime.now()` 的本地时间零点（`DateTime(now.year, now.month, now.day)`）
- **测试怎么传**：固定值（`DateTime(2026, 10, 17)`）
- **跨时区的坑**：个体户单机单时区，暂不考虑。但如果将来多时区同步，这是隐患——**登记待办即可**

### ④ 手机端的数据新鲜度

手机壳读镜像——镜像可能**滞后于主机**（最后一次同步后主机有新单）。

**「今日销售」如果按镜像算**——用户**刚在手机上开了单还没推**，镜像里没这张 ⇒ 显示 0（但用户以为开了 1 单）。

**这与 `stockViewOf` 的「未同步影响」同源问题**。但 `deltaOf` 对单据能算叠加（`±quantity`），**对金额算不出**（客户端不跑规则）——所以手机端的「今日销售」**无法叠加未同步部分**。

**建议**：

- **手机端加一行小字**：「数据截至 X 分钟前（同步时间）」
- 如果怕误导，**手机端不显示「今日销售」数字，只显示「今日同步了 N 条」**——诚实但不完整
- 或：手机端显示「今日销售（仅已同步）」+ 「有 N 条未同步」

**我倾向最后一种**——诚实、有信息、与 `stockViewOf` 同口径。

### ⑤ 空库判据

提案说：

> 空库不显示，不干扰首次开张引导

**「空库」的判据要明确**：

- **甲**：`documents` 为空（有商品没开单也算「空」）
- **乙**：`products` 为空
- **丙**：任何业务数据

**建议甲**：概览页的卡是「经营概览」——没开过单就没经营数据，商品档案存在但没单据 = 空。

### ⑥ 响应式布局

**提案没提**：

- 桌面：三张卡横向排列？网格？
- 手机：三张卡竖排？**竖排会很长**——概览页本身还有「数据在哪 / 备份橙卡 / 导航提示」

**建议**：

- 桌面：三张卡横排（每卡占 1/3）
- 手机：卡片竖排但**紧凑**（减少 padding）+ 「快捷入口」做成一行图标 + 文字（不占整行）

### ⑦ 卡片是否可点

- 「今日经营」卡：点击能做什么？（跳单据页筛选今天的？）
- 「要留心」卡：应收点击跳往来方？负库存点击跳库存？

**如果不可点**：用户会以为是静态数字，也可以接受——但**失去了「点进去看详情」的机会**。

**如果可点**：需要「带筛选参数跳转」——可能超范围（单据页现在有筛选功能吗？没有的话要加）。

**建议**：

- 概览页卡片**不可点**（先做静态的）
- 快捷入口单独放（销售/采购/送货）

## 四、几个实施细节

### ⑧ 「今日销售额」的金额格式

应显示为：
- `¥1,234.50`（千分位 + 两位小数，与其它地方一致）
- 还是 `¥1234.5`（去千分位）？

**建议**：与项目其它金额**完全一致**——用 `Money.formatGrouped`（带千分位）。

### ⑨ 「欠款 N 家，列 top 1 店名+金额」

提案说：

> 应收合计 ¥A（欠款 N 家，列 top 1 店名+金额）

**「列 top 1 店名+金额」是把最大欠款的客户标出来**——用户看到「欠款 ¥5,000（其中张三 ¥2,000）」会立刻想到「该催张三了」。

**好设计，但要注意**：

- 如果**停用的客户欠款最多**——要不要显示？（按 OBS-05 结论，应该显示——「已停用但账未结清」）
- 如果用户不关心 top 1，加这个会增加信息密度

**建议**：

- **显示**——它提供的行动价值很高
- 如果停用客户的欠款最多，**标注「（已停用）」**——让用户知道这个客户档案已停用

### ⑩ 负库存的显示

「负库存 M 种」——**红字**是对的（这是警告）。

但**如果 M > 10**（比如新开店忘记录期初，全商品负库存）——「负库存 12 种」显示没问题，但**红字大面积出现会让用户紧张**。

**建议**：

- M = 0：不显示这一项（或显示「无负库存」绿色）
- M = 1–5：红色
- M > 5：加一句「新开张忘记录期初？」的提示（呼应 5.3 期初录入）

**这是次要的，可以后续优化。**

## 五、测试建议补充

提案说：

> core 两查询 test + selfcheck 镜像；根侧 widget 测试（有数字 / 空库不显示 / 入口跳转）+ 手机镜像实例化同源断言

**好的框架，但要补**：

- **「补录单据不进今日销售」的测试**——按 `occurred_at` 算的边界
- **「跨日重置」的测试**——传入 `dayStart` 是昨天 vs 今天，数字不同
- **「手机端未同步影响不叠加」的测试**——镜像有 1 单 + 有 1 单未同步，今日销售是否只算镜像的 1 单

**加这三条，测试才算完整。**

## 六、一句话收束

**方向对，可以做。但 5 处必须先明确：**

**① 「今日销售」的三个口径要定**（按 `occurred_at`、含赊账、**送货单独显示**——送货模式多的用户会被漏掉）；**② 文案要加「按单据日期」**——补录单不进今日销售，用户会困惑；**③ 快捷入口建议换成「高频动作」**（销售/采购/送货）而不是「查询类」——查询类导航已覆盖，放概览页是重复；**④ 手机端要处理数据新鲜度**——镜像滞后，加「仅已同步 + N 条未同步」的诚实口径；**⑤ 响应式布局要考虑**——桌面横排、手机紧凑竖排。

**附带 5 个次要建议**：空库判据明确（`documents` 为空）、卡片建议先不可点（跳转需筛选参数，超范围）、金额格式与项目统一（千分位）、`top 1 欠款`的「已停用」标注、`M > 5` 的「忘记录期初」提示。测试补 3 条：补录边界、跨日重置、手机端未同步。
