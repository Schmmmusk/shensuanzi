## 二、R-15 裁定：同意方向，但要改两处

### 同意「警告不拦人」

与数据目录同一原则：**中老年用户被拦住会认为「软件坏了」**。条码重复是真实世界的常态（同箱拆卖、同款不同批次），拦下来会挡住合法操作。

### 但改两处

#### 改动一：内联提示，不是弹窗

你的原话是「建档时警告」，但「警告」可以是两种形态，对用户的影响差别很大：

| 形态 | 中老年用户的行为 |
|---|---|
| 弹窗「条码已存在，继续吗？[是][否]」 | 每次都停下来读一遍 → 烦 → 逐渐不读 → 可能误点「否」 |
| **表单内橙色提示**（输入条码时实时出现） | 眼睛扫到就看到了，**不打断输入**，不增加点击 |

**裁定：内联提示。** 在条码输入框下方显示一行橙色文字：

```
⚠️ 这个条码已经给「娃哈哈矿泉水 550ml」用过了。
   保存后扫码会显示两条商品供选择。
```

**第二句是关键**——它同时说清了「为什么允许」和「扫码时会发生什么」。用户不会以为软件坏了，因为他知道下一步是什么。

#### 改动二：扫码行为必须配套修改

这是我想加的一条。当前 R-15 描述里写「扫码取最早建档那条」——**这个行为和「允许重复 + 警告」是矛盾的**：

```
用户看到警告 → 继续保存 → 有两条同条码商品
   ↓
以后扫码 → 系统静默选最早那条
   ↓
用户扫「A 商品」→ 系统弹出「B 商品」
   ↓
用户：？？？软件坏了
```

警告让他知道重复了，但扫码时**静默挑一条**又抹掉了这个信息。

**裁定：`findByBarcode` 返回列表，不只取最早的一条。**

| 匹配数 | 行为 |
|---|---|
| 0 条 | 提示「没找到这个条码」 |
| 1 条 | 直接使用 |
| **≥ 2 条** | **弹出选择器**，列出所有匹配项（名称 + 售价 + 建档时间），让用户点选 |

这样「允许重复」在整个链路里是自洽的——建档时提醒、扫码时呈现，不静默、不猜测。

**为什么必须现在改**：v1 还没做扫码，所以现在改只是把 `ProductDao.findByBarcode` 从「返回 `Product?`」改成「返回 `List<Product>`」，**零迁移**。等 Android 端上线了再改，会连带 UI、同步、测试一起动。

**一个附带好处**：这个设计天然支持「同款不同批次」（比如不同进货价的矿泉水）。用户扫码后自己选是哪一批——这正是真实店铺里会发生的事。

### 措辞建议

内联提示里的名字**用商品名**而不是编号：

| ❌ | ✅ |
|---|---|
| 这个条码已被占用（P0007） | 这个条码已经给「娃哈哈矿泉水 550ml」用过了 |

用户认名字不认编号。`ProductDao.findByBarcode` 拿到的第一条记录里就有 `name`，无需额外查询。

### 落地清单

| 层 | 改动 |
|---|---|
| `ProductDao.findByBarcode` | 返回类型 `Product?` → `List<Product>`，ORDER BY `(created_at, id)`（**不再 LIMIT 1**） |
| `ProductService` | 新增 `barcodeOwners(String barcode) → List<Product>`（供表单查询）；`create` / `update` 保存逻辑**不变**（允许重复） |
| `ProductDraft` | 新增纯函数 `barcodeNotice(List<Product> owners) → String?`（格式化提示文字），`dart test` 可覆盖 |
| `product_form_dialog.dart` | 条码输入框下方加一行橙色提示，实时更新 |
| `testing.md §R` | 补：`barcodeOwners` 返回多条；`barcodeNotice` 的文案格式；重复条码保存成功后 `findByBarcode` 返回 2 条 |
| `Agents.md §四` | 补一行裁定：「**条码重复：允许，建档时内联提示，扫码时显示选择器**」 |
| `Agents.md §五` | R-15 从「待裁定」移到「已裁定并落地」 |
