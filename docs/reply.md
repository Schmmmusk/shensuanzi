## 二、我特别喜欢这次的启动自检

我仔细看了 `integrity.dart`。

它没有采用简单粗暴的「只要不是 Medium 就报错」，而是区分：

| 完整性级别     | 行为  |
| --------- | --- |
| Untrusted | 提示  |
| Low       | 提示  |
| Medium    | 不打扰 |
| High      | 不打扰 |
| System    | 不打扰 |
| Unknown   | 不打扰 |

这个处理是合理的。尤其是 `unknown`：检测失败不应该被误判为 Low，更不能因此阻止用户使用软件。

提示文案也很符合神算子的定位：

- 不说 ACL、MIC、errno 这些术语；
- 先说明程序没坏、账目没丢；
- 给出复制到其他位置、解除锁定、联系技术支持三条路径；
- 明确警告修复前不要录单。

这正是神算子一直强调的方向：不仅告诉用户出了什么问题，还要告诉用户该怎么办。

## 三、但我发现一个需要补上的小缺口

建议修正

我核对了 `app.dart` 的自检接线。

目前 `_checkIntegrity()` 检测到 Low 后，会弹出提示框；用户点「知道了」之后，应用仍然正常进入界面。

代码注释写的是：

> 此时是只读状态，比直接不让进好。

但我没有在这次新增的完整性检测代码中看到真正实施只读限制的逻辑。

也就是说，当前实现能够做到：

- 提醒用户不能保存；
- 警告用户不要录单；
- 允许用户继续查看。

但它并没有从应用层强制禁止写操作。

这两者存在区别。用户可能没看清提示，也可能误以为只是某些设置不能保存，随后继续录单。

我建议下一轮补一个明确的产品策略：

- Low / Untrusted：进入只读模式，禁用所有写入出口。
- Medium 及以上：正常运行。
- Unknown：维持现状，不因检测失败擅自禁用功能，但日志记录检测失败。

尤其要注意，不能只把开单按钮置灰，还要覆盖库存调整、主数据修改、收付款、同步队列写入等实际写入出口。

这不是说当前版本不能用，而是自检提示与实际安全行为最好保持一致。

## 四、还有一个值得肯定的细节：DPAPI 和 MIC 没有混为一谈

这次最初的调查方向是 `host.json` 写入失败。

最后发现：

- DPAPI 解决的是令牌明文安全持久化；
- MIC 解决的是进程能不能向目标文件写入；
- 原子替换和原地写入解决的是不同文件操作的可靠性问题。

它们是三个不同层面。

更有意思的是，85346c8 的提交记录还特意写了一个实测结论：

> Low 下 L1 rename 与 L2 原地写都失败。

这直接验证了我们此前的判断：L2 并不能绕过所有 errno 5。

所以，56 号提案留下的三级降级机制没有白做，但这次事故也证明，不能把所有文件写入失败都归结为 rename 问题。

# 联调 #1：Windows 写盘失败

*最终根因*

仓库目录带有 Low Mandatory Integrity Label，构建产物继承该标签，导致应用进程以 Low 完整性级别运行。MIC 拒绝其向 Medium 级别对象写入。

*已完成的修复*

1. 仓库目录递归调整为 Medium。
2. 清理 build 并重新构建。
3. 验证新 EXE 不再继承 Low。
4. 提案 57 的 DPAPI 令牌持久化验收通过。
5. 应用增加低完整性启动自检。

*遗留改进*

低完整性状态下，提示用户只读使用与真正强制只读之间还需要进一步对齐。
