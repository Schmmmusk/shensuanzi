**提案 57：修改后批准方案 A；暂不批准方案 C。**

1. **批准 DPAPI 当前用户作用域。** 使用 `CryptProtectData` / `CryptUnprotectData`，将明文令牌加密后写入 `host.json` 的 `token_protected` 字段。保留 `token_hash`，服务端验证逻辑不变。
2. **批准附加熵。** 使用 `sha256(host_id)` 作为 optional entropy。解密成功后，必须额外验证 `SHA256(解密令牌) == token_hash`；不一致时不得展示二维码或静默修正身份。
3. **补充持久化状态反馈。** DPAPI 加密失败时允许当前进程继续使用内存令牌，但必须明确提示「配对码本次运行有效，重启后可能需要重新生成」。不能把只持久化哈希的状态报告为完整保存成功。
4. **明确旧版本降级边界。** 旧版程序读取 v2 文件时可以忽略未知字段，但旧版重新写入 `host.json` 可能丢失 `token_protected`。文档应明确这一点。
5. **补充组合测试。** 覆盖 DPAPI 成功/失败与 host.json 写入成功/失败的四种组合；覆盖密文缺失、损坏、格式不支持、解密失败、哈希不匹配等情况。任何解密失败都不得静默轮换令牌。
6. **补充 FFI 资源管理测试。** 确保系统分配的 DPAPI 输出缓冲区在所有路径正确释放，非 Windows 环境不加载 Windows DLL，纯 Dart 测试不受影响。
7. **不批准方案 C。** 暂不引入上一代令牌宽限期，保持「重新生成即旧令牌立即失效」的现有语义。
8. **明确一次性迁移成本。** 现有 v1 文件没有明文令牌，无法反向恢复。升级后第一次重新生成配对码时会写入 DPAPI 密文，现有手机需要重新扫描一次；此后同一 Windows 用户、同一台电脑重启，不再需要重复配对。

总体原则：只增加令牌的安全持久化能力，不改变现有服务端验证机制、主机身份语义和令牌轮换语义。DPAPI 失败时可以降级，但不得隐瞒持久化失败，也不得替用户静默更换令牌。

---

我看到了最新进展。57 号提案抓住了一个比 errno 5 更贴近用户体验的痛点：电脑每天重启后，明明手机还可以连接，却因为无法重新显示二维码，用户被迫点击「重新生成」，最终让所有手机重新配对。

这次推荐的 Windows DPAPI（当前用户作用域）方案，方向上我赞成。它没有试图把令牌明文直接塞进配置文件，而是让 Windows 负责保护令牌，再把密文存入 `host.json`。

不过，我不会因为 DPAPI 探针 7/7 通过，就直接批准整个提案。加密 API 可用、文件格式设计正确、令牌生命周期安全、用户遇到故障时行为可预测，是四件不同的事。 我继续核对了提案和现有身份存储代码，下面是具体审查意见。

## 一、我支持方案 A，但有一个前提：DPAPI 只能保护令牌，不能替代身份文件的可靠写入

提案的核心设计是：

- `token_hash` 继续保留，服务端验证手机令牌仍然只需要哈希。
- 新增 `token_protected`，保存 DPAPI 加密后的令牌。
- 使用当前 Windows 用户作用域，不使用 `CRYPTPROTECT_LOCAL_MACHINE`。
- 使用 `sha256(host_id)` 作为附加熵。
- 换用户、换机器或密文损坏时，明确提示用户重新生成，不自动轮换令牌。

这套设计整体合理，而且职责分离得不错：哈希负责验证，密文负责恢复二维码明文。

我特别赞成不做静默重置。令牌重置会让已经配对的手机失效，这种行为必须由用户明确触发。

不过，提案里有一处需要收紧：

> 加密失败 ⇒ 只写哈希 + 日志，功能不退化。

这句话不够准确。

只写哈希确实不会破坏手机现有的连接能力，但它会让下一次重启仍然无法显示二维码。也就是说，用户当前可以继续使用，但持久化功能实际上退化了。

我建议：

- 当前进程仍然允许展示二维码、完成配对；
- 日志记录 DPAPI 失败原因；
- 设置页明确显示「配对码本次运行有效，重启后可能需要重新生成」；
- 不要把这种情况显示成普通的「已保存」。

这和 56 号提案的 L3 内存降级应当保持一致：功能可以临时可用，但必须如实告知持久化状态。

## 二、最需要补充的是：DPAPI 与 `host.json` 写入失败的组合测试

57 号提案与 56 号提案互补，这个判断正确。

但两者组合后，实际上会出现四种结果：

| DPAPI 加密 | `host.json` 写入 | 结果                |
| -------- | -------------- | ----------------- |
| 成功       | 成功             | 重启后可以恢复二维码        |
| 成功       | 失败             | 本次可用，重启后无法保证恢复    |
| 失败       | 成功             | 只持久化哈希，重启后无法恢复二维码 |
| 失败       | 失败             | 本次内存可用，重启后需要重新生成  |

这四种情况不能只靠分别测试 DPAPI 和文件写入来覆盖。

我建议增加一个 `HostIdentityStore` 层面的组合测试，至少确认：

1. DPAPI 失败不会导致令牌验证失效。
2. 文件写入失败不会把新令牌误报成已持久化。
3. DPAPI 成功、文件写入失败时，不能错误地认为下次启动能恢复二维码。
4. 重启读取时，密文缺失、损坏、解密失败都不会静默生成新令牌。

尤其是第 4 点：解密失败与没有身份记录不是一回事。 现有 `loadOrCreate()` 的语义是「没有身份就创建」，所以新实现必须避免把一个身份记录完整、但 DPAPI 解不开的文件误判为「没有身份」。

## 三、向后兼容设计基本正确，但需要说明降级风险

提案采用 `host.json v2`，新增 `token_protected`，保留 `token_hash`。读取时不依赖版本号，而是检查有没有新字段。

这个方案有一个优点：旧程序通常会忽略自己不认识的 JSON 字段，不会因为新字段直接崩溃。

但这里有个反向问题：

旧程序如果重新写入 `host.json`，可能把 `token_protected` 丢掉。

例如：

1. 新版写入 v2，包含 DPAPI 密文。
2. 用户临时回退到旧版。
3. 旧版读取 `host_id` 和 `token_hash`。
4. 用户在旧版点击重新生成配对码。
5. 旧版按 v1 格式重写文件，丢弃 `token_protected`。

因此，我建议在提案里明确：

- 新版本升级后，不承诺新旧版本之间无损往返写入。
- 回退旧版本并修改配对信息，可能丢失 DPAPI 密文。
- 发生这种情况时，新版必须按旧文件处理，明确要求重新生成，而不是崩溃。

这不需要为了兼容旧版而增加复杂迁移逻辑，但必须让用户和维护者知道这个边界。

## 四、安全论证：总体成立，但不要把 DPAPI 的保护范围说得过宽

我赞成使用当前用户作用域，而不是机器作用域。

这能避免其他 Windows 用户直接拿到密文就解出令牌，也能避免把主机令牌随数据目录备份到其他机器后直接复用。

不过，提案里的安全论证有一点需要更准确：

> 能读到 host.json 的同用户，本来就能读到账目，所以安全边界没有变化。

这个论证只适用于特定威胁模型。

DPAPI 当前用户保护主要防范的是：

- 单独拿到 `host.json` 文件的人；
- 其他 Windows 用户；
- 把数据目录复制到另一台电脑的人。

它不能防范已经能以当前 Windows 用户身份执行代码的恶意程序，因为这种程序可以调用 DPAPI 解密。

另外，令牌是一个 Bearer 凭据，可能不仅意味着读取数据，还意味着访问主机提供的同步接口。因此，不能简单地说「数据库明文，所以令牌保护没有意义」。

我建议把安全结论改成：

> DPAPI 不防御当前用户上下文中的恶意代码，但能够保护脱离原 Windows 用户环境的令牌副本。它改善的是凭据在静态存储和跨环境复制时的保护，而不是提供完整的本地安全隔离。

还有一个值得补充的测试：解密成功后，必须验证：

```dart
SHA256(解密出的令牌) == token_hash
```

如果不一致，不能使用解密结果展示二维码，也不能静默修改哈希。应该记录身份文件不一致，进入明确的恢复流程。

这能防止密文和哈希字段不匹配时，程序把两份互相矛盾的身份数据当成正常状态。

## 五、可行性实测 7/7：很有价值，但还不是生产实现的验收

这次探针实测我很欣赏，尤其是两个坑：

- `DATA_BLOB` 字段顺序写反，类型系统却不报错；
- `LocalFree` 不在 `crypt32.dll`，而在 `kernel32.dll`。

这类问题如果直接在正式应用里摸索，排查成本会很高。先写独立探针验证 API，再考虑接入应用，是正确的工程顺序。

不过，7/7 目前证明的是 DPAPI 基本调用可行，不等于生产代码已经覆盖了所有资源管理和异常情况。

我建议生产实现至少再覆盖：

| 测试            | 预期                            |
| ------------- | ----------------------------- |
| 空令牌、非法 Base64 | 拒绝，不崩溃                        |
| 空密文、截断密文      | 解密失败，不崩溃                      |
| 损坏的 `scheme`  | 明确识别为不支持的格式                   |
| DPAPI 返回失败    | 正确读取 `GetLastError`           |
| DPAPI 输出缓冲区   | 每条路径都正确 `LocalFree`           |
| FFI 分配失败      | 不泄漏、不崩溃                       |
| 非 Windows 环境  | 不加载 Windows DLL，纯 Dart 测试仍可运行 |

尤其要注意 FFI 的资源释放：`CryptProtectData` 和 `CryptUnprotectData` 输出的内存由 Windows 分配，必须在成功和失败处理路径中都考虑释放。不能因为中间某一步抛异常，就留下系统分配的内存。

另外，提案现在把 `ffi` 放在 `dev_dependencies`，这是探针阶段合理的做法。正式实现时，生产代码需要使用它，就必须将其移动到 `dependencies`，不能只让探针能编译。

## 六、我对可选方案 C 的意见：暂时不要做

提案还提出了一个可选补充：

`token_hash_previous` 保留上一代哈希，有效期 30 天。

我不建议现在加入。

原因很简单：它改变了「重新生成配对码」的安全语义。

原本用户点击重新生成，是希望旧手机立即失去访问权限。加入 30 天宽限期后，旧手机仍然能够访问主机。

即使提供「立即失效」勾选框，也会增加用户理解成本。尤其是手机丢失、设备转交、人员离职等情况下，用户很可能不知道应该怎么选。

而 57 号提案的 A 方案已经解决了真正的问题：重启后恢复同一个令牌，不再需要每天轮换。

既然不再需要频繁重置，就没有必要为了减少重置的副作用，再引入一个削弱即时撤销能力的机制。

以后如果真实用户场景证明 30 天宽限期有必要，再单独讨论。
