# 审查意见

先说结论：

- **这是一份极其克制、标准的重构提案。** 手术刀切得很准——只抽 `ListHeader` 等外壳组件，不碰底层迥异的行 UI，完美避开了“为了复用而强行抽象”的泥潭。
- **6 个待裁定项，我全部同意你的推荐方案。**
- **但在落地时，有 3 个隐藏的工程细节需要注意（特别涉及搜索性能）。**

---

## 一、关于 3 个决策点的意见

### ① 单据页「真实总数」：选甲（加 COUNT 查询）
**绝对支持甲。** 数据显示到 200 条就静默截断，本质上是对用户的欺骗。尤其是对账时，老板发现系统里说“共 200 单”，但其实有 348 单，会引发信任危机。
- **工程提醒**：`listDocuments` 和 `countDocuments` 的 `WHERE` 构造器**必须完全一致**。同时，因为单据页支持“按内容搜索”（四路 `LIKE`），在数据量大时 `COUNT` 可能会慢。**必须确保这两个查询在同一个防抖（debounce）触发下执行**，避免用户敲一个键，同时发两次全表扫。

### ② 往来方/账户：只加文本搜索
**同意。** 角色/类型筛选在开单页（选择器）和单据页已经足够了，主数据页再放一排筛选会让中老年用户眼花缭乱。一个大大的搜索框（“搜索姓名 / 电话 / 备注”）是最直接的解法。

### ③ 行箭头加在哪些行：只加在「跳走」的行
**极度赞同。** `ui_principles.md` 里明确提到“所有功能必须有常驻可见的入口 + 文字标签”。箭头（`chevron_right`）是移动端和现代 UI 的通用语言，代表“点击会有新页面”。如果用在不跳转的行上（比如打开弹窗），会破坏用户的预期。

---

## 二、落地时的 3 个工程细节提醒

### 1. 搜索框防抖（Debounce）必须统一
对于**库存页**（搜索查 5 个聚合）、**单据页**（搜索走四路 LIKE）和**往来方/账户**，如果用户在输入框里连打 5 个字，触发了 5 次 `setState` 和全量 SQL 查询，在低配机器上会明显卡顿。
- **建议**：在 `ListHeader` 的 `onChanged` 回调外部，统一包一层 `Debounce`（比如 300ms），或者使用 `TextField` 的 `onEditingComplete` 和清空按钮触发，而不是每次按键都实时查库。

### 2. `ListHeader` 里的 Key 不要丢
目前的测试用例（比如 `products_page_test`）可能会通过 `find.byKey(Key('products-search'))` 来定位输入框。在抽离 `ListHeader` 时，**务必让外部传入的 `searchKey` 依然能挂到内部的 `TextField` 上**，否则会导致大量现有的 Widget 测试红掉。

### 3. 清空按钮的交互闭环
单据页加“清空筛选”按钮时，点击后**不仅要重置筛选条件的状态，还要重置搜索框里的文字**，并且触发一次全量刷新。
- **建议**：文案最好写成“清空全部筛选”，或者用带垃圾桶图标的文字按钮。
