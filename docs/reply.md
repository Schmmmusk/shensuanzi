## 二、落地时必须写死的 4 个工程暗坑

方案逻辑很严密，但在写 Dart 代码时，这四个地方极易翻车，请务必盯紧：

### 1. `dispose` 里的草稿写入必须是**同步的**
方案里写：*“页面 dispose（用户直接关窗口）⇒ 立刻写一次”*。
- **坑**：如果你在 `dispose()` 里调 `await file.writeAsString(...)`，代码一执行到 `await`，当前的 widget 就被销毁了，如果用户紧接着关闭整个 App，这个异步写盘**一定会被中断**，数据直接丢失。
- **解法**：在 `dispose()` 里必须用同步写盘 `file.writeAsStringSync(...)`。因为此时只是序列化后的几十 KB JSON 字符串，同步写大概只要 1-2 毫秒，不会造成卡顿。

### 2. 手机端（`mobileShell`）不要瞎拦截
方案里写：*“本批不动手机端，只做桌面”*。
- **坑**：如果你在 `SalePage` 里加了这个逻辑，手机壳（`mobileShell == true`）里同样会生效。由于手机端是推入路由，频繁返回很容易触发 `dispose`，导致草稿疯狂读写。
- **建议**：**顺其自然让它生效**。手机端用户同样面临填一半退出丢失的风险。由于你已经用 `QueueSink` 把单据写进队列了，草稿的写入机制在手机端一样适用且安全（只要确保手机的数据目录路径 `path_provider` 可写即可）。

### 3. 草稿里的商品名匹配（`findByExactName`）
方案提到：*“先按名字精确匹配现有商品”*。
- **坑**：名字里可能带空格，比如用户输入了 `" 蒙牛纯牛奶"` 或 `"蒙牛纯牛奶 "`，你如果不用 `trim()` 去数据库查，就会匹配不到，导致新建一个多余的。
- **解法**：查库前必须 `name.trim()`，而且 SQL 最好用 `TRIM(name) = ?`，保证绝对精确匹配。

### 4. 查价页的防抖与扫码枪
方案说：*“输入即筛（300ms 防抖）”*。
- **坑**：如果是 USB 扫码枪，它会瞬间输入十几个字符并在最后加一个回车。如果加了 300ms 防抖，扫码枪输入完，页面还要等 300ms 才出结果，用户会觉得卡。
- **解法**：监听输入框的 `onSubmitted`（回车）。如果扫码枪带了回车，立刻打断防抖，无条件去查一次 `findByBarcode`。如果没有查到，再退回按名字模糊搜索。
