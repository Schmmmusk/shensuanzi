## 一、方案 A 的核心论证确认

提案说：

> 主数据行**客户端全知**（用户填什么就是什么），与单据本质不同（金额/状态权威值由主机规则算出，不能乐观写）。

**这个论证是成立的。** 它与 `data_model.md §七` 的「客户端不跑规则」不冲突：

- 主数据：`name` / `unit` / `sell_price` / `package_size` 全是用户直接输入的字段 → 客户端**全知** → 可以乐观写。

**这是「客户端不跑规则」原则的精确边界，不是破例。** 提案把它写成「`data_model.md §4.4` 第 3 条例外」——这个措辞要改，**它不是例外，是原则的延伸**。

## 二、方案 A 必须补写的 5 处边界

### ① 客户端 `max(code)+1` 必须与主机同序【必须明确】

`data_model.md §2.1` 明确：

> **取最大编码时必须 `ORDER BY LENGTH(code) DESC, code DESC`** —— 先比长度再比字典序，等价于「数值最大」。

**客户端的 `max(code)+1` 必须用同一逻辑**，否则会生成主机认为已存在的 code。

**建议明确：**

> 客户端生成 code 的查询：`SELECT code FROM products ORDER BY LENGTH(code) DESC, code DESC LIMIT 1` —— 与 `ProductCodeGenerator` 逐字同逻辑。这一条要写进 D1 的实现要点。

### ② 主机端 code 改派的实现位置必须写清【硬缺口】

提案说：

> 主机端同 code 异 id ⇒ 主机改派 code（主数据本就允许 UPDATE + 乐观锁）

**但没说这个逻辑写在哪一层。**

`Agents.md 4.1` 明确：

> **建档只有一条路径** —— 建档 / 编辑**必须走 `ProductService`**（生成编码、校验、补版本都在里面）；Windows 界面与将来的 `SyncServer.createMasterData` **共用同一条路径**。

**所以 code 改派必须发生在 `ProductService` 里**，而不是 `SyncServer` 里。`SyncServer.createMasterData` 只是转发。

**这意味着 `ProductService.create()` 的签名要改**——它现在自己生成 code，之后要接受调用者传入的 code 并在冲突时改派。

**建议明确：**

> `ProductService.create()` 增加可选参数 `preferredCode`：
> - 不传 → 走现有逻辑，自己生成 code（Windows UI 路径，行为零变化）
> - 传了 → 检查是否被**异 id** 占用；占用则走改派逻辑生成新 code；否则用传入的
>
> `ProductService` 是唯一入口，`SyncServer.createMasterData` 调用它，不自己写 code 冲突逻辑。

### ③ 「在 push 确认前编辑」是硬缺口【必须裁定】

场景：

1. 客户端乐观创建 P0042（本地 `sync_version = 0`）
2. **主机还没确认**（队列里 `pending`）
3. 用户又编辑了这个产品（改名）

此时客户端发出 `updateMasterData`，`base_version = 0`。主机收到时：

- **如果 `createMasterData` 已经先处理了**：主机有 P0042，`sync_version = 0` → `base_version` 匹配 → 成功
- **如果 `createMasterData` 还没处理**（队列乱序或重试）：主机没有 P0042 → `base_version` 找不到目标 → **rejected**

**第二个场景怎么办？**

**建议明确：**

> `QueueSink` 对同一实体的多次操作，在队列里**按 entity_id 合并**——如果队列里已有该 entity 的 `createMasterData`，新编辑**更新那个条目**，不追加新的 `updateMasterData`。这样保证 push 顺序是「先 create 后 update」，主机不会收到乱序。
>
> 这是 `SyncQueueDao` 的增强，D2 要处理。

**如果不做这个合并，v1 Android 真机上「建完立刻改名」就会出死信。**

### ④ 镜像 `upsert` 的幂等性必须确认【要检查】

客户端乐观写了 P0042，之后 pull 回来主机的 P0042（或改派的 P0043）。**镜像落库必须是 UPSERT，不是 INSERT。**

如果现有 pull 逻辑是按 id 插入，遇到已存在的 id 会怎么办？

**建议 D1 明确：**

> 镜像 pull 对主数据表用 `INSERT ... ON CONFLICT(id) DO UPDATE`。乐观行 + 权威行天然收敛到同一行。

这是 `SyncClient` 的现有行为确认，不是新增——但如果没做，D2 会看到重复行。

### ⑤ `readOnlyMasterData` 命名已过时【建议改名】

提案说：

> `readOnlyMasterData` 语义从「弹引导」替换为「**本地建档 + 入队**」

**这个名字现在是反的**——它不再「只读」，而是「本地可写 + 入队」。

**建议改名：** `canCreateMasterDataLocally` 或 `localMasterDataEnabled`。语义清晰，避免后来人看代码时被误导。

D2 顺手改，成本极低。

## 三、方案 A 的其他细节

### 6. `rejected` 后三态条明细的文案要具体

提案说：

> 三态条「失败」明细提示「请到电脑上重新建」

**这个文案太笼统。** `rejected` 的原因可能很多：

- id 冲突（两台手机同时建同名）
- 校验失败（用户填了非法值，但客户端漏了）
- 权限问题（主机侧白名单拒绝）

**建议：**

> 三态条明细显示主机的 `rejected` 原因（主机返回的 message），并给一句「下一步怎么办」。**具体文案由主机决定，不在客户端造句**——符合「错误信息由领域层给出」原则。

### 7. `updateMasterData` 的 `base_version` 来源要写清

提案说：

> `updateMasterData`（base_version 乐观锁，镜像行自带 sync_version）

**但要写清「镜像行的 sync_version 什么时候更新」**：

- pull 下来 → 覆盖
- 乐观写 → 初值 0
- push 成功 → **不更新**（等 pull 回来）
- push 的 `applied` 回执是否含新版本？**要看协议 §8.1**

**这是 D1 要确认的现有行为**，不是 D2 新增。如果协议里 `applied` 回执不带新版本，那客户端必须等 pull 才能拿到新版本——这是正确的，但要写清。

### 8. 乐观行与 pull 的竞争【要有顺序保证】

场景：

1. 客户端乐观写 P0042
2. 同时，另一台手机也建了 P0042 并推到主机
3. 主机给后来的改派为 P0043
4. 客户端 pull，收到主机的 P0042 和 P0043

**客户端的乐观行 P0042 与主机的 P0042 是同一 id 吗？**

- 如果是**同一 id**：pull 覆盖乐观行，没问题。
- 如果是**不同 id**：客户端会有两行 P0042（乐观 + 权威），冲突。

**这是 D1 要处理的关键边界**——乐观行的 id 由客户端生成，主机的 id 也是客户端生成的（同一个），所以是同一 id。pull 覆盖即可。

**但要在 D1 写清这个断言**，否则实现者可能想歪。

## 二、方案 B1′ 逐条评价

### 1. 流水页整页限幅 `maxFactor: 1.0`

**方向对，但 1.0 太硬。** 理由：

- 提案说「页内全是单号/数字，放大收益低」——**这个判断对**。这个页面的主要信息是「单号 + 金额 + 日期」，其中金额已经 17 号加粗，单号是等宽数字——放大对可读性提升有限，但挤爆布局的代价很大。
- **但 1.0 意味着完全取消放大**。用户在 200% 缩放下，其他页大字、这一页回到原尺寸，**切换页面时的视觉落差会非常突兀**——中老年用户会以为「这一页坏了」。

**建议改为按屏幕宽度动态限幅，而不是硬编码 1.0：**

> 窄屏（`< 600`）时限幅到 `maxFactor: 1.15`（与 §CH 提案 B1 的初步值一致），保留少量放大余量；宽屏不限幅。

或者：**限幅到「当前宽度下 title 和金额都不截断」的最小值**——用 `LayoutBuilder` 实测。

**`maxFactor: 1.0` 只在极端情况（如 200% + 极窄屏）作为兜底**，不要作为默认值。

### 2. 行重排（两行布局）

**推荐，这是治本措施。** 理由：

- 两行布局符合 `ui_principles.md §1.1`——**所有信息常驻可见 + 文字标签**：
  - 行 1：类型标签（灰小字）+ 金额（大字加粗）
  - 行 2：docNo（加粗，独占整行）+ 日期（灰）
- docNo 独占一行，**不再与金额抢宽度**，从根本上消除「中间硬折」问题。
- 金额单独一行，可以**保留 17 号加粗**，不牺牲可读性。

**唯一要确认的是：** 两行布局在**桌面宽屏**下是否也需要？如果桌面宽屏下 `ListTile` 一行放得下全部信息且不折行，那桌面可以保持现状。

**建议：** 行重排**仅窄屏**。宽屏保持单行。

### 3. AppBar 收窄为「导出」+ Tooltip 保留完整说明

**这里有一个违反 `ui_principles.md §1.1` 的隐患。**

`ui_principles.md §1.1` 明确写：

> | 悬浮提示（hover） | 不会悬停 → 看不到 |

**把「导出该往来方的全部流水」放进 Tooltip，用户永远不会看到这个 Tooltip。** 也就是用户只知道「导出」按钮，不知道它导的是什么。

**建议改为：**

- **按钮文字保留「导出」**（符合 §1.1：文字必须在）。
- **完整说明放到「点击后」的确认对话框里**：用户点「导出」→ 弹一个对话框「将导出 XXX 的全部 N 条流水」→ 用户确认 → 执行。
  - 这样完整说明**在动作发生前呈现**，且是用户主动触发的，不是被动 hover。
  - 用户永远能看到「我要导什么」。
- **或者更简单：按钮文字改成「导出流水」**——四个字，比「导出」多两字，语义更完整，比「导出该往来方的全部流水」短得多，不会挤压 title。

**我推荐第二种：按钮文字改为「导出流水」**。成本最低、语义清晰、不引入对话框。
