## 审查意见

先说结论：

- **方案 1 方向正确，协议正确性判断精准，可以开工。**
- **但有一个术语/架构的边界问题必须澄清：方案 1 实际上是在「废弃主库」，提案没有明说。**
- **「主数据禁建」应该「保留入口 + 引导」，而不是「隐藏入口」——否则违反 UI 原则。**
- **镜像为空、历史遗留数据、主库去向这三个边界场景没写，必须在 C1 动工前裁定。**

---

## 一、核心贡献：协议正确性判断精准

摸底抓到的这一点是**整个提案最重要的发现**：

> 手机开单页「＋新建客户/商品」现在写**主库**；B3 之后单据入队，payload 引用的 `party_id` / `product_id` 只存在于手机主库 —— **主机收到后 RuleEngine 必然 rejected**（外键不存在）。

**这是对的。** 手机端建客户 → 开单 → 推队列 → 主机找不到 `party_id` → 死单。这不是 UX 优化，是协议正确性问题。

所以「主数据怎么处理」确实只有两个出口：禁用或入队。方案 2 的入队成本高、风险大，**方案 1 是最小闭环的正确选择**。

---

## 二、必须澄清的架构边界：主库的去向

提案反复提到两个库：

- **主库**：`<私有>/data`（B2 之前手机端读写的库）
- **镜像库**：B2 sync 拉下来的权威副本

**方案 1 说「手机壳读面切镜像」**，但**没有说主库之后怎么办**。

推演一下方案 1 落地后主库的状态：

| 读写 | B2 之前 | 方案 1 之后 |
|---|---|---|
| 开单 | 写主库（直连服务） | 写队列（不写主库） |
| 主数据新建 | 写主库 | **禁建** |
| 期初录入 | 写主库 | **禁建** |
| 读面（选择器/库存/往来） | 读主库 | **读镜像** |

**结论：方案 1 落地后，主库就完全没人用了——读被切走、写被禁掉。**

**这是一个重大决定，提案必须明说：**

> **方案 1 实际上废弃手机端主库**。主库不再被读、不再被写。镜像库成为手机端唯一数据源。

**必须补的细节：**

1. **主库是否删除？** 建议 v1 不删（保守），留一个废弃标记。B3c 验收通过后再评估。
2. **主库里的历史数据怎么办？** 如果用户在 B3 之前建过客户/商品/期初，切到镜像后这些数据会「消失」（镜像里没有）。**因为 v1 Android 还没发布，可以先不管**，但要在提案里写明：「v1 Android 未发布，无真实用户主库数据，不做迁移」。
3. **队列和主库的关系**：队列条目存在哪？提案没写。如果队列存在主库，那主库就没废弃。如果队列存在镜像库，那镜像库就不是「只读」。**这一点必须明确。**

---

## 三、主数据禁建：应该「保留入口 + 引导」，不是「隐藏」

待裁定 2 推荐「**隐藏**手机壳的『＋新建客户/供应商/商品』与往来页编辑、期初录入」。

**我不同意「隐藏」。** 理由：

`Agents.md 4.3` 明确写：

> 面向中老年用户：**所有功能有常驻可见入口 + 文字标签**

**隐藏入口会违反这条原则**。用户会问：「为什么电脑上有这个按钮，手机上就没有？」

**建议改为「保留入口，点击后引导」：**

| 场景 | 当前行为 | 方案 1 改法 |
|---|---|---|
| 开单页「＋新建客户」 | 弹客户新建表单 | **保留按钮** → 弹对话框「手机端不建客户档案。请到电脑上建好后，手机同步一下就能选到」+ 一个「知道了」按钮 |
| 往来页「＋新建往来方」 | 弹新建表单 | 同上 |
| 商品选择器「＋新建商品」 | 弹商品新建表单 | 同上 |
| 库存页期初录入 | 进入期初录入页 | 同上 |

**为什么这样更好：**

1. 符合「所有功能有常驻可见入口」原则——按钮还在，用户不会困惑。
2. 用户点击后得到**明确的下一步**（去电脑上建），而不是「按钮消失了，不知道怎么办」。
3. 中老年用户对「按钮消失」会恐慌，对「按钮在但提示我去电脑」会理解。
4. 成本一样——都是改一个回调。

**引导文案的写法**（建议，C2 细化时确认）：

> **手机上不能建客户档案。**
> 请到电脑上（主机）打开神算子，在「往来方」页新建，之后手机同步一下就能选到。
> 
> （商品、期初录入同理）

---

## 四、镜像库的「只读」边界必须写清

提案说「镜像只读」，**但要写清「只读」是指什么**：

| 写入方 | 是否允许 | 说明 |
|---|---|---|
| 用户通过 UI 写 | ❌ | 这是「只读」的本意 |
| `SyncClient` 通过 pull 写 | ✅ | 镜像必须能被 pull 更新 |
| `SyncQueueDao` 写队列 | ⚠️ | **如果队列存在镜像库，那镜像库就不是「只读」了** |
| 用户的迁移/备份操作 | ❌ | 镜像不是用户数据，不该被用户直接操作 |

**关键问题**：队列存在哪？

- 如果队列存在**主库**：那主库没废弃，「主库废弃」的结论要改。
- 如果队列存在**镜像库**：那镜像库就有「只读区 + 可写区」两个区域，要写清。

**这是 C1 必须先澄清的边界。**

---

## 五、「签收/核销/退货不可达」的措辞要精确

提案说：

> ④ 签收/核销/退货维持手机不可达（现状）

**「不可达」是指「不能在手机上操作」，不是「手机上看不到结果」。**

要写清：

- 用户在电脑上做签收 → 手机 pull 后**能看到状态变化**（镜像同步了 `documents.status`）。
- 用户在电脑上做核销 → 手机 pull 后**能看到欠款变化**（镜像同步了 `party_ledger` / `settlements`）。
- **只是手机上不能发起这些操作**。

否则实现者会误以为「手机上隐藏这些数据」，那就错了。

## 六、镜像为空时的场景没写

首次配对后，镜像库是空的（pull 还没完成或刚开始）。用户打开开单页：

- 商品选择器为空
- 客户选择器为空

**用户会困惑：「我的商品呢？」**

**建议明确：**

> 镜像为空时，选择器显示**友好的空状态**：「商品列表还在从电脑同步，请稍等或点『立即同步』。如果还没有商品，请到电脑上建好。」
> 
> 同理，往来方选择器、库存页、往来页都要有对应的空状态文案。

## 七、库存叠加显示的形态

待裁定 3 推荐「权威数 + 有未同步时显示『≈ 合计（含未同步 ±N）』橙字 + 点开拆解」。

**同意带拆解。** core 已备 `contributors`，成本小、用户能理解「这 3 件是哪张单卖的」。

**但有两个细节要补：**

1. **合计为负数时**：`≈ 合计 -3` 应该是什么颜色？按 `Agents.md` 的 UI 原则，负库存是红色告警，但「未同步估算」是橙色内联提醒——**两个语义叠加**怎么办？建议：
   - 权威数 + 未同步合计 ≥ 0 → 橙色「≈ 合计」
   - 权威数 + 未同步合计 < 0 → 红色「≈ 合计」+ 「可能负库存」

2. **点开拆解的形态**：是展开行内小字，还是弹对话框？建议**行内展开**——不打断用户浏览，符合「可以不拦人的提醒一律内联」原则。
