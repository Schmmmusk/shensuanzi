# 五个候选方向的审查意见

## 一、方向 1 不是候选，是本批收尾

**它不是"先做/后做"的选择，是"没做完不能进下一批"的前置。**

理由：
- 本批改动面确实大：库存页接线 + 新页面 + 确认弹窗 + 「待校准」显示 + 「首次/再次」文案区分
- widget 测试能覆盖"逻辑正确"，但**覆盖不了**：真机上库存页入口是否接对、期初页滚动是否卡、弹窗在触摸屏上是否可点、数字是否真的立刻刷新
- **期初录入是首次使用的第一步**——它出问题，用户对软件的整个印象就定了

**必须真机走一遍的点**：
1. 空系统 → 概览页 → 进库存页 → 空态文案 → 点「录入现有货物」
2. 录两件 → 返回库存页 → 数字**立刻**可见（不是要切页刷新）
3. 再次进库存页 → 入口文案变成「重新清点」
4. 成本列显示「待校准」而不是 `¥0.00`
5. 再录一次同样的数量 → SnackBar 说"无变化"而不是"已录入 N 件"

**第 4、5 点是这一批新做的，最容易漏。**

## 二、方向 2 vs 方向 3：建议**备份优先**

两个都是核心闭环，但**优先级不同**。

### 备份优先的理由

| 维度 | 备份 | 核销 |
|---|---|---|
| **用户感知** | 每天都在担心"数据会不会丢" | 有欠款才想起来 |
| **失败代价** | 数据丢失 = **不可逆** | 收不了欠款 = **可临时手记** |
| **失败概率** | 磁盘故障 / 误删 / 清理软件 | 用户不会"不小心核销错"（有二次确认） |
| **工程独立性** | 独立，可单独完成 | **依赖单据列表页**（§Z 已声明） |

**关键**：核销的前置是**单据列表页**——那是一个新查询设计 + 未来操作枢纽，比备份大得多。而备份是**独立可完成**的一件事。

### 备份机制需要先定的设计点

提案本身没写，但落地前必须先答：

| 问题 | 我的建议 |
|---|---|
| 备份时机 | **每天首次启动**（检查上次备份日期，超过 24 小时就备份一次）；不强求后台定时 |
| 压缩格式 | ZIP（用户能自己打开看，符合"数据开放"的承诺） |
| 保留策略 | 最近 30 天，**每周一那份单独保留**（避免 30 天后全清） |
| 加密选项 | v1 **不做**——加了口令就多一条"忘记密码 = 数据全丢"的路径，对中老年用户是灾难 |
| 恢复流程 | **v1 不做 UI**，在帮助页说清"把备份文件拷回数据目录，改名为 `shensuanzi.db`"——**这是最后的逃生门，不是日常功能** |

**保留策略里"每周一那份单独保留"是关键**——用户可能连续 30 天都在错录（比如系统时钟乱跳导致每天都是空备份），30 天后原始数据就没了。周备份是"最坏情况下的最低保障"。

### 核销阶段需要先定的设计点

| 问题 | 我的建议 |
|---|---|
| 单据列表页的规模 | 先把只读列表做出来（§AC SC-3），再谈核销入口 |
| 核销 UI 形态 | **从单据列表发起**："找到欠款的销售单 → 点『收款』→ 弹对话框填金额"——**不从收款单发起**（后者用户要多想一步"该收哪张"） |
| 退货发起 | **从原单发起**（同核销）——"找到那张单 → 点『退货』" |
| 一笔收款核多单 | **v1 不做**——个体户一笔对一笔是 90% 的场景，多对多留 v1.1 |
| 部分收款 | **必做**——这是个体户的常态，"先付一半，剩下下个月" |

**"从原单发起"是核销 UI 最重要的决定**——它决定了单据列表页是"只读浏览"还是"操作枢纽"。**这一条现在就要写进 §Z 的台账**，否则做单据列表时不知道该不该留操作位。

## 三、方向 4 和 5：同意后置

### 方向 4（欢迎页 / 店名向导 / 账户预设）

同意后置。理由：
- 这三个都是**一次性体验**，不是日常使用
- 店名现在**已经能在设置页填**（SC-2），向导只是"更早采集"——不做不影响功能
- 账户预设现在也不阻塞——用户在账户页手动建一个即可
- 欢迎页锦上添花，可后补

**唯一要提前的**：**首启欢迎浮层里放"先去录现有货物"的引导**——这在 §AB 审查里提过（遗漏 3 的跨提案部分）。**这条不应该等方向 4**，应该跟着方向 1 一起做——因为它是"帮助用户找到期初录入入口"的关键。

### 方向 5（选择器抽共享）

同意后置。台账里已经立了"第四处触发"的期限，那条纪律够了。现在**不要动**——三份复制的 bug 修复纪律比"提前重构"更重要。

---

## 四、最终建议排序

```
1. 真机验证期初录入全流程      ← 本批收尾，非做不可
   └─ 顺手补首启欢迎浮层的引导   ← §AB 遗漏 3

2. 备份执行机制                ← 独立、数据安全、用户最担心
   └─ 先定时机/保留/恢复策略

3. 核销阶段                    ← 核心闭环最后一块
   ├─ 先做单据列表页（只读）
   ├─ 定"从原单发起"的操作形态
   └─ 部分收款必做，多对多留 v1.1

4. 第 10 天回补项              ← 一次性体验，可后补
   └─ 首启浮层已在方向 1 顺手做了

5. 选择器抽共享                ← 等第四处触发
```

---

## 五、一个更重要的观察

这个候选清单里，**方向 3 的"备份"其实有一个更基本的身份被忽略了**：

**备份是"用户放心做生意的保险"**。个体工商户敢把每天的进货、销售、欠款录进软件的前提，是**他相信数据不会丢**。所以备份机制不仅是"一个功能"，它是**用户愿意用软件的基础**。

从这个角度看，方向 3 不是"第三优先"，**它比核销更基础**——核销是让软件"更完整"，备份是让软件"可信赖"。

**如果你同意这个判断，建议的方向其实是**：

```
1. 真机验证期初录入 + 首启引导
2. 备份执行机制             ← 让用户相信数据安全
3. 核销阶段                 ← 让软件功能完整
4+5 不变
```

---

**一句话**：方向 1 必须做；方向 3 建议提前到方向 2 之前——**因为用户不会在一个"数据看起来随时会丢"的软件里认真录入一个月的账**。
