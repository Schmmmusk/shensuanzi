# 二、新发现的 P0：方向错误的流水仍可能通过抢救 建议阻止验收

这是我本轮最重要的发现。

我重新对照了 `RuleEngine` 的实际写入规则，发现抢救器现在有三处都使用了绝对值比较。

问题是：库存、资金和往来流水的正负号不是展示信息，而是业务含义本身。

## 1. 库存流水：销售出库变成入库，也可能被判完整

当前 `_stockProblem()`：

```dart
lineQty[pid] += qty.abs();
stockQty[pid] += qty.abs();
```

它确实可以发现数量不符，但完全忽略了方向。

而真实规则是：

| 单据类型              | 库存流水数量       |
| ----------------- | ------------ |
| `purchase`        | 正数，入库        |
| `sale`            | 负数，出库        |
| `delivery`        | 负数，出库        |
| `sale_return`     | 正数，入库        |
| `purchase_return` | 负数，出库        |
| `stocktake`       | 根据盘点差额，正负均可能 |

假设一张销售单销售 10 瓶可乐：

- 明细数量：10
- 正常库存流水：-10
- 损坏后的库存流水：+10

现有判据计算：

$ |10|=|{-10}|=|10| $

无论实际库存增加还是减少，检查都通过。

最终用户可能恢复出一笔卖出 10 瓶，库存却增加 10 瓶的交易。

这显然不可接受。

相关代码：[库存完整性检查](packages/shensuanzi_app/lib/src/rescue.dart, 1018~1075)

建议修复：按 `doc_type` 检查预期方向，而不是只比绝对值。

对一般交易单据，可以比较每个商品的有符号数量合计：

$ \text{stock quantity sum} = \begin{cases} +\text{line quantity sum},&\text{采购、销售退货}\\\ -\text{line quantity sum},&\text{销售、送货、采购退货} \end{cases} $

盘点继续保留目前已经裁定的特殊策略，不要强行要求它满足一般单据的方向规则。

建议加两条反向灵敏度测试：

- 销售库存流水由 -10 改为 +10，必须判不完整。
- 采购库存流水由 +10 改为 -10，必须判不完整。

## 2. 往来流水：客户欠款变成客户预付款，也可能被放行

`_partyProblem()` 当前比较的是：

```dart
sum.abs() != totalCents.abs()
```

但往来流水的正负号同样具有明确语义。

| 单据类型                       | 正常往来流水方向 |
| -------------------------- | -------- |
| `sale` / `delivery`        | 正数       |
| `purchase` / `sale_return` | 负数       |
| `purchase_return`          | 正数       |
| `payment`                  | 正数       |
| `receipt`                  | 负数       |

例如，一张 ¥100 的销售单，应该增加客户欠款，往来流水是 +100。

如果坏页把它变成 -100：

- 金额绝对值仍是 100；
- 行数不变；
- 往来方仍然存在；
- 现有检查通过。

但业务含义已经完全反过来了：客户欠你 100，变成你欠客户 100。

这不是小误差，而是账务方向错误。

建议根据 `doc_type` 检查有符号金额合计。散客、散采仍按现有规则豁免。

## 3. 资金流水：付款变成收款，同样可能通过

`_moneyProblem()` 对 `receipt/payment` 也采用了绝对值比较。

但 `RuleEngine._settle()` 明确规定：

- `receipt`：`money_ledger.amount` 为正数。
- `payment`：`money_ledger.amount` 为负数。

因此，正常付款单 -100 被破坏为 +100 后，现有检查仍然会认为金额正确。

恢复后的账户余额会反着计算。

这三项其实是同一个根本问题：

抢救器目前检查了数量级和金额级，却没有完整检查方向级。

我建议不要分别打三个补丁，而是把预期方向明确整理成按业务类型分支的判据，再分别测试库存、往来和资金流水。

# 三、另一个 P1：收付款单的必填引用尚未完整复核

上次你们新加的 `_ledgerRefProblem()` 有一处条件值得再补。

目前代码只有在单据上的 `party_id` 或 `account_id` 非空时，才进行对应的一致性比较。

但 `RuleEngine._settle()` 明确要求：

```dart
if (doc.accountId == null) ...
if (doc.partyId == null) ...
```

也就是说，正常的 `receipt/payment` 单据必须同时拥有账户和往来方。

现在假设坏库中的一张收款单变成：

- `party_id = NULL`
- `account_id = NULL`
- 资金流水仍指向一个存在的账户；
- 往来流水仍指向一个存在的往来方；
- 核销记录也完整。

当前检查可能出现以下结果：

1. `_firstMissingRef()` 不会把 NULL 判为缺失引用。
2. `_ledgerRefProblem()` 发现流水引用的账户、往来方都存在，但因为单据字段为空，不进行一致性比较。
3. `_partyProblem()` 因为单据没有 `party_id`，把往来检查当作不适用。
4. 资金和核销金额仍能匹配。

最终这张违反规则层要求的收款单可能被导入。

建议：

- 对 `receipt/payment`，强制检查 `account_id`、`party_id` 都存在。
- 资金流水账户必须与收付款单账户一致。
- 往来流水往来方必须与收付款单往来方一致。
- 普通散客销售等允许没有往来方的业务，继续按原规则处理。

参考：[RuleEngine 收付款单必填校验](packages/shensuanzi_core/lib/src/rules/rule_engine.dart, 790~810)、[抢救引用检查](packages/shensuanzi_app/lib/src/rescue.dart, 1280~1320)。
