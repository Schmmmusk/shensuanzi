## 二、对测试脚本的审查意见

你提供的这四个 Python 脚本质量极高，完全符合企业级性能测试的标准。有几个细节非常值得称赞：
1. **`perf_seed.py` 的体量控制与自洽校验**：能直接在写完后用 SQL 反算 `paid_amount`、校验 `seq_no` 无空洞、校验外键，确保了压测数据不是垃圾数据。
2. **`perf_monitor.py` 的 `ctypes` 直接读进程指标**：没引入 `psutil` 这种第三方库，纯标准库读取 CPU/内存/句柄，方便分发。
3. **`perf_bench.py` 的 `EXPLAIN QUERY PLAN`**：不仅测时间，还能把执行计划抓出来，这对排查“为什么慢”至关重要。

### 需要微调的小细节（不影响大局）
- **`perf_bench.py` 里的 `LIKE` 转义**：你的 `q_doc_search` 里写的是 `d.doc_no LIKE '%1%'`，在压测脚本里跑没问题，但真实生产代码里（因为用户可能输入 `50%`）是做了 `ESCAPE '\'` 处理的。建议在压测脚本里也补上 `ESCAPE '\'`，做到**压测与生产同构**。
- **`perf_seed.py` 的外键开关**：脚本里开了 `PRAGMA foreign_keys = ON`，这很好，但注意 `Emitter.flush()` 里的依赖顺序（单据 -> 明细 -> 流水）。请确保 `money_ledger` 和 `party_ledger` 的插入在 `documents` 之后，当前代码里的 `order` 元组是对的。

## 三、针对 4c 热路径修复的落地提醒

### 1. 开单页缓存（4c-1）
在页面状态里缓存 `stockSnapshot`。
- **坑**：用户在 A 行选了商品甲，缓存了快照；然后去 B 行选了商品乙，这时候需不需要重取？不需要。但如果用户在选商品时**新造了单**（在后台/另一台电脑），本地缓存肯定不知道。
- **解法**：在 `_afterSaved`（保存成功）时把缓存置为 `null`（失效），下次 build 时自然重取。在用户从商品选择器选完商品回来时，**不需要**重取。

### 2. 库存页合并聚合查询（4c-2）
把 `stockByProduct`、`inTransitByProduct`、`costByProduct` 合并成一条。
- **坑**：如果在 SQL 里用多个 `LEFT JOIN` 做聚合，很容易产生**笛卡尔积**，导致 `SUM` 成倍放大。
- **正确写法**：用标量子查询，或者针对每个聚合分别 `GROUP BY` 后用 `UNION ALL` 再聚合，或者写一个 `WITH` (CTE) 把三个表按 `product_id` 聚好再 `LEFT JOIN`。
- **断言**：合并后，务必跑一次 `EXPLAIN QUERY PLAN`，确认没有全表扫两次。

### 3. 单据页两段查询（4c-3）
先查 ID（`LIMIT 200`），再 `IN (IDs)` 查完整数据。
- **坑**：`IN` 的参数个数限制。SQLite 默认 `MAX_VARIABLE_NUMBER` 是 999（新版是 32766），`LIMIT 200` 是绝对安全的。
- **断言**：注意如果在两段查询之间刚好有数据被删除，第二段可能查不到某些 ID。代码里需要 `if (row == null) continue;`（或者直接忽略），不要抛出空指针异常。

## 四、门槛与门禁的落地

把性能门槛（§五）写进 `docs/testing.md` 是非常好的。
但**不要**把耗时的 `perf_bench.py` 直接塞进 CI 的常规门禁里（因为跑一次要几秒到几十秒）。建议：
- **CI 门禁**：只跑 `EXPLAIN QUERY PLAN` 断言（毫秒级）。
- **发版前人工检查**：跑一次 `perf_bench.py` 对比上一个版本的 CSV，如果 p95 劣化超过 30%，则拒绝发版。
