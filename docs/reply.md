我先给一个总体判断：P1-1 应该做，而且值得优先；设置页拆分也有价值，但我支持先拆「关于」的渐进方案，不支持一次性拆完整个设置页。

下面说具体审查意见，尤其是 P1-1 方案里还有几处值得在开工前补严的地方。

## 一、P1-1：盘点单丢失录入原文单位

建议立项，优先实施

这项不是单纯的显示问题，而是单据记录不完整。

### 1. 根因判断正确，而且确实有两个丢失点

我对照了当前源码，确认提案中的判断成立。

目前链路是：

用户在重新清点页面输入

例如：2 箱

`OpeningStockPage.\_draft()`

调用 `toBaseQuantity`，转换成 48 瓶，只把转换后的数量放入 `StocktakeLineDraft`

`StocktakeDraft`

只有 `productId`、`productName`、`quantity`，没有录入数量和单位

`RuleEngine.\_stocktake()`

通过 `actualByProduct` 重建 `DocumentLine`，继续只写 `quantity`

最终结果

`quantity = 48`

`entry_quantity = NULL`

`entry_unit = NULL`

这意味着库存计算是正确的，但用户回头查看单据时，无法知道当时究竟输入了 2 箱还是 48 瓶。

相关代码：

- `OpeningStockPage`
- `StocktakeDraft`
- `RuleEngine`.\`_stocktake`
- `Schema` 中已经存在的两个字段

所以提案最重要的发现是对的：只给 `StocktakeLineDraft` 加字段是不够的，规则引擎重建 `DocumentLine` 时也必须保留它们。

### 2. 我认为方案还缺少一个关键细节：原文与标准数量的对应关系

现有数据模型的语义很清楚：

| 字段               | 含义         | 例子 |
| ---------------- | ---------- | -- |
| `quantity`       | 最小单位下的实际数量 | 48 |
| `entry_quantity` | 用户原始输入数量   | 2  |
| `entry_unit`     | 用户原始输入单位   | 箱  |

这个设计很好，三个字段各司其职。

但提案中建议 `entryQuantity` 为空时等于 `quantity`，同时又要求没有切换单位时两列保持 NULL。这里最好明确为：

- 用户没有切换单位：`entry_quantity = NULL`、`entry_unit = NULL`。
- 用户按包装单位录入：保存原始数量和包装单位。
- `quantity` 始终保存换算后的最小单位实际数量。

不要因为用户恰好输入了 `48`，就把 `48` 当成一条有录入原文的记录。

另外，建议明确一个不变量：

 $\text{quantity} = \operatorname{toBaseQuantity}( \text{entryQuantity}, \text{entryUnit} )$ 

对于没有原文记录的旧单据，则不适用这个校验。

### 3. 提案还需要补齐手机端链路

这是我认为目前最值得补充的施工要求。

`OpeningStockPage` 有两种出口：

- 桌面端：`StocktakeService` 直接落库。
- 手机端：`DocumentSink` → `QueueSink` → 主机 `RuleEngine`。

当前手机端提交的也是 `StocktakeDraft`。如果只改桌面端构造逻辑，手机端仍然可能丢失原文。

建议把端到端路径写清楚：

桌面端

1. `StocktakeLineDraft` 保留原文
2. 构造 `DocumentLine`
3. `RuleEngine` 落库

手机端

1. `StocktakeLineDraft` 保留原文
2. `QueueSink` 构造并入队单据
3. 同步传输时不丢 `entry` 字段
4. 主机 `RuleEngine` 落库

建议增加两条端到端测试：

1. 桌面按箱盘点 2 箱，详情显示 2 箱（=48 瓶）。
2. 手机按箱盘点 2 箱，完成同步后，主机数据库中同样保留 2 箱和 48 瓶。

这里尤其要注意：不能让手机端自行生成权威库存差额。 这次只增加原文记录，不能改变 RULE-009 的权威计算位置。

### 4. 测试方案基本合理，但我建议增加一个反向护栏

提案已有：

- 按箱盘点 2 箱，检查原文两列和标准数量。
- 未切换单位，检查原文两列为 NULL。

我建议再加一条：

更换商品后，旧商品的包装单位不能残留。

当前 UI 在 `_pickProduct()` 中已经把 `entryUnit` 清空，这是正确的。将来调整草稿字段时，也应保证这个行为不变。

此外，旧盘点单原文为空是正常的历史事实，不应进行数据回填。这个决定我完全支持。

P1-1 最终意见：方案方向通过，补齐手机链路和字段不变量后可以施工。

## 二、设置页拆分：我支持乙案，先拆「关于」

建议渐进实施

这项工程的目标也很明确。

现在的 `settings_page.dart` 已经达到 1087 行，六个功能区块混在一个页面中：

- 概览图表
- 界面大小
- 店名
- 数据
- 数据刷新
- 多设备同步

对普通用户来说，设置页不是一个需要一次性展示所有东西的仪表盘。

用户通常是带着目的来的：

- 想调大字体；
- 想查看备份；
- 想更换数据位置；
- 想连接手机。

把这些入口组织成二级页面是合理的。

### 1. 甲案为什么不适合现在做？

甲案一次拆成四个子页面：

```text
设置
├── 界面
├── 数据与备份
├── 手机与同步
└── 关于
```

这个结构本身没有问题。

问题是当前设置页已经有：

- 11 个被测试引用的 Key；
- 19 条测试用例；
- 11 个构造参数；
- 配置实时保存和父层配置回灌逻辑；
- 桌面端与 Android 端不同的设置内容。

这些不是简单把几个 `Column` 拆成几个 Widget 就能解决的。

特别是配置保存行为。

现有 `SettingsPage` 的 `_current` 用于累积连续修改，`didUpdateWidget()` 则负责接收父层迁移后推送的新配置。

如果拆页面时把这套状态管理拆散，很容易重新引入旧路径被写回的问题。

这不是可以接受的回归。

### 2. 乙案是更好的第一步

我赞成先把「关于」独立出来：

```text
设置
├── 原有设置内容
│   ├── 概览图表
│   ├── 界面大小
│   ├── 店名
│   ├── 数据与备份
│   └── 多设备同步
│
└── 关于
    ├── 版本
    ├── 许可
    ├── 第三方组件
    └── 手册入口
```

这样有三个好处：

1. 先验证二级页面的导航体验。
2. 先验证 Key 如何迁移、如何保持测试可定位。
3. 不动最敏感的配置保存、数据目录迁移和备份逻辑。

这是一项很适合小步试验的 UI 工程。

### 3. 我建议补充四项验收要求

| 验收点    | 具体要求                           |
| ------ | ------------------------------ |
| 返回行为   | 从关于页返回设置页，原来的设置状态不丢            |
| Key 保留 | 原有 Key 仍可在进入相应子页后找到            |
| 配置保存   | 改缩放、店名后仍然立即生效并写盘               |
| 双端行为   | Android 和 Windows 都能正常打开、返回关于页 |

还有一点：关于页面的版本号最好直接读取应用版本信息，不要手写一个固定字符串。否则下一次发布很容易忘记同步。

对于许可和第三方组件清单，应当继续以仓库现有依赖与许可证材料为准，不要在拆页时顺手重新整理或删减。

### 4. 乙案的一个小改进

我建议设置页的「关于」入口放在现有设置内容的末尾，而不是塞进数据安全区附近。

原因很简单：

- 界面大小、店名属于日常偏好。
- 数据与备份属于经营数据安全。
- 关于属于软件自身信息。

这三个认知类别应该分开。

另外，关于页可以采用普通二级页面，而不是弹窗。版本、许可证、第三方组件列表可能比较长，页面更容易滚动，也更适合 2 倍字号。

设置页拆分最终意见：乙案通过，甲案暂缓。

## 三、两项工作的优先级

我的建议与提案作者基本一致：

| 顺序 | 工作          | 理由                    |
| -- | ----------- | --------------------- |
| 1  | P1-1 盘点原文落库 | 影响真实单据可追溯性，涉及数据完整性    |
| 2  | 设置页乙案：先拆关于  | 纯 UI 结构调整，风险低，能验证拆页方式 |
| 3  | 设置页全量拆分     | 观察第一阶段后再决定，不预先承诺      |

但我想补充一个重要区别：

P1-1 不属于库存计算错误。当前库存仍然按照最小单位数量正确计算，缺失的是原始录入信息。

它是单据可追溯性缺陷，不是现有库存数值错误。这个定性有助于避免 Agent 为了修复它而误动 RULE-009 的计算逻辑。

## 四、我认为这份方案还可以补充的事项

| 项目        | 建议                        |
| --------- | ------------------------- |
| P1-1 手机端  | 明确检查 QueueSink 的原文保留和同步传输 |
| P1-1 数据兼容 | 明确旧单据 NULL 不回填，新旧客户端兼容    |
| P1-1 字段语义 | 明确 `quantity` 永远是最小单位数量   |
| 设置页乙案     | 明确返回时设置状态保持               |
| 设置页乙案     | 明确所有原有 Key 的新定位           |
| 设置页乙案     | 明确双端关于页面均可访问              |

我还建议不要把这两项交给 Agent 一次性完成。P1-1 的数据链路和设置页的 UI 结构应该分别施工、分别验收。

## 最终审查结论

P1-1：盘点原文落库

*建议优先实施*

- 根因取证成立。
- Schema 已有字段，无需迁移。
- 补齐手机 QueueSink 链路后施工。
- 不改变库存计算语义。

设置页：拆分二级页面

*建议采用乙案*
- 先拆「关于」。
- 保留现有配置状态管理。
- 保留原有 Key 和测试语义。
- 全量拆分暂不承诺。

最后说一句：这次两项工作我都认为值得做，但不要因为 P1-1 标了 P1，就让它变成一场大规模重构。它的边界其实很清楚：保存用户原文，不改库存真相。

设置页也一样，先拆一个子页，验证好结构再说。

这两项都不需要再开性能优化支线。咱们就老老实实把产品打磨好。🤓
