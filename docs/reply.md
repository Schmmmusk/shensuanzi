# 对施工清单 55 的具体意见

总体上我赞成这个清单，施工拆分也比较合理。但有几个细节，我认为值得在 Agent 开始对应任务前补进文档。

## 1. 退款上限：UI 应该显示剩余可退款金额

55 中提出：

> 原单真实收款大于零时，退款上限 = 真实收款。

这里还差一步。

假设：

- 原单实际收付 100 元；
- 第一次退货已经实际退了 80 元；
- 现在第二次退货。

此时第二次最多只能再退 20 元，而不是 100 元。

所以我建议把界面实际使用的额度定义为：

$$ \text{剩余退款额度} = \max(0,\text{原单实际收付}-\text{累计实际退款}) $$

本次实际退款上限：

$$\min(\text{本次退货金额},\text{剩余退款额度}) $$

规则层当然还要再校验一次。UI 主要负责让用户从一开始就知道还能退多少钱，而不是等提交时才发现超过上限。

还有一个措辞问题：销售、送货原单对应的是实际收款，采购原单对应的是实际付款。施工文档最好统一称为原单实际结算金额，再按业务方向解释。

## 2. 完整性判定：我建议再补一条金额不变量

这是我认为整个 55 最值得加强的地方。

我们已经考虑了：

- 每个商品的明细行数与库存流水行数相符；
- 每个商品的数量合计相符；
- 收付款单的核销总额相符；
- 核销双方必须都能找到。

很好。

但还有一种情况：

| 数据       | 原始状态 | 抢救后 |
| -------- | ---- | --- |
| 销售单金额    | 50   | 50  |
| 商品明细金额合计 | 50   | 40  |
| 库存流水对应数量 | 5 行  | 4 行 |

如果丢失的明细行和对应库存流水行一起消失，剩余两边的行数与数量依然匹配。

因此，我建议增加这条检查：

$$\sum(\text{document\\\_lines.amount}) = \text{documents.total\\\_amount}$$

这不是和库存流水的 `total_cost` 比金额。后者确实不能简单比较，因为成本、让价和折扣口径不同。

这是在验证单据自己的金额与明细金额是否一致。

而且，规则引擎已经有 `_requireLinesTotalMatches()` 这一业务不变量，抢救模块理应复用同样的判断思想。`stocktake`、`receipt`、`payment` 等例外仍按各自规则处理。

另外，55 还没有明确列出 `party_ledger` 的完整性判据。

神算子的应收应付真相在这张表里。缺少它，就可能出现商品库存已经恢复、单据金额也恢复，但客户欠款却少了一笔的情况。

同理，`receipt/payment` 不仅要核对 `settlements`，还应该检查对应的 `money_ledger`。规则引擎中每张收付款单都会写资金流水；自动收付款也会写相应资金和核销记录。

我建议完整性判定至少覆盖：

| 数据关系        | 应验证的内容               |
| ----------- | -------------------- |
| 单据 ↔ 明细     | 行数、金额合计              |
| 明细 ↔ 库存流水   | 按商品核对行数、数量           |
| 单据 ↔ 往来流水   | 按 `party_id` 和业务金额核对 |
| 收付款单 ↔ 资金流水 | 账户、金额和方向             |
| 收付款单 ↔ 核销   | 核销总额、双方引用完整          |

这样才真正对得起“按业务单元判断完整”的设计目标。

## 3. WAL 复制：已经做得不错，但方案与实现有一处不一致

我对最新 `rescue.dart` 做了核对。

当前 `_FileSnapshot` 比较的是：

- 文件是否存在；
- 文件大小；
- 最后修改时间（毫秒）。

而 53 号方案中仍写着要比较：

- 文件大小；
- 修改时间；
- WAL 的 salt。

实现里的注释则明确解释了为什么没有读取 salt。

这不是说当前实现一定有问题，但方案与代码的检测标准不一致，最好统一一下。

另外，这种文件状态比较是一道实用的防护，不是独占锁。它不能从数学意义上证明复制期间文件绝对没有发生过任何变化。考虑到抢救通常是在应用已经无法正常打开、没有活动数据库连接的情况下使用，我认为当前轻量方案有现实价值，不必因为这个问题就马上引入复杂的跨平台文件锁。

我的意见是：把文档更新为实际实现的检测边界，明确它的定位是检测文件变化并安全失败，而不是提供完整的 SQLite 在线快照机制。

## 4. 经营图表：有一个业务口径必须先定

55 里保留了这个问题：

> 在途送货算不算营收？

这是一个真正的产品决策，不是 SQL 写法问题。

目前 `todaySummary()` 把未取消的送货也计入今日销售，因此按现有行为，正在运输但尚未签收的送货也在其中。

而新的 `dailyNetRevenue()` 若使用：

```dart
status != 'cancelled'
```

同样会把在途送货算进去。

我倾向于第一阶段保持与现有 `todaySummary` 一致，避免不同页面对同一经营数据采用两套口径；但最好在界面上明确说明销售额包含未签收送货，或者至少显示未签收数量。

这项应当在编写 `dailyNetRevenue()` 前定案。

至于自然周、空白日补零、按类型拆开查询、`buildDailySeries()`，我都赞成照 55 的定义执行。

# 三、我对接下来施工顺序的建议

之前原定顺序已经挺合理，我只建议把完整性判定的补充条件一起纳入：

| 顺序 | 施工内容                                      | 我的意见             |
| -- | ----------------------------------------- | ---------------- |
| 1  | 退款规则与 UI 上限                               | 先落规则层，再接 UI      |
| 2  | `refundedAgainstCentsOf()` 改用 settlements | 必须独立提交并对拍        |
| 3  | 抢救完整性判定                                   | 补金额、往来流水、资金流水检查  |
| 4  | Schema v7 索引                              | 独立提交，完整跑迁移链      |
| 5  | 时间序列聚合与纯函数                                | 查询与业务口径测试先完成     |
| 6  | 图表 UI 原型                                  | 暂时不急，后续再验字号和窗口适配 |

其中第 2 项一定不要省掉对拍测试。因为它修改的是已有显示数据的来源，出现新旧算法不一致时，必须先查清 `paid_amount` 缓存为什么与 `settlements` 不同，不能直接把差异当成历史脏数据忽略。
