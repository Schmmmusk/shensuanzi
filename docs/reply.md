# 审查意见

先说结论：

- **强烈推荐选甲（全量格式化），且必须作为当前阶段的第一步。**
- **这不仅是因为那 204 个文件，更因为如果现在不改，以后每次改代码都会像“狗啃”一样，夹带着格式变动。**
- **用 `git diff -w` 和全量测试作为安全绳，这是极低风险的“物理级”隔离。**

---

## 一、为什么必须选甲？

Dart 3.7 换用 Tall Style 后，**所有使用新版 SDK 的 IDE（如 VS Code / Android Studio）在你每次保存文件时，都会用新风格重新格式化当前文件。**

如果你选乙（只修那两处）或丙（不弄），接下来会发生什么？
- 你今天去改 `sale_page.dart` 的逻辑，保存时，IDE 自动把整个文件按 Tall Style 重排了。提交时，你的逻辑改动里混着几百行格式变动，Review 极其痛苦。
- 你明天去改 `mobile_shell.dart`，同样的事情再发生一次。
- 最终仓库里的代码风格会变成“一半旧风格，一半新风格，取决于谁在什么时候改过它”。

**长痛不如短痛。趁着现在 0.6.1 刚发布，仓库处于相对稳定的状态，一次性完成迁移，把 `format` 纳入门禁，从此一劳永逸。**

---

## 二、如何安全执行甲？（防翻车四步法）

既然是全仓重排，绝对不能和业务代码混在一起。请严格按以下流程操作：

1. **切断一切正在修改的业务代码**。如果有没提交的修改，先 `git commit` 或 `git stash`。
2. **在一个全新的分支（或就地在 main 上）执行**：
   ```bash
   dart format .
   ```
3. **提交为孤立 commit**：
   ```bash
   git commit -am "chore: apply Dart 3.7 tall style formatting across repo"
   ```
4. **核验物理隔离（关键步骤）**：
   ```bash
   git diff HEAD~1 -w
   # 或者 git diff HEAD~1 --ignore-all-space
   ```
   **预期结果：输出为空，或只有极少量因为换行导致的问题。** 如果输出为空，就绝对证明**一行逻辑代码都没动**。
5. **跑全量门禁**。确认 `flutter analyze` 没报错，`flutter test` 全绿，`typecheck` 全绿。
6. **加入门禁**：立刻在 `tool/` 下或 CI 脚本里加上 `dart format --output=none --set-exit-if-changed .`。

---

## 三、关于 Git Blame 变得难看的补救

选甲最大的副作用是：`git blame` 会显示这些代码都是今天写的，导致追溯历史变难。

**解法**：
告诉将来的自己（或者如果有其他协作者）：在查历史时，使用命令忽略这个格式提交：
```bash
git blame --ignore-rev <该commit的哈希> <文件名>
```
如果是在 GitHub 网页端，也可以在 blame 视图里点击“忽略空白”（Ignore whitespace）或者直接看上一个版本。

---

## 四、为什么不选乙和丙

- **乙（只修两处）**：治标不治本，且 `format` 进不了门禁。以后每次改代码都在夹带格式重排，Review 成本极高。
- **丙（推到 0.7）**：掩耳盗铃，0.7 的时候文件更多，改起来更痛。

---

## 五、一句话收束

**直接上甲。用 `dart format .` 扫全仓，单独开一个 commit，用 `git diff -w` 证明没有逻辑变动，然后把 `dart format` 钉死在门禁里。这是完成“尺寸与结构（批 3）”和“错误定位（批 1）”之前，必须扫清的场地地雷。**
