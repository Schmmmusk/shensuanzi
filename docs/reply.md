# 两个欠账的审查意见

## 总评

**都同意做，但归不同批次。** 欠账 1（列表过滤）落 **1a**——核销上线后它会立刻变成用户体验问题；欠账 2（连接泄漏）落 **Schema 批次**——它是迁移失败路径的一部分，与迁移测试共用一套夹具。

---

## 一、欠账 1：列表过滤自动生成的收付款单

### 同意两个判断

**判断 1：约定未落地确实是欠账。**

`data_model.md` 与 `rules.md` 都写了"默认过滤"，但 `_summaries` 只按 `doc_type` / `occurred_at` 过滤。核销上线后用户会看到：

```
销售单：卖给老王 ¥5,000（已收）
收款单：收到老王 ¥5,000（自动生成）  ← 混在列表里
```

用户看到"一笔交易两条记录"，会以为系统记重了。**这是核销上线后立刻会撞到的问题**，必须 1a 一并处理。

**判断 2：`ref_doc_id IS NOT NULL` 单独作过滤条件会误伤退货单。**

核对 `ref_doc_id` 的使用场景：

| `doc_type` | `ref_doc_id` | 是否该显示在列表 |
|---|---|---|
| `purchase` / `sale` / `delivery` | `null` | ✅ 显示 |
| `sale_return` / `purchase_return` | **指向原单** | ✅ **显示**（退货是独立交易，必须出现） |
| `receipt` / `payment`（自动生成） | **指向来源主单** | ❌ 过滤 |
| `receipt` / `payment`（手动） | `null` | ✅ 显示 |

所以 `ref_doc_id IS NOT NULL` 会**连退货单一起滤掉**——退货单凭空消失在列表里，用户看不到自己退过什么。

**精确条件**：

```sql
doc_type IN ('receipt', 'payment') AND ref_doc_id IS NOT NULL
```

### 文档措辞一并修正

`data_model.md:361` 与 `rules.md:21` 两处都要改：

```markdown
UI 单据列表默认**过滤掉自动生成的收付款单**，条件为：
`doc_type IN ('receipt', 'payment') AND ref_doc_id IS NOT NULL`。

⚠️ **不能只写 `ref_doc_id IS NOT NULL`** —— 退货单（`sale_return` /
`purchase_return`）也填 `ref_doc_id`（指向原单），单独用它会把退货单一起滤掉。
```

**为什么两处都改**：`data_model.md` 是字段级说明，`rules.md` 是"统一资金流原则"末尾的应用注记。它们现在措辞一致（都错），要一起纠正——这是 `testing.md §零` 的镜像纪律在**文档层**的体现。

### 落入 1a 的理由

- 核销上线后，用户第一眼就会看到自动生成的收款单**混在列表里**——**这是产品的第一印象问题**
- 列表页的行行为在 1a 里本来就要改（行点击从"复制单号"变"打开详情"），过滤条件**同一次改动一起落地**
- 加一个 WHERE 子句 + 改两行文档，**成本几乎为零**

## 二、欠账 2：`Db.open` 迁移失败未 dispose

### 判断准确，是真 bug

看 `schema.dart` 的迁移执行器——`migrationStep` 抛错时（迁移 SQL 失败 / 版本跳跃 / 迁移缺失），调用栈会往上抛，但**已经在 `sqlite3.open(path)` 建立的连接不会关闭**。

后果分两层：

| 层 | 后果 |
|---|---|
| **Windows 文件句柄** | `.db` 文件被持有，临时目录删不掉——**自检里已经出现了** |
| **长期运行** | 每次失败的打开都漏一个连接，反复尝试会累积 |

**这不是"理论上会漏"，而是自检已经在报**——只是暂时被当成"临时目录偶发问题"忽略了。**它是一个真实的、可复现的资源泄漏。**

### 一行修复

```dart
Db open(String path, {bool foreignKeys = true}) {
  final sqlite3.Database raw = sqlite3.open(path);
  try {
    // PRAGMA 设置、_migrate、_createAll 都在这里
    ...
    return Db._(raw);
  } catch (e) {
    raw.dispose();
    rethrow;
  }
}
```

**归 Schema 批次（§AK 消歧三件事）而非 1a**，理由：

1. **它和迁移失败路径是同一主题**——迁移失败的恢复（备份 / 回滚 / 通知用户）是 Schema 批次的内容，连接清理是这部分的**底层**依赖
2. **它的验证测试要放在迁移测试里**——"迁移失败 → 连接关闭 → 临时目录可删"这条断言和 §AK 的 fixture 测试共用夹具，放在 1a 会割裂
3. **1a 不涉及迁移失败**——核销是纯业务 UI，不触碰 `_migrate` 路径

## 三、一个需要记录在案的观察

`ref_doc_id` **同时承担两种语义**：

| 用途 | 谁在用 |
|---|---|
| **退货的"原单"** | `sale_return` / `purchase_return` |
| **自动收付款的"来源主单"** | `receipt` / `payment`（自动生成） |

**这不是 bug**——v1 里两种语义**互斥**（一个单据不会既是退货又是自动收付款），靠 `doc_type` 就能区分。

**但它是隐患**——将来如果有人写"查这张单关联了哪些单据"的查询，会发现"关联"有两个含义，必须再加 `doc_type` 分支。

**v1 不改**（拆字段涉及 schema 变更，代价大），但**记录在 `reply_review.md` 的候选清单**：

> **§AL（候选）`ref_doc_id` 语义拆分**：退货的"原单"与自动收付款的"来源"是两种语义。v1 靠 `doc_type` 区分，未拆字段。**触发条件**：出现第一个需要"双向查关联单据"的功能（例如"这张单被谁退过、被谁核销过"的一览页）。**优先级**：低——v1 的所有查询都能用 `doc_type + ref_doc_id` 精确表达。

**这条记下来，是为了将来改字段时知道曾经做过这个取舍**——而不是某天有人发现"两个语义挤一个字段"以为是新 bug。

## 四、批次归属汇总

| 欠账 | 归属 | 理由 |
|---|---|---|
| **列表过滤自动生成的收付款单** | **1a** | 核销上线后立即可见；列表页行行为同批改，一次做完 |
| **文档措辞修正**（`data_model.md:361` / `rules.md:21`） | **1a** | 与实现同批，避免"改了代码忘了文档" |
| **`Db.open` 迁移失败 dispose** | **Schema 批次（§AK）** | 与迁移失败恢复是同一主题，测试共用夹具 |
| **`ref_doc_id` 语义拆分候选** | **记录在案** | 无具体触发，但要知道这个取舍存在 |

---

**一句话**：两个欠账都真、都该修，**但归不同批次**——欠账 1 是"用户马上会看到"，欠账 2 是"底层资源泄漏，和迁移失败是一套"。
