# 二、退款模块：延迟退款补上了，但现在有两个新缺口

先肯定已经完成的部分。

最新的 `_settle()` 已经加入延迟退款检查。对于销售退货，用户先选择不立即退款，之后再通过独立付款单退款时，规则会重新检查原单的真实收款和累计已退金额。

新增测试也验证了：

- 原单只收了 ¥1000；
- 两张各 ¥750 的退货单先挂账；
- 第一张退货单退款成功；
- 第二张退货单再次退款时被拒绝。

这条路径此前确实可以绕过限制，现在已经有了保护。

但是，**我仔细看了这段检查，发现它目前只覆盖了其中一类延迟退款。**

## 1. (P0) 采购退货的延迟退款没有进入这道检查

当前代码的关键条件是：

```dart
if (moneyOut && SettlementService.isReturnType(target.docType)) {
  // 检查原单真实收款和累计退款
}
```

这里的问题在于，销售退货与采购退货的资金方向不同。

| 业务 | 退货单类型 | 实际结算方向 | 正确的资金方向 |
|---|---|---|---|
| 销售退货 | `sale_return` | 向客户退款 | `payment`，钱流出 |
| 采购退货 | `purchase_return` | 供应商退钱给我方 | `receipt`，钱流入 |

目前 `moneyOut` 为 `true` 才执行延迟退款上限检查。

因此，销售退货的延迟退款进入检查，但**采购退货通过 `receipt` 单完成的延迟退款会跳过它**。

构造一个场景：

- 原采购单总额 ¥1000；
- 我方实际支付 ¥500；
- 先创建两张各 ¥400 的采购退货单，暂不收退款；
- 之后供应商分别通过两张收款单退回 ¥400。

按目前的代码结构，采购退货通过 `receipt` 结算时，不会进入 `moneyOut` 分支。每张退货单单独看都没有超过自己的 ¥400 总额，但累计退回 ¥800，超过了原采购单实际支付的 ¥500。

这会让账上出现一笔没有实际支付依据的供应商退款。

**修复建议：不要用 `moneyOut` 作为“是否需要检查退货累计额度”的唯一条件。**

应该根据退货单类型决定应接受的结算方向：

- `sale_return`：通过 `payment` 核销，检查原销售单真实收款与累计退款；
- `purchase_return`：通过 `receipt` 核销，检查原采购单真实付款与累计退回金额。

两者的资金方向相反，但约束思想相同：


$\text{累计退回金额}\leq\text{原单实际结算金额}
$

建议增加一条直接通过 `RuleEngine.dispatch()` 创建 `receipt` 并核销采购退货单的测试，验证累计退回超过原采购单实际付款时必须拒绝。

这项我会列为 P0。

## 2. (P0) 同一张付款单分配给两张退货单，仍可能突破原单累计上限

这是另一个比较隐蔽的问题。

当前 `_settle()` 已经先把本次核销金额按 `targetId` 汇总：

```dart
incoming[targetId] = (incoming[targetId] ?? 0) + allocation.amount;
```

这个设计是正确的，它能够防止把同一张单拆成多条核销记录，从而绕过**单张目标单据**的金额上限。

但是，延迟退款上限检查又是逐个 `incoming` 目标进行的。

假设：

- 原销售单实际收款 ¥1000；
- 两张销售退货单各 ¥600；
- 两张退货单此前均未退款；
- 用户创建一张 ¥1200 的付款单，同时给两张退货单各核销 ¥600。

逐张检查时：

| 目标 | 历史累计退款 | 本次核销 | 单独检查 |
|---|---:|---:|---|
| 退货单 A | ¥0 | ¥600 | 不超过 A 的 ¥600 |
| 退货单 B | ¥0 | ¥600 | 不超过 B 的 ¥600 |

但原单实际只收到 ¥1000，而本次准备退款 ¥1200。

问题出在：检查 A 时，数据库里还没有本次付款单的核销记录；检查 B 时也是如此。两次检查都读取同一份历史累计退款，无法看到本次另一条 allocation。

**所以现在虽然已经检查每张退货单的上限，却还没有把同一笔收付款单中、属于同一原单的多张退货单金额合并后检查。**

建议在 `_settle()` 中增加一层聚合：

1. 遍历本次全部 allocations；
2. 找出作为目标的退货单；
3. 根据退货单的 `ref_doc_id`，将本次金额按原单分组；
4. 对每个原单计算：

$
\text{历史累计已退}
+
\text{本次所有相关退货单的核销金额}
\leq
\text{原单实际结算金额}
$

5. 任意一个原单超额，整张收付款单拒绝。

这项检查必须发生在写入收付款单、资金流水和核销记录之前。

### 建议补充的测试

- 同一原单有两张挂账退货单，一张付款单分别核销两张，合计超额时拒绝。
- 两张退货单属于不同原单时，分别计算各自额度，不应错误地将两笔额度合并。
- 同一付款单中混合普通销售核销与销售退货核销时，退货额度检查只计算属于该原单的退款部分。
- 对采购退货使用 `receipt` 完成延迟退款，同样验证累计上限。

这四条能把本轮新加的规则覆盖得更完整。

# 三、数据抢救：整体已经很接近验收，但不要忽略核销金额的符号

这轮代码把资金、往来和库存判定拆开，思路比之前清楚得多。不过，我还有一个需要核对的地方。

## 1. 主单的已收金额与核销合计：当前采用直接比较

当前 `_moneyProblem()` 对普通业务单据使用：

```dart
if (settledCents != paidCents) {
  // 判为不完整
}
```

这比之前直接比较 `money_ledger` 和 `paid_amount` 正确得多。

不过，抢救器的职责是判断数据能否安全恢复，而不是简单假定所有历史库都完全符合当前写入规则。

这里建议确认两点：

- `settlements.amount` 的符号是否始终为正数；
- `paid_amount` 是否在所有主单类型中都表示正数的已结算金额，而不是按收付款方向带符号。

从当前规则引擎的写入方式看，核销金额确实以正数记录，`paid_amount` 也使用核销合计刷新，所以这项比较有明确依据。

我暂时没有发现这里存在实际缺陷，不把它列为当前阻塞项。只是后续如果加入旧版本数据库的迁移或导入兼容，应该保留这条业务口径说明，避免以后有人看到采购付款的方向相反，就擅自把 `paid_amount` 也改成负数。

## 2. 核销双端传播的方向是正确的

`_propagateSettlements()` 现在会检查：

- 收付款单是否仍然存在且完整；
- 被核销的目标单据是否存在且完整；
- 任意一端不完整时，另一端是否也被标记；
- 多条核销关系相互关联时，结论是否继续传播。

我认可这个设计。

特别是对于 `target_doc_id = null` 的预收、预付场景，代码没有错误地要求必须存在第二张业务单据。这是必要的例外，因为预收、预付本身就可能暂时没有核销目标。

需要注意的是，当前传播是根据**读到的核销关系**进行的。若某条 `settlements` 记录本身完全没有读出来，单靠这条记录自然无法传播。此时需要依赖收付款单核销总额与 `total_amount` 的差异来发现问题。

这也是为什么 `_settlementProblem()` 不能省略。

目前它已经检查：

- 收付款单完全没有核销记录；
- 核销合计与本单金额不一致。

我建议在后续测试中再补一条：删除一部分核销记录，但不删除收付款单和目标单据，确认双方都会被判定为不完整。

这条测试与“收款单整张丢失”不同，能够验证核销金额不完整时，传播机制是否真的起作用。
