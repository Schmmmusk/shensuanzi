1. 恢复清单先行：设计正确，但状态回写有缺陷
提交 86d83b6

这次改动我整体赞成。

以前打开恢复窗口，就要逐份执行 `PRAGMA quick_check`。现在先用 `listRecoveryCandidates()` 读取目录、文件大小和时间，全部候选先展示出来；用户选定某一份后，才在工作 isolate 中体检。

更重要的是，`_restoreSync()` 仍然在改动现有数据库之前执行完整体检。坏备份不会因为“清单先行”而获得覆盖现有数据库的机会。

这次是把等待放到了用户作出选择之后，而不是放松恢复条件。方向合理，测试也覆盖了坏文件进入清单、选中坏文件后被拦截等情形。
P2：检查结果回写时丢失原始来源和时间
recovery.dart 第 627 行：
```dart
final _CandidateRef ref = _CandidateRef(
  path: candidatePath,
  fileName: p.basename(candidatePath),
  source: RecoverySource.autoBackup,
  time: null,
);
```

这里把所有候选都当成了自动备份，而且时间直接置空。

但候选实际可能来自三种来源：
- 自动备份；
- 用户手动备份；
- 升级前留存的 .before-vN。
当体检失败，`checked` 会返回给对话框，`recovery_dialog.dart` 第 201 行 用它替换原来的行。

于是，原来的手动备份会变成“自动备份”，原来的时间也可能显示成未知。用户刚刚选中的那份备份，其来源信息反而被修复代码弄错了。

建议恢复时传入原候选的 `source` 和 `time`，或者在生成检查结果时保留原候选元数据，只更新体检相关字段。
P2：`checked == null` 的语义不够准确
还有一个相关的小问题：

`RecoveryRestoreResult.checked` 的注释把 `null` 解释为“没有做过体检”。

但 `_restoreSync()` 在体检已经通过、后续改名或复制失败时，也返回 `checked: null`。

结果就是：用户已经成功完成了备份体检，但列表仍然显示“还没检查”。

建议区分三种情况：
- 备份未能体检：维持未检查或标记读取失败。
- 备份已体检且不合格：回写实际的不可用结论。
- 备份已体检且合格，但接回失败：回写 ok，保留来源、时间和单据数量，允许用户重试。
这项修复不用再额外执行一次 `quick_check`，直接使用已经得到的检查结果即可。
P1：上一轮的回滚问题仍然存在
recovery.dart 第 733 行

`_rollbackArchive()` 仍然吞掉文件改名失败；`_deleteQuietly()` 也仍然吞掉删除失败。

而恢复失败路径仍可能返回“数据没有动过”。如果清理半成品失败，或者旧库回滚不完整，这句话就不一定成立。

这项不是本轮新引入的问题，而是上一轮审查指出后，当前版本仍未解决的遗留风险。

我的建议是把它列为恢复模块的优先修复项：回滚必须返回逐项结果，只有确认旧库和 sidecar 全部恢复原位，才能使用“数据没有动过”这句文案。回滚失败时则明确列出残留路径，避免用户继续误操作。

5. 新提案：冷库页面成本

这是本轮我最想讨论的部分。
先看已经有的证据
三页都在 `initState` 中同步执行查询，查询完成后才完成首次页面构建。仓库的历史记录显示：
环境	概览	库存	单据
L13 NVMe 真机	320 ms	209 ms	88 ms
虚拟机 SATA	3189 ms	2676 ms	2146 ms

而且库存页曾经测到：虚拟机冷缓存下，单独的在途查询就用了 2565 ms，几乎占满 2676 ms 的首次页面耗时。

这些数据确实支持一个结论：数据库尚未进入热缓存时，磁盘读取会严重影响首屏出现时间。 查看历史真机与虚拟机对照记录。
但我不完全接受提案中的“93% 是冷读”
提案计算方式是：

$3189\text{ ms}-225\text{ ms}\approx2964\text{ ms}$

再将 2964 / 3189 得到约 93%。

问题在于，这里的 3189 ms 是历史首次进入页面的测量结果，而 225 ms 是 2026-11-18 热缓存条件下的 SQL p95。它们不是同一次运行、同一代码版本、同一个缓存状态下的分项计时。

因此，93% 更适合作为冷读惩罚的估计值，而不是已经测出的物理磁盘 I/O 占比。

此外，“压 SQL 帮不了慢盘”也说得太绝对。

减少 SQL 的计算开销，和减少 SQL 实际读取的数据页，是两件不同的事。如果原查询要扫描大量 `stock_ledger`、`documents` 或 `money_ledger`，使用汇总表或改变查询策略就可能减少实际读取页数，进而降低冷缓存环境下的 I/O 成本。

这不表示我建议马上做 schema v9。账目软件引入增量维护汇总表确实存在数据一致性风险。但目前的证据还不足以断言物化汇总表在慢盘上几乎没有收益。

建议先补一次同条件的冷缓存分项测量：

在同一台机器、同一份数据库、同一个提交上，分别记录概览页各查询的实际耗时和冷缓存表现。再结合查询计划确认究竟哪些查询读取了大量数据页。这样才有依据判断丙方案是否值得做。
对甲、乙、丙、丁的看法
甲：骨架先行
*推荐优先考虑*

这是低风险的体验改善。先让用户看到页面框架，减少“点了没反应”的错觉。

但它不会消除真正的卡顿：SQL 仍在 UI isolate 中同步执行，骨架出现之后，交互依然会被阻塞，直到查询结束。

乙：工作 isolate 查询

这是解决慢盘环境真实卡顿的方案。我赞成暂缓，先看甲的真实用户反馈，再决定是否值得投入。

将多条查询放进一个稳定的只读事务，尽量复用已有的 Db.readTransaction()，同时处理切换数据库、重连和过期结果回写。不能只做到“不卡 UI”，却让几张卡显示不同时间点的数据。

丙：物化日汇总表

目前不建议立项，但原因应该是证据不足、维护成本高，而不是预先断言它不能减少慢盘 I/O。先用实际读取量验证收益。

丁：慢盘提示

可以作为甲的辅助文案，但“首屏超过 1.5 秒”需要明确计时起止点和提示触发条件，避免普通机器偶尔抖动就打扰用户。


还有一个技术细节：甲使用 `addPostFrameCallback` 的确可以把查询安排在渲染流水线完成之后。Flutter 文档明确说明，`post-frame` callback 在主渲染流水线刷新后执行；`FrameTiming.buildDuration` 的测量终点则是 `FlutterView.render`。因此，首屏骨架有机会先显示，再执行同步查询。

这也意味着验收时应分别看两件事：骨架多久可见，以及用户多久恢复交互。前者很可能明显改善，后者不会因为甲而自然改善。
