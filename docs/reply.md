# 二、退款上限：核心计算正确，但安全边界放错了地方

这项我认为是本轮最重要的代码问题。

## 1. 规则目前写在 `ReturnService`，没有写进 `RuleEngine`

[ReturnService.create()](packages/shensuanzi_core/lib/src/documents/return_service.dart) 现在会检查：

- 原单真实结算金额是否大于零；
- 之前已经实际退了多少钱；
- 本次退款加上历史退款是否超过原单真实结算金额。

计算来源也正确：全部从 `settlements` 读取，不依赖 `paid_amount` 缓存。

问题是，这道闸只保护经过 `ReturnService.create()` 的调用。

[SyncServer.\_createDocument()](packages/shensuanzi_host/lib/src/sync_server.dart) 收到客户端的单据创建请求后，是直接调用：

```dart
_engine.dispatch(
  document: document,
  lines: lines,
  immediatePayments: immediate,
  allocations: allocations,
  now: now,
);
```

而 [RuleEngine.\_return()](packages/shensuanzi_core/lib/src/rules/rule_engine.dart) 目前没有这三项退款上限检查。

这意味着：**绕过 `ReturnService`，直接通过主机同步入口创建退货单，仍然可以绕过新增加的退款上限**。

哪怕当前 Android 界面没有完整开放这条退货操作路径，也不能把安全性建立在“客户端暂时不会这样发请求”上。主机规则层才是真正的权威边界。

我的建议很明确：

- 把真实收款、累计实际退款和本次退款上限检查移入 `RuleEngine._return()`。
- 放在 `RuleEngine.dispatch()` 已开启的事务内部。
- `ReturnService` 保留额度查询，给 UI 展示提示即可，不再承担最终安全保证。
- 增加一条直接调用 `RuleEngine.dispatch()` 的测试，证明绕过 `ReturnService` 也无法制造超额退款。

这样也顺便消除了“检查额度”和“真正写入退货单”不在同一个事务里的问题。

## 2. 超过本次退货金额时，实际行为与施工清单不一致

这里还有一个很具体的交互问题。

[ReturnDraft.recordedRefundCents](packages/shensuanzi_core/lib/src/documents/return_draft.dart) 使用了：

```dart
Overpay.clamp(..., totalCents)
```

也就是说，用户本次退货金额是 30 元，却输入了退款 40 元，系统会把真正落库的退款金额压到 30 元，而不是拒绝。

但 [ReturnPage.\_confirm()](lib/src/ui/return_page.dart) 展示确认信息时，使用的是 `draft.refundedCents`，它计算的是用户原始输入金额。

于是可能出现：

用户输入

# ¥40

> 本次退货金额：¥30
>
> 确认对话框显示

# 立即退款 ¥40

> 实际落库

# 退款 ¥30

> 多出的 ¥10 没有进入资金流水。

这不是单纯的文字问题，而是用户确认的金额与实际付款金额不一致。

而 `55` 的测试表明确写着“想退 40，应该拒绝”。我支持这个要求：退款金额超过本次退货金额，就应该明确提示并拒绝，而不是悄悄截断。

至少要先把校验补上，再增加测试覆盖这条路径。

## 3. UI 显示的额度最好区分两个概念

目前 `refundableCentsOf()` 计算的是原单还剩多少累计退款额度。

但是本次实际能退的钱，应该是：

 $ \min(\text{原单剩余退款额度},\text{本次退货金额}) $

建议 UI 把“原单累计剩余可退款额度”和“本次最多可退”区分开。否则原单还剩 100 元可退，本次退货只有 30 元时，用户可能看到一个容易误解的 100 元上限。

# 三、数据抢救：我发现了几个必须修复的判定问题

[当前 rescue.dart](packages/shensuanzi_app/lib/src/rescue.dart)

先肯定一下：这次的实现已经有了按业务类型区分的判断、按商品统计明细行与库存流水、检查往来金额、检查资金金额和收付款单核销金额的雏形。

但它还没有完全符合神算子的真实数据模型。

## 1. 严重 正常的收款单、付款单可能反而被判为不完整

问题在 `_moneyAmountMismatch()`。

目前它的逻辑是拿某张单据的资金流水合计，与 `documents.paid_amount` 比较。

但神算子的真实数据模型不是这样：

- 收款单、付款单创建时，`paid_amount` 被明确设置为 0。
- 资金流水记录在对应的收款单、付款单自己的 `document_id` 上。
- 收付款单的真实金额在 `total_amount`。
- 核销关系才负责关联收付款单与原始业务单据。

这些行为可以直接在 [RuleEngine.\_settle()](packages/shensuanzi_core/lib/src/rules/rule_engine.dart) 和自动收付款实现里看到。

因此，一张正常的 100 元收款单：

| 字段                  | 正常值    |
| ------------------- | ------ |
| `total_amount`      | 10000  |
| `paid_amount`       | 0      |
| `money_ledger` 对应流水 | +10000 |

当前检查却会比较：

 $$|10000| \ne |0| $$

于是它会被判断为资金记录与已收金额不一致。

更糟的是，资金流水缺失时，`_moneyAmountMismatch()` 又直接返回 `false`。所以这条逻辑可能出现正常的收款单被判错，而缺少资金流水的收款单反而通过这一项检查的情况。

我认为这是目前抢救代码里最需要修正的一处。

正确方向应该是按单据类型分别检查：

- `receipt/payment`：资金流水金额与本单 `total_amount` 对应。
- 销售、采购、送货、退货等主单：通过 `settlements` 核对实际结算金额，不能拿主单的 `money_ledger` 去比，因为实际资金流水属于独立生成的收付款单。

## 2. 严重 整张往来流水丢失时，可能仍然被判完整

看 `_ledgerAmountMismatch()`：

```dart
if (partyId is! String || partyId.isEmpty) return null;
if (party.isEmpty) return null;
```

这里第二个条件意味着，只要这张单的往来流水一条都没有，就不进行金额检查。

代码注释称“一条都没有由前面的分支处理”，但目前 `_assemble()` 对普通销售、采购、送货和退货单并没有一个明确的分支来处理“只有往来流水丢失，其他流水都还在”的情况。

例如：

- 销售单有完整明细；
- 库存流水完整；
- `party_id` 仍然有效；
- 所有 `party_ledger` 全部丢失。

此时库存流水行数正常，往来检查因为 `party.isEmpty` 返回 `null`，资金流水检查也可能直接跳过。

这张单就可能进入 `importable`。

这会导致商品库存恢复了，客户欠款却没恢复。

应该根据业务类型和 `party_id` 明确判断是否预期存在往来流水。对于应该记往来的单据，不能把“完全没有”视为“不适用”。

## 3. 严重 核销检查目前只检查了收付款单这一侧

这里有两个问题。

首先，`_firstMissingRef()` 虽然收到了 `settle` 参数，但实际没有使用它。

其次，`settle` 是按 `receipt_doc_id` 分组的，因此当前 `_settlementMismatch()` 只检查收付款单自己核销出去的总额。

它还没有充分检查：

- 核销记录的 `receipt_doc_id` 是否存在；
- 非空的 `target_doc_id` 是否存在；
- 两端单据是不是都能被完整恢复；
- 某一端无法恢复时，另一端是否也应该进入待确认。

举个例子：

一张销售单原本通过收款单核销 100 元。损坏后，收款单或核销关系没有被完整找回。

如果销售单本身的明细、库存和往来流水仍然存在，它可能继续被判为完整；但 `_writeNewDatabase()` 写入新库时，会因为收款单不在 `ok` 集合里而跳过这条核销关系。

最终恢复出来的销售单就可能失去这笔已收款记录。

恢复后的账本里，销售单还在，但这笔钱不见了。

这一项不能仅仅检查 `SUM(settlements.amount)`，而应当针对每条核销关系检查两端。只要任意一端缺失，就要明确处理关联的另一端，不能悄悄把关系丢掉。

## 4. 库存流水目前只核对行数，没有核对 55 写的数量合计

施工清单 55 目前写的是：

> 每个商品的行数相等，且数量合计相符。

但 `_hasMissingStockRows()` 实际只统计了：

```dart
Map<String, int> lineRows;
Map<String, int> stockRows;
```

然后逐商品比较行数，没有比较数量合计。

所以它能发现“少了一整行库存流水”，却不能发现“库存流水的数量字段已经错了”。

例如：

| 数据     | 原始值 | 损坏后 |
| ------ | --- | --- |
| 明细数量   | 10  | 10  |
| 库存流水数量 | -10 | -8  |
| 行数     | 1   | 1   |

当前检查会认为行数匹配。

我建议按施工清单补上数量合计检查，并且对明细和流水商品 ID 的集合取并集，避免库存流水中出现明细没有的额外商品时漏检。

另外，`stocktake` 目前直接跳过库存流水检查。55 的要求是只对产生差额的明细核对，而不是什么都不检查。当前测试只证明了零差额盘点可以通过，还没有证明有差额的盘点丢失流水时能够被识别。

## 5. 明细金额与单据总金额的检查，文档和实现也还没对齐

55 已经明确确认，这两个金额可以比较：

$$ \sum(\text{document\\\_lines.amount}) = \text{documents.total\\\_amount} $$

而且规则引擎本来就有 `_requireLinesTotalMatches()` 这一业务不变量。

但当前 `_assemble()` 还没有这项检查。

它很重要，因为如果某商品的一行明细和对应库存流水一起丢失：

- 剩余明细行数与库存流水行数仍然一致；
- 剩余商品的库存流水行数仍然一致；
- 但单据金额与剩余明细金额合计会不一致。

这正是金额不变量能补上的漏洞。

我完全同意施工清单对“售价不能拿去和库存成本比”的修正，但不要因此漏掉明细售价合计与单据金额这个本来就应该检查的关系。

# 四、还有一个测试设计问题：抢救夹具需要更贴近真实数据库

[rescue_test.dart](packages/shensuanzi_app/test/rescue_test.dart) 里的 `makeDb()` 当前直接给销售单写入 `money_ledger`，并把 `paid_amount` 设置成相同金额。

但真实规则引擎会生成独立的 `receipt/payment` 单，再把资金流水挂在这个收付款单上，并通过 `settlements` 关联原单。

这意味着当前夹具和生产数据模型并不完全一致。

这很可能也是为什么这次没有及时发现上一节提到的资金流水检查问题。

我建议调整测试夹具：

至少用真正的 `RuleEngine` / `SaleService` / `SettlementService` 创建一组真实交易，再对生成的数据库进行删行、改值和核销关系破坏。

这样测试才是在模拟真实业务，不是在模拟一个简化版账本。

也请务必补一张正常的 `receipt` 和一张正常的 `payment` 抢救测试。如果正常收付款单都不能被正确导入，这个模块就不应该验收。
