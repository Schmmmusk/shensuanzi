# 一、我在新代码里发现的几个问题
下面这些是我根据当前源码做的审查，不是实际运行测试得出的结果。
## 1. 需要修正
 净额为零时，可能被误判成没有销售记录
在 revenue_chart.dart 中：
```dart
if (weeks.isEmpty || total == 0)
  _emptyHint(theme)
```

这里把 `total == 0` 当成了没有销售记录。

但想象一种情况：
日期	销售	退货	净额
第一天	¥500	¥0	¥500
第二天	¥300	¥300	¥0
合计	¥800	¥300	¥500

这时总额不是零，尚且能正常显示。

但假设两天净额分别是 +¥500 和 −¥500，合计就是零。这并不代表没有发生过销售和退货。 当前界面却会显示：
最近 30 天还没有销售记录。

这明显不准确。

更合理的判断是：是否存在销售、送货或退货记录，而不是净额是否为零。

## 2. 需要修正
 活跃天数的平均值计算也有类似问题。

当前代码：
```dart
final int activeDays =
    rows.where((d) => d.netCents != 0).length;
```

它用净额是否为零来判断当天有没有生意。

如果某天销售 ¥500，又恰好退货 ¥500，那么当天确实发生了经营活动，但净额为零。这一天就不会进入分母。

于是：

> 平均每个有生意的日子

这个数字会偏高。

建议依据实际业务活动判断：有销售或送货单据，或者发生了退货，都应该算作一个有经营活动的日子。当前 documentCount 只统计销售和送货，因此还需要结合退货活动判断，必要时单独增加退货单数。

## 3. 需要核对
 原单缺失的退货会被整个过滤掉
这是我认为数据层值得特别留意的地方。

目前第三条查询使用：
```sql
JOIN documents o ON o.id = r.ref_doc_id
```

这意味着：如果退货记录存在，但关联的原单已经缺失，那么这条退货记录不会进入查询结果。

可是提案 54 的边界约定明确写着：
原单读不到（数据缺失）⇒ 保守按冲减处理。

当前实现和方案不一致。考虑到神算子已经有数据抢救机制，这不是完全可以忽略的边界。

可以考虑改为 `LEFT JOIN`，并在筛选条件中明确区分：
- 原单不存在：仍然扣减退货；
- 原单存在且未作废：扣减退货；
- 原单存在但已作废：不再重复扣减。
同时增加一条原单缺失的测试，避免今后回归。

## 4. 可读性问题
 手机尺寸下金额标签缩小到了 13sp
方案 54 的硬规则是字号不小于正文、至少 15sp。

但当前绘图代码是：

```dart
size: compact ? 13 : 15
```

这意味着窄窗口会把金额标签降到 13sp。

这和提交说明中「15sp 不打折」的表述不一致。

还有一点：当前 TextPainter 按文字的自然宽度布局，没有根据每根柱子的实际可用宽度检查金额标签是否相互重叠。390px 的窗口测试只能证明 Flutter 没有抛出布局异常，不能证明画布上的文字没有重叠。

建议专门拿较大的金额数据做一次窄窗口渲染验证，而不是只用普通金额验证。

## 5. 比例表达问题
 欠款横条的 4% 下限会扭曲比例
`balance_bars.dart` 中有一段：

```dart
final double ratio = maxCents <= 0
    ? 0
    : (cents / maxCents).clamp(0.04, 1.0).toDouble();
```

我理解这么做是为了防止小额欠款显示成一条看不见的细线。

但是它会造成比例失真。

举个例子：
- 应付 ¥10,000；
- 应收 ¥10。
真实比例是 1000:1。

但横条会显示成 100% 对 4%。用户看到的比例变成了 25:1。

数字本身没错，但横条已经不再是严格按比例绘制的了。

我建议考虑用最小像素宽度或独立标记保证可见性，而不是直接把比例下限设为 4%。这样既能看见小额欠款，也不会让图表暗示错误的比例。

# 二、我还想追问两个产品问题

## 第一，负数柱的金额标签为什么只显示绝对值？

目前绘制时使用了：
```dart
Money.formatGrouped(p.netCents.abs())
```

柱子向下、颜色变红，确实能暗示它是负数。但金额本身没有负号。

我倾向于直接显示 −¥500，不要让用户再通过柱子的位置判断正负。图表的金额标签应该能够独立表达数值。

## 第二，在途送货目前只展示张数，没有展示对应金额。

方案中提到过「含未签收 N 张 · ¥X」，但现在界面只显示：
其中 N 张送货还没签收（钱可能还没到手）

用户知道有多少张，却不知道其中涉及多少钱。

既然图表的总额包含在途送货，那么单独提示在途金额会更有价值。否则一笔 ¥100 的在途订单和一笔 ¥100,000 的在途订单，在这条提示里没有区别。
