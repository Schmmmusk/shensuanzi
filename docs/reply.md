## 一、对两个裁定点的确认

### ① 单据列表：选甲（只做两段查询，不打日桶索引）
你拆解发现 456ms 里，**排序花了 120ms，派生表全量物化花了 105ms**。把这俩一解决，降到 147ms（3.1倍），对单机用户已经非常流畅了。
而打日桶表达式索引虽然能降到 20ms，但**绑死建库时区**这个坑太深了，为了 100 多毫秒的收益引入如此巨大的脆弱性，绝对得不偿失。

### ② 账户余额：选不加
账户页是典型的低频页，64ms 的加载速度用户完全无感。为了省 50ms 去升 v6 加个 2MB 的索引，不仅浪费迁移风险，也破坏了“只在刀刃上加索引”的纪律。同意保持零 schema。

## 二、方案中的高光时刻

1. **`recent_products` 的 430 倍极速（429ms → 1.0ms）**
   你用“按时间倒序扫最近 K 张单”代替“全量扫单再 Group By”，并严谨地证明了“遇到第 20 个不同商品即停”在数学上等价于“Max(occurred_at) 倒序取 20”。这种把业务逻辑转化为拓扑逻辑的思路，太漂亮了。
2. **对 `doc_search` 果断说“不”**
   测了 4 路开销，试了 3 种改法，发现都不行，立刻悬崖勒马。**“知道什么不做”比“知道怎么做”更难。**
3. **对 `in_transit` 的放弃理由**
   指出 86ms 是因为“种子数据造了 14563 张在途单”，真实店铺根本不可能有这么多在途。不被假数据骗，保持了对真实场景的敏锐感知。

## 三、落地时的 3 个工程防坑点

虽然你的方案逻辑很严密，但在写 Dart/SQLite 代码时，这三处必须死守：

### 1. 两段查询的「内存重排」
第一段查出了 200 个 `id` 的**有序列表**。
第二段执行 `SELECT ... WHERE id IN (...)` 时，SQLite **绝对不保证**返回的顺序与 `IN` 列表里的顺序一致。
**防范**：第二段查回来之后，在 Dart 内存里，必须按照第一段的结果对第二段的结果进行**重新排序**。
```dart
final List<String> orderedIds = stage1Result;
final Map<String, Row> rowMap = stage2Result.map((r) => MapEntry(r['id'], r));
final sortedDocs = orderedIds.map((id) => rowMap[id]).whereType<Row>().toList();
```

### 2. `recent_products` 的兜底与 `INDEXED BY`
- 你提到了 `INDEXED BY idx_documents_occurred`，这非常关键。SQLite 的查询规划器有时会自作聪明去选 `type_status` 索引导致退化成 122ms。
- 兜底逻辑：如果扫了 2000 张还不够 20 个商品，说明销量极低。这时**不能直接放弃**，必须退回全量查询 `GROUP BY`。
```dart
if (uniqueProducts.length < limit) {
  return _fallbackToFullQuery(); // 慢就慢点，但数据必须对
}
```

### 3. 单据页搜索（`doc_search`）的 UI 防抖
既然 `doc_search` 的硬底是 ~300-400ms，这意味着如果用户敲 5 个字母，就会触发 5 次 400ms 的查询，这会让打字非常卡。
**建议**：既然底层不优化了，必须**在 UI 层加防抖（Debounce）**。用户停止输入 300ms 后再触发查询。这算是曲线救国，能极大提升手感。
