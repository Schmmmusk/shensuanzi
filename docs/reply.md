## 一、问题 1：自动补传的触发点

### 先把候选列全

| 候选 | 触发条件 | 优 | 劣 |
|---|---|---|---|
| A. 开单后一次 | 保存入队后 | 已实现，无额外成本 | 断网开单 → 恢复后不补 |
| B. 回前台 | App 从后台回到前台 | 与用户操作绑定，可预测 | 用户不切 App 就不触发 |
| C. 网络恢复 | 监听网络状态变化 | 响应快 | 需监听、移动网络下频繁触发、耗电 |
| D. 定时 | 周期轮询 | 不需要用户操作 | 需后台服务、Android 后台限制、耗电 |
| E. 手动按钮 | 用户点「立即同步」 | 完全可控 | 依赖用户主动 |

### 推荐组合：**A + B + E**

**理由三条：**

1. **与项目「UI 原则」一致**。`ui_principles.md §1.1` 明确：中老年用户**不会主动探索**，也不会理解「App 在后台悄悄同步」。**A + B + E 全部是用户可感知、可预测的行为**，不引入「看不见的后台动作」。

2. **避开 Android 的后台限制**。D（定时）会被 Android 的 Doze / 后台执行限制砍掉，要做就得引入 `WorkManager` 之类的依赖——**违反「core 零新依赖」原则**，并且会引入用户无法理解的「为什么有时同步有时不同步」。

3. **C（网络恢复）的收益边际**。用户在店里，Wi-Fi 大概率稳定；断网场景少。真要断网，用户会主动看三态条。**C 的复杂度（网络状态监听 + 移动网络省电策略）换来的收益，不如把「回前台」做扎实**。

**落地形态：**

```text
1. 开单保存成功 → 异步触发一次 push()（已实现）
2. App 从后台回前台 → 触发一次 push()（新增，覆盖「用户离开 App 又回来」）
3. 三态条「待同步 N 条」可点 → 手动「立即同步」（已实现）
```

**三条都不需要新依赖**（第 2 条用 `WidgetsBindingObserver.didChangeAppLifecycleState`）。

**必须同步改的文案**：

- 设置页「多设备同步」的说明，从「开单后自动同步」改为「开单后、回到 App 时自动尝试同步；也可点『立即同步』」。
- 这与 M02 报告的问题直接相关——现在 UI 承诺了「联网自动补传」，但实际没有。**要么实现，要么改承诺**。我推荐**实现 + 改文案到准确**。

### 不推荐的理由（针对 C/D）

- **C**：引入网络监听插件（`connectivity_plus` 之类），违反「core 零新依赖」，且需要为移动网络单独做省电策略。**收益不匹配成本。**
- **D**：需要 `WorkManager` 或前台服务，Android 14+ 对后台服务限制更严。**这个复杂度对中老年用户场景不值得。**
- **C + D 还有个隐患**：用户无法理解「为什么刚刚还显示待同步，过了一会自己就同步了」——**暗行为在中老年用户那里等于「软件不可预测」**。

## 二、问题 2：saleReturn / purchaseReturn 移出白名单

### 先说结论：**不要移出。**

### 为什么提案想移出

从 R06 报告看，问题是：

> 往来方 B 的收款可核销 A 的销售单；付款也可核销销售单，实际资金减少而销售单被标为结清。

**这里的问题不是「saleReturn / purchaseReturn 在白名单里」，是「没有 party_id 校验 + 没有方向校验」。**

### 为什么不建议移出

**saleReturn / purchaseReturn 代表真实的债务，需要被核销。**

举例：

1. 客户退回商品 → `sale_return` 生成，`party_ledger` 为 -50（我们欠客户 50）
2. 我们通过银行转账退给客户 50 → 生成一张 `payment` 单
3. **这张 payment 单应该核销 `sale_return`**，表明「这笔退货的退款义务已履行」

如果移出 `sale_return`，这张 payment 单就没有核销目标，`sale_return` 永远显示「未退款 50」，即使我们已经退款。

**同理采购退货**：供应商退我们钱，`receipt` 单应该核销 `purchase_return`。

### 正确修复：加校验，不移出

**两层校验：**

**① party_id 一致**

```text
目标单 party_id 与收付款单 party_id 均有值时必须相等
（散客/散采允许一边为 null）
```

**② 方向约束**

```text
销售系（sale / sale_return / delivery）只接受 receipt
采购系（purchase / purchase_return）只接受 payment
```

**这两条校验完全覆盖 R06 报告的问题**：

- 「B 的收款核销 A 的销售单」→ 被 ① 拦住
- 「付款核销销售单」→ 被 ② 拦住

**校验之外，不动白名单。**

### 为什么要"重裁"，我建议裁什么

提案说「移出属语义变更，需重裁」——**对，但移出不是正确答案**。真正的裁定应该是：

> **保留 `saleReturn` / `purchaseReturn` 作为核销目标；新增 party_id 与方向校验；不改变白名单。**

这个裁定的价值在于：

- **它是向后兼容的**：现有合法 payload（sales 核销 sales、purchases 核销 purchases）不受影响。
- **它不引入语义变更**：`sale_return` / `purchase_return` 的「已收/已付」语义本来就应该存在——只是之前没启用。
- **它给「退款入口」留了空间**：如果将来 UI 要支持「原单详情页 → 退款给客户」，那张 payment 单就能核销 sale_return。**如果现在移出，这条路就堵了。**

### 如果一定要移出——移出的代价

假设强行移出：

1. **现有数据**：`settlements` 表里如果已经有指向 sale_return / purchase_return 的记录，移出后这些记录就变成「孤儿」——核销关系还在，但类型不允许了。
2. **「退款」这条业务链断掉**：sale_return 的「未退款」状态无法收口，用户只能手工记「我欠客户 X 元」。
3. **R04 修复更难**：R04 的修复方向是「原单详情页加退款入口 + 退货页显示未退款额」。**这需要核销目标就是 sale_return**。移出后 R04 就没法修。

**所以：移出 = 把 R04 和 R06 一起堵死。**

## 三、两条建议的最终落地形态

| 项 | 裁定 |
|---|---|
| Android ⑥ 自动补传 | **A + B + E**：开单后 + 回前台 + 手动按钮。不做网络恢复、不做定时。同步改 UI 文案。 |
| saleReturn/purchaseReturn | **不移出**。加 party_id 校验 + 方向校验。保留为核销目标。**这是 R04 修复的前置条件。** |
