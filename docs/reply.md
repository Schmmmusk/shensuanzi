## 二、#31 方案甲审查

### 读码事实确认

四条事实全部可 grep，**协议零改动**这个结论成立。**方向对。**

### ⚠️ 四处必须补

#### ① 「结构自愈」假设不够强——需要补一条硬约束

方案说：

> 若 stocktake 条目先到 ⇒ 商品不存在 ⇒ 规则层拒 ⇒ 条目进退避重试 ⇒ 建档落库后自然成功

**问题**：这只在「master op 一定能成功」的前提下成立。**但 master op 也可能失败**（网络异常 / 主机临时故障 / 其它 constraint 冲突）——一旦 master op 重试到死信，stocktake 也会重试到死信。

**结果**：两条 op **同时进死信**，用户看到「有 2 条失败」，但不知道「这两条是一件事」。

**需要明确**：

> **同一商品的 master op 与 stocktake op 必须绑定**——要么都成功，要么都不做。
> 
> 实现上两条路：
> - **甲（推荐）**：**合成一条 op**（`createMasterData` payload 里加个可选 `opening_quantity`），host 端在 apply 建档后**同一事务内**处理 stocktake——**结构上不分叉，无自愈需求**
> - **乙**：两条 op，但给它们一个共享的 `group_id`，host 端 + 客户端都按组处置

**建议选甲**：现在的方案「一次提交 = 两条队列条目」是**协议层新增了一个「成组」的隐含语义**，却没有显式表达——一旦乱序 / 部分失败，就退化为「用户看到两条独立失败」。

**这条是硬约束，不是可以「事后自愈」的。**

#### ② 「同步前显示权威值」需要 UI 补偿

方案说：

> `deltaOf` 对 stocktake = 0 ⇒ 同步前手机显示库存 = 权威值，不显示期初量——诚实口径

**技术上诚实，但用户体验反直觉**：用户刚填了「当前库存 10 件」，商品列表里显示 **0**——用户会疑惑「我刚填的 10 件呢？」，甚至重复建商品。

**需要 UI 补偿**：

- 商品列表行：`isPending` 状态**除了「待同步」小字，再加「期初 10 件」提示**
- 或：在商品列表里对该商品显示 `权威值 + 期初量` 的组合（类似 `stockViewOf` 的叠加逻辑），并**明确标注「同步前是估算」**

**这与 §CV 一贯的「未同步影响必须可见」一致**——`unsyncedDelta` 对单据能做叠加，对 stocktake 不能算 diff，但**可以显示「待同步的期初量」**（不参与库存计算，只作为提示）。

#### ③ 编辑已有商品时改库存的场景没覆盖

方案只说「新建商品带当前库存」。**编辑一个已有商品想改库存呢？**

两个选择：

- **甲**：编辑时不改库存（保持现状）——用户只能通过「录入现有货物」改
- **乙**：编辑时也能填「当前库存」——走 stocktake

**建议明确写清**：本次只做**新建时可选填库存**，**编辑时改库存另开一项**（与「整页期初录入手机化」同批）。

**否则**：用户建完商品发现填错了，想改库存，会去编辑页——发现没有字段，以为软件有问题。

#### ④ 表单单位换算与 stocktake lines 的对应要写清

方案说：

> 走 #44 的 `baseQuantityValue` 口径换算成最小单位

**对的**——但需要写清：

- stocktake 的 `lines.quantity` = **实际数量**（不是 diff）
- **用户填「3 箱」，lines.quantity = 36（换算后）**
- `entry_quantity = 3` / `entry_unit = '箱'` 只记**录入原文**（与 v3 口径一致）

**这是 v3 口径的正确应用，但要显式写进方案**——否则实现者可能填 3，host 端按 3 记库存。

## 三、#43 审查

方案说「约 11 处原始异常直出，修法机械度高（复用 #54 判据）」——**方向对，但要补一条**：

**「11 处」的位置需要列出清单**。因为：

- 哪些是 **UI 层**（改文案）
- 哪些是 **core 层**（改分类）
- 哪些是 **host 层**（改回执）

**三层的修法不同**。#54 刚立的判据是「SQLite 异常 vs 路径异常」，适用于 core；UI 层要的是「分类文案 + 详情进日志」；host 层要的是「领域分类 + 通用中文」。

**先列清单，再动手**——否则容易「改一处漏三处」。
