### 一处小建议（不阻塞）

**6 处特征串里的「文案 3 条字面量」**——将来某天产品决定改文案（比如「本地未同步」改成「本地待传」），**同构测试会红，且红得与功能无关**。

**建议**：文案的特征串改为**比对三页之间是否一致**，而不是比对**字面值**。

```dart
// 现在（写死）：
expect(salePage.contains('本地未同步'), isTrue);
expect(deliveryPage.contains('本地未同步'), isTrue);

// 更好（比对同构）：
final saleSnippet = extractSnippet(salePage, '当前库存');
final deliverySnippet = extractSnippet(deliveryPage, '当前库存');
expect(saleSnippet, deliverySnippet);
```

**这样产品改文案时，只要三页同步改，测试就不红**——它守的是「同构」，不是「文案内容」。

## 二、#42 甲 审查

### 方案框架确认

**四层结构（L1–L4）方向对**，与上一轮我审 #42 时给的框架一致。**逐枚举政策表**是这份提案最有价值的部分——它把「跳过 vs 兜底」的语义后果摆到了台面上。

### ⚠️ 必须补的三处

#### ① `DocStatus` 兜底 `draft` 是有风险的——请重新考虑

看 `data_model.md §3.1`：

> `status` 判定规则：`paid_amount >= total_amount ? settled : confirmed`
> `draft` / `confirmed` / `in_transit` / `delivered` / `settled` / `cancelled`

**`draft` 在项目语义里不是「保守兜底」，是「未提交」**——它可能：

- 不出现在某些筛选（如「已确认单据」）
- 在开单页/编辑页被当作「草稿」允许修改
- 影响 `DocumentDao._summaries` 的统计口径

**兜底成 `draft` 会让一张真实存在的单「看起来像没保存」——比「看不见」更糟**（用户看得见但状态错，会做出错误判断）。

**我建议三选一**：

| 候选 | 后果 |
|---|---|
| **甲**：兜底 `confirmed` | 保守但合理——「已确认但未结清」是绝大多数已保存单据的真实状态 |
| **乙**：跳过该行（和 `DocType` 同款） | 该单从界面消失——只靠 L4 告知 |
| **丙**：**引入第 7 个枚举值 `unknown`** | 语义最准，但要动 `DocStatus` 枚举 + 状态机 + UI 文案 |

**我倾向甲**：`confirmed` 是「已保存、未结清」的默认状态；兜底为它，比 `draft`（未提交）安全，比 `unknown`（要动枚举）便宜。

**请重新裁定这一行。**

#### ② `SyncQueueStatus` 兜底 `failed` 也需要复核

**`failed` 的语义是「死信，退出自动重试，等人工处理」**——把一条未知状态兜底成 `failed`，用户会看到「N 条失败，请处理」的提示。

**但真实情况可能是**：这条队列条目是**新版本客户端写入的新状态**，主机版本还不知道——**它根本没坏，只是主机不认识**。

**把它标成 `failed`，等于把「兼容性问题」伪装成「同步失败」**——误导用户去「处理」一个根本不需要处理的东西。

**建议**：

| 候选 | 后果 |
|---|---|
| **甲**：跳过该行 + L4 计数 | 用户看到「有 N 条同步记录读不出来」——准确，但不吓人 |
| **乙**：兜底 `pending` | 让主机尝试重传，失败后自然进 `failed`——但可能死循环 |
| **丙**：保留现状（兜底 `failed`）+ 文案区分 | UI 里把「未知状态兜底」和「真的失败」分开显示 |

**我倾向甲**——「跳过 + 计数」是诚实的，和 `DocType` 同款。

#### ③ `ReadFailureLog` 的生命周期与复位语义没写清

提案说「`ReadFailureLog` 挂在 `Db` 上」——**但没写**：

- **每次查询后复位？** 还是**累积到显式清空？**
- 如果累积：用户看一次「有 3 条读不出来」提示后，**这 3 条会永远显示**吗？
- 如果每次查询复位：多个页面并发查询时，**后查的会覆盖先查的计数**吗？

**这三种语义完全不同，都会影响 UI 显示的「N」是真是假。**

**建议明确**：

```dart
/// 读失败日志。
/// 
/// - 累计模式：进程生命周期内所有读失败的计数，直到 [clear] 显式调用
/// - UI 层在「用户确认提示」后调用 [clear]（而不是每次 build）
class ReadFailureLog {
  int get totalSkipped;
  void record(...);
  void clear();
}
```

**并说清：**

- **谁来 clear**（AppShell 点击提示条的「知道了」时？）
- **什么时机 clear**（每次启动？每次同步成功？）
- **并发场景**（多个 DAO 同时读，计数如何汇总）

#### ④ 顺带：`fromWireOrNull` 会**静默掩盖真错**

如果所有枚举都用 `fromWireOrNull` + 跳过/兜底，**开发期自己写的错**（比如枚举拼写错误）也会被静默吞掉。

**建议加一条**：

> **`fromWireOrNull` 返回 `null` 时，`ReadFailureLog.record` 必须记录「列名 + 原值」**（进日志，不进 UI）。
> 这样开发期能在主机日志里看到「哪些值是库外的」——**区分「用户数据真坏了」和「代码写错了」**。

**否则**：开发期发现不了自己的枚举拼写 bug，只看到「有 1 条数据读不出来」——定位不了。

### 其他细节

- **接线 1 选 A**（`Db` 挂 `ReadFailureLog`）—— ✅ 与「判断放纯 Dart」一致，DAO 零改动
- **接线 2 选 A**（`AppShell` 顶部条）—— ✅ 与 `mobile_shell` 状态行先例一致
- **接线 3 文案**：草案可以，但建议**别用「N 条数据读不出来」**——「读不出来」用户不理解。改成：

  > **有 N 条记录暂时显示不全。** 可能是一份旧备份或手工改过的数据。
  > [知道了] [去设置看怎么办]

  **「显示不全」比「读不出来」更接近用户能理解的现象。**

- **§六「我会自带的东西」**：五条全对，尤其第 5 条「根 `lib/` 无编译门禁 ⇒ L3/L4 交你复跑」——诚实。

## 三、落地顺序建议

提案 §五 给了两个选项：「一起做」/「先 core 再 UI」。

**我建议：先 core（L2 + L1），再 UI（L3 + L4）。** 理由：

1. **L2 + L1 就治好了「整页变灰」**——这是用户真正的痛点（#42 现象）
2. **L3 + L4 是「第二道防线」+「不静默」**——它们依赖 L2 + L1 的计数通道，先后顺序不会颠倒
3. **你能「今天就拿到 7 个 DAO 的自验结果」**——这是提案自己指出的优势
4. **UI 两层次批可以做**——不用担心「做了一半 UI 看不见效果」

**唯一要守的**：**L4 不能拖到以后**——它是 #42 甲里「不静默」的兑现。**L2 + L1 落地时，L4 的计数通道必须同步建好**（哪怕 UI 条留到下批）。
