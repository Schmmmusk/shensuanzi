## 一、深度复盘：为什么会发生“响应丢失”？

你遇到的情况在弱网或局域网波动时极其经典：
1. 手机：把 `XS...001` 发给电脑。
2. 电脑：收到请求，写入 SQLite，事务提交（主机落了库）。
3. 电脑：生成 HTTP 200 响应，往回发。
4. 网络：**咔嚓**（Wi-Fi 瞬断、或者手机切后台导致 Socket 挂起）。
5. 手机：超时没收到 200，标记该条目 `pending`，留待重试。
6. 手机：用户点“立即同步”查队列，看到 `pending`，所以显示“待同步 1 条”。

**你的判断完全正确：徽标没撒谎，UI 也没毛病，是底层的状态机缺少了“确认补偿”机制。**

## 二、方案审查：为什么是“乙 + 丙”？

### 为什么否决甲（定时退避重试）？
虽然这是个很标准的解法，但在你的架构里：
1. **费电/消耗性能**：在没有新单据产生的时候，定时器一直在后台空转，中老年用户的手机本来就卡。
2. **治标不治本**：如果网络一直不畅，定时重试只会不断加重客户端和服务器的负担，而且用户还是会疑惑“为什么一直在转圈”。

### 为什么选乙（推送后对账）？
这就相当于金融里的**“日终对账”**。
- 客户端说：“我这还有 1 笔 pending。”
- 主机说：“我库里已经有这笔单了。”
- 客户端：“好，那我把这笔从 pending 划掉。”
这利用了项目里早就设计好的**幂等键（ID）**，天然安全，既快又准。

### 为什么选丙（UI 兜底）？
因为乙只能解决“网络瞬断”导致的问题，如果主机的服务真的挂了，或者局域网彻底断开，对账也会失败。这时候，给三态条加一个【重试】按钮，让用户有个手动戳一下的宣泄口，非常重要。

## 三、落地时的 3 个工程暗坑（务必盯紧）

### 1. 不要拉全量，拉实体交集（性能防呆）
你在乙方案里写：“`pushAll` 结束后若仍有 `remaining`，拉一次 pull”。
- **坑**：如果直接调一次全量的 `pull`，在数据量大时可能会卡住界面。
- **解法**：只对剩下 `pending` 的那几个 `entity_id`，去主机查一下是否存在。比如发一个特殊的局部查询，或者在 `pull` 的参数里带上特定的实体 ID，而不是从头拉一遍全量流水。

### 2. 状态更新后的 UI 刷新（呼应原 F16）
当你用对账逻辑把那 1 条 `pending` 改成 `sent` 后，**必须让 `MobileSyncService` 触发一次 UI 层的状态更新**。
- 因为你刚才推翻了路由缓存的假说，那就说明在同一个页面下，UI 是能正常响应的。只要对账成功后，主动调用一次 `notifyListeners` 或者更新三态条的 `ValueNotifier`，徽标立刻就能变绿。

### 3. 测试必须“造出丢失的响应”
要写红这条测试，你不能真的去拔网线。
- **解法**：写一个 Mock 的 `Transport`。让它把请求发给 Server 并成功落库，但在返回 200 时，故意抛出一个 `SocketException`（模拟响应丢失）。
- **断言**：此时队列一定是 `pending`。然后再触发一次 `syncNow`，断言对账逻辑生效，队列被清空，状态变为 `sent`。
