## 二、落地第 0 批的 4 个暗坑防范

### 1. P0-1（单号撞号）：注意测试用例的构造
- 提案说：改 `ORDER BY LENGTH(doc_no) DESC`。
- **防范**：测试用例里，不仅要有 `XS...-999`，最好直接造 999 条单据（或者在测试库里批量插入 999 个单号），然后调用生成器，看会不会返回 `...-1000`，而不是重复的 `...-999`。

### 2. P0-2（商品编辑丢列）：动态 SET 清单的排除项
- 提案说：`ProductDao.update` 的 SET 清单以 `toRow().keys` 为单一来源生成。
- **防范**：`toRow()` 会把 `id`, `created_at`, `sync_version` 等全包含进来。在动态生成 SQL 时，**必须显式排除主键 `id` 和只读字段（如 `created_at`）**。SET 子句里绝对不能出现 `WHERE id = ? SET id = ?` 这种自杀操作。

### 3. P0-3（窗口升序反了）：`doc_window_truncated` 的处理
- 提案说：截断时置 `doc_window_truncated` 标志。
- **防范**：主机响应加了新字段，客户端 `SyncClient` 的 JSON 解析器必须能认它（否则直接解析异常）。而且客户端拿到这个标志后，**不能马上清除队列条目**，必须等下一次拉取确实把最新的补上了才能清。这属于协议层变更，要在 `core` 的 DTO 和 `host` 的响应里同步加，千万不能只加一半。

### 4. B-1（拒收全量）：多商品场景的比对
- 提案说：退货量 == 原单剩余量才收口。
- **防范**：不是简单地比总数量。原单可能有商品 A 和商品 B。必须是 `{A: 原量, B: 原量}` 的 Map 完全相等，才能作废原单。测试用例里必须加一条“多商品部分退货”的场景。

### 5. B-2（创建态归一）：销售退货也要归一
- 提案说：`_prepare` 后按 `doc_type` 归一创建态。
- **防范**：`sale_return` / `purchase_return` 也属于主单，创建时也必须是 `confirmed`，不能是 `settled`（因为退货不一定马上退款）。盘点是 `confirmed`。收付款单是 `settled`。
