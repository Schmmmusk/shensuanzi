# 审查意见

先说结论：

- **选甲（编译期开关）。完全正确，毫不犹豫。**
- **这份报告不仅是一次极具工程价值的自我纠错，更是一次对“性能优化陷阱”的完美避坑。**

看到报告开头那句“我把参数顺序排反了……它测的根本不是我要测的东西”，我忍不住笑出了声。这就是做底层性能测试最真实的写照——**有时候你花了三天三夜去优化一个算法，最后发现是因为测量脚本写错了，导致测出来的数据全是假的。**

我们来看看这份报告里极其出彩的几个点：

### 一、 亮瞎眼的“自我打脸”与复盘

1. **参数传反的乌龙**：把 `LIMIT` 传成了 13 位的毫秒时间戳，导致“最近 30 天”实际查出了 16 万行数据。
2. **极度珍贵的教训**：**“性能测量必须同时断言返回行数。”** 这个教训必须写进 `testing.md` 的测试规范里。只要只看耗时，不看行数，测出来的数据就是废纸。
3. **反转的真相**：修正后，默认档（最近 30 天）的 SQL 耗时只有 **142 ms**。之前以为“默认档更慢需要优化”，结果人家本来就是最快的一档（因为查得少）。

### 二、 认清现实：停止在 SQL 层死磕

你算了一笔账：真机切页耗时 1.34 秒，而 SQL 即使全量跑也只有 212 毫秒，默认档更是只有 142 毫秒（占 11%）。
**这说明 80% 以上的卡顿根本不赖数据库，而是赖应用层的 Dart 代码、Flutter 的引擎渲染或者主线程的阻塞。**

所以，砍掉“继续加索引”的念头是绝对理智的。你甚至试了复合索引 `(receipt_doc_id, target_doc_id)`，发现耗时没变（215.7 vs 218.0 ms），立刻悬崖勒马，没有为了加索引而加索引。这省下了一次毫无意义的 schema 升级。

---

### 三、 埋点方案与开关选型（选甲）

**强烈同意选甲：`const bool kStartupTrace = bool.fromEnvironment('SSZ_STARTUP_TRACE');`**

- **为什么乙不行**：Windows 用户双击 exe 启动，你要他们去改环境变量？这简直是反人类。
- **为什么丙不行**：`kDebugMode` 是 JIT 模式，JIT 和 AOT（Release）的启动速度、帧渲染效率差几十倍，在 Debug 下测出来的“卡顿”对真机毫无参考价值。
- **为什么甲完美**：编译期常量，加上 Dart 的 Tree Shaking，在正式打包时会把包含这个常量的 `if (kStartupTrace)` 代码块**整段抠掉**，连一个字节的机器码都不会留下。对正式包的性能、体积影响绝对为 0。

**对 T0 到 T5 六个埋点的建议：**
- **T0（main 第一行）到 T1（bootstrap）**：如果这里耗时超过 0.5 秒，说明 Flutter 引擎初始化（比如加载 `app.so`、初始化 Skia 引擎）极慢。这通常发生在老 CPU 上（单核性能太弱）。
- **T2（Db.open）**：如果这里慢，大概率是 WAL 恢复，或者迁移脚本在跑。
- **T3（预加载完成）**：这里如果慢，看是不是 `config` 读取或者主数据拉取有全表扫描。
- **T4（首帧构建）**：这里如果慢，通常是 Widget 树太深，或者首次加载时做了太多布局计算（比如中文字体测量）。
- **T5（切页耗时）**：如果第一次切页很慢，第二次很快，说明是内存没缓存；如果每次切页都慢，说明那个页面的 `build` 里做了重 I/O。

### 四、 落地提醒（极其关键的一个暗坑）

**千万不要在 `main()` 里用同步 API 写 `startup-trace.jsonl`！**
打点是为了测启动速度，如果你在 T0 打点的时候执行了一句 `await file.writeAsString(...)`，这就把 I/O 阻塞加到了启动路径上，**你测出来的 4 秒里，可能有一半是你自己的埋点造成的。**

**解法**：如果在 `main()` 里打点，先把时间戳存在全局变量里（内存），等首帧渲染完毕（T4），再统一把 6 个时间戳**一次性、异步**地写进文件。或者用 `debugPrint` 输出，因为 `debugPrint` 是异步缓存的，不会卡死主线程。
