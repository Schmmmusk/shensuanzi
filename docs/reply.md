我审查了 0.7.1 当前代码。我的意见是：选择 A 作为第一阶段的方向，但必须把“旧主库损坏”和“镜像库损坏”分开处理。 这两种情况的恢复策略不应该相同。

而且，仓库目前有一个很容易被忽略的架构细节：手机上实际上存在不止一份数据文件。把它们分清楚之后，A、B、C 的风险会发生变化。

## 一、先厘清手机上的三份数据

根据当前代码，手机端的数据大致是这样分布的：

| 文件或位置                         | 用途                                       | 重要程度 |
| ----------------------------- | ---------------------------------------- | ---- |
| `data/shensuanzi.db`          | 旧的手机本地主库。C2 接线后已经不再是手机业务数据的主要读写来源，但仍被保留  | 较低   |
| `mirror/shensuanzi_mirror.db` | 电脑业务数据的手机镜像，同时包含 `sync_queue`、同步游标等客户端数据 | 很高   |
| `data/drafts/*.json`          | 开单页面的草稿文件                                | 需要保护 |

这里有两个重要事实：

第一，手机现在真正用于业务查询和离线开单的，是镜像库。`QueueSink` 把新单写入镜像库中的 `sync_queue`，而不是旧的 `data/shensuanzi.db`。

第二，未同步队列不是普通镜像数据。镜像中的商品、单据、库存等数据可以从电脑重新拉取，但手机还没上传的单据可能只存在于手机上。

相关代码可以对照阅读：

- [MirrorView：手机端主库的废弃与镜像职责](packages/shensuanzi_app/lib/src/mirror_view.dart)
- [MobileSyncService：镜像和同步队列](packages/shensuanzi_app/lib/src/mobile_sync_service.dart)
- [DraftsStore：草稿文件存储](packages/shensuanzi_app/lib/src/drafts_store.dart)

这意味着：如果损坏的是旧主库，镜像可能完全正常；如果损坏的是镜像库，问题就严重得多。

## 二、为什么当前会出现整个 App 不可用？

我在 `app.dart` 里找到了直接原因。

手机启动时，`_prepareMobile()` 大致按这个顺序执行：

1. 调用 `_openDatabase()` 打开旧的本地主库。
2. 打开手机镜像 `openMirror()`。
3. 构建手机端界面。

问题在第一步：

`_openDatabase()` 如果失败，会捕获异常并设置 `_dbFailure`。它不会把异常继续抛给 `_prepareMobile()`。

所以，即使第二步成功打开了健康的镜像，`_dbFailure` 仍然存在。

而 `_buildHome()` 的判断顺序是：

```text
_dbFailure != null
    ↓
直接显示启动错误页
    ↓
不会进入 MobileShell
```

也就是说，旧主库的打开失败，实际上成为了手机端进入业务界面的硬性门槛。

这与 C2 之后的架构定位已经不太一致了：既然手机业务读面已经迁移到镜像，就不应该让一份不再承担主要业务职责的旧主库决定整个 App 能否启动。

参考：[app.dart](lib/src/app.dart)

## 三、逐个评价 A、B、C

### A：降级使用镜像 · 推荐作为第一阶段方案

这个方向符合目前的架构演进。

旧主库打不开，但镜像完整时，手机至少可以继续查看从电脑同步来的业务数据。

我赞成第一阶段采取保守策略：

- 允许进入手机主界面。
- 商品、库存、往来等能够由镜像提供的页面继续展示。
- 明确告知用户目前使用的是手机上的镜像数据，并显示最近一次同步时间。
- 暂时禁用开单、主数据修改等写入操作。
- 保留同步状态、数据导出和日志入口。
- 不删除、不覆盖损坏的旧主库。

这里有一个值得讨论的地方：开单是否一定要禁用？

从当前代码看，手机开单由 `QueueSink` 写入镜像里的 `sync_queue`，并不依赖旧主库。因此，如果镜像本身通过了完整性检查，理论上仍有条件安全地进行离线开单。

不过，我赞成第一阶段先禁用。因为我们还需要验证旧主库不可用时，所有页面、提交出口、同步回调和数据导出是否都真正与它解耦。

等验证充分后，可以再考虑恢复镜像队列写入能力。

A 的真正工作量主要在于：不能只把 `_dbFailure` 清掉就算完事。必须检查依赖旧主库的页面，例如单据列表、单据详情和部分收付款相关功能，不能让它们拿着空服务继续运行。

### B：自动重建空库 · 不建议直接采用

B 最大的问题不是技术上能否创建空库，而是它可能误伤不可恢复的数据。

这里要区分两种情况。

**情况一：损坏的是旧主库 `data/shensuanzi.db`。**

由于手机业务的主要读写已经迁移到镜像，重建这份旧主库并不必然导致未同步队列丢失。

但既然它已经不再是主要业务数据源，我认为也没有必要急着重建。保留原文件、让 App 使用健康镜像，反而更加简单。

**情况二：损坏的是 `mirror/shensuanzi_mirror.db`。**

这才是 B 真正危险的地方。

目前 `sync_queue` 就在镜像库里面。如果直接删除镜像库并创建一份空库，未同步订单、失败队列和其他客户端状态都会随之丢失。

现有 `SyncClient.rebuildMirror()` 其实已经考虑了这个问题：它只删除九张镜像业务表，重新建表，并清理同步游标，保留 `sync_queue` 和 `clock_offset`。

但它有一个前提：SQLite 数据库必须先成功打开，才能执行这个事务。

如果数据库文件已经彻底打不开，这条重建路径就不一定能运行。

而且，设置页现有的“重建本机数据副本”也存在这个限制：它先调用 `_meta()`，而 `_meta()` 又会调用 `openMirror()`。镜像打不开时，甚至无法进入真正的重建步骤。

参考：[SyncClient.rebuildMirror()](packages/shensuanzi_core/lib/src/sync/sync_client.dart) · [设置页的重建流程](lib/src/ui/settings_page.dart)

因此，B 不能只是“弹一次确认框，然后重建”。

至少应该先：

1. 保留原数据库文件及其 `-wal`、`-shm` 文件。
2. 对原文件的副本尝试抢救 `sync_queue`。
3. 保存能够恢复的未同步单据，必要时生成可分享的清单。
4. 创建新的镜像库。
5. 从电脑完整拉取权威业务数据。
6. 恢复能够确认归属和完整性的队列数据。

无法恢复的队列必须明确告诉用户，不能假装已经找回。

### C：只改提示

*不推荐作为最终方案*

我不赞成。

“数据在电脑上，重新配对即可”并不总是正确的恢复指导。

尤其是镜像文件损坏时，当前 `syncNow()` 会在访问网络和主机之前调用 `openMirror()`。镜像都打不开，重新配对并不能解决本地数据库打不开的问题。

而且用户看到的是 App 整体无法使用。对他们来说，知道电脑上的数据没有丢，只解决了一半问题。

C 只能作为特殊情况下的临时提示，不能作为 0 号问题的最终处理方案。

## 四、我的最终建议：A 为主，增加一条镜像损坏恢复路径

我建议把手机存储故障分成三个状态，而不是用一个 `_dbFailure` 包办所有情况。

状态 1：旧主库不可用·**降级运行**

镜像完整，可以进入手机端业务界面。第一阶段只读，展示最近同步时间和恢复指引。

状态 2：镜像可打开，但数据异常 · **尝试修复**

尝试完整性检查、队列保护和镜像重建。能保留的未同步数据必须先保留，再从电脑重拉。

状态 3：镜像文件无法打开· **隔离恢复**

不直接覆盖原文件。先保留原件和 WAL 相关文件，尝试独立抢救队列；之后再创建新镜像、重新拉取。

这套方案的核心原则是：

电脑上的业务数据是可重新获取的；手机上尚未上传的操作是必须优先保护的。

我甚至认为，从长期架构来看，`sync_queue` 不应该永远和可随时重建的镜像业务数据放在同一个物理数据库文件里。

目前逻辑上虽然已经把两者区分开了，但物理文件损坏仍然会同时影响它们。未来可以考虑将待同步队列迁移到独立的本地存储，使镜像可以无条件重建，而队列拥有独立的持久化和恢复能力。

这不是要求你现在立刻拆库，而是值得记录的架构演进方向。

## 五、另外三个问题，我的优先级判断

| 编号 | 问题                  | 建议                           |
| -- | ------------------- | ---------------------------- |
| 0  | 手机本地库损坏导致 App 不可用   | 优先处理，先把旧主库与镜像解耦              |
| 1  | `host.json` errno 5 | 保持现有降级；根因仍需诊断，不能把“已降级”当成彻底解决 |
| 4  | 手机镜像里的探针单           | 等架构调整时清理，避免和正常业务数据混淆         |
| 6  | 概览页滚动三屏             | 产品取舍，暂时不动                    |

我的裁定：选 A，但不要把 B 完全放弃。

A 解决的是“旧主库损坏，镜像仍然健康”的可用性问题；B 的安全版本则应该成为“镜像文件本身损坏”时的独立恢复流程。两者并不冲突。

我认为这比在 A、B、C 中强行挑一个更符合神算子目前的架构。

还有一个特别值得记住的教训：我们花了不少精力让镜像能够从主机重新拉取，却没有充分保护镜像旁边那份真正不能从主机重新拉取的数据——手机自己的未同步队列。可重建的数据和不可轻易重建的数据，应该有不同的故障边界。 👍
