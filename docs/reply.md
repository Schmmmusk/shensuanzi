**提案 56：建议修改后批准第一、二阶段，暂缓第三阶段。**

1. **批准诊断埋点。** 增加失败阶段、原始 errno、目标文件是否存在、文件属性、父目录写入测试、各阶段操作结果和重试结果。诊断信息只进入日志，不显示原始异常给普通用户。

2. **有条件批准 L2 原地重写。** 保留 L1 → L2 → L3 的三级降级策略，但必须补充截断后写入失败、flush 失败、进程异常退出等故障注入测试。不得把内存恢复旧内容描述为完全可靠的回滚，也不得假设 L2 一定能绕过文件占用。

3. **修正验收标准。** 当前只持久化令牌哈希，重启后无法恢复二维码明文。L2 成功不等于重启后能够显示原二维码。当前阶段验收应改为：主机身份稳定、已有配对设备仍能连接、写盘失败不再导致令牌状态异常。若要实现重启后直接显示原二维码，应另行设计令牌明文的安全持久化机制。

4. **暂缓 schema v8。** 等诊断结果和 L2 实测结果出来后，再决定是否需要将主机身份迁入数据库。

5. **不修改用户 ACL，不要求管理员运行，不添加 requireAdministrator manifest，不擅自迁移数据目录。**

总体原则：先查清楚失败发生在哪一步，再做最小范围的可靠兜底，不以牺牲现有数据安全和普通用户的使用体验换取表面上的修复。

---

先给结论：

**方向值得推进**

我支持先做诊断埋点，再评估原地重写；但暂时不建议原样批准提案 56。里面有两个重要的技术判断需要修正，其中一个直接影响最终验收标准。

# 一、这次终于把问题从「权限」拆成了具体故障

提案中最有价值的判断是：

> 现象不是「没有权限」，而是「改不了名」。

这个思路值得保留。

目前的实现是：

```text
生成 host.json 内容
       ↓
写入 host.json.tmp
       ↓
rename 覆盖 host.json
       ↓
失败后重试三次
       ↓
仍失败：使用内存令牌
```

这次真机报错发生在 `PathAccessException`，`errno = 5`。

同一个数据目录里的 SQLite 数据库能够正常读写，而 `host.json` 的写入失败。这确实让我们应该重点调查文件替换操作，而不是上来就要求用户修改权限。

但我认为提案里有一句话说得太绝对：

数据库能写，不足以证明 host.json 的文件权限没有问题。

原因是 Windows 的文件操作权限并不只有一种。

例如：

- 写入一个已存在文件，需要相应的写入权限。
- 删除或替换一个文件，需要文件自身的删除权限，或者父目录的删除子项权限。
- 打开文件时，其他进程设置的共享模式也会影响后续替换操作。

因此，即使 `shensuanzi.db` 和 `host.json` 的 ACL 看起来相同，也不能仅凭数据库能写，就彻底排除权限相关问题。

另外，`ERROR_ACCESS_DENIED (5)` 也不是文件被其他进程占用的专属错误。杀毒软件、受控文件夹访问、文件系统过滤驱动等，都可能产生类似结果。

我的建议是把提案中的结论调整为：

> 当前证据更支持「文件替换操作受阻」，应优先调查目标文件的共享模式、替换权限以及安全软件拦截，而不是直接修改整个数据目录的 ACL。

这样更严谨，也不会过早锁定根因。

# 二、诊断埋点：我完全支持，应该优先实施

提案第三节的诊断字段设计，我认为是这次最应该先落地的部分。

尤其是：

| 字段                | 价值                        |
| ----------------- | ------------------------- |
| `stage`           | 区分创建目录、写临时文件、rename 哪一步失败 |
| `errno`           | 保留原始系统错误码                 |
| `target` / `temp` | 确认实际操作路径                  |
| `attrs`           | 排除文件属性造成的影响               |
| `parentWritable`  | 判断父目录是否能够正常创建文件           |
| `retry`           | 判断短暂故障是否能通过重试恢复           |
| `integrity`       | 辅助判断进程完整性级别               |

我特别赞成让诊断信息只进入日志，而不进入普通用户界面。

不过，我想补充两个字段：

- 操作前目标文件是否存在：首次创建和覆盖已有文件是两种不同情况。
- 每次操作的具体结果：临时文件创建成功、写入成功、flush 成功、rename 失败，不能只记录最终异常。

这样下一次复现时，我们能明确知道究竟是：

```text
临时文件创建失败
```

还是：

```text
临时文件写入成功
目标文件存在
替换目标文件失败
```

这两种情况的调查方向完全不同。

另外，提案中的 Process Monitor 和 `handle.exe` 调查方式很实用。它们可以帮助我们找到具体拦截操作的进程，而不是靠猜测杀毒软件。

我的意见：诊断埋点可以直接批准，不需要等长期架构方案。

# 三、L2 原地重写：值得尝试，但不能把它当成无风险方案

提案第四节提出：

```text
L1：临时文件 + rename
       ↓ 失败
L2：读取旧内容 → 原地重写
       ↓ 失败
L3：内存令牌
```

我理解这个设计的目的：如果问题只发生在 rename，那么绕过文件替换，直接写入原文件，有机会解决问题。

这个方向是合理的。

但是，L2 有一个必须认真处理的风险：

原地重写会失去原子替换的保护。

假设原文件内容是：

```dart
{
  "host_id": "abc",
  "token_hash": "..."
}
```

原地写入时，通常会经历：

1. 打开目标文件。
2. 截断旧内容。
3. 写入新 JSON。
4. flush。

如果第二步成功、第三步失败，原文件就可能变成空文件或不完整 JSON。

提案提出先把旧内容读进内存，失败时再写回去。这可以降低风险，但不能完全解决问题：

- 恢复写入本身也可能失败。
- 程序在截断后突然崩溃，内存中的旧内容也随之消失。
- 断电同样可能留下不完整文件。

所以我建议增加一个约束：

L2 必须先经过专门的故障注入测试，不能只测试正常写入。

至少覆盖：

| 故障时机        | 预期结果                |
| ----------- | ------------------- |
| 打开文件失败      | 旧文件保持完整             |
| 截断后写入失败     | 尽力恢复旧内容，记录恢复结果      |
| 写入过程中进程异常退出 | 下次启动能够识别损坏文件，不应直接崩溃 |
| flush 失败    | 不得报告持久化成功           |
| L2 失败       | 正确降级到 L3            |

此外，原地重写也不保证绕过所有文件锁。如果另一个进程以不允许写入共享的方式打开文件，L2 一样可能失败。

所以我赞成把 L2 作为第二级尝试，但不要在提案里承诺它一定能解决文件占用问题。

# 四、我发现一个比 L2 更重要的问题：验收标准与现有令牌设计矛盾

必须修正

这是我审查时最在意的地方。

提案第六节的验收标准是：

> 连续两次重启，不点「重新生成」也能画出同一个配对码。

但我检查了当前 `auth.dart`，发现它明确规定：

- `host.json` 只持久化 `host_id`、`token_hash`、`created_at`。
- 明文令牌不落盘。
- `HostIdentity.load()` 读回的 `plaintextToken` 恒为 `null`。
- 只有刚生成或重置令牌时，内存中的 `plaintextToken` 才非空。

也就是说：

即使 L1 原子写完全成功，重启后也无法从哈希恢复二维码里的明文令牌。

这是当前安全设计的主动选择，不是写盘失败造成的。

因此，提案中这两件事必须区分：

| 目标             | 当前方案能否实现      |
| -------------- | ------------- |
| 令牌哈希成功持久化      | L1/L2 可以尝试    |
| 重启后继续验证已有手机的令牌 | 哈希持久化即可       |
| 重启后直接显示原来的二维码  | 仅保存哈希做不到      |
| 不重置令牌就重新显示原二维码 | 需要改变明文令牌的保存策略 |

换句话说，L2 即使成功，也不能自动实现提案所说的「重启后仍能画出同一个二维码」。

如果你们希望真正实现这个目标，就必须另行讨论明文令牌的安全持久化，例如使用 Windows DPAPI 等机制保护令牌，或者重新设计配对凭据生命周期。

但这会引入平台依赖、密钥保护、备份迁移等问题，不能悄悄塞进 L2。

我建议把当前阶段的验收标准改成：

1. 连续两次重启，`host_id` 保持不变。
2. 已经配对的手机仍能使用原令牌正常连接。
3. 不需要因为写盘失败而重新生成令牌。
4. 如果需要展示新的配对二维码，仍然按照现有安全设计明确执行令牌重置。

如果你希望的是「重启后无需重置就能给新手机展示原二维码」，那就应该另立一个令牌持久化设计提案。

这是两个不同的问题。

# 五、长期迁移到 schema v8：方向可以保留，但现在不要做

提案第五节提出把主机身份放进数据库：

```sql
CREATE TABLE host_identity (
  k TEXT PRIMARY KEY,
  v TEXT NOT NULL
);
```

我认为这个方向有道理，但现在还不是最合适的实施时机。

原因有三个：

1. 目前数据库迁移链刚刚经历了真实设备上的 v3 → v7 成功验证，没必要马上增加新的迁移复杂度。
2. `host.json` 是主机身份数据，放进业务数据库会增加数据库初始化、恢复和身份读取之间的耦合。
3. 数据库能写不代表数据库永远不会损坏。把身份搬进去，只是改变故障边界，并没有消灭故障。

我会先完成诊断和 L2 评估，再根据真实现场决定是否需要 v8。

而且，如果未来真的迁移，我建议不要只考虑 SQLite 表结构，还要明确：

- 数据库损坏时主机身份如何恢复？
- 备份恢复后是否会意外恢复旧令牌？
- 用户更换数据目录后身份如何处理？
- 手机端是否需要对应字段？（目前看不需要）

这些都比增加一张小表重要。
