# 一、退款上限：这次改对了，但还有一个洞

本次改进通过

这次提交最重要的变化有三个：

1. `_requireRefundWithinCap()` 已经移入 `RuleEngine`。
2. 校验放在 `_return()` 的 `insertIfAbsent()` 之前。
3. `ReturnService` 不再使用 `Overpay.clamp()` 静默截断退款金额，而是把原始金额交给规则层拒绝。

相关代码：[RuleEngine](packages/shensuanzi_core/lib/src/rules/rule_engine.dart)、[ReturnService](packages/shensuanzi_core/lib/src/documents/return_service.dart)。

这次还补了一条非常有价值的测试：直接调用 `RuleEngine.dispatch()`，绕过 `ReturnService`，证明未收款的送货单仍然不能退款，而且拒绝后数据库里没有留下半张单据。

这就对了。主机规则层才是真正的权威边界。

但是，接下来是重点。

## 1. P0 后续单独退款仍然可以绕过累计退款上限

目前 `_requireRefundWithinCap()` 被调用的位置是：

```
RuleEngine._return()
```

它检查的是创建退货单时传入的 `immediatePayments`。

但神算子支持另一种正常业务流程：

先退货、暂不退款，之后再单独创建付款单或收款单完成退款。

这不是我臆想出来的路径。现有架构明确支持：

- `sale_return` 由 `payment` 核销；
- `purchase_return` 由 `receipt` 核销。

而且 `RuleEngine._settle()` 的 `allocatableTargetTypes` 已经包含这两种退货单，`settleDirections` 也已经明确规定了正确方向。

[RuleEngine.\_settle()](packages/shensuanzi_core/lib/src/rules/rule_engine.dart)\
[SettlementService.settle()](packages/shensuanzi_core/lib/src/documents/settlement_service.dart?)

我们来构造一个场景：
```text
原始交易

销售总额

¥100

实际收到

¥50

第一次操作：退货，但不立即退款

退货金额

¥80

立即退款

¥0
```
当前规则允许通过：没有立即退款，不触发退款上限检查。

第二次操作：单独创建付款单
```markdown
核销目标

这张 ¥80 的销售退货单

实际付款

# ¥80
```
目前这条路径缺少原单累计退款上限检查

原单只实际收过 ¥50，却可能通过独立核销支付 ¥80。

为什么会这样？

因为 `_settle()` 目前检查的是：

$\text{该退货单已核销额}+\text{本次核销额} \leq \text{该退货单总金额} $

它并没有进一步检查：

 $\text{原单累计实际退款} \leq \text{原单真实收款}$

于是新加的安全检查只保护了“创建退货时立即退款”，没有保护“之后单独退款”。

修复建议：在 `RuleEngine._settle()` 中，针对 `sale_return` / `purchase_return` 核销目标增加原单累计退款校验。

还有一个容易遗漏的细节：

如果一张付款单同时核销同一原单下的两张退货单，不能分别检查两个退货单是否超额，而应该把本次所有分配金额按原单 `ref_doc_id` 汇总，再与原单剩余退款额度比较。

否则，同一笔收付款请求可能通过拆分 allocation 绕过累计上限。

建议测试三种情况：

- 延迟退款超过原单实际收款，必须拒绝。
- 同一原单有多张退货单，一次付款分配给两张，累计超额必须拒绝。
- 退款分多次完成，累计不超过原单实际收款时正常通过。

这是我目前对退款模块最重要的意见。

## 2. UI 有一个小问题：把“已经全部退完”说成“从来没收过钱”

[ReturnPage.\_refundSection()](lib/src/ui/return_page.dart)

目前 `_refundableCents <= 0` 就显示：

> 这张单还没收到过钱，所以没有可退的款。

但 `refundableCentsOf()` 的实际计算是：

$\max(0,\text{真实收款}-\text{累计已退款})$ 

因此，以下两种情况都会得到 0：

- 原单从来没有收到钱；
- 原单收到的钱已经全部退回。

第二种情况下，当前提示明显不准确。

建议服务层提供一个包含不同状态的退款额度结果，例如：

| 实际情况  | UI 提示         |
| ----- | ------------- |
| 从未收款  | 这张单还没收到过钱     |
| 已全部退回 | 这张单收到的钱已经全部退回 |
| 仍有余额  | 这张单还剩 ¥X 可退   |

这属于小问题，不会造成错账，但对于面向非技术用户的软件，状态表达必须准确。

# 二、数据抢救：这轮仍然是最大风险区

暂不建议验收

这次最新提交没有修改 `rescue.dart`，所以上一轮发现的缺陷仍然存在。

我重新对照了生产规则和抢救测试，发现至少四处需要处理。

## 1. P0 正常的收款单、付款单可能被判定为不完整

位置：[rescue.dart](packages/shensuanzi_app/lib/src/rescue.dart)

现有逻辑：

```dart
_moneyAmountMismatch(myMoney, paidCents)
```

而 `paidCents` 来自：

```dart
doc['paid_amount']
```

问题是，神算子的真实规则中：

- 普通销售单创建后，主单的 `paid_amount` 记录核销缓存。
- 实际资金流水挂在自动生成的 `receipt` 单上。
- 收款单、付款单创建时，`paid_amount` 被明确设置为 0。
- 收付款单真正的金额在 `total_amount`。

所以，一张正常的 ¥100 收款单会有：

| 字段                | 值     |
| ----------------- | ----- |
| `total_amount`    | 10000 |
| `paid_amount`     | 0     |
| `money_ledger` 合计 | 10000 |

目前 `_moneyAmountMismatch()` 会比较：

$10000 \ne 0 $

然后将正常收款单判为缺少或不匹配资金流水。

而且，该函数在 `money.isEmpty` 时直接返回 `false`，因此也不能可靠地发现缺失资金流水。

修复方向：按单据类型处理。

- `receipt/payment`：`money_ledger` 合计应与本单 `total_amount` 对应。
- `sale/purchase/delivery/return`：真实收付款应通过 `settlements` 核对，不能拿主单自己的 `money_ledger` 与 `paid_amount` 机械比较。

我还发现，当前 `makeDb()` 测试夹具直接在销售单 ID 下写资金流水，并将主单 `paid_amount` 设成同样金额。

这和生产规则引擎生成独立收付款单的结构不同。

这恰恰解释了为什么前面的测试没有抓住问题。

建议尽快用真实 `RuleEngine` 生成收款单和付款单，再拿生成出来的数据库测试抢救。 测试数据的结构必须与真实数据一致。

## 2. P0 整张往来流水丢失，仍可能被判完整

当前 `_ledgerAmountMismatch()`：

```dart
if (party.isEmpty) return null;
```

注释说“一条都没有由前面的分支处理”，但 `_assemble()` 对普通销售、采购、送货和退货单，并没有一个专门处理“只有往来流水全部丢失”的分支。

假设一张普通赊账销售单：

- 单据存在；
- 明细完整；
- 商品库存流水完整；
- `party_id` 有效；
- `party_ledger` 整张丢失。

这时：

- 库存行数检查通过；
- `_ledgerAmountMismatch()` 因为流水为空，返回 `null`；
- `_moneyAmountMismatch()` 也可能通过；
- 最终可能被放入 `importable`。

结果就是：货恢复了，单据恢复了，客户欠款却不见了。

修复时应该根据单据类型和 `party_id` 明确判断预期流水：

有往来方且规则要求生成往来流水，就必须存在对应流水；没有往来方的散客、散采场景则按业务规则豁免。

不要用“流水为空”来推断“不适用”。

## 3. P0 核销关系两端仍然没有完整性检查

这里有一个特别明显的线索：

`_firstMissingRef()` 接收了 `settle` 参数，但函数内部没有使用它。

也就是说，相关代码已经预留了核销检查的入口，却还没有真正实现。

与此同时，`_writeNewDatabase()` 写入核销数据时会过滤：

```dart
if (!ok.contains(receipt)) continue;
if (target is String && !ok.contains(target)) continue;
```

这会产生一个危险情况：

- 原单和收款单都被抢救读出来；
- 其中一方因为其他问题被标记为不完整；
- 另一方仍然被认为完整；
- 写入新库时，涉及不完整端的核销记录被直接跳过。

用户最终拿到的是一份结构上能打开的账本，但某笔收付款与它原本核销的单据失去了联系。

我建议核销关系必须按双端依赖处理。

只要一条核销关系的一端缺失或不完整，就要明确处理另一端，不能只把关系过滤掉、保留另外一张单据。

同时还要检查：

- `receipt_doc_id` 指向的收付款单是否存在且完整；
- 非空 `target_doc_id` 指向的目标单据是否存在且完整；
- 被核销的两端是否都满足业务规则。

这项不能只靠 `SUM(settlements.amount)` 判断。

## 4. P1 库存流水仍然只检查行数，没有真正核对数量

[`_hasMissingStockRows()`](packages/shensuanzi_app/lib/src/rescue.dart)

当前它只统计：

```dart
lineRows[productId]
stockRows[productId]
```

然后比较数量，也就是每个商品出现了多少行。

但施工清单 55 要求的是：

行数相等，并且数量合计也相符。

例如：

| 数据      | 明细 | 库存流水 |
| ------- | -- | ---- |
| 商品 A 数量 | 10 | -8   |
| 记录行数    | 1  | 1    |

目前检查仍然会通过。

另外，代码只遍历 `lineRows.entries`，没有检查库存流水中出现、但明细中不存在的商品 ID。

还有一个例外没有实现完整：`stocktake` 现在直接跳过库存流水检查，而方案要求的是只对确实产生库存差额的明细要求流水，不是所有盘点单都跳过。

我建议把判据实现成真正的逐商品核对：

$ \text{明细行数}=\text{库存流水行数} $

$ |\text{明细数量合计}|=|\text{库存流水数量合计}| $

并按业务类型定义符号。对于盘点，则根据盘点规则计算哪些明细应有流水。

# 三、测试夹具：我认为需要专门做一次重构

我这次越来越觉得，抢救模块的问题不只是少了几条断言。

它的测试数据库与真实账本之间的差异，已经大到会影响测试结论。

目前 `rescue_test.dart` 的 `makeDb()` 直接手写：

- 销售单；
- 两行明细；
- 两条库存流水；
- 一条直接关联销售单的资金流水；
- 一条直接关联销售单的往来流水。

但真正的 `RuleEngine` 会：

1. 创建销售主单；
2. 写入库存流水；
3. 写入主单往来流水；
4. 若有立即收款，创建独立 `receipt` 单；
5. 在收款单上写资金流水；
6. 写入 `settlements`，关联收款单与销售单。

这种区别不是无关紧要的实现细节，而是数据库关系本身不同。

我建议测试夹具分成两类：

A. 正常业务夹具

通过 `SaleService`、`PurchaseService`、`DeliveryService`、`ReturnService` 和 `SettlementService` 构造真实业务。

B. 损坏注入

在正常业务生成的数据上，针对性地执行 `DELETE`、`UPDATE`、移除外键目标等操作，模拟页损坏后残留的数据形态。

这样测试才能回答真正的问题：

> 一份原本由神算子自己生成的合法账本，遭遇局部数据丢失之后，抢救器能否识别出哪些业务单元已经不完整？

我会把这项作为抢救完整性功能的验收前置条件。
