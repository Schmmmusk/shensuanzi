# 二、新增的库存 Top 10：方向正确，但发现了一个业务口径问题
第三批功能已接入
新增代码的主要结构：
- `QueryDao.topStockByValue()`：一条 SQL 聚合库存流水、关联商品、按资金价值排序。
- `StockValueRow`：传递商品名称、数量、单位、价值。
- `StockTopCard`：展示商品名称、占用金额、数量和单位。
- `OverviewPage`：把库存榜接到图表区域后面。
按资金占用排序，而不是按数量排序，这个决定我完全赞成。代码也没有把数量不同的商品强行换算成同一个单位。

但有个问题值得你们认真处理。
## 1. 需要修正
 成本未校准的库存被当成 ¥0
当前查询的关键条件：
```sql
WHERE s.qty > 0
ORDER BY s.cost DESC, p.name ASC
```

它只检查库存数量为正，没有区分成本是否已知。

这和现有库存页的设计产生了冲突。

我特意核对了 `stock_page.dart` 的成本状态判定，那里明确有三种情况：
情况	当前库存页文案
从未入库	未进货
期初录入、有正数量流水，但成本余值为零	待校准
成本正常	显示金额

而且代码注释明确说明：直接显示 ¥0.00 会让首次使用的用户以为软件出了问题。

现在的库存榜却会把这些商品选进去：
```dart
valueCents: row['cost']! as int,
```

然后直接显示：
```dart
'¥${Money.formatGrouped(row.valueCents)}'
```

这会把「成本未知」表达成「占用资金为零」。

更麻烦的是，当前横条还有 4% 的最小比例，零成本商品可能获得一条可见的彩色横条。

我建议让 `StockValueRow` 明确携带成本状态。成本未校准的商品不要假装拥有一个确定的资金占用值，可以不参与 Top 10，或者放在单独的待校准提示中。

2. 建议修正
 库存榜又出现了 4% 比例下限
`stock_top.dart` 中：
```dart
final double ratio = maxValue <= 0
    ? 0
    : (row.valueCents / maxValue).clamp(0.04, 1.0).toDouble();
```

这里和前一轮欠款横条遇到的问题一样。

提交记录给出的四个例子是：
商品价值	实际比例（相对 ¥12,600）
¥12,600	100%
¥3,800	30.16%
¥1,000	7.94%
¥50	0.397%

最后一项会被抬到 4%，放大约十倍。

这不是一个严重的计算错误，但图表长度本来就在表达金额关系，最好不要让它产生另一套比例。

建议沿用 `BalanceBarsCard` 的处理方式：比例照实计算，只保证最小 4px 可见。

另外，库存榜也需要明确处理负成本。当前库存页已经考虑了 costCents < 0 的情况，甚至在库存数量为正时也会将负成本标红；但库存榜只过滤 qty > 0，没有过滤或单独处理负价值。

这类记录不适合直接作为普通的正向资金占用条展示。建议把零成本、负成本两种状态都加入 DAO 和 UI 测试。

# 三、性能方面：有一个值得提前关注的地方
当前 `OverviewPage.build()` 中直接执行：
```dart
final List<StockValueRow> stockTop = hasDocs
    ? q!.topStockByValue()
    : const <StockValueRow>[];
```

这条 SQL 不是近 30 天查询，而是对整个 stock_ledger 按商品分组，再排序取前十。

虽然覆盖索引能够帮助它减少回表，但它依然需要处理完整的库存流水聚合。

问题在于：这个查询放在了 build() 里面。

例如，用户点击「立即备份」，_backupNow() 会通过 setState() 改变 _busy；这会触发页面重建，进而再次执行库存榜查询。备份结束时还会再触发一次。

所以它不是单纯的「打开概览时查一次」。

我建议按照项目已有的页面查询纪律，把这类全历史聚合放到适当的加载时机，并缓存结果；业务数据发生变化、重新进入概览时再刷新。

这里我暂时不判定它一定会卡顿。当前提交没有给出这条新查询在 478 MB 造数库上的耗时，也没有给出新增库存榜之后的整页 settled 数据。

建议把它列入下一轮低配性能验收，而不是凭 SQL 只有一条就认定性能达标。
