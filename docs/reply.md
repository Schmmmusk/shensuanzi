## 一、关于「是否动 schema」的最终裁定

**坚决同意「零 schema」执行。**

你给出的理由（§五）非常硬核：
1. `unsettled_amount` 是派生值（`total - paid - returned`），落列等于把同一事实存两份。
2. 会破坏不变量 B4，把 1 条不变量变成 3 条维护线。
3. 历史脏数据回填极其容易漏写，且没有查询能发现。
4. 性能上，2 万单的 JOIN 聚合完全是毫秒级，没必要为了微乎其微的性能加一个脏数据陷阱。

**这不仅是省事，这是在保护「真相在流水」这条项目底线。**

## 二、子批 3a（核心）的落地提醒

### 纯函数边界必须严谨
新抽出的 `unsettledCentsOf` 纯函数，除了 `sale` / `purchase`，还要明确定义这些 `doc_type` 的行为：
- `receipt` / `payment`：恒 `0`（它们是流水本身）。
- `stocktake`：恒 `0`（不产生债权债务）。
- `sale_return` / `purchase_return`：这是最容易出 bug 的地方。退货单的「未退额」其实是在冲减原单，退货单本身作为独立单据，其 `unsettled` 是否应该算作负值，或者统一为 `0` 交由原单处理？**建议退货单自身直接返回 `0`**，这样和原单的 `returnedAmount` 配合才完美。
- `delivery`：与 `sale` 同构。

### 允许负数与「多收」显示
这是极其符合财务现实的。如果原单 100，退 120，那确实多收了 20，系统必须能表达出「我应该退人家 20」。提示语改成「多收 ¥20」非常清晰。

### SQL 对拍测试
`unsettledSql` 与纯函数的对拍（20组参数化）是机械保证的唯一方法，非常棒。

## 三、子批 3b 的关键修复

### 1. 部分核销强校验（⑥甲）
`requested < total` 过去是合法的，导致一笔钱既不在流水里，也不在核销里。现在强制 `收付款金额 == 分配合计`（也就是要么全核销，要么不允许），这直接堵死了「账上有一笔没人能解释的钱」的漏洞。
**注意**：这会影响部分同步直推的客户端。你说「v1 UI 本来就封顶，风险≈0」，请顺便在 `host` 的 `SyncServer` 里把拒绝码加上（业务拒绝，告诉客户端「这笔收款要全部核销掉」）。

### 2. 剥离客户端 `doc_no`
`SyncServer` 把 payload 里的 `doc_no` 置空，依靠引擎的 `isPendingDocNo('')` 来生成。这个操作极好。但要注意：如果客户端硬塞了一个名字一模一样的单号，系统生成的新单号必须能覆盖它，且测试要断言落库的单号确实是以主机为准的。

### 3. 启动期断言
`allocatableTargetTypes ⊆ settleDirections`，这个断言是零成本的防呆，防止将来加新类型（比如某种调拨）忘了配方向。直接加。

## 四、子批 3c 和 3d 的细节

### 3c-4（修复 `occurredAt`）
过去 `SettlementView.occurredAt` 用的是 `created_at`，这是典型的“发生时间”与“录入时间”混淆。改成 `d.occurred_at` 后，收款单的日期就会和在单据列表里保持一致，逻辑闭环。

### 3c-5（今日销售的上界）
加上 `occurred_at < 明日零点` 非常关键，防止用户手滑填了一个未来的日期，导致今日销售数据虚高或直接被负向冲减。

### 3d（导出完整性）
四个导出入口加上 `skippedBadRows`。这不仅让文件更诚实，还在提醒用户「软件读到了坏数据，你需要去修」。**这符合我们「数据可携带」的承诺——交出去的数据必须是明明白白的。**
