# 审查意见

先说结论：

- **选甲，毫无疑问。** 用 `sync_version = base_version + 1` 来接手客户端的版本号，用最小的代码改动（一行）解决了两条时间线上的逻辑死角，极其优雅。
- **但提案中有一处明显的逻辑矛盾（涉及 `create` 操作），必须在落地前修正，否则会导致建档行为破坏。**
- **关于「已知残余（不修）」，我非常赞同。**

## 一、必须修复的逻辑矛盾：`create` 的版本号

提案在「甲（推荐）」的说明中写道：
> `create` 没有 `base_version` ⇒ 仍是 0（行为不变）。

但是，提案给出的公式是：
> `'sync_version': 0` 改为 `'sync_version': (op.baseVersion ?? 0) + 1`

**这里的矛盾在于**：如果是 `create` 操作，`op.baseVersion` 是 `null`，带入公式就是 `(null ?? 0) + 1 = 1`，而不是 `0`。这会导致所有新建的主数据（商品、客户、账户）初始版本变成 `v=1`，这违背了现有“初始 `sync_version = 0`”的既定契约，大概率会让相关测试红掉。

**修正方案**：
`sync_server.dart` 里的 `_insertMasterData` 是被 `createMasterData` 和 `updateMasterData` 共同调用的。要在代码里明确区分：
```dart
// _insertMasterData 内部
'sync_version': op.baseVersion == null ? 0 : op.baseVersion! + 1,
```
这样既保住了 `create` 的 `0`，又实现了 `update` 乱序时的版本接手。

## 二、精妙的推演逻辑确认

提案里的时间线推演（§四）非常完美，我复核了一遍：

**分支 A（U2 先到，U1 后到）**：
- U2 带着 `base=1` 到达，主机 upsert 写入 `v=2`（因为 `1+1=2`）。
- U1 带着 `base=0` 到达，比对 `2 != 0`，**触发 conflict**，主机返回 `server_state`（也就是 U2 写入的新值 11.5）。
- 客户端收到 conflict，用 11.5 覆盖本地，并**清理掉队列里的 U1**。
- **结果：收敛到新值（U2），旧值（U1）被完美拦截。**

**分支 B（U1 先到，U2 后到）**：
- U1 带着 `base=0` 到达，主机 upsert 写入 `v=1`（因为 `0+1=1`）。
- U2 带着 `base=1` 到达，比对 `1 == 1`，**匹配成功**，更新为 `v=2`。
- **结果：收敛到新值（U2），一切正常。**

## 三、其他细节确认

1. **关于 `base_version` 异常大（比如 999999）**：
   你说“属客户端 bug，不额外兜底，可留一句日志”，完全同意。主机端不应该为了防御客户端的错乱而加一堆业务分支，直接返回 conflict 让客户端用 `server_state` 洗一遍即可。这符合我们一直以来的「坚决不改底层逻辑，用事实洗地」的风格。

2. **关于「已知残余（不修）」**：
   提案说：*“旧编辑被新编辑覆盖”的场景里，提示语「已在别处被修改」字面不准，但处置是对的，不修*。
   **非常赞同。** 如果改文案，可能会让真正的「多端并发冲突」提示变弱，反而得不偿失。用户只要看到「本地已按主机对齐」这个实际结果就行了，纠结提示语字眼不如保持现状。

3. **测试设计（先红后改）**：
   4 条测试用例完全覆盖了分支 A、分支 B、参数化终态相同，以及 create 回归。非常好。

4. **文档同步**：
