以下是针对这些问题的审查意见与决策建议：

---

### 一、两个 P1 级致命伤（必须立刻修）

#### 1. F1：草稿只活一次导航（逻辑自噬）
- **死因**：`dispose()` 里判定表单为空就去删草稿。但用户切走时，草稿可能还在 `_restoreRaw` 里没点“恢复”，当前 UI 当然是空的，于是把还没恢复的草稿给“合法”杀掉了。
- **解法**：完全同意 `_restoreRaw != null` 时一律不删。**宁可多留一份脏数据，绝不吞掉用户半滴心血。**

#### 2. F14：换主机后同步永久死锁（经典的“以为用户不会这么干”）
- **死因**：判定换主机的条件依赖 `pairing.json` 存在。但用户点“忘记主机”时这个文件就被删了，导致判定 `previous == null`，跳过了重建镜像。结果旧主机的商品还在镜像里，新主机一推同编码的商品，直接 UNIQUE 撞死。
- **解法（按你的裁定：自动归档）**：这个策略极度优秀。个体户经常换电脑、换店面，这个坑迟早要踩。
  - 镜像库必须自带 `hostId`（比如建一张 `mirror_meta` 表）。
  - 换主机时，把旧镜像和未推送队列移到 `archive/旧主机ID-时间/`，然后再清空、全量拉取。
  - **测试红线**：一定要补一条“`pairing.json` 不存在但镜像非空”的测试，把这个坑彻底钉死。

### 二、决策点裁定建议

#### 针对修复方案
- **D1（F3：退款提醒）**：**选甲**。商品全退了，但钱没退，状态写「已结清」是自欺欺人。必须显示「还欠客户退款 ¥X」。
- **D2（F10：导出漏单）**：**选甲**。会计拿 CSV 去对账，少 5 张自动收付款单会直接导致对账爆炸。导出必须是“当前条件下的全量”，不管界面有没有隐藏派生单。
- **D3（F4：详情页跳转成环）**：**选乙**。关联单据（退货单/收款单）是“证据”，不能删也不能展平（太长），加个面包屑/「返回原单」按钮是最平衡的解法。
- **D4（F12：SnackBar 久不消退）**：**选甲**。统一抽个 `showNotice()` 方法，**每次弹之前先清空队列**。默认 3 秒，长文案 6 秒。中老年用户看提示，只要字够大、停留够久就行，不能让他们排队等。

#### 针对商品名称自动补全
- **D1′（覆盖确认）**：**选乙（前缀豁免）**。用户输入“大”想选“大米”，如果每次都弹“要覆盖吗”会把人烦死。只有当输入框里的词**完全不是候选词的前缀**（比如本来是“可口可乐”，非要换成“大米”）才弹窗。
- **D2′（手机端手打）**：**选甲（只做桌面）**。手机端目前是“点此选商品”的单元格，如果要改成手打+补全，还得把 `QueueSink` 改造支持无缝建档，风险太大。先给手机选择器加个搜索框，足以解决痛点。

### 三、隐藏的“神仙发现”与破防点

#### 1. `LocalIp.choose` 选错网卡（极其致命的真实缺陷）
- 测试环境装了 `natpierce`（内网穿透工具），软件误把这个虚拟网卡当成了局域网 IP，导致手机扫码后一直超时。
- **分析**：神算子的目标用户是“个体户”，很多老板店里装了监控、收银机、或者梯子/穿透工具，机器上可能有三四个虚拟网卡！
- **修正**：**手机端必须加“手动输入 IP 地址”的兜底入口**。二维码扫不到，允许用户手动输 `192.168.x.x`。同时，主机端的 IP 选择器要展示所有网卡并加上备注（如：WLAN、以太网、虚拟网卡）。

#### 2. F17：离线单不影响手机库存显示
- 手机断网开单后，库存页显示的还是权威镜像的数字，没有显示未同步的 `±quantity`。
- **分析**：这部分功能在 `stock_page.dart` 里其实是有的（渲染 `unsynced`），但没生效。可能是 `stockDelta` 为 null，也可能是 payload 解析失败。这里必须用 Debug 包去手机上把队列数据 dump 出来看。不要猜，必须实证。

#### 3. 补全方案里的输入法防抖（IME Composing）
- 在 `onChanged` 里重建候选列表时，一定要判断 `if (value.composing.isValid) return;`。中国用户打字，“kele”还没选词成“可乐”时，千万不能触发全表搜索，否则会把输入法搞崩溃。

# 关于自动归档的补充

在实际业务场景中，IP 冲突简直是家常便饭：比如老王家和老李家用的都是默认的 `192.168.1.1` 网段，或者老板在店里和家里各放了一台电脑，路由器分配的局域网 IP 恰好都是 `192.168.1.100`。如果系统只认 IP，那扫码换主机时就会发生严重的**“串账”**（把 A 店的旧数据推到 B 店，或者因为 IP 没变而拒绝归档重置）。

### 为什么必须用 7 位 UUID（`host_id`）？

1. **UUID 是唯一身份标识**：电脑的 IP 可以随 DHCP 租约变化，但生成数据库时绑定的 `host_id` 是这台设备的“出生证明”。
2. **天然的安全边界**：如果不校验 `host_id`，只要有设备在局域网内伪装成该 IP，手机就会毫无防备地继续推送队列，这存在严重的数据污染风险。

---

### 具体的落地逻辑（防呆设计）

结合你提出的校验 `host_id`，我们梳理一下手机端扫码后的完整判定流程：

**情况 A：同一个老东家，重扫码（IP 变了，但 `host_id` 没变）**
- *场景*：老板换了路由器，电脑 IP 从 `192.168.1.100` 变成了 `192.168.1.101`，老板重新扫码。
- *判定*：扫到的 `host_id` == 镜像库里的 `host_id`。
- *行为*：**只更新 `pairing.json` 中的 IP 和端口**，**绝对不归档、不重建镜像**，本地未同步的队列正常推给新 IP。

**情况 B：换了一家店/换了电脑（IP 没变甚至一样，但 `host_id` 变了）**
- *场景*：老王在 A 店的电脑 IP 是 `192.168.1.100`。他去 B 店，B 店的电脑 IP 也是 `192.168.1.100`，他拿手机扫码。
- *判定*：扫到的 `host_id` != 镜像库里的 `host_id`。
- *行为*：**触发归档**。把旧镜像和队列打包移动到 `archive/<旧 host_id>/`，清空当前镜像，用 B 店的新 `host_id` 重建镜像并全量拉取。

**情况 C：全新手机首次扫码（手里啥都没有）**
- *场景*：刚下载 App 的新手机扫码。
- *判定*：镜像库里没有历史 `host_id`。
- *行为*：直接建库建表并写入该 `host_id`，全量拉取，没有“归档”这一步。

---

### 给你的防呆测试建议（非常重要）

在落地这条逻辑时，一定要补上这两个极端的测试用例：
1. **同 IP、异 UUID**：模拟手机扫了一个与之前 IP 完全相同的二维码，但传过来的 `host_id` 是新的。必须触发归档，证明系统不依赖 IP 判断身份。
2. **同 UUID、异 IP**：模拟老东家换了网，手机扫码后，`host_id` 相同。必须**不触发归档**，且本地积压的 `pending` 订单能正常补传，证明系统对 IP 变化是平滑容忍的。

### 一句话总结

**先修 P1（草稿状态和换主机死锁），再统一下 SnackBar，然后把补全组件接上桌面三页，别忘了给手机加个“手动输入 IP”的兜底，最后把判定依据从“网络层（IP）”拔高到“应用层（host_id 身份）”，就这么干！**
