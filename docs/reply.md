# 对数据抢救功能的部分审查

## 1. 高优先级：损坏数据库抢救时，只复制了 `.db`，没有处理 `-wal`
相关代码位于`rescue.dart`：抢救入口与复制逻辑

核心操作是：
```dart
source.copySync(copy);
```

它复制的是 `shensuanzi.db` 主文件。可是，项目的数据库明确工作在 `SQLite WAL` 模式中，数据库的当前状态可能由主文件和 `shensuanzi.db-wal` 共同构成。

SQLite 官方文档也明确说明，WAL 模式下，已提交的事务可以先保存在 WAL 中，之后才被 checkpoint 写回主数据库文件。

这意味着什么？

如果损坏时仍有有效的已提交事务留在 WAL 中，而抢救流程只读取主文件，就有可能漏掉这些本来还能够找回的数据。

这不是说每次抢救都会丢数据，而是当前代码没有充分处理这种失效情形。

值得注意的是，你的 P0 恢复模块已经正确意识到 .db、-wal、-shm 需要一起管理，避免旧 WAL 覆盖新恢复的数据库。说明你已经理解这个问题，只是这条规则还没有完整贯彻到 P1 损坏抢救流程。

我建议：
- 先明确损坏文件存在 WAL 时，抢救流程到底采用什么策略。
- 在临时工作目录中保留必要的 WAL 证据，并针对主文件与 WAL 的不同损坏组合设计处理方式。
- 增加回归测试：构造一个有尚未 checkpoint 的已提交事务的数据库，再模拟主文件损坏，检查可找回的数据是否包含该事务。
- 只有验证通过之后，才把这条恢复路径视为可靠。
不要简单地把 WAL 文件复制到旁边就结束。主文件已经损坏时，WAL 是否能够应用、应用后哪些页仍然有效，也需要验证。

## 2. 高优先级：抢救模块判断一张单据是否完整的标准，仍然偏粗
相关代码位于`rescue.dart`：完整性判断

当前逻辑大体上是：
```dart
final bool expectsLedger =
    myStock.isNotEmpty ||
    myMoney.isNotEmpty ||
    myParty.isNotEmpty;
```

随后，只有完全没有任何库存、资金、往来流水的单据，才会触发相应的缺失流水问题。

这个规则能抓住“该单据的所有流水都没读回来”的情形，但**不能保证**所有必要流水都找回来了。

举个更具体的例子：一张有多个商品明细的销售单，假设对应的部分库存流水因为坏页没有读出来，但至少还有一条库存流水成功恢复。那么 `myStock.isNotEmpty` 仍然为真，程序可能认为这张单已经通过了流水存在性检查。

同样的问题也可能出现在资金或往来流水上。

这正好与抢救功能自身的设计目标冲突：*你希望不完整的单据不要被当作完整记录导入，以免库存和账目出现无法解释的差额。*

我建议把完整性判定进一步细化为按业务类型验证预期数据，而不是只验证是否存在任意一条流水。例如，销售、采购、送货、退货和收付款单应该分别判断必要的流水关系；如果无法判定一笔业务是否完整，应进入待确认，而不是轻易标记为完整。

还要照顾盘点的特殊情况：盘点没有库存差额时，确实可以不产生库存流水，所以不能简单要求每张盘点单都必须有流水。判断必须遵循真正的业务规则。

测试也要针对部分缺失，而不只是删除一张单的全部流水。否则，最危险的情况仍可能漏过去。

## 3. 高优先级：正常备份从同步复制改成后台复制后，要验证并发写入安全
相关代码：

 `backup.dart`：checkpoint、后台复制和校验
 `app.dart`：备份运行流程

你已经把文件复制放进 `Isolate.run()`，这是正确的性能方向。这样用户不必因为复制几百 MB 的文件而整段时间无法操作界面。

但这也改变了并发行为：
1. 备份先执行 `wal_checkpoint(TRUNCATE)`。
2. 随后把 .db 主文件的复制放到另一个 `isolate`。
3. 应用本身继续运行，其他业务操作仍有机会写入数据库。
而 SQLite WAL 的自动 checkpoint 默认会在 WAL 达到一定阈值后触发。此时，如果复制正在读取主文件，新的 checkpoint 可能同时修改这个文件。SQLite 官方对 WAL 和 checkpoint 的描述见 WAL 文档。

所以，在后台复制期间，不能仅凭之前执行过一次 checkpoint，就认为正在复制的主文件一定是一个稳定快照。

现有 `quick_check` 可以发现部分结构损坏，但它并不能保证每一笔应当被包含的业务数据都在备份里。一个结构完整、但遗漏了部分并发写入的数据库，也可能通过完整性检查。

这是一项需要优先用测试定案的风险，不等于我已经证明现有备份出现过损坏。

我建议新增一项专门测试：在备份过程中持续提交业务写入，同时验证备份的完整性和业务一致性。还要明确备份代表哪个时间点的数据。

如果测试暴露出不安全的并发窗口，就需要考虑 SQLite 一致性快照机制，或者暂时阻止业务写入。不能只依赖 `quick_check` 通过就判定备份可靠。
4. 次高优先级：数据抢救会阻塞 UI，进度显示可能无法实时更新
相关代码：

 `rescue.dart`：同步复制与文件处理
 `rescue_dialog.dart`：执行中的界面

抢救入口声明为 `async`，但关键路径里使用 `copySync`、`readAsBytesSync`、`writeAsBytesSync`，并同步执行大量 SQLite 查询；执行中的对话框则通过回调更新进度。

问题在于：`async` 本身并不会把同步工作自动移到后台。当这条路径在 UI `isolate` 上执行时，长时间同步处理会占住事件循环，页面无法正常绘制。

这意味着大文件抢救时，用户可能看到进度停滞甚至窗口暂时未响应。特别是文件头修复路径会把整个数据库文件读进内存，478 MB 的数据库就需要大约相同量级的额外文件内容内存空间，还不包括 SQLite 和 Flutter 运行时的其他开销。

这属于低频但重要的灾难恢复路径。考虑到用户此时本来就已经遇到问题，我不希望软件又让他分不清“正在抢救”与“程序卡死”。

可以考虑把文件复制、SQLite 读取与新库写入放到独立 isolate 中，通过消息传递进度；但这属于单独的 UI 与执行模型改造，应该配套测试，不要和前面两项数据安全修复混在一次提交里。
