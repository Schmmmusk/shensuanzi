① 迁移前备份：甲是正确选择
这里最重要的不是生成一份漂亮、整洁的数据库，而是尽可能保留迁移前的原始数据状态。

`VACUUM INTO` 的前提是 SQLite 能够读取源库。迁移前备份恰恰需要应对源库可能存在损坏的情况。

所以我支持：
- 检查 checkpoint 的完整性；
- 先复制到临时文件；
- 比对源文件和副本大小；
- 成功后再原子重命名；
- 不增加启动阶段的 `quick_check`。
这里有个小细节需要施工时注意：`busy == 0` 并不意味着 checkpoint 一定完整，必须同时核对 log 和 checkpointed。你们方案已经考虑到了这一点。

还有一个前提：必须保证复制期间没有新的写入者。 提案所描述的迁移阶段满足这个条件，但应当通过调用顺序和测试把它固定下来，而不是只依赖注释。
② 镜像归档：乙是正确选择
镜像归档的目标是保存一个可读取、可恢复的逻辑快照，不需要字节级保真。

因此 `VACUUM INTO` 比 checkpoint 后直接拷贝更合适。

我特别赞成失败后返回 `null`、不阻断换主机。因为这份归档是辅助保护，不应该让它的失败把主机切换流程也拖死。

不过，上一轮提到的两个问题仍然要写进施工要求：
1. manifest 缺失或不合法的归档目录不能被当成正常归档展示；
2. 未完成归档目录需要清理，不能留下一个看起来有效的空壳。
③ 手机导出：我支持失败阻断分享
建议明确裁定为“要”
这项行为变更，我认为值得做。

手机导出的核心价值不是“尽量给用户一个文件”，而是把手机上尚未同步的业务数据带走。

如果快照失败还继续分享，就可能让用户误以为数据已经安全转移。

我支持以下行为：
用户点击导出
    ↓
生成数据库快照
    ↓
从快照读取 sync_queue
    ↓
生成未同步单据清单
    ↓
所有文件准备完成？
    ├─ 是：打开分享面板
    └─ 否：提示失败，不分享


特别强调：文字清单必须从最终快照读取，而不是从正在运行的同步服务读取。 这样才能保证清单和数据库中的队列状态一致。

失败提示也不要只说“导出失败”，建议明确告诉用户：
数据整理失败，尚未生成完整导出文件。请重启软件后重试，原有数据不会因此被删除。

当然，最后一句需要以实际失败处理确实不破坏源库为前提。
④ 抽取共用原语：赞成，但不要为了统一而强行统一实现
`Db.snapshotTo()` 和 `Db.copyAsIs()` 的语义区分非常有价值。
原语	应当保证的事情
`snapshotTo`	生成一致、可读取的逻辑快照
`copyAsIs`	尽可能原样保留源数据库字节

我建议这两个方法的命名和文档都保留这种明确区别。

但有一点：`BackupService` 已经在独立 isolate 里工作，不必为了复用 `snapshotTo()` 而强行把它改成依赖主 isolate 的 Db 对象。

共用的是语义和可靠性约束，不一定非要共用同一个底层调用入口。

另外，`snapshotTo` 的实现最好明确支持：
- 目标临时文件；
- 只读校验；
- 成功后原子替换；
- 失败清理；
- 目标路径不能覆盖源库；
- Windows 下目标文件已存在时的替换行为。
这几个要求比抽象本身更重要。

决策 2：超卖置顶
赞成，但必须修正候选范围
我支持把超卖独立放在最前面。

但是，我发现提案目前存在一个逻辑冲突：
- `shortageCandidates()` 只筛选 `safety_stock > 0`；
- 超卖定义为在店可售小于 0；
- 安全库存为 0 的商品不会进入候选集合。
这意味着：

某商品即使已经超卖，只要没有设置安全库存，它就可能完全不出现在超卖段。

这不符合“超卖比普通缺货更严重”的产品定义。

我的建议是把两个判定拆开：

$超卖 = 在店可售 < 0$


$需要补货 = safetyStock > 0
\land 在店可售 \le safetyStock
\land 在店可售 \ge 0$

这样即使商品没有设置安全库存，只要发生超卖，也能被发现。

建议补两条测试：
1. 安全库存为 0、在店可售为 −3，必须进入超卖段；
2. 安全库存为 0、在店可售为 3，不进入任何缺货段。
这一项我建议先修订提案，再裁定放行。

四、Android 概览页增加 `stockDelta`

五、`effectiveInStoreOf` 下沉 `core`
*赞成*
这是一个很好的分层调整。

当前函数：
```dart
int effectiveInStoreOf({
  required int book,
  required int unsynced,
  required int inTransit,
}) => book + unsynced - inTransit;
```


本质上是业务领域规则，而不是 UI 规则。

把它放进 core 的 `util/in_store.dart`，可以让：
- 库存页；
- 概览页；
- 缺货榜计算；
- 未来可能出现的库存预警；
都使用同一套公式。

但请注意：下沉之后，原来的 UI 函数必须彻底移除，不能出现 core 一份、UI 又保留一份的情况。

测试也应该从“验证某个页面算对了”升级为“验证所有调用者都使用 core 的唯一公式”。
