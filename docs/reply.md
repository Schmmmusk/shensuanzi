# 一、退款模块：这次可以给高分了
两项 P0 修复通过源码审查
## 1. 采购退货方向终于处理正确
上次的问题是，延迟退款检查写成：
if (moneyOut && isReturnType(target.docType))


采购退货通过 receipt 完成结算，moneyOut == false，因此整个类型被漏掉。

现在改成了按目标是否为退货单判断，不再依赖资金流向。具体方向仍然由已有的 settleDirections 检查。

同时，提示文案也按业务方向区分：
- 销售退货：只收到过多少钱、已经退了多少、最多还能退多少。
- 采购退货：只付出去过多少钱、已经收回多少、最多还能收回多少。
这是正确的职责划分。资金方向由核销规则负责，累计额度由统一的退款规则负责。
## 2. 同一笔收付款单的多个退货目标，现在按原单聚合
这次新增的 `_requireReturnSettlementWithinCap()` 是本轮的关键。

它先遍历 incoming，再按照退货单的 ref_doc_id 聚合：

$\text{历史累计退回}
+
\text{本次同原单全部核销}
\leq
\text{原单实际结算额}
$

而且它正确区分不同原单，不会把两张无关销售单的退款额度混在一起。

新增测试覆盖了：
| 测试场景 | 预期
| 采购退货通过收款单延迟退款，累计超额 | 拒绝
| 一张付款单核销同一原单的两张退货单，合计超额 | 拒绝
| 一张付款单核销不同原单的退货单，各自额度足够 | 通过

我还核对了检查位置：它在 `_settle()` 的目标检查循环之后、写入收付款单和流水之前执行，仍然处于 `dispatch()` 的数据库事务中。

因此，之前发现的两条绕过路径，这次都堵住了。

相关实现：RuleEngine；退款上限测试。

这一部分我认可。

有个小小的测试增强建议：目前多目标聚合的拒绝测试主要覆盖销售退货的付款方向。可以再加一条采购退货的同原单多目标聚合测试，用 receipt 方向验证同一逻辑。代码看起来是通用的，但资金方向相反，值得留一条回归钉。

这是我最想表扬的部分。
## 1. 混合业务夹具，终于覆盖了方向相反的真实业务
新增的 `makeMixedLedger()` 不是手工拼几张看起来合理的表，而是通过实际业务服务生成：
混合账本的组成：

| --- | --- |
| 采购 + 当场全款付款 | 覆盖 |
| 销售 + 部分收款 | 覆盖 |
| 销售退货 + 延迟退款 | 覆盖 |
| 采购退货 + 延迟收款 | 覆盖 |
8 张
正常账本全部导入，0 条待确认。
这比只测销售和自动收款强不少。
特别是采购退货：资金方向、往来方向都与销售退货相反。如果测试夹具只关注销售，很多错误假设确实可能一直绿灯。
这次你们终于有了一本可以用来检验多种业务关系的混合账本。
## 2. 盘点边界的处理，我赞成
我仔细看了 `_stockProblem()` 的新实现和新增测试。

目前采取的策略是：
- 零差额盘点没有库存流水，允许通过。
- 有差额盘点且流水完整，允许通过。
- 库存流水条数多于盘点明细，判为不完整。
- 不假装能够识别“本来应该有、但已经丢失”的盘点流水。
这个判断是有道理的。

因为盘点明细中的 `quantity` 存的是实际数量，而不是差额；差额只在库存流水里。如果库存流水本身已经损坏，就不能再从它反推出原本应该存在的差额，然后用这个推算结果验证它自己。

这次没有为了让检查显得更严格而强行增加误报规则，我认为是成熟的取舍。

将来若需要可靠地判断盘点流水是否丢失，应当在业务数据中增加独立的盘点时账面数量快照，而不是让抢救器猜。

相关实现：`rescue.dart`；盘点测试。

# 三、我又发现一个 P0：部分明细与对应库存流水一起丢失，可能被放行
**建议修复后再验收**
这次请重点看这里。

当前 `_stockProblem()` 已经检查了：
- 按商品统计明细与库存流水行数；
- 按商品统计数量绝对值合计；
- 是否存在流水里有、明细里没有的商品。
这些都很好。

但它没有检查：

$\sum(\text{document\_lines.amount})=\text{documents.total\_amount}$


而且这不是一个可有可无的额外规则。

我专门查了 `DocumentLine` 模型和 `RuleEngine._requireLinesTotalMatches()`：
- `DocumentLine.amount` 是金额真相，已经包含让价。
- `unit_price` 是派生展示值，不能重新计算金额。
- `linesAmountMatchesTotal()` 明确规定：除 `stocktake`、`receipt`、`payment` 外，明细金额合计必须等于单据总额。
- 规则引擎在创建正常业务单据时，确实强制执行这条不变量。
因此，数据抢救器也应该复用它。
一个可以直接复现的场景
假设销售单是两行商品：
项目	金额	数量
可乐第一行	¥10	1
可乐第二行	¥10	1
单据总额	¥20	2

原本对应两条库存流水。

现在数据库损坏，导致第一行明细和对应的第一条库存流水都没有被抢救出来。

剩余数据是：
检查项	剩余状态
明细行数	1
库存流水行数	1
明细数量合计	1
库存流水数量合计	1
往来流水金额	¥20
单据总额	¥20

目前的检查全部可能通过：
- 行数相等。
- 数量相等。
- 往来流水金额与单据金额相等。
- 资金核销也没有差异。
最终，抢救器可能把这张单标记为完整并导入。

但新数据库中，单据显示 ¥20，实际明细只有 ¥10。

这正是数据抢救功能最应该防止的情况：每张表单独看都像是合理的，组合起来却不是原来的业务。
怎么修？
建议增加一个与 `RuleEngine._requireLinesTotalMatches()` 一致的检查：
`sum(line.amount) == document.total_amount`

但要明确三个例外：
- `stocktake`
- `receipt`
- `payment`
不要把 `unit_price` × `quantity` 用作验收公式，因为 `amount` 才是真正的金额来源。

建议补一条专门的破坏测试：
1. 用真实 `SaleService` 生成两行销售明细。
2. 删除其中一行明细。
3. 删除与它对应的一条库存流水。
4. 运行抢救。
5. 断言整张单进入待确认，不得导入。
这条测试可以直接检验刚才的漏洞。

另外，55 号文档目前存在一个内部矛盾：金额检查边界表明确说“明细 `amount` 与单据 `total_amount` 可以比较”，但实现要点第 3 条又写着“不用金额比对”。我认为后者应修正为：
不比较明细售价与库存成本；但必须检查明细金额合计与单据总额。

这样文档、数据模型和代码才是一致的。

# 四、另一个 P1：未知单据类型目前可能被当成完整数据导入
这个问题更隐蔽。

当前组装代码：
```dart
final DocType? type = DocType.fromWireOrNull(wire);

final bool expectsLines =
    type != null &&
    type != DocType.receipt &&
    type != DocType.payment;
```

当数据库里出现一个当前程序不认识的 `doc_type` 时，`type == null`，于是：
- `expectsLines` 为 `false`；
- 不检查它是否需要明细和库存流水；
- 后面的收付款单核销检查又有 `type != null` 条件，因此也不执行；
- 如果它没有往来方，且 `paid_amount`、核销额都为零，其他检查可能全部通过。
最终它可能被放进 `asm.importable`。

这直接违反了 55 号施工清单里自己写下的要求：
类型不认识 ⇒ 默认不完整。

这条规则我支持。抢救器不知道某个新单据类型的业务语义，就不应该擅自把它当成已经恢复完整的业务记录。

修复很简单：在按类型判定的最前面，将 `type == null` 明确标为未知类型，不加入 `importable`。

测试也简单：插入一张 `doc_type = 'future_type'` 的单据，确保它进入待确认列表。

未来 Schema 新增单据类型时，再由对应版本的软件识别和恢复。

# 五、再补一个 P1：流水自身的外键引用还没有逐行验证
这是我沿着 `_firstMissingRef()` 继续看时发现的。

目前该函数检查的是：
- 明细引用的商品是否存在；
- 单据的 party_id 是否存在；
- 单据的 account_id 是否存在。
但它没有检查每条流水自己的引用字段。

例如：
- `money_ledger.account_id`；
- `party_ledger.party_id`。
在当前业务规则中，资金流水应当对应其收付款单的账户，往来流水应当对应其业务单据的往来方。

如果损坏把某条 `party_ledger.party_id` 改成另一个仍然存在的往来方：
- `_partyProblem()` 只看金额合计；
- `_firstMissingRef()` 只看单据自身的 `party_id`；
- 金额仍然相等；
- 因此可能被判完整。
结果就是，一笔欠款被恢复到了错误的客户名下。

如果流水引用的是一个不存在的账户，情况更糟：目标数据库启用了外键约束，写入新库时可能直接触发外键错误，导致整次抢救失败，而不是把这张单放进待确认列表。

我建议把以下关系补进业务完整性检查：
数据	应检查的关系
`party_ledger.party_id`	必须存在，并与所属单据的 `party_id` 一致
`money_ledger.account_id`	必须存在，并与所属收付款单的 `account_id` 一致

这两条都是规则引擎写入时可以保证的业务不变量，值得在抢救时复核。
