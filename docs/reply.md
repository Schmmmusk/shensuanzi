## 审查意见

先说结论：

- **行为目标成立，选甲。**
- **提案的核心观察（甲/乙/`!priceTouched` 三者等价）精准——它揭示了 bug 的真正根因：`priceTouched` 被当 `pricePrefilled` 用。**
- **断言要加两条——提案自己问的「要不要加数量不变」不但要加，还要再加一条「取消选择器不动价」。**
- **修复后要写清「为什么可以无条件」——否则后来人会加回守卫。**

## 一、行为目标确认

> 每次在行内选中商品（含重选同一商品）⇒ 单价框重新预填为新商品的目录价，旧值被覆盖。

**同意。** 三个理由：

1. **切换商品必须覆盖**——旧商品的价格对新商品无意义。
2. **重选同一商品也要覆盖**——它是「确认选这个商品」，应当回到该商品的初始态；如果保留手改值，行为就变成「有时覆盖有时不覆盖」，比一律覆盖更难理解。
3. **一致的行为 > 试图保住手改值**——中老年用户无法理解「为什么刚才选同款还保留，这次选同款却覆盖了」。

**唯一的代价**（手改价 → 误点同一商品 → 手改丢失）**建议接受，不加提示**。加提示会让行为又变成两套；SnackBar 也救不回手改值。

---

## 二、核心观察的评价

> **甲 / 乙 / `!priceTouched` 守卫三者行为完全等价** —— 因为 `attachProduct()` 已复位 `priceTouched = false`。

**这个观察是整个提案最有价值的部分。** 它说明了三件事：

1. **`_pickProduct` 的守卫本不该存在**——`attachProduct` 复位 `priceTouched`，意图就是「让价格可以重新跟随」；守卫把它锁死了。
2. **`pricePrefilled` 是冗余标记**——grep 只有这一处读一处写，事实上和「`priceTouched == false`」表达同一件事。
3. **`priceTouched` 的语义被误用**——它是「用户手改过」，却被当成「是否预填过」的守卫。

**选甲**——不是因为它行为不同（三者等价），而是因为**消除「同一件事两个标记」**是 bug 的真正温床。未来语义扩展（如「记住手改值」）时，一处改 vs 两处同步——成本差异巨大。

## 三、断言方案

提案给了 4 条，**我建议 6 条**：

| # | 断言 | 备注 |
|---|---|---|
| 1 | 选 A ⇒ `10.00` | 基础 |
| 2 | 改选 B ⇒ `25.00` | **修复前必红**（反向验证核心） |
| 3 | 再选回 A ⇒ `10.00` | 覆盖「重选」边角 |
| 4 | 手改价 → 再选 B ⇒ `25.00` | 锁定「手改不阻挡覆盖」 |
| **5** | **换商品后数量不变** | **新增**——锁定「不碰数量」的边界 |
| **6** | **打开选择器但取消 ⇒ 单价不变** | **新增**——`picked == null` 时不覆盖，是对称边界 |

**第 5 条提案自己问要不要加——要加。** 理由：修复时最容易「顺手把数量也清了」；这是「不改」的显式声明，与「改」同等重要。

**第 6 条你没提，但它是「何时不该覆盖」的对称断言。** 看代码：

```dart
final Product? picked = await _showProductPicker(context);
if (picked == null || rowIndex >= _rows.length) return;  // ← 取消时直接返回
```

这条 `return` 不被改动——但要有断言挡住它。

## 六、注释要写清「为什么可以无条件」

修复后代码：

```dart
row.attachProduct(picked);
row.unitPrice.text = Money.format(picked.costPrice);
```

**看起来像是「忘了守卫」**——后来人很可能加回守卫。**必须写注释说明为什么可以无条件**：

```dart
row.attachProduct(picked);  // 复位 priceTouched = false（新商品的初始态）
// ⚠️ 无条件预填：换商品（含重选同一商品）时，旧价对新商品无意义，
// 必须覆盖。与「切单位」（§BG 方案 A）判据不同 —— 那里是「未被手改才跟随」，
// 因为切单位是同一商品的价格换算；这里是不同商品的价格重置。
// 详见 §CV·二五 裁定。
row.unitPrice.text = Money.format(picked.costPrice);
```

**「两个场景逻辑不同」这一点必须在注释里说清**——否则将来有人看到 §BG 的「未被手改才跟随」会以为这里是同一个场景。

## 七、与 §BG 的兼容性

§BG 方案 A 说的是「切单位时价格是否跟随」——逻辑是「未被手改才跟随」。

本次修复是「切商品时价格是否跟随」——逻辑是「总跟随」。

**两者不矛盾，因为场景不同**：

| 场景 | 变更对象 | 旧价的意义 | 判据 |
|---|---|---|---|
| 切单位 | 同一商品 | 用户手改的价仍是他的意愿 | 手改过 ⇒ 不跟随 |
| 切商品 | 不同商品 | 旧价对新商品无意义 | 总覆盖 |

**但这一点要在 `docs/ui_principles.md` 或对应 UI 契约文档里补一句**——把「两个场景判据不同」写成显式规则。否则：

- 将来做「切单位 + 切商品」组合场景时，会有人**用同一个判据统一**，又出 bug
- 当前已经在 `priceTouched` 的既有语义上做过一次「误用」——别再留第二次
