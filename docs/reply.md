- 收付款单或盘点单出现不应该有的流水。

盘点库存流水则单独允许 `either`，没有被误伤。

# 二、最后两个值得收尾的边界

现在进入挑细节的阶段了。这两项不是要推翻当前实现，而是补齐它的安全边界。

## 1. P1：流水引用字段为 NULL 时，当前检查可能跳过

位置：[`_ledgerRefProblem()`](packages/shensuanzi_app/lib/src/rescue.dart)

目前代码中有这样的判断：

```dart
if (pid is! String) continue;
```

以及：

```dart
if (aid is! String) continue;
```

它们的本意是跳过无法识别的字段值，但在抢救场景里，这可能放过损坏数据。

例如：

- 一条 `party_ledger` 的 `party_id` 被损坏成 NULL；
- 金额与单据仍然相符；
- 这条流水的引用检查被跳过；
- 最终尝试写入新库时，触发 `party_id NOT NULL` 约束。

`money_ledger.account_id` 也有同样的问题。

更特殊的是，盘点库存流水的 `product_id` 如果损坏成 NULL，当前 `_stockProblem()` 的盘点分支也会跳过非字符串 ID。

这些字段在 Schema 中都有非空要求。

建议将“无法识别的引用”当作不完整，而不是跳过。

至少覆盖：

- `party_ledger.party_id` 必须是有效的非空字符串；
- `money_ledger.account_id` 必须是有效的非空字符串；
- `stock_ledger.product_id` 必须是有效的非空字符串，包括盘点流水。

这样可以避免一条坏流水拖垮整个恢复事务。

## 2. P1：`transfer` 是已知类型，却是当前规则引擎不支持的类型

这个问题很容易被忽略。

[`DocType`](packages/shensuanzi_core/lib/src/models/document.dart) 中存在 `DocType.transfer`。

但 `RuleEngine.dispatch()` 明确规定：

> v1 不实现调拨，收到该类型一律拒绝。

而抢救器目前的未知类型判断是：

```dart
if (type == null) {
  // unknownType
}
```

`transfer` 可以正常解析成 `DocType.transfer`，因此不会进入 `unknownType`。

与此同时，三种 `ledgerDirectionOf()` 函数都使用 `_ => LedgerDirection.absent`。这意味着一个没有额外流水、明细金额又自洽的 `transfer` 单据，可能通过当前完整性判定。

结果就是：恢复后的数据库可能包含当前版本业务规则明确不支持的单据。

我的建议是：

为抢救器明确区分“类型未知”和“当前版本已知但不支持恢复的类型”。至少 `transfer` 应进入待确认，而不是直接导入。

顺带建议将符号表中的 `_ => absent` 改为显式列出 `DocType.transfer`。这样未来新增单据类型时，编译器能够提醒你们更新符号定义，而不是悄悄按 absent 处理。

这两项都不需要大改架构，属于最后一轮边界收口。
