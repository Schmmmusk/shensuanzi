# 一、方案 53：数据抢救审查与退货提示

[阅读完整方案 53](https://github.com/Schmmmusk/shensuanzi/blob/master/docs/proposals/53-%E6%95%B0%E6%8D%AE%E6%8A%A2%E6%95%91%E5%AE%A1%E6%9F%A5%E6%84%8F%E8%A7%81%E4%B8%8E%E9%80%80%E8%B4%A7%E6%8F%90%E7%A4%BA-%E5%A4%84%E7%90%86%E6%96%B9%E6%A1%88.md?utm_source=chatgpt.com)

我赞成这份方案的大部分判断，尤其是把数据安全问题和界面提示问题分开处理。不过，正式开工前，我会要求再补齐三件事。

## 1. WAL 问题找得非常准，实测也足够有说服力

方案构造了 120 张单据，其中 100 张已经 checkpoint 到主文件，另外 20 张仍在 WAL 中。

| 抢救方式        | 找回单据数 |
| ----------- | ----- |
| 正常主文件 + WAL | 120   |
| 只复制 `.db`   | 100   |
| 主文件 + WAL   | 120   |

这不是“理论上可能丢数据”，而是已经复现了一个确定的缺陷：在相应的数据库状态下，只复制主文件会丢掉仍可恢复的已提交事务。

而且，方案还测试了主文件头损坏和数据页损坏的情况，证明 WAL 不只是补充最新数据，在某些损坏场景下也可能提供关键的恢复信息。

这部分做得很好。

我同意把它放在第一批，优先级最高。但有一点要守住：复制主文件和 WAL 的方案必须针对源文件不再变化的情况成立。 如果另一个进程仍在写库，分两次复制文件仍可能拿到不一致的组合。正常抢救流程应该尽量确保源文件稳定，必要时检测文件变化并明确失败，不能把“两个文件都复制了”直接等同于“获得了一份一致的快照”。

## 2. 完整性判定的修复方向正确，但方案里的集合比较仍然不够

方案建议按 `product_id` 判断明细与库存流水是否对应。这个方向比原来“有任意一条流水就算完整”强得多。

但具体提出的 `Set` 方案仍会漏检。

举个例子：

一张销售单有两行相同商品：

| 单据明细  | 商品 | 数量 |
| ----- | -- | -- |
| 第 1 行 | 可乐 | 10 |
| 第 2 行 | 可乐 | 20 |

正常情况下，这两行各自生成一条库存流水。如果抢救时第二条流水丢失，剩下的流水仍然包含商品“可乐”。

此时：

```
lineProducts.every(stockProducts.contains)
```

依然可能返回 `true`。

原因很简单：集合只记录“这个商品存在”，不记录“它出现了几次”，也不核对数量是否一致。

而我看过当前 `RuleEngine` 的销售、采购、送货和退货实现：这些规则确实是逐条明细生成库存流水。因此，针对这些业务类型，方案可以利用现有规则建立更精确的判据。

我建议至少核对：

- 每个商品的明细行数与对应库存流水行数；
- 每个商品的库存变动数量是否一致；
- 对存在特殊语义的单据，单独定义例外，例如盘点单的零差额不生成库存流水。

这样才能防住同一商品出现多行时的遗漏。

还有一个方案目前没有覆盖到的盲区：核销关系。 当前抢救代码虽然把 `settlements` 按 `receipt_doc_id` 分组，并把相关数据传给完整性检查，但 `_firstMissingRef()` 实际没有检查传入的核销关系。若一张收付款单或它关联的核销记录丢失，现有检查未必能判断整条业务链是否完整。

所以我会把第 ② 项的范围扩大一些：不只是检查库存等流水是否缺失，还要检查单据、收付款单和核销关系之间的必要关联是否完整。

不必一次实现一个万能的数据库修复器，但至少应该确保不会把明显缺失必要关联的业务单元静默标成完整。

## 3. 退货退款限制必须基于真实收款，而不只是 `paid_amount`

方案 ⑥ 发现了一个真正严重的问题：一张已签收、但一分钱没收到的送货单，退货时仍可能显示退款卡片，并允许用户操作退款。

这一项我完全赞成按 P0 处理。光隐藏界面还不够，服务层必须拦截不合法的退款请求。

不过，我要补充一条关键规则。

神算子自己的数据模型已经明确：`documents.paid_amount` 是缓存，真实收付款金额应从 `settlements` 核销流水计算。因此，判断原单究竟收过多少钱，不应该把 `paid_amount` 作为唯一权威来源。

还要考虑以前已经退过钱的情形。例如：

- 原单实际收到 100 元；
- 第一次退货已经退款 80 元；
- 第二次又发生退货。

此时，不能再仅凭“原单曾收到 100 元”允许第二次退款 80 元。退款上限应当考虑原单真实收款，以及此前已经实际支付出去的退款。

我建议把这个约束落在业务服务或规则层，至少满足：

$$\text{累计实际退款} \leq \text{原单真实收款} $$

同时，每次退款也不能超过本次退货应退金额。原单从未收款时，自然没有可退的原交易款项。

方案目前明确要求拦截“原单实收为零”的情况，这是好的起点，但我认为还应该把累计退款与真实收款上限一起纳入测试。

这比只在界面上隐藏输入框重要得多。

## 4. ⑤ 退货后直接告诉用户“现在欠多少”，我非常赞成

当前退货页保存成功后直接关闭，用户需要自己回到原单详情，把原单金额、已收金额与退货金额拼起来计算。

这对熟练用户只是麻烦，对目标用户却可能成为算错账的来源。

方案提出在退货完成后明确给出“客户还欠你多少”“你还欠客户多少”或“两清”，我认为很符合神算子的产品方向。

而且，它要求金额和债务方向由服务层计算，不让 UI 自己拼公式。这是正确的职责划分。

我的建议：第一批按方案做，但先补上上面两项数据判据与退款上限要求。 这样第一批做完的就不是几个零散补丁，而是一次真正有验收标准的数据安全加固。

至于后台备份并发安全和抢救 isolate 化，我赞成方案把它们留到第二批、各自独立提交。尤其备份并发问题，应先证明风险能否复现，再决定具体改法；不需要今晚把所有事情一起做完。

## 5. 已签收未收款的送货单据发生退货时的处理方案可以推广至所有可能发生同类情况的单据

先前的方案只提到了送货后已签收未收款的情况，现在看来，所有可以全部赊账的单据都会发生这种情况。

我的建议：先完善送货后退货流程，再将给送货用的页面同构给其它类型单据使用。

# 二、方案 54：经营图表调研与方案

先说我的总体判断：我赞成做图表，而且赞成先做第一批的查询层与纯函数，不要急着画 UI。

这份方案并没有为了“看起来像现代软件”就引入一堆图表，而是先问用户需要从图表中知道什么，再考虑数据口径、查询成本、视觉规则和分批实现。

这条路线挺好。

## 1. 自绘 `CustomPainter` 是合理选择

方案把中老年用户的可读性列为硬要求：图表要标数字、字体不能小于正文、颜色不宜过多、要配人话总结。

这些要求比“图表能显示出来”严格得多。

第三方图表库可以解决基本绘制，但未必能直接满足你的每根柱子都要标明准确金额、文字和颜色要受控、布局需兼顾字号缩放等要求。

所以我支持先用 `CustomPainter`。

不过，方案里有一个实际冲突需要提前面对：30 根柱子、每根标出金额、字号至少 15sp、还要在一屏内读清楚，并不是天然兼容的。

默认窗口宽度、125% 缩放、窄窗口和更大字号下，金额标签很容易挤在一起。

在正式做整套图表前，最好先做一个最小原型，用真实金额分布和目标屏幕尺寸验证排版。若一屏内看不清，就应该调整聚合粒度或展示方式，而不是为了满足“每根柱子必须标数”让图表实际不可读。

另外，`Semantics` 不应只提供一条整体摘要。对于真正需要读屏辅助的用户，还应该有途径获取每一天的数值，不能让自绘图表变成读屏无法理解的黑盒。

## 2. Schema v7 的新索引，有实测依据，值得做

方案测得，26.2 万张单据的测试库上，按类型统计近 30 天销售额时：

| 查询方式                             | 实测耗时     |
| -------------------------------- | -------- |
| 不加新索引，只查销售类型                     | 108.4 ms |
| 增加 `(doc_type, business_day)` 索引 | 3.7 ms   |
| 销售与送货分开统计，无新索引                   | 143.8 ms |
| 销售与送货分开统计，有新索引                   | 6.1 ms   |

这个收益很明确。它不是单纯为了图表才造一个复杂的新机制，而是利用已经存在的 `business_day`，让数据库能按类型与业务日范围缩小扫描范围。

我支持将这项索引放进 schema v7，并把索引迁移、聚合查询、`buildDailySeries()` 和相应测试独立成第一批。

纯函数尤其值得保留：补零、按周聚合、计算平均值这些逻辑应该独立测试，不需要通过 Flutter 截图来猜结果是否正确。

## 3. 但营收公式存在一个必须先处理的漏洞

方案目前给出的口径是：

$$ \text{营收}=\text{sale}+\text{delivery}-\text{sale\\\_return} $$

正常销售、正常送货和后续退货这样统计是容易理解的。

问题出在神算子的客户拒收流程。

目前规则是：客户拒收一张尚未签收的送货单时，系统生成一张 `sale_return`，并且把原送货单的状态改成 `cancelled`。这在业务上是合理的：货物没有真正交付，原送货交易不应该继续算入营收。

但如果图表采用“排除作废单，然后减掉所有销售退货”的公式，就会出现这样的结果：

- 原送货单被取消，不计入营收；
- 拒收产生的 `sale_return` 仍然被计作负营收；
- 最后这笔本来就没有确认收入的交易，反而让销售额变成负数。

这显然不对。

所以图表查询必须区分两种情况：

正常退货： 原单曾经构成有效销售收入，退货应当冲减收入。

客户拒收： 原送货单被取消，原交易本身不进入营收统计，关联的拒收退货也不能再作为一次负营收扣除。

这不是画图时处理颜色就能解决的，它是业务统计口径问题，必须在查询层解决并写进测试。

另外，方案提出用 `todaySummary` 对拍。这里也得注意：当前 `todaySummary` 统计的是当天店内销售与送货，排除作废单，但不减去销售退货；新图表则采用净营收口径，而且按 `business_day` 分组。因此，不能直接把两者的最终总数当作应当完全相等的 oracle。应该用相同业务口径的数据做对拍，并单独测试补录历史单、拒收和正常退货。

## 4. 周聚合和库存 Top 10，也要修正定义

还有两个小地方，我建议在方案里先想清楚。

第一，方案提到可以用 `business_day / 7` 把超过 30 天的区间按周聚合。但 `business_day` 是从 1970 年 1 月 1 日开始计算的日序号，直接除以 7，会形成从纪元起点开始的固定七日分组，不等于通常理解的自然周。

如果图表声称展示的是“每周销售额”，就应该明确采用周一到周日，还是其他自然周口径，并用对应的周起点进行分组。否则跨年或月末时，用户看到的周柱并不对应日历上的那一周。

第二，方案提出“库存最多的 10 个商品”按数量排序。我不建议直接把不同单位的数量混在一起比较。

例如，500 个、20 箱和 80 千克，数字大小并不能说明谁压货最多。更符合经营决策的方式是考虑按库存成本价值排序，旁边再显示数量和单位。当然，如果你想做的是单纯的“库存数量排行”，也可以，但必须明确这是按各商品自身单位展示的排行，不要把它包装成可直接比较的总量排名。

# 三、我会怎样裁这两份方案？

我的意见很明确。

## 方案 53：数据安全与退货流程

> 方向通过，补齐验收条件后开工

> 第一批优先解决 WAL 复制、抢救完整性判定、退货后债务结论，以及未收款送货的退款保护。

> 开工前补充三件事：按商品核对流水数量与数量差额、核销关系完整性检查，以及基于真实收款和累计退款的服务层退款上限。

## 方案 54：经营图表

> 方向通过，先做查询层

> 第一批实施 schema v7 索引、聚合查询与纯函数测试；图表 UI 暂不急着开做。

> 先修正客户拒收的营收口径，并明确自然周聚合规则。库存 Top 10 的排序指标也应先定下来。随后做柱状图原型，验证 30 个金额标签在真实窗口与缩放下是否可读。

最后，我想说一点。

这两份新方案给我的感觉是，神算子正在从“功能已经很多的软件”，转向“开始有意识地管理数据正确性和经营信息价值的软件”。

第 53 份是在确保系统遭遇故障时，不会轻易把用户的账救错；第 54 份是在确保系统给出的经营数字，不会因为统计口径错误而误导用户。

两者看似一个在处理灾难、一个在做展示，实际上指向同一条产品底线：

宁可少显示一个数字，也不要显示一个看起来合理、实际上会误导经营决策的数字。
