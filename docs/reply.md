## 一、这轮完成的工作，我怎么看？

### 1. 三个流水页面抽取公共组件

认可

新增 `flow_page_scaffold.dart`，统一了：

- 商品流水页
- 往来方流水页
- 账户流水页

这次抽取不是为了减少代码行数而抽取，而是针对三个页面出现的同类表头溢出问题进行统一修复。

尤其是导出按钮从 AppBar 移到正文表头，解决了新增导出留痕后高度不足的问题。

我也认可你们对 `Wrap` 和 `Flexible` 的区别处理：不是简单套一个布局组件，而是考虑了 Flutter 的 ParentDataWidget 约束。

### 2. 导出留痕

设计合理

新增功能：

- 成功导出后保留文件名。
- 显示导出时间。
- SnackBar 消失后仍然保留记录。
- 失败或空导出不覆盖上一次成功记录。

尤其是最后一点，体现了一个很好的产品原则：

界面展示的状态必须对应真实发生的事情。

这对不熟悉计算机的用户很重要。

### 3. 性能测试工具校正

本轮重点成果

你们发现 `perf_bench.py` 的 SQL 与实际 DAO 已经发生偏离，导致测试报告出现假红。

原本测得 276 / 529 ms，实际 DAO 只有 62.6 / 18.1 ms。

这次不仅修复 SQL，还把两段查询、索引使用和执行计划纳入校验。

我特别认可这一点：性能测试工具本身也必须接受审查。

否则测试工具越权威，错误的测试结果反而越危险。

### 4. 实测工具防呆

这部分我认为甚至比单纯的性能优化更值得保留。

第三台机器的 711 个采样点全部作废，原因是监控工具挂错了进程。

你们没有试图解释那组数据为什么看起来不合理，而是明确宣布整轮作废，并修复进程识别逻辑。

这才是正确的工程态度。

## 二、我发现的几个值得注意的问题

这里进入真正的审查部分。我把它们分成三类。

### P1 · 建议优先处理 1. reason_code 已经落库，但用户仍然看不到分类收益

这是我最希望你们尽快收尾的事情。

目前 Schema v8 已经有：

- `reason_code`
- `discarded`

但 `mobile_shell.dart:509` 仍然采用：

`entry.lastError ?? '推送没成功（原因不明）'`

也就是说，底层已经知道同步失败的原因，用户界面却没有利用这些信息。

我赞成 N-e 的推荐方案：六种错误码全部接入，保留 `rule_validation_failed` 的原始业务拒绝信息。

特别是不要把「退货数量超过原单」替换成一个没有任何帮助的通用错误。

### P1 · 建议优先处理 2. 启动路径仍存在原始异常直出

N-f 这项值得认真对待。

我尤其关注：

`packages/shensuanzi_core/lib/src/db/database.dart:278`

升级前自动备份失败时，异常可能直接进入用户界面。

这不是普通页面操作失败，而是启动和数据库升级路径上的异常。

此外，`settings_page.dart`、`recovery_dialog.dart` 等位置还可能泄露绝对路径、SQL 或底层异常信息。

我支持 N-f 的推荐方向：

- 内部日志保留完整异常。
- 用户界面提供可理解的解决建议。
- 确实存在日志出口时才提示查看日志。
- 不允许为了隐藏异常而丢失排障证据。

### P2 · 产品与性能决策 3. 毛利趋势不能只做一张漂亮的图

N-a 是我最想与你讨论的产品问题。

我支持：

- 按 `business_day` 聚合。
- 退货发生当天将销售额和对应成本都记负数。
- 按实际出库成本计算毛利。
- 盘亏成本也纳入相应的成本口径。

但这里必须特别注意一个边界：

销售收入、出库成本、退货退款和盘点损失不能混成一条没有区分的流水。

否则图表虽然能算出一个数字，却无法解释这个数字是怎样形成的。

建议毛利趋势的查询结果至少保留收入、销售成本、盘点损失和退货调整几个可解释的组成部分。

这样用户点击某一天时，才有机会理解为什么当天毛利发生变化。

### 4. 压测门禁覆盖率不足

N-d 的问题也成立。

目前最慢的两项：

| 查询            | p50    |
| ------------- | ------ |
| doc_search    | 446 ms |
| today_summary | 253 ms |

恰恰没有性能门禁。

不过我不建议不加验证就直接把 600 ms 和 350 ms 写死。

应该先在低配机上测量，再决定阈值，并且明确统计的是 p50 还是 p95。

这里还有一个小问题：`perf_bench.py` 文件头的说明目前仍然只介绍 `count_roots` 和 `list_roots` 两条门禁。将来增加门禁时，要同步修改工具说明，避免出现新的文档与实现偏差。

第三，N-g 不要因为想赶进度就强行关闭。

## 四、开发治理方面，我还有两点表扬

### 1. 新增纪律 21：Agent 不执行 Git commit

我非常赞成。

你们已经遇到 PowerShell 中文提交信息编码损坏的问题。

现在明确规定 Agent 只交付：

- 修改了哪些文件。
- 对应的提交信息。

最终提交由你本人完成。

这不只是防止编码事故，也是把最终版本历史的控制权留在项目负责人手中。

### 2. 测试必须具备反向灵敏度

这点尤其让我欣赏。

例如导出按钮测试，不只是验证正常情况下能不能显示小字，还要求故意撤掉实现后，相关测试必须变红。

这比单纯追求测试数量有价值得多。

一个测试如果无论功能有没有实现都能通过，那它实际上没有提供有效保护。

## 五、我认为目前最合理的推进顺序

我不建议把 N-a 到 N-k 一股脑全部交给 Agent 实现。

建议分成四批：

第一批：用户可感知的可靠性

优先

- N-e 同步错误分类
- N-f 异常处理
- N-j 文档纠正

第二批：数据与发布安全

- N-h Schema v8 老库升级验证
- N-g 剩余实物验收

第三批：经营分析

- N-a 毛利趋势
- N-c 概览页调整

第四批：体验与工具完善

- N-d 性能门禁
- N-i 保存锁输入
- N-b 数据封存决策记录
- N-k 名称保持现状

这里有一个例外：N-d 的门禁测量可以提前进行，不必等前三批结束。

## 六、最后的总体评价

我这次看到的变化，其实很值得你自己回头看看。

神算子早期的开发重点是：

- 把功能做出来。
- 把架构搭起来。
- 让 Windows 和 Android 能够协同工作。

而现在，项目已经开始关注：

- 测试工具是否可信。
- 文档是否与代码一致。
- 异常是否泄露内部信息。
- 低配设备能否正常使用。
- 历史数据能否安全升级。
- AI Agent 是否遵守开发纪律。

这说明项目正在从「功能实现阶段」逐渐转向「工程质量与产品成熟度建设阶段」。
