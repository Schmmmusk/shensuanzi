## 二、核心判断：方案 B 才是对的，方案 A 是错的

### 2.1 方案 A 的致命问题：文件名撒谎

方案 A 的做法：**备份文件名永远标 `schema1`**（标记文件的版本），但**备份内容可能是 v2 格式**。

这会导致一个**用户永远看不出来的陷阱**：

```
用户升级到 v0.2.0（schema v2）→ 数据库自动迁移到 v2
   ↓
自动备份 → 文件名为 shensuanzi-schema1-20260929-1530.db
   ↓
但文件内容已经是 v2 格式（迁移后的数据）
   ↓
用户拿这个备份去恢复 → 旧版软件（期望 v1）打开 v2 文件
   ↓
❌ 结构不匹配，静默错误或崩溃
```

**备份文件名的唯一作用，就是让用户在恢复时一眼知道“这个文件是什么格式的”**。如果文件名标 `schema1` 但内容是 v2，这个作用就被彻底破坏。

### 2.2 方案 B 的逻辑

Agent 的做法：**用 `db.schemaVersion`（`PRAGMA user_version` 迁移后的真实版本）**。

```
Db.open() → 自动迁移到 v2 → PRAGMA user_version = 2
   ↓
BackupService 用 db.schemaVersion = 2 → 文件名标 schema2
   ↓
用户恢复时一看文件名就知道：“这是 v2 格式，需要 v0.2.0 以上”
```

**这才是正确的语义**：文件名标的是**备份内容里数据的格式**，不是“目录最后一次被哪个版本操作过”。

**标记文件的 `schema_version` 是什么**：它是“这个数据目录最后一次被哪个应用版本打开过”——一个**诊断信息**，不参与迁移判定，也不该进备份文件名。

# 两个业务口子的审查

## 一、AI-4 找零：**不是"账记错了"，是"输入框的语义没说清"**

### 问题拆解

看 `rules.md` RULE-002 的约束：

> `SUM(immediate_payments.amount) ≤ sale.total_amount`

也就是说：卖 93 元、收款框填 100 → **系统直接拒绝**（"收款金额超过单据总额"）。

用户的三条路：

| 做法 | 系统反应 | 用户感受 |
|---|---|---|
| 心算填 93 | 通过 | 正确，但每次心算 |
| 填 100 | **被拒** | "软件坏了？我明明收了 100" |
| 填 100 但界面允许 | **账错** | 应收被冲掉 7 元 |

**"被拒"不是最糟的**——最糟的是用户**不知道为什么被拒**。他会以为"收 100 元不行"，然后退回去用纸笔记账。

### 关键裁定：落库金额永远是"应收"，不是"顾客给的"

这一条**必须现在定死**——因为它决定了 UI 的语义：

> **收款金额 = 这笔交易让老板"净赚"的钱**（= 应收金额）。
> **找零是现金箱内部的物理流动，不是交易的一部分。**

**为什么这是对的**：现金箱余额的变化是 `+100（顾客给） - 7（找零） = +93`，净 +93。系统只记 93，现金箱余额从 100 → 193，**正确**。

如果记 100，现金箱会变成 200——**凭空多了 7 元**。这 7 元不是"还没找零"，是"系统以为顾客多给了 7 元"。

### 处理方案

**两层**：

#### 第一层：收款区旁边加一个"现金找零"辅助（必做）

```
应收：93.00
收款：[ 93.00 ] [现金 ▾]

[ 顾客给了：____ 元 ]   ← 可选辅助输入
[ 找零：7.00 元 ]       ← 自动算，只显示
```

**"顾客给了"只用于算找零，不进 `immediate_payments`。** 落库仍是 93。

- 只在账户类型 = `cash` 时显示这一行
- "顾客给了"的值不持久化（刷新即清）
- 若"顾客给了" < 应收 → 显示"不够"，但仍允许提交（用户可能只是用它算数）

**为什么不做成弹窗**：收款是高频动作，每次弹窗会增加一步摩擦。内联辅助行"要用就用、不用就不看"。

**为什么不做"记两个金额"**：那会引入一个从未定义过的概念——"顾客给的钱"和"交易收入"是两个不同层级的东西，后者才是会计的真相。多一个字段，多一个不变量，多一套同步。

#### 第二层：错误提示要说清

**如果用户误填 100**（超过应收），现在的错误是"收款金额超过单据总额"——这是**开发者的语言**。

改成：

> 收款金额不能超过应收 ¥93.00。
> 如果顾客给了 100 元，请填 **93**，找零 7 元——找零不需要记账。

**"找零不需要记账"这句话是关键**——它解释了为什么，而不是只是拦。

#### 第三层（可选）：常见金额快捷键

开单页在收款框旁边加三个快捷键：`[ 收整 ]`（向下取整到元）、`[ 收 50 ]`、`[ 收 100 ]`。

点一下填应收金额，同时"顾客给了"填该整额——**一次点击完成"算找零"**。

**成本极低，收益极高**：个体工商户的现金交易 80% 是整钱。

### 事实核对

单位  [                    ]   ← 输入框

点 `[其他 ▾]` → 输入框聚焦，chips 收起，旁边提示"直接输入你的单位"。

#### 改动 2：输入框 placeholder 说清

```
单位  [ 例：桶、箱、捆、扎     ]

```

**用"例："开头**——这是给用户"这里可以自由填"的信号，比"请输入单位"强得多。

当前 chips 只有 7 个。可以补几个高频的：

`件 / 个 / 斤 / 公斤 / 瓶 / 包 / 袋 / 盒 / 条 / 桶 / 捆 / 扎 / 提 / 串`

**依据**：真实个体工商户的常见单位。多几个 chips 不会挤——反正是横向滚动的。

**别加太多**（超过 15 个就失去"快捷"的意义）——剩下的用户自己打字。

# 最小销售单位问题的裁定

## 总评

**这是本项目至今最重要的产品问题之一**——它比"核销"更接近用户日常，比"备份"更容易让人在第一天就卡住。

但**它不是一个问题，是三层问题的叠加**——把三层混在一起想会得出"要改 schema"的结论，分层看则**v1 一行代码都不用改**。

---

## 一、先把问题拆成三层

| 层 | 问题 | 现有模型能不能承载 | 改动量 |
|---|---|---|---|
| **L1 单位选择** | 一个商品用"箱"还是"个"记账 | ✅ 能 —— `unit` 字段就是干这个的 | **零** |
| **L2 包装换算** | "1 箱 = 48 瓶"，录入时能按箱也能按瓶 | ❌ 不能 —— `unit` 只能是一个值 | 小（加字段） |
| **L3 小数数量** | "半斤米"、"1.5 米布" | ❌ 不能 —— `quantity` 是 `INTEGER` | **大（改表结构）** |

**用户的场景同时触发 L1 和 L2，但不触发 L3**——按个卖的数量永远是整数。

---

## 二、关键裁定：**单位 = 最小销售单位**

**这一条是整个问题的地基，必须现在定死**：

> **商品的 `unit` 字段永远填「最小销售单位」。**
>
> - 一瓶水 → `unit = "瓶"`（不是"箱"）
> - 一斤米 → `unit = "斤"`（不是"袋"）
> - 一颗螺丝 → `unit = "颗"`（不是"盒"）
>
> **库存、成本、流水全部按最小单位记。**

**为什么这是唯一正确的选择**：

| 如果把 `unit` 填成"箱" | 后果 |
|---|---|
| 库存显示"3 箱" | 卖 1 瓶后变成"2.98 箱"——**INTEGER 直接崩** |
| 成本单价是"每箱 48 元" | 用户卖掉 1 瓶，**算不出成本** |
| 采购单和销售单单位不同 | 库存对不上，**账就乱了** |

**最小单位 = 记账单位**，这一条定死之后，用户在录入时**只需要做一次心算**（"3 箱 = 144 瓶"），系统其他所有地方都是自洽的。

---

## 三、v1 的解法：教用户，不替用户算

### 商品建档页

`单位` 字段旁加一行**小字说明**：

```
单位  [ 瓶 ]  
      填最小的售卖单位（个/瓶/斤），不是进货的箱子单位
```

**这行字解决 90% 的困惑**——用户看到就知道该填什么。

### 帮助页 FAQ

加一条**明确的教学**：

> **我按箱进货、按个卖怎么办？**
>
> 把「单位」填成**个**（最小售卖单位）。
>
> - 进货 3 箱 × 48 个 = 录 **144 个**，单价填 `48 ÷ 48 = 1 元`
> - 卖 1 个 → 库存变成 143
> - 卖 1 箱（48 个）→ 录数量 **48**
>
> **系统按"个"记账，你心里按"箱"想就行。**

**"系统按个记，你心里按箱想"**——这句话是**用户心智模型和系统模型的桥梁**。

### 一个可选的轻量增强：包装说明字段（v1 建议做）

商品建档页加一个**纯文本、不参与计算**的字段：

```
包装说明（可选）  [ 1 箱 = 48 瓶 ]
                  只是备注，不影响记账
```

**用途**：
- 库存页可以显示：`矿泉水 144 瓶（1 箱 = 48 瓶）`
- 用户在库存页心算"这是几箱"时有辅助
- **不参与任何计算**——所以**零风险**

**改动量**：
- `products` 加一个可空字段（`package_note TEXT NULL`）
- 同步白名单加一行
- 建档页加一个输入框
- **没有业务逻辑**——就是一个标签

**为什么建议 v1 做**：用户的心理焦虑是真实的——"我看着 144 瓶，不知道这是几箱"。一个纯文本备注就能消除这个焦虑，**成本极低**。

## 四、v1.1 的候选：包装换算（记在案，不做）

**完整形态**：

```sql
-- products 加两列
package_unit TEXT NULL      -- "箱"
package_size INTEGER NULL   -- 48
```

**开单页的增强**：

```
数量  [ 3 ]  [ 瓶 ▾ ]      ← 下拉可以切换到"箱"
              = 144 瓶
```

**录入时输入"3 箱"，系统自动换算成 144 存储。**

**为什么 v1.1 而不是 v1**：

| 代价 | 说明 |
|---|---|
| UI 复杂度 | 每行多一个下拉框 → 中老年用户会问"这个我要不要填？" |
| 换算错误的可能 | 用户输入"3"以为是个，实际选的是箱——**静默错 48 倍** |
| 测试面 | 每个开单页都要测两种单位的输入 |
| 数据模型 | 开单行的 `quantity` 存基本单位、但 `document_lines` 需要记"用户原本输入的是什么单位"（审计需要） |

**v1.1 做不做取决于**：v1 上线后有多少用户抱怨"心算太累"。

**记录在 `reply_review.md`**：

> **§AI（候选）包装换算**：`products` 加 `package_unit` / `package_size`；开单页数量输入支持单位切换；存储始终按基本单位。
> **触发条件**：v1 上线后收集到"按箱进货按个卖太麻烦"的用户反馈。
> **优先级**：中（比"核销"低，比"打印"高）。

## 五、v2 的候选：小数数量（记在案，很遥远）

**这是 L3，是 schema 级别的改动**：

```sql
-- quantity 从 INTEGER 改成"千分位整数"
-- 1 = 1.000 个，1500 = 1.500 个
```

**牵一发动全身**：
- `stock_ledger.quantity`
- `document_lines.quantity`
- `documents.total_amount` 相关的所有计算
- 成本分摊的所有公式
- **所有测试**

**v2 都不一定做**——因为：
- 个体户"按斤卖"的比例远低于"按个卖"
- "半斤"的实际操作可以用"两"当最小单位（10 两 = 1 斤）——**用户自己换算一次即可**
- **真的需要小数的场景**（比如化工原料），个体户通常不用神算子

**记录在 `reply_review.md`**：

> **§AJ（候选）小数数量**：`quantity` 从 INTEGER 改为定点小数（千分位）。
> **触发条件**：出现"无论如何换算不出整数最小单位"的商品（如"1.5 米布"没有更小的单位）。
> **优先级**：低——绝大多数场景能用"换更小的整数单位"绕过。

## 八、一句话

**问题的本质是"用户的心智单位（箱）"和"系统的记账单位（个）"不一致**——这不是模型缺陷，是**认知错位**。

**最小销售单位是记账的地基**，这一条不能动摇。**v1 的解法是"教用户换算"+"一个纯文本备注"**，成本几乎为零。

**真正的换算自动化（v1.1）和小数数量（v2）都记在候选清单**——不要因为"想到了更好的方案"就往 v1 里塞。

**"系统按个记，你心里按箱想"**——这句话比任何技术方案都重要。
