这次有意思了，而且我认为你们抓到的不是一个普通的性能问题，而是一个会让大数据量用户永远无法完成首次同步的 P0。

我先说结论：最新提交 `1cc7371` 把性能实测、同步故障证据、待裁定事项和测试工具都集中到了一个提交里。我的审查重点会放在三处：

1. P0 的两个根因是否都定位准确，修复方案是否完整；
2. 26.4 万单的实测数据能否支撑手机性能结论；
3. 58 号提案中的五项裁定，哪些值得现在定，哪些需要调整推荐。

先提醒一个细节：发行说明中的性能数据是 Redmi 真机、Release 包测得的；而我现在审查的是提交记录和代码，不会把仓库记录的测试结果冒充成我亲自复测的结果。

## 一、P0：大库同步拉不完——定位基本成立，必须优先修

P0 · 建议立即处理

我核对了 `SyncClient`、`MobileSyncService` 和 `SyncServer` 的实际代码。两个根因确实能在代码中找到对应位置。

### 根因 1：200 页的硬上限

目前配置是：

```dart
pageLimit = 500;
maxPullPages = 200;
```

服务端每页最多返回 500 条，客户端最多拉 200 页：

$ 500\times200=100000 $

而且 `maxPullPages` 是整轮拉取的页数限制。到顶后，代码确实会把 `hasMore` 设为 `true`，不会谎报同步完成。

这部分设计原本是合理的：防止服务端分页异常时无限循环。

问题在于，原先对个体户数据规模的假设已经被真实数据推翻了。

26.4 万张单据需要约 529 页，200 页当然不够。

我支持把上限提高到 2000 页。它对应每个分页实体最多 100 万条，作为防止无限循环的安全上限，比 10 万条合理得多。

不过，我建议把注释中的「够用 10 年」改成更客观的说法：这是容量上限，不是对未来十年业务规模的保证。

### 根因 2：新镜像没有持久化 host_id

这一处我认为比页数上限更严重。

我核对了 `syncNow()`：

```dart
final String? mirrorHostId = meta.hostId;

final bool identityMismatch = mirrorHostId == null
    ? meta.hasAnyData()
    : mirrorHostId != pairing.hostId;

if (identityMismatch) {
  archive.snapshot(...);
  client.rebuildMirror();
  meta.writeHostId(pairing.hostId);
  rebuilt = true;
}
```

问题在于：

- 新镜像没有身份标记；
- 新镜像又没有业务数据；
- `identityMismatch` 因而为 `false`；
- 程序不会进入写入 `host_id` 的分支。

之后，下一次同步发现镜像有数据但没有身份标记，就会认为它属于一台无法确认身份的旧主机，归档并重建。

这就形成了恶性循环：

## 错误同步循环

1. 首次同步：创建镜像，拉取 10 万条。
2. 镜像没有 `host_id`，但已经有业务数据。
3. 第二次同步：判定身份不明，归档并重建。
4. 重新从头拉取，仍然只拉到 10 万条。
5. 重复上述过程。

大库无法正常完成同步

代码里还有一个值得注意的细节：`rebuildMirror()` 只重建业务表和索引，并不会主动写入 `mirror_meta.host_id`。身份写入目前散落在特定分支里。

我的修复建议：不要只在某一个重建分支补一行代码。

应该在同步流程完成所有镜像身份判定、必要的重建之后，统一确保：

```dart
meta.writeHostId(pairing.hostId);
```

然后再开始 pull。

当然，要保证这次写入不会掩盖真正的身份切换问题：必须先完成旧主机数据归档、队列挂起等安全处理，再写入新身份。

这样能覆盖：

- 全新空镜像；
- 身份不明的旧镜像；
- 主机身份不匹配后重建的镜像；
- 主机 schema 版本较高而重建的镜像。

### P0 验收，我建议加四条

| 测试          | 预期结果                         |
| ----------- | ---------------------------- |
| 首次配对、空镜像同步  | 同步后存在正确的 host_id             |
| 首次同步后再次同步   | 不归档、不重建                      |
| 更换主机        | 旧数据按原流程归档，新镜像写入新 host_id     |
| 超过 200 页的数据 | 一轮同步可以拉到底，`hasMore == false` |

还有一条必须做：模拟中途断网，然后重新同步。

你们原来的分页设计是每页独立事务、每页推进游标，理论上支持断点续传。这次不能因为提高页数上限而破坏这个性质。

我建议把 A5 乙作为本轮必须完成的事项，而不是普通优化。

## 二、手机性能实测：结果不错，但还不能宣布性能问题彻底解决

初步表现良好

仓库记录的测试设备是：

- Redmi 2312DRA50C
- Snapdragon SM7435
- 8GB RAM
- Android 14
- Release 包

测试结果：

| 指标    | 80 单  | 26.4 万单    |
| ----- | ----- | ---------- |
| 冷启动   | 462ms | 1.34～1.55s |
| 首次冷启动 | —     | 4.4s       |
| 内存    | 184MB | 280MB      |
| 切页    | —     | 1 秒以内      |

这组数据有一个很好的信号：

数据规模增加约 3300 倍，常规冷启动只增加不到 1 秒，内存增加约 96MB。

对于一款面向普通商户的手机开单终端，这是相当不错的初步结果。

但我有三个保留意见。

### 1. 首次冷启动 4.4 秒要单独看待

1.34～1.55 秒与 4.4 秒之间差异明显。

我希望后续把启动拆成：

- 系统进程启动；
- 数据库打开；
- 数据库迁移；
- 镜像自检；
- 首屏渲染；
- 首次数据查询。

否则我们不知道 4.4 秒究竟来自数据库缓存、文件系统冷读，还是应用本身的初始化。

### 2. 同步过程出现了明显掉帧

这是我最关心的性能问题。

你们记录的网速是 2.16～2.98MB/s，26.4 万条数据传输量不小。

提高页数上限可以解决「拉不完」，但不能自动解决「拉的时候界面卡顿」。

我建议记录三个指标：

- 同步期间 UI 帧耗时；
- 单页下载与落库耗时；
- 同步期间内存峰值。

尤其要确认 SQLite 的事务操作、JSON 解析和大量数据映射有没有在 UI isolate 上造成阻塞。

如果确实是主 isolate 负担过重，再考虑把数据处理迁移到独立 isolate。现在不建议为了优化而先重构。

### 3. 测试规模还可以再扩大

26.4 万单足以暴露分页上限问题，但还不足以证明长期运行时不会出现内存、存储空间或数据库索引问题。

我建议保留这套性能基准工具，未来至少再测：

- 50 万单；
- 100 万单；
- 低存储空间；
- 同步过程中切后台、恢复前台。

特别是同步中途被 Android 系统回收进程，恢复后能否继续，是很有价值的真实场景。

## 三、58 号提案：逐项裁定建议

我逐项看了 `docs/proposals/58-待裁定汇总-2026-11-01.md`。

整体质量不错：每一项都有现象、选项、代价和推荐，不需要再把历史讨论全部翻出来。

我的建议如下。

### A1：概览页太长

*支持乙*

把压货 Top10 挪到库存页，概览只留「压货最多的 3 个 →」。

我支持。

概览的职责是让用户快速知道今天的经营情况，而压货榜属于库存管理。

不过我建议保留概览上的前三名入口，并且点击后能直接定位到库存页的压货榜，而不是只跳到库存页顶部。

### A2：schema v8

*支持乙*

不做。

这项我没有异议。

Low 完整性导致数据库也无法写入，搬迁 `host_id` 到数据库并不能解决根因。

现在 `host.json` 已经具备 DPAPI 持久化和写入降级机制。为了少一个文件引入一次 schema 迁移，不值得。

### A3：只读态下「新建往来方」按钮仍然是蓝色

*支持乙*

置灰按钮，并把「要建往来方请在电脑上操作」放进红色提示条。

这里是 UI 一致性问题，修复成本低，应该做。

而且这不是单纯追求视觉统一。对不熟悉软件的人来说，按钮外观就是操作能力的暗示。

### A4：手机手动填地址与配对码

*支持乙，但需要安全约束*

我赞成增加 6 位数字短码，也赞成先修正文案。

但这里我想强调：6 位数字短码不是普通验证码，它实际上是一个临时配对凭据。

因此至少需要以下保护：

1. 使用密码学安全随机数生成器，不能使用时间戳或简单递增数字。
2. 5 分钟过期，一次性使用，成功后立即失效。
3. 对错误尝试次数进行限制，防止暴力猜测。
4. 电脑端必须明确显示待配对设备，并由用户主动确认。
5. 短码不能进入普通日志。
6. 同一时刻多个待配对请求不能互相覆盖或串号。

还有一个关键点：电脑确认时，最好显示手机的设备信息或请求来源，让用户知道自己正在批准哪台设备。

否则，短码虽然比 100 字符配对串好用，却可能引入新的配对安全问题。

我支持乙，但建议把这些要求纳入提案验收标准，而不是等开发完成再补。

### A5：大库同步

支持乙，P0 优先

修复 host_id 持久化，提升 `maxPullPages` 至 2000。

这是我唯一认为不能拖到普通排期的事项。

另外，建议把「同步未完成」的 SnackBar 改成明确的结果对话框，也就是丙。

但我不建议为了这个对话框延迟 P0 修复。可以先完成乙，丙随后补上。
