# 项目审计

**审计的定位不是“找茬”，是“证明项目的状态是可知的”。** 对神算子，审计应分三层：

**第一层：代码与规范一致性（每季度一次）**

- **`Agents.md` 的裁定表 vs 代码实现**：逐条核对“已裁定并落地”的声明是否属实。这是项目最大的**文档-代码漂移风险**——已经有前车之鉴（§AI-1 的设置页占位、§AQ·五的门面漏转发）
- **不变量 B1-B8 在代码中是否都有对应断言**：`testing.md §B` 列了 8 条不变量，需要审计“每条在 `test/` 和 `tool/selfcheck` 里都有镜像”
- **文档中的“待裁定”是否过期**：§AR 的待办总览是否准确反映实际状态

**第二层：依赖与许可证（每次发版前）**

- `THIRD_PARTY.md` 的依赖清单与 `pubspec.lock` 是否一致
- 所有依赖的许可证是否与 AGPL-3.0 兼容（AGPL 有传染性，但 Flutter/Dart 生态多数是 BSD/MIT/Apache，兼容）
- **字体声明**：已声明“不内嵌字体”，审计确认打包产物里没有 `.ttf` / `.otf`

**第三层：安全审计（重大版本前）**

参考离线 Windows 应用的审计方法论：**适配 OWASP MASVS 到桌面场景**，覆盖数据存储、网络通信、供应链完整性。对神算子，最小的安全审计清单：

1. 数据流图：数据从用户输入 → SQLite → 备份 → 恢复的全链路
2. 信任边界图：本地面（SQLite 文件）→ 网络面（HTTP 服务）→ 更新/供应链
3. 逐条核对 `threat_model.md` 的“防”与“不防”是否仍然准确
