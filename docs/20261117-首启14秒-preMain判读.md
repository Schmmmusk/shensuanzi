## ⓪ 结论先说

**那 14 秒不在 Dart 的时间轴上。** 三次带埋点的启动，进程内合计只有 **43–87 ms**：

| 启动时刻 | `T4_first_frame` | `T2p_sqlite_open` | `T2_db_open` | `T3b_backup_status` |
|---|---|---|---|---|
| 17:10:07 | 39 ms | 83 ms | 84 ms | 87 ms |
| 17:19:04 | 49 ms | 85 ms | 85 ms | 87 ms |
| 17:21:21 | **21 ms** | **42 ms** | 43 ms | 43 ms |

⇒ 首帧 21–49 ms 就画完了，开库最贵的一步 42–85 ms，**没有任何一处是秒级**。
所以 14 秒只能落在 `CreateProcess` → `main()` 之间：加载 34 MB 的 exe / DLL、
杀软首次扫描、Flutter 引擎初始化、Dart isolate 起来。

## ① 三份数据各自排除了什么

| 观测 | 数值 | 排除了什么 |
|---|---|---|
| `T2p_wal` − `T2p_sqlite_open` | **0–1 ms** | WAL 回放（`-wal` 也是 0 字节，双重排除） |
| `T2p_configure` / `T2p_migrate` | 各 **0–1 ms** | pragma、迁移链、`_backupBeforeMigration` |
| `io_write_mb`（11-10 那份监控） | 全程 **0.00 MB** | 启动期有任何写盘 |

四条合起来：**进程内没有可疑项**。剩下的只能是进程外。

## ② 与 11-10 那份结论的冲突，以及怎么解释

`docs/20261110-第四次真机实测-判读.md` §⑤ 记的是 `T2_db_open = 9822 ms`（关火绒后）。
同一个键，这次是 **43–85 ms** —— 差 **100–200 倍**。

解释不在代码，在**机器**：11-10 那组数是**机房机器**（`F:` 盘，六层过滤栈：
还原保护 `DFFilter` + 微软电脑管家 + 未识别 + 火绒 + …）；这一组是**虚拟机**（`C:` 盘，
只有 `WdFilter` + `luafv`）。同机对照已记在
`docs/20261111-虚拟机0.7.8验证-判读.md` §一：`sqlite3.open()` 83–85 ms（冷）/ 42 ms（热）。

⇒ **「冷启慢在开库」这句话对虚拟机不成立**，它描述的是机房机器。
`docs/windows_build.md` §8.4.1 的那段已按此更正（纪律 17）。

## ③ 为什么之前「看不见」这一段

`StartupTrace` 的计时器**在 `main()` 第一行才起表**，所以：

- `T0_main` 恒为 **0**（它就是零点）；
- 文档表格里却写着「`T0_main` 慢了说明加载器 / 引擎开销」—— **描述与实现不符**，
  这次一并改掉了。

进程创建时间在内核里有账（`kernel32!GetProcessTimes`），只是我们从来没去读。
**「埋点看不见」被当成了「没有」**，这就是这次绕远路的原因。

## ④ 新埋点：`preMain`

| 项 | 内容 |
|---|---|
| 文件 | `packages/shensuanzi_app/lib/src/process_age.dart`（新建） |
| 做法 | `GetProcessTimes(-1, …)` 取**进程创建时间**（FILETIME，100 ns 粒度），与 `DateTime.now()` 相减 |
| 调用点 | `StartupTrace.startClock()` —— 也就是 `main()` 第一行，**始终开**（正式包也跑） |
| 输出 | `启动完成 到数据就绪 preMain=<n>ms elapsed=<n>ms db=<n>MB`（`level: 启动`） |
| JSONL | `startupLine` 多一个 `"preMainMs":<n>` 字段（**不进 `marks`**，否则「T0 恒 0」不变量失效） |
| 拿不到时 | 输出 `preMain=?`（非 Windows / 调用失败 / 时钟回跳），**绝不抛、绝不阻断启动** |

两个刻意的设计：

1. **不用「记本次启动时间再比文件时间戳」** —— 那会引入第三个时钟源
   （文件系统精度 / 时区 / 缓存），而 `GetProcessTimes` 与 `DateTime.now()` 同源，直接相减。
2. **不用 `package:ffi` 的 `calloc`** —— 为一次 32 字节分配新增依赖不值当；
   沿用 `windows_drives.dart` 的做法（`LocalAlloc` / `LocalFree`，零新依赖）。

## ⑤ 下一次冷启动怎么读（判据表）

在**同一台 VM** 上，先彻底退出、再冷启一次（跑过一次缓存就热了），看那一行：

| `preMain` | 含义 | 下一步 |
|---|---|---|
| **≥ 10 000 ms**，`elapsed` 几十 ms | 时间全在**进程启动 / DLL 加载 / 杀软首扫** | 查 Defender 首次扫描（事件日志 1116/1117）、把安装目录加排除后复测 |
| 几十 ms，`elapsed` 也小（合计 < 200 ms） | **程序其实很快**，14 秒在更外层（资源管理器启动、用户双击到进程创建的间隔、或掐表方式） | 改用「进程创建时间 vs 窗口出现时间」外部计时核对 |
| 介于两者（1–3 s） | 引擎初始化 / 首次 `flutter_windows.dll` 加载 | 用 `frame-cost.jsonl` + 进程监控（`Disk Queue`）细分 |

⚠️ **必须冷启**：这台 VM 的三次冷/热对比（42 vs 83 ms）已经说明缓存影响有多大。
