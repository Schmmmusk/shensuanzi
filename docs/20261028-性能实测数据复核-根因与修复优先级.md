## 二、根因（代码级，带实测）

### A. 单据页：每帧 ≈450 ms 的 SQL，其中 **300 ms 花在「共 N 条」上**

> ⚠️ **本节已更正（2026-10-28 18:40）**。第一版复核时我按「单段查询」测，
> 得出「441 ms → 0.3 ms」的结论 —— **那是错的**：生产代码在 4c（2026-10-24）
> 早已改成**两段查询**，且排序用的是**日桶表达式**（`(occurred_at + 偏移)/86400000`），
> 用不了 `created_at` 索引。按真实 SQL 重测后结论如下。

单据页每次 `build` 跑三条 SQL（`documents_page.dart:268/278` → `DocumentDao`）：

| 段 | 实测 p50 | 说明 |
|---|---|---|
| 第一段：取 200 个 id | **131.7 ms** | `TEMP B-TREE FOR ORDER BY`（日桶表达式用不了索引，**4c 已裁定保留**） |
| 第二段：这 200 行的聚合 | **20.1 ms** | 只对 200 个 id 聚合（4c 的成果，原先要 105 ms） |
| **计数：`countDocuments(rootsOnly)`** | **299.7 ms** | ← **最大的单笔开销** |
| 合计 | **≈ 452 ms/帧** | |

`countDocuments` 为什么这么贵 —— `EXPLAIN` 显示它把两个派生表**整表物化**了：

```
MATERIALIZE r                       ← 退货汇总（26 万行）——**COUNT 根本用不到它**
MATERIALIZE s                       ← 核销汇总（10 万行）——**也用不到**
CORRELATED SCALAR SUBQUERY 3        ← 每行再查一次 settlements
USE TEMP B-TREE FOR count(DISTINCT)
```

它复用了 `_docFrom`（为列表准备的三个 join），但 **`COUNT(*)` 只需要 `WHERE`**。
去掉两个用不到的派生表后实测：**299.7 ms → 61.5 ms（4.9 倍）**。

**关键补充**：这 452 ms 是**在 `build()` 里跑的** —— 每一次 `setState`（输入一个字、
点一下复选框、悬停）都会重跑一遍。所以真正的病根不只是「SQL 慢」，
而是 **「慢 SQL 挂在渲染路径上」**。这两件事要一起修：
① 把计数降到 61 ms；② 把查询移出 `build()`，按「筛选条件 + 数据版本」缓存。

### B. 备份：卡的是**校验**，不是拷贝

> ⚠️ **本节已更正（2026-10-28 18:50）**。第一版说「`copySync` 同步拷贝卡住 UI」——
> **错了**：拷贝早在 5a（2026-10-24）就搬进 `Isolate.run` 了（`backup.dart:415`）。

真正卡主线程的是拷贝**之后**对副本做的完整性校验（`backup.dart:425`，跑在主 isolate 上，
因为 `Db.open` 不能跨 isolate）。在 478 MB 库上实测：

| PRAGMA | 实测 |
|---|---|
| `integrity_check`（现用） | **3105 ms** |
| `quick_check` | **850 ms** |

3.1 秒正好对上真机那次「备份时界面假死」，也对得上备份事件的总耗时 4.17 秒
（拷贝在后台 + 校验在主线程 + checkpoint）。

**修法**：`integrity_check` → `quick_check`。校验对象是**刚拷出来的副本**，
最可能的故障是「拷贝不完整 / 被截断」，`quick_check` 走遍所有页、验证 B 树结构，抓得住；
它少做的是「索引与表内容逐条比对」（就是那慢的 2.2 秒），而这对一份**逐字节拷贝**不是风险点。

**残余**：850 ms 仍会卡一下。要彻底不卡，得把校验也搬进 isolate（需要在该 isolate 里
重新初始化 sqlite3 原生库，属独立改造）—— 建议放到下一批，先拿到「3.1 秒 → 0.85 秒」的收益。

### C. `perf_bench` 的盲区：它测的不是页面跑的查询

`doc_count` 是裸 `COUNT(*)`（3.5 ms），而单据页跑的是带两个全表聚合 + 逐行子查询的
`countDocuments`（267 ms）。**75 倍差距**，报告里却是一片绿。

这直接导致上一轮的误判方向：bench 显示"库不慢"，于是把锅推给"界面重建"。
**已经在 `perf_bench.py` 补了 `count_roots` / `list_roots` 两条**（与 DAO 的 SQL 逐字一致），
下一轮 bench 会如实报出 267 / 441 ms。

### 首屏内容：T0 + 1.21 s

- 概览页在 **T0+1.016 s** 开始构建，构建本身 **194 ms**，画完在 **T0+1.21 s**。
- 也就是说 `T3(14 ms)` 到「首屏开始构建(1016 ms)」之间有 **≈1.0 秒**空档。

### 切页：**166–374 ms**（不是 2 秒）

| 页面 | 首次 | 第二次 | 已知 SQL | 差额 ≈ 构建/布局 |
|---|---|---|---|---|
| 库存 | **374 ms** | — | ≈180 ms（stock 43 + cost 44 + in_transit 93） | ≈194 ms |
| 单据 | **249 ms** | **223 ms** | 142 ms（默认 30 天） | ≈80–107 ms |

两条重要观察：

1. **单据页第二次(223 ms) 与第一次(249 ms) 几乎一样** ⇒ 页面之间**没有任何缓存**，
   每次进入都重跑一遍查询 + 全量构建。这与用户「每次点都卡」的体感一致。
2. **商品页只要 24 ms** —— 它 SQL 便宜、行也简单。说明 166–374 ms 不是「Flutter 天生慢」，
   而是**每个页面的查询 + 行构建成本**。

### 与 `perf_monitor` 的 1.3 秒对不上，为什么

`perf_monitor` 记的是「**进程忙**的持续区间」（0.2–0.5 s 采样，含导航动画与后续重绘），
埋点记的是「**该页第一帧画完**」。两者量的不是同一个终点：
埋点是**下限**（第一帧），用户感知的是**上限**（页面可交互 / 内容齐）。

⇒ 下一步若要解释 1.3 秒，应把埋点从「首帧」延伸到「稳定」
（例如连排 3 帧都无新任务，或首帧后 300 ms 内无重建）。

## 三之四、第四轮埋点（2026-10-28 21:00，`host=L13`，477.3 MB）

这一轮换了台机器，**首屏那 1 秒空档没有复现**：

|---|---|---|

| 开库（`T2`） | 14 ms | **14 ms** |
| 服务装配（`T3`） | 14 ms | **14 ms** |
| **首屏内容** | **T0 + 1.21 s** | **T0 + 0.13 s** |
| 概览页构建 | 194 ms | 125 ms |
| 库存 / 单据 / 往来方 / 账户 / 商品 | 374 / 249 / 218 / 166 / 24 | **332 / 221 / 201 / 158 / 7** |
| 单据页第二次 | 223 ms | **218 ms** |

**两条结论**：

   下周拿到机器再验；`T3b` 点位已就位）。
2. **首屏那 1 秒是单机现象**（很可能是那台机器的备份目录 / 磁盘首次访问），**不可复现**。
3. **切页 158–374 ms 在两台机器上高度一致** ⇒ **这才是真正可复现的问题**。

### 还没回答的问题：用户体感的「2 秒」 vs 埋点的「220 ms」

埋点量的终点是「**该页第一帧画完**」，用户体感的终点是「**页面稳定、可以操作**」。
两者之间可能还有若干次重绘（图片、字体、二次 setState）。

⇒ **下一步不是优化，是把这个缺口量出来**：让 `TracedPage` 在首帧之后继续观察，
直到「连续 N 帧无重建」或「静默 500 ms」，记一个 `settled` 时长。
拿到它才知道 220 ms 该不该优化、以及优化到多少才算够。

## 三之五、第五轮：`settled`（用户实际等多久）—— 2026-10-28 21:11，`host=L13`

| 页面 | 首帧 | **稳定** | 尾段 | 帧数 |
|---|---|---|---|---|
| 库存 | 355 ms | **800 ms** | 445 ms | 9 |
| 单据 | 242 ms | **380 ms** | 138 ms | 12 |
| 往来方 | 188 ms | **383 ms** | 195 ms | 16 |
| 账户 | 162 ms | **380 ms** | 218 ms | 18 |
| **商品** | **7 ms** | **2774 ms** | **2767 ms** | **110** |
| 单据（第二次） | 221 ms | **384 ms** | 163 ms | 14 |

### 结论一：用户实际等的是 **380–800 ms**，不是 2 秒

「首帧」到「稳定」只差 140–220 ms（库存 445 ms）。也就是说**大头就是首帧本身**
（= 查询 + 行构建），后续重绘只占三成。⇒ 优化方向仍是 SQL 与构建，不是「补一个 loading」。

### 结论二：**商品页是异常点** —— 首帧 7 ms，却要 2.7 秒才稳定，期间画了 110 帧

首帧 7 ms 说明列表瞬间就出来了；之后 2.7 秒里持续重绘（≈40 fps）。
这与「商品页体感慢」完全吻合，而且**任何只看首帧的指标都发现不了它**。

两种可能，需要下一轮分辨：
1. **有东西在持续动画**（滚动条淡出 / 进度指示 / 某个 `AnimatedXxx`）—— 那就是缺陷；
2. **鼠标移动**经过列表行触发 hover 重绘 —— 那是测量污染（用户点完就往下一个导航移）。

判据：让商品页**只停留不动鼠标**再测一次 —— 若 `frames` 掉到个位数，就是 ②。

### 结论三：单据页第二次（384 ms）≈ 第一次（380 ms）

⇒ 仍**零缓存**：每次进页面都重跑查询 + 全量构建。

| 五条主查询（概览+各页） | 冷连接实测合计 **542 ms** | ❌ 只占 13% |
| SQLite 页缓存太小（默认 2 MB） | 调到 16/64/256 MB 实测 **536–553 ms**，无差别 | ❌ 排除（不是杠杆） |

剩下的 ~3.4 秒在 Flutter 引擎初始化 + 首帧构建里。**要定案只能加埋点**：
在 `main()` → `bootstrap` → 首帧 之间打时间戳（release 包写到日志文件），
或下一轮用 `perf_monitor` 的 `--fast-interval 0.05` 抓 50 ms 粒度。
**在那之前，我不会说"首启慢是因为 X"** —— 这一轮的教训正是别照着猜的根因改代码。
